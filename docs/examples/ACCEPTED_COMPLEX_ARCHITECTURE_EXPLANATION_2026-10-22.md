# Bridge Kit 0.11.0、0.11.1 和 0.11.2：到底解决了什么？

按照 [AI Research Toolkit《复杂架构的可信解释标准》](../../COMPLEX_ARCHITECTURE_EXPLANATION_STANDARD.md)，先从实际问题和机制解释，再用源码、真实运行和验收结果判断它是否可信。

最重要的结论是：

**0.11.0 建立了当前 Bridge 的核心运行体系；0.11.1 修复了这个体系中的进度邮件问题；正在准备的 0.11.2 则要消除剩余的真实使用缺陷，并证明所有正式能力可以在正常入口使用。**

但有一个必须先说清楚的事实：截至本轮读取的仓库状态，正式 release 仍是 **0.11.1**，提交 ba9013b9…；0.11.2 目前是**通过实施前独立审查的执行方案**，还不是已经实现、测试并发布的版本。

因此，能说明为什么 0.11.2 的设计有希望解决问题，但不能把这当作已经解决的证明。

## 一、三个版本分别做什么？

| 版本 | 主要工作 | 实际意义 |
| --- | --- | --- |
| 0.11.0 | 整合机器安全策略、执行身份检查、可靠配置写入、长期运行、进度估计、共享邮件通知 | 让复杂任务从启动、运行到恢复拥有一致的基础机制 |
| 0.11.1 | 修复长期运行的邮件发送频率，并整理正式发行与历史待办 | 避免频繁进度更新导致邮件刷屏，或反而永远收不到周期邮件 |
| 0.11.2（拟实施） | 修复进度真实性、状态与 ETA 不一致、终态保存顺序、通知硬预算、Git 权限诊断；补齐正式能力验收 | 把过去「各模块存在或局部测试通过」，提升为能够核查的实际正常使用结果 |

0.11.0 并不是从零创造了整个 Bridge。Lite、Review、Control、Overleaf、视觉和文本复核等能力在更早版本已经存在。

真正发生的变化是：0.11.0 将过去这些能力执行时遇到的共同问题，集中到少数可复用的运行机制中解决。

0.11.1 的范围则很窄，不能把 0.11.0 的全部成果重复算成它的新功能。

从产品价值看，0.11.2 也不是再增加一种模式，而是要证明**已有模式及其支撑机制真正连接起来，并且不靠错误的完成判断蒙混过关**。

## 二、0.11.0 为什么是一次重要改版？

以前的 Bridge 已经能够交接任务、安排独立复核，也有不少 Git 和后台运行工具，但这些功能仍可能在真正执行时各自发生问题。

0.11.0 的核心工作，就是让它们具有更一致的执行基础。

### 1. 首先解决：Codex 到底在执行哪份任务？

假设你批准了一份科研算法方案，随后 Codex 在另一个工作树启动了同名任务，或者执行前方案文件已经变动。

这时即使它完成所有测试，也不能说明执行的是你批准的方案。

0.11.0 加入了执行前的来源核对：仓库、工作树、分支、提交以及必须读取的文件内容，都要匹配任务合同。

这不是让 Codex 自己说一句「已经检查」。在 Bridge 管理的执行入口中，检查发生在子进程启动之前。

实际 C2 记录验证过错误仓库、错误分支、错误提交、错误来源文件等情况，结果均为**零次业务进程启动**；合法任务则可以启动。[执行身份测试原始结果](https://github.com/YuukiAS/GPT_Codex_AI_Bridge_Kit/blob/release/results/bridge-core--product-scope-reset/f3c882c/C2_CONTEXT_AND_SOURCE_TRUTH.json)。

这项机制确实解决了特定问题：错误任务不能通过该受管入口继续执行。但它不会自动约束所有独立 shell 或不使用 Bridge 的程序。

### 2. 其次解决：安全操作为什么反复要求审批？

这部分最容易产生误解。

原始 Git 命令很灵活。例如 git push 可以发布普通提交，也可以更新不该动的远端引用。直接允许整个命令，权限太宽；完全不允许，又会让普通任务不断中断。

Bridge 的方案是保留几个用途明确的受限入口。

例如，publish-first 只允许首次发布任务元数据，不能夹带业务代码；bootstrap 只按冻结任务身份建立对应分支和工作树；materialize-worktree 恢复已有任务时，必须核对原任务证据，不能凭相似的分支名称直接接管。

这些入口并不是为了替 Git 增加一堆别名，而是把原本具有多种危险用途的命令，缩小成事前可以验证的一种操作。

对于普通安全读取，0.11.0 则尽量交给机器规则直接低打扰运行。

**这有两种不同的保护：包装器内部的动态检查，以及 Codex 实际加载的审批规则。** 包装器被调用才能执行自己的检查；机器规则也只有在正确环境中真正加载才有效。两者不能互相冒充，更不能宣称全系统所有 Git 路径都无法绕过。

### 3. 再解决：长任务断线、重启和进度怎么办？

0.11.0 的 Persistent Run 不需要整个 Codex 会话始终存在。

它将已经批准的前台任务交给独立的监督程序管理。每次运行绑定一个确定的身份、一个 tmux 会话、一个监督程序和一个业务子进程。

如果你断开 SSH，业务进程可以继续运行。重新连接后，系统根据原运行身份查找状态，而不是重新启动一份。

如果原运行状态不确定，它不会因为会话暂时不可见就擅自重启，更不会把「查不到进程」写成「任务完成」。

**这里最重要的保护不是自动恢复得多积极，而是防止无法确认原任务状态时重复启动、重复消耗计算资源。**

同时，进度由实际项目提供：运行程序报告完成多少单位，Bridge 再计算比例和预计完成时间。Bridge 本身不根据 PID、CPU 或 GPU 使用率猜测科研任务完成了多少。

这也是它为什么不能替 CAT-TRACE 决定统计采样进度。

### 4. 最后解决：通知为什么不用每个仓库重新配邮箱？

0.11.0 把 Notifier 收敛为机器级共享服务。一台机器使用一份私有 Gmail 配置，各项目复用，具体工作流只提供已经产生的事实。

Lite、Review、Control 和 Persistent 可以通过同一个 Notifier 发消息，但完成判断仍由各自有权的流程负责。

自动邮件发送前还可以调用已安装的 Clear Writing，让机器状态转化为自然中文，同时检查事实没有被改变。

这套机制有一个非常重要的真实正例。

0.11.0 的正式验收实际运行了一次约五秒钟的业务进程，产生启动和终止两个事件，经过 Supervisor、已安装的 writing-style 0.5 和 Gmail。

| 观察事实 | 实际结果 |
| --- | --- |
| 业务子进程 | 1 次 |
| Clear Writing 调用 | 2 次 |
| Gmail SMTP 接受 | 2 次 |
| 自动重试 | 0 次 |

这份证据很有价值，因为它不是分别调用几个辅助函数，而是走通了完整的真实链路。[完整运行回执](https://github.com/YuukiAS/GPT_Codex_AI_Bridge_Kit/blob/release/results/bridge-core--product-scope-reset/v6/391ff88/replacement/OBSERVATION_SUMMARY.json)。

但它也有明确局限：这个进程运行得很短，而且没有量化进度。因此**它证明邮件链路可用，却没有证明量化进度、ETA 和邮件在同一个长期任务中始终一致**。SMTP 接受也不等于收件箱确认收到。

这正是 0.11.2 要补的一项证据。

## 三、0.11.1 为什么还要修一次？

0.11.0 原本打算让普通进度通知按照固定间隔发送，但存在相反的两个问题。

如果每五分钟进度发生一点变化就触发邮件，长任务会产生大量无价值通知。

但如果每次观察到新进度都重新开始计时，通知间隔又可能永远达不到——任务一直推进，你反而一直收不到周期邮件。

0.11.1 把两件事分开：**观察进度可以频繁发生，但发送邮件的间隔要从上一次逻辑投递开始计算。**

例如，任务每五分钟报告一次，默认每六十分钟给你发一次普通摘要；中间的小变化更新状态，不产生邮件。重要阶段变化、严重异常、预计完成时间大幅变化或进程退出，则允许提前通知。

正式回归验证了每五分钟更新、到第六十分钟才触发普通周期投递的行为。0.11.1 同一候选的 Python 3.9、3.12 完整测试和托管持续集成通过，并完成正式发行及当时的 Longleaf 版本读回。

但这次**没有重新进行真实 Gmail 长任务**。因此它的直接证据是节流算法回归，加上适用的 0.11.0 邮件链路证据，不能表述成 0.11.1 已经真实连续发信验证了一小时。

## 四、0.11.2 到底要解决哪些仍然存在的缺陷？

这是最重要的部分。它主要不是新增功能，而是修复现有能力之间没有彻底接通的地方。

### 1. 让 UNKNOWN 不再掩盖没有上报进度的问题

当前正式合同允许直接选择 Progress mode: none。如果项目确实无法量化，这完全合理。

但如果任务明明可以报告完成单位，却因为使用默认模板而关闭量化进度，Bridge 就没有数据计算 ETA。

0.11.2 要求新任务在冻结 Goal 时讲明进度是否可量化，由哪个真实程序产生、完成单位是什么、应该多久更新一次。

更重要的是，它要区分以下情况：刚开始运行，还没有足够数据计算 ETA；生产者持续报告，但完成数量暂时没有增长；进度文件临时损坏；生产者长期没有新报告；真实业务程序已经退出或发生异常。

例如，任务约定每 300 秒报告一次，计划采用 max(900, 3 × 300)，也就是 900 秒作为来源超期门槛。

如果十五分钟没有新的有效报告，Bridge 应明确指出**进度来源已经超期**，同时保留最后一次有效数据。

它不能因为这样就擅自说「科研计算已经死锁」，但也不能继续毫无解释地显示 UNKNOWN。

这解决的是**进度报告是否履约**，不是强迫每个任务必须拥有 ETA。

### 2. 修复一个已经被真实结果直接证明的 ETA 不一致

这里有最有说服力的实证。

0.11.0 开发期的一次真实 Persistent 运行，业务程序连续报告：

| 实际观测时刻（UTC） | 完成进度 |
| --- | --- |
| 15:56:49 | 1/4 |
| 16:02:04 | 2/4 |
| 16:07:04 | 3/4 |

跨越 615 秒后，监督程序计算出预计完成时刻为 **16:12:11**。

但同一次运行的主要 status 结果中，重新读取的原始进度字段仍然显示 eta=UNKNOWN，尽管监督程序绑定记录已经有具体预计时间。

这是直接证实的**同一次运行的状态不一致**，并非推测。[ETA 与状态不一致的原始数据](https://github.com/YuukiAS/GPT_Codex_AI_Bridge_Kit/blob/release/results/bridge-core--product-scope-reset/f3c882c/C4_NATIVE_ETA.json)。

为什么会这样？当前 observe_binding_progress() 在监督程序中保存带 ETA 的结果，而 _run_status() 又通过 _progress_status() 单独规范化原始进度文件。这两个读取路径不是同一个最终结果。

0.11.2 的修复是让运行绑定中的**已持久化规范化快照**成为正常状态查询、历史、ETA 和通知的共同来源。

这不是换一个更高级的预测算法，而是消除两个路径对同一运行给出不同答案的问题。

还要注意：上述任务最终在 16:08:19 就退出，早于当时预测的时间范围。这说明已有 ETA 算法确实计算了结果，但并不说明它预测得准。因此新版本保留经验速度估计，不将快慢区间冒充统计置信区间。

### 3. 防止邮件故障破坏运行状态

当前正式监督程序里，启动业务子进程后，部分关键运行状态先经过邮件调用，再保存到绑定文件；终止时也存在类似顺序。

假设业务进程已经退出，但 Gmail 发送卡住，监督程序又在这个时间窗口异常终止。

那么业务事实可能已经发生，而状态文件尚未可靠记录。

0.11.2 要改变的是顺序：**先保存真实运行事实，再尝试外部邮件。**

启动时保存 PID、启动身份和运行状态。退出时先读取最后有效进度，保存真正由 child.wait() 得到的退出码与终态，然后再尝试通知。

如果邮件失败，你仍然应当能够查询到真实终态。邮件成功与否，不能倒过来决定业务是否完成。

这个修改直接消除「外部通知阻塞了核心运行状态持久化」的因果关系。

### 4. 给通知次数增加真正的硬上限

0.11.1 虽然修复了普通周期邮件，但重要阶段变化、异常和 ETA 大幅变化仍然可以触发提前通知。

不同事件有不同身份，普通事件去重不能阻止它们累计超过预算。

0.11.2 提出的机制，是每次运行最多预留六个外部通知名额：五个用于启动、进度或异常，一个专门留给真实终止事件。

一条通知在调用模型或 SMTP 前，必须先在运行绑定中**永久占用一个合法名额**。即使之后失败、结果未知、进程崩溃，名额也不返还。

Notifier 在真正启动外部发送程序之前，还要核对这个名额与当前运行、事件和身份一致。原来的显式重试入口也不能借失败事件绕过该预算。

为什么非得做两层检查？因为监督程序管的是正常自动发送，Notifier 自己还有重试入口。只在监督程序里检查次数，就可能被另一个正式入口绕过。

这个机制的可验证目标很明确：即使出现第七条不同的合法候选通知，**新增模型调用为零，新增 SMTP 尝试也为零**，真实业务仍然继续运行。

它不是新的中央通知平台，只是在现有监督程序和发送入口之间补上一次额度证明。

### 5. 修正 Git 保护中判断结果看似安全、实际范围更宽的问题

0.11.1 的 sync-current-branch 使用的仓库身份解析能够接受 GitHub SSH 或本地远端形式，但该低打扰操作原本承诺的范围是 GitHub HTTPS。

还有一处源码将执行策略的 no_match 转换为 prompt。

两者的问题不同。

前者让包装器接受的远端范围比授权范围宽；后者可能让验证工具把「没有匹配任何规则」错误报告成「已经匹配需要审批的规则」。

0.11.2 要求只在当前同步入口收紧 HTTPS 校验，不改动其他确实需要本地 Git 仓库的通用函数。同时保持 no_match 的真实含义，让具体 Codex 审批和沙盒机制决定后续行为。

这也解释了本轮为什么要使用隔离候选程序：**测试新版的动态检查，不能用旧版受信程序来冒充。**

## 五、为什么 0.11.2 还要检查十二项能力？

这里需要把「增加功能」和「验收已有功能」分开。

当前正式能力总共分为十二项，0.11.2 没有计划重新实现全部十二项。

| 能力 | 本轮实际重点 |
| --- | --- |
| Host | 修复 HTTPS 安全边界和审批诊断，验证正常 Git 操作 |
| Lite | 用一次正式小任务证明来源核对和结果交接 |
| Review | 复用已完成的真实复核与远端发布证据 |
| Control | 通过一个真实、有限的任务证明角色隔离和合法状态推进 |
| Persistent | 重点修复和验收真实进度、恢复、状态及终态 |
| Notifier / Clear Writing | 真实发信，加上六席预算及异常边界验证 |
| Overleaf | 核对历史真实同步、源码未变及相关回归，不新增真实同步 |
| 视觉复核 | 核对真实图像与复核结果，保留既有功能 |
| 文本复核 | 核对历史全文、审核和结果证据 |
| 文本转换 | 补一次实际加密转换，同时修复必要的付费前预算约束 |
| 生产插件回放 | 直接调用已安装的正式插件，而不是只测试辅助代码 |
| 发行与机器安装 | 核实 0.11.1 已发行事实与 0.11.2 候选身份；正式发布另行批准 |

这里也必须解释之前质疑的 Text Transform 和 0.25 美元。

文本转换是一个早已存在的可选功能，让私有文稿经加密传输、外部模型处理，再以密文返回。它与 Persistent 的技术原理没有直接关系。

之所以出现在本次执行包，是因为要求「除 Program Run 外的正式能力都要有可信验收」，而它缺少足够明确的真实转换正向证据。

**这并不意味着为了修复 ETA 就需要增加付费系统。** 当前方案只允许复用已有 paid_review，对这一项真实转换设置最多一次模型生成和 0.25 美元保守费用上限，并在付费前保存预算记录。

它是本轮最容易再次扩大范围的部分。因此验收应只看实际文本是否从正式加密入口进入模型、是否产生符合要求的转换结果、预算有没有生效、完整输出能否由指定接收者解密。

如果这些已经可以靠现有机制实现，就不应该再发展新的通用付费架构。

## 六、为什么新版的验收方式比以前更可信？

最关键的改进是：**它终于区分了普通能力的真实正例，与罕见故障的可控反例。**

以前为了验收 ETA 和六席通知预算，方案一度要求寻找某个自然运行十分钟以上、还恰好产生许多重大邮件事件的科研任务。

这很容易导致为了测试而扩大科研计算、增加无意义阶段，甚至改变原项目。

最新方案不再这样做。

ETA 的计算正确性使用受控时间验证。具体取三个进度点：0 秒完成 2/12，300 秒完成 5/12，600 秒完成 8/12。若保持同一阶段和总量，近期速度为每 300 秒完成三个单位，剩余四个单位，因此预计还需要 400 秒。

这能检查算法是否按照规定工作，而不必实际等待十分钟。它**不能证明真实墙钟已经经过十分钟，也不能证明 ETA 在任意科研任务中准确**。

六席预算的第七次阻断、崩溃恢复和重试风险，同样用同一候选正式执行路径的确定性故障回归验证，不消耗七封真实邮件来制造异常。

但是关键正向能力仍需要一条真实链：正式启动一次业务任务，业务自身产生进度，Supervisor 读取并保存，状态查询可以获得对应数据，Notifier 实际调用 Clear Writing 和 Gmail，最后保存真实终态。

本轮计划采用的实际业务，就是要求的十二项 Bridge 能力核查。它有实际交付物：逐项证据索引及完整验收报告，而不是为了凑运行时间空跑。

还有一个值得肯定的修正：业务程序退出前不能宣布自己的终止通知已经成功。它只记录运行中可知的结果；退出以后，由现有执行任务读取真实终态和邮件回执，再完成最后的判定。

这避免了验收脚本给自己尚未发生的未来事件提前打勾。

## 七、最后：凭什么相信这次真的能够收尾？

这里要分为三个层次判断。

**第一，已有体系不是纸面设计。**

0.11.0 已有真实运行身份检查、量化进度与 ETA 记录、启动和终止通知的完整发信证据。0.11.1 有明确的通知节流回归、完整测试、正式发布及当时的机器安装读回。

这些是真实成果，不能因为还需要修复某些路径，就把全部工作判成没有价值。

**第二，0.11.2 针对的剩余问题是可定位、可直接验证的。**

例如 ETA 双重读取问题，有同一次运行的矛盾原始数据；通知硬预算，可以通过第七次事件的外部调用数量为零验证；终态保存顺序，可以通过在通知失败后读取已持久化的终态验证；Git 远端范围，可以通过错误 SSH/local 远端在副作用发生前被拒绝验证。

这些机制都有明确的反证条件。如果修复无效，预设检查就应失败，而不是靠一份漂亮报告解释成通过。

**第三，这次还没有实现后的最终正向证据。**

这是目前不能跨越的事实边界。

实施前的独立 Critic PASS 只意味着执行方案已获审查，不能证明 0.11.2 源码已经正确实现。即使最终候选完成本地测试，还需要核实相同候选在正常入口确实被调用，原始产物能被读取，外部动作符合授权。

而且「全部十二项通过验收」也不等于「整个世界上再没有 Bridge 相关问题」。它证明的是冻结版本、正式产品范围、代表性任务和明确风险边界下的能力；它不能替代项目自身的科学正确性、前端质量、其他插件的专业能力或其他机器尚未进行的部署验证。

尤其不能把**0.11.2 候选验收通过**直接写成**0.11.2 已正式发布并在所有机器安装**。目前正式发布还需要单独授权和实际安装回读。

所以当前判断是：

**0.11.0 解决了核心执行基础设施；0.11.1 修正通知频率；0.11.2 的方向是在同一体系内关闭真实缺陷和证据缺口，而不是继续发明架构。它值得实施，但是否真正达到「除 Program Run 外全部完成」，只能由实施后的同一候选、正常入口、原始产物和最终验收共同证明。**

目前可以把已经批准的 0.11.2 执行交接交给 Codex，先完成受限源码实施和无外部副作用的回归。真实付费、Gmail、远端消费者写入以及正式发布仍按冻结合同分别取得授权。接下来应优先看真正跑出来的结果，而不是再产出一轮新的宏大设计。

## 为什么这份回答被用户认可（供今后迁移写法）

这份范例的价值不在于标题数量或内容长度，而在于以下因果组织：

1. **先钉住真正的版本差异**：旧版已有功能、0.11.0 体系整合、0.11.1 单点修复、0.11.2 拟实施缺口分别说明，没有把旧成果重复算作新成果。
2. **每个机制对应一种具体失败**：来源核对对应错任务执行；受限 Git 包装器对应授权过宽和重复审批；一个监督程序对应断线后重复启动；机器级 Notifier 对应每仓库重复配置。
3. **关键机制讲到可证伪的位置**：进度报告超期阈值、ETA 的三个实际观测点和双读取冲突、先落盘后发信、六席通知在外部调用之前占额、危险远端拒绝。

5. **解释验收为什么不必折磨业务**：真实正向业务走完整链，罕见的第七次通知、崩溃和异常使用确定性反例；不为凑十分钟或七事件额外扩大科研任务。
6. **最后划清证据强度与完成界限**：现有实证有效，但实施前 PASS 不等于 0.11.2 已实现，测试通过不等于正常入口通过，候选通过不等于正式发行或全机器安装。
