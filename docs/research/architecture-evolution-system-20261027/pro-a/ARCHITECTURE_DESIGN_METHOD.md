# 架构设计方法：把可实现的机制留在设计阶段

## 1. 结论与证据边界

架构工作集应同时承担阅读工具和**有限的设计合同**。它能让若干明确遗漏更难被隐藏：没有传递对象的边、没有消费方的输出、声称已有实现却没有源码、只有职责没有关键机制、修改了冻结决定却没有原因。但它不能证明架构完备，也不能保证 AI 理解了自己填写的内容。

这一判断来自三个案例的具体困难：DA 有可讲清的设计而无新接线；Mica 同时有已批准新规格和较旧运行代码；CAT 具有模型、算法、实现与可靠性不同步的演进。现有 R2 已能画出完整概览，仍没有解决这些跨层约束。工具对它们有实际表达和机械核对价值，至于是否降低真实返工，需要下一次真实任务测量。[共同设计要求](https://github.com/YuukiAS/AI_Research_Toolkit/blob/23a1c4840f665e66f7af95ffadaadd96dc999e7f/COMPLEX_SYSTEM_DESIGN_GUIDE.md) · [三个项目](THREE_PROJECT_STRESS_TEST.md)

设计合同的目标，是让 Chat 交出一份 Codex 可以实现的范围明确的方案。合同不把所有研究未知赶走；它把“本轮必须决定”“允许研究”“实现者可自行处理的局部细节”区分开。

## 2. 责任始终清楚

| 角色 | 负责的判断与行动 | 遇到边界时怎么办 |
| --- | --- | --- |
| Chat | 理解产品目标，确定能力、架构、核心机制、接口、取舍、最终冻结与返修决定 | 主动调查关键事实；决定哪些未知阻塞实施、哪些可进入独立实验 |
| GPT Work | 独立查遗漏、构造反例、审产品或科研结果；必要时做复杂验收 | 报告事实、推理和影响，交回 Chat 作设计决定 |
| Codex | 在已明确范围内实现、运行已授权检查、补充源码与运行观察 | 核心机制缺失、设计矛盾或无法实现时停止该部分并带证据返回设计；继续不受影响的已明确任务 |

Codex 可以在冻结设计明确允许的自由度内选择局部命名、常规代码组织或等价实现细节。用户能力、安全默认、关键状态机、科研目标、误差标准、对外合同和失败语义不属于可静默补齐的“合理默认”。如果某项所谓局部选择改变了这些内容，就应回到 Chat。

Work 的判断独立性与最终决定权是两件事。Work 可以充分反对方案并给出反例；Chat 必须回应实质问题，却不因此把最终架构权默认转交 Work。相同原则也适用于第二位独立 Pro：其价值是提供独立方案或证据，而不是自动形成多轮投票流程。

## 3. 一次完整设计怎样形成

以下是依据依赖关系安排的工作顺序，不是要求每个任务填同一套表。小改动可以在一段正文里完成，大系统可以按组件展开。

### 第一步：冻结要解决的问题，暂不冻结技术方案

先写用户最终应获得什么能力、当前哪里失败、已有哪项能力不能坏、哪些范围本轮不处理。区分用户原话、既有正式标准、设计者推断和待调查事实。

验收描述应落到可观察的结果。例如“用户确认清空后，原生重挂载不能悄悄把同一份旧草稿当作新输入保留；用户开始输入新的内容时，恢复机制不得抢写”。这比“增强可靠性”更能约束后续状态和机制。[Mica 清除机制](https://github.com/YuukiAS/Mica-for-ChatGPT/blob/7059c0dc24b908b57bd0e1f475142ba4f4520621/extension/src/reliability/stale-composer-recovery.ts#L224-L252)

### 第二步：先调查会改变方案的事实

问题若依赖外部 API、DOM、宿主钩子、现有调用链、数值稳定性、部署边界或成熟工具能力，先做有范围的事实调查。输出是固定来源和明确观察，不是另一份万能方案。

优先查会排除路线的事实。例如 Mica 是否已经有共享生命周期信号，直接决定一条关系究竟是新增还是保留；LikeC4 主干已有模型差异、稳定版尚未包含该能力，直接影响“自己做多少”的判断。本轮两项都经过原始资料核对，不能靠旧印象补齐。[开源调查](OPEN_SOURCE_RESEARCH.md)

事实足够稳定、已有项目惯例明确的局部任务，不需要再启动完整技术研究。缺少事实时，也不要让独立审查者反复审同一份未经核查的假设。

### 第三步：从能力推导系统对象和责任

列出支撑用户能力必须存在的对象、状态和外部边界，再分配职责。一个组件应有清楚的责任；同一责任被两个组件各自决定时，应解释唯一决定权和执行分工。

此时建立系统图，但不把画完图当作架构完成。每条关系要说明传递的对象、控制含义或依赖条件；谁发布，谁消费；是否已有实现；缺少接收者时会发生什么。输出不能停在文件落盘，必须有真实消费方或明确的终点依据。

DA 的新职责说明就是一个具体例子：DA 产生失败与缺证，workflow-core 选择原任务下一处理，Bridge 递送。把 DA 直接连到 Bridge 并让 Bridge 猜下一步，会丢失已经明确的分工。[职责原文](https://github.com/YuukiAS/AI_Skills_Collection/blob/fd6916ad5fdd5fb905544b6a127f9b0d31a737e1/docs/design/ai-reliability-architecture/ARCHITECTURE_ZH.md#L89-L106)

### 第四步：把关键组件展开到足以实施的机制

逐个追问本轮实现范围内的关键组件：什么事件进入，状态如何变化，数据如何变换，在哪个点调用其他对象，何时拒绝，失败如何结束或恢复，旧能力靠什么保留。

不同对象需要不同证据密度。DOM 组件应解释事件、观察范围、身份、重挂载、取消和清理。科学算法应解释模型目标、近似或数值路径、适用域、误差、失败语义、独立参照和未闭合问题。Skill 应解释哪些句子控制哪个行为、触发条件和实际消费边界。

外部成熟组件可以作为有明确合同的黑盒，不要求把其全部内部算法重新设计。被抽象掉的内容只要不会把本项目关键产品决定转移给实现者，就可以保留抽象。无法展开关键自有机制则是设计缺口，应显式标记，不能用“由 Codex 实现”遮盖。

### 第五步：比较真正有竞争力的路线

至少包括最强现有替代。比较应围绕用户成本、当前能力、关键风险、实现与维护成本，而不凭架构术语计分。本任务必须认真比较 Markdown + Git、CAT 模块演进文档、现有 R2、LikeC4 与轻量扩展；“自己写一个平台”没有默认优先权。

决定需说明放弃某条路线的实质原因及重新考虑条件。未采纳的方案仍能作为未来证据来源；不要求每次把所有被排除路线都显示在首页。

### 第六步：沿场景检查完整链

正常、失败、恢复和旧能力保护至少各选一个与本轮风险相关的真实场景。沿同一系统图和机制正文逐步追踪：当前对象是什么，谁消费，何时得到下一状态，证据在哪里，失败由谁处理。

检查的目的不是增加故事数量，而是找断点。对已存在实现的组件，还应从源代码反向走回设计：实际入口是否相同，隐藏消费者是否遗漏，旧函数是否仍被调用。对未实现组件，走到真实边界就停止，不编造一个接通的宿主或不存在的 API。

### 第七步：给独立判断一个明确问题

只有当独立思考可能改变结论时，才安排第二位 Pro 或 Work。输入包括目标、不可改变的约束、直接来源和候选范围；输出要求问题、反例、影响与依据。不要只让审查者润色同一份方案。

审查结束后，Chat 一次性归并实质分歧，更新相应组件、关系和决定。若需要新实验，先明确该实验将区分哪些路线；如果没有新信息，只是反复交换相同意见，应停止循环并明确剩余分歧及决策依据。

### 第八步：按范围冻结，并形成实现交接

冻结的是有范围、有来源的设计截面。一个科研模块仍待研究，不妨碍冻结与它独立的基础原语；一个尚未证明的宿主接点，也不能因为其他组件已清楚就被顺带批准。

冻结记录应绑定设计版本、依赖前提、允许修改范围、必须保持的能力、关键机制和验收定义。实现分支和测试记录随后引用这个截面，不能在执行中偷偷改写它。

## 4. 什么时候一个 Chat 足够，什么时候需要更多独立判断

| 情况 | 适当配置 | 需要得到的增量 |
| --- | --- | --- |
| 既有机制内的局部调整，事实与标准清楚 | 一个 Chat，配合实现事实调查与针对性检查 | 清楚说明影响、保持项与实施范围 |
| 外部接口或现有实现不确定 | 先做技术事实调查 | 准确入口、能力与限制；先减少错误前提 |
| 大架构选择、多个现实路线、不可逆投入或强相关盲点 | 第二位独立 Pro 可有价值 | 独立构造方案、发现原方案遗漏的对象或不同取舍 |
| 候选方案已形成，但失败机制、科学反例或产品体验难以自评 | GPT Work 独立审查 | 提供足以改变方案的具体发现，核对真正用户结果 |
| 标准已冻结的机械实现或可直接判定修复 | 原实现者与已授权验证即可 | 无需为角色齐全再加模型回合 |
| 关键争议需要实验才能判断 | 有范围的独立实验或观察 | 预先说明哪项结果会保留、撤销或修改哪条路线 |

独立 Pro 与 Work 不要求串联使用，也不要求无限返修到所有评论消失。本轮两个独立研究分支本身由用户安排；本分支没有读取另一位 Pro 的材料，其价值应在随后共同评估时判断。

## 5. 可以冻结的条件

本轮实施范围应同时满足以下条件，范围以外的未知可保留。

- 用户能力、不能降低的承诺和已有能力保护有明确来源。
- 系统责任、关系对象和关键交互点清楚；重要输出有消费者或有依据的终点。
- 核心自有机制能展开到算法、状态、事件或规则；实现者不必临时决定核心产品行为。
- 关键外部事实已调查，必要实验给出了足以选择路线的结果；未证明前提标明边界。
- 正常、失败、恢复和旧能力保护的链路可以逐步走通；权限与取消不会被假设掉。
- 适合本轮的验证标准、参照和观察方式明确；程序可以稍后实现，专业标准不能靠实现者自签。
- 重要取舍与剩余问题已有归属；独立发现得到实质回应，或明确保留有理由的异议。

“结构校验通过”只能作为其中很小一部分。没有机械方式能从字段齐全推导科学正确、产品体验良好或需求完备。

## 6. Codex 应拿到什么

交接包应能让实现者在不重新设计产品的情况下开始工作。内容直接引用正式来源，避免再复制成另一个过期任务摘要。

1. 本轮冻结修订、范围与原始要求，以及版本向量中的实际源码基线。
2. 需要实现或修改的组件和关系，关键机制正文、真实现有锚点或明确的“尚无实现”。
3. 输入输出、状态、异常、取消、恢复、兼容及性能／数值约束。
4. 不可改变的用户能力、科学目标、接口与旧行为；允许实现者决定的局部自由度。
5. 已确定标准、参照、测试和观察计划；已有检查程序的位置与缺程序的补齐责任。
6. 受阻时向谁报告、哪些情况必须返回设计、允许继续哪些不受影响的工作。
7. 实现结束需要回填的事实：准确提交、文件／符号／规则、真实消费点、测试运行与尚未验证范围。

目录和函数可以作为**实施计划位置**出现，但必须与已有源码锚点分开。验收所需观察不能仅因环境不便被降为 fixture；当前权限或设备不具备时，应报告准确缺口。

## 7. 哪些情况必须返回设计

必须返回的情况包括：核心状态或接口没有定义；原模型或数值目标互相矛盾；外部事实推翻关键前提；实现发现必须改变用户能力、错误语义、权限默认或验收标准；既定设计在已有约束下无法成立。

返回材料应具体：当前设计要求什么，直接事实是什么，哪一步无法执行，影响哪些对象，哪些部分仍成立。Codex 可以给出实现约束与局部备选观察，但最终架构决定仍由 Chat 作出。Chat 接受修订后，新增变更记录、调整范围、重新冻结受影响部分；已有实现和证据随关系检查其适用性。

文件重命名、无歧义的源位置更新、标准明确但测试缺失、普通实现 bug，不必自动升级成架构重设计。问题分类是为了少返工，不能成为把普通事实都推回用户的流程负担。

## 8. 结构化表示到底能逼迫 AI 想完整多少

| 观察到的问题 | 可以自动判断的部分 | 仍需要独立判断的部分 |
| --- | --- | --- |
| 组件无法展开 | 本轮关键组件没有机制内容 | 是合理黑盒，还是核心设计空洞 |
| 箭头没有真实对象 | 缺少关系对象或交互点 | 该对象是否充分、协议是否可执行 |
| 找不到 consumer | 图中没有消费关系或终点说明 | 运行时消费是否隐藏在反射、事件或外部系统 |
| 声称已有实现却无 source anchor | 绑定缺失、链接与固定提交不一致 | 源码是否真正实现合同、是否正常入口采用 |
| 修改没有理由 | 没有记录、范围错误、旧原因被覆盖 | 理由是否正确，证据是否足以支持决定 |
| 实现时临时创造核心机制 | 报告可以指向具体设计缺口 | 哪些属于已授权局部自由度，哪些必须返修 |
| 组件差异与用户能力关系不清 | 可以要求说明影响或不变项 | 内部重构是否值得成为架构修订 |

填写完整字段仍可能造出一份漂亮的错误架构。因此真正有用的是三者配合：结构暴露断点，来源约束事实，场景与独立判断检验含义。系统应把失败精确送回相应组件，不奖励总字段数、总卡片数或审查轮数。

本轮已实现的检查及其反例见[原型测试](prototype/tests/model.test.mjs)。这些检查支持“设计更可追问”，尚不能证明长期返工下降。下一步应记录一次真实设计到返修的维护成本和遗漏变化，再决定是否继续建设。
