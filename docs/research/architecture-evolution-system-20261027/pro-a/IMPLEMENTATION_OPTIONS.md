# 最终形态、实施取舍与停止条件

## 结论：值得验证一种工作方式，暂不建设一个平台

唯一推荐是 **Git 内少量架构元数据、原有 Markdown 设计、固定版本的来源与证据，加一个生成式静态阅读器**。用户平时打开离线 `index.html` 或本地只读页面；Chat 在原仓库修改设计和变更记录，Work 审查证据与反例，Codex 更新真实实现观察及已明确的映射。页面提供整体架构、机制下钻、实现定位和有意义的版本比较，但不成为另一个编辑数据库。

这项推荐针对的是已经出现的两类需求：一类是 R2 已经验证的“从整体图理解组件与运行路径”；另一类是本轮新增的“继续找到真实实现，并理解它为什么从旧方案变为当前方案”。第一类已有可复用基础，不值得再重做一次高层展示；第二类需要少量共享语义和来源约束，单靠换图形库解决不了。[1][2]

应先以本轮原型验证表示方法，再在一个真实返修周期内试用。若新增记录使维护比 Markdown 更费时，或者没有减少源码查找、解释历史和设计返工，就停止扩展阅读器，保留仍有价值的模块说明、决策记录与固定来源链接。当前没有证据支持“覆盖 80–90% 需求”或“已经减少某个比例返工”这样的量化收益。

## 1. 七条现实路线怎样比较

下表比较完整工作方式，不把 UI 样式或框架数量当作产品能力，也不使用自定权重算一个伪精确总分。

| 路线 | 已经能做好的事 | 对本任务仍需补的部分 | 维护负担与适用条件 | 本轮决定 |
|---|---|---|---|---|
| Markdown + Git history | 原文清楚、历史可追溯、几乎没有额外运行成本；可容纳公式、算法、代码链接和 ADR | 读者要自己拼出当前系统、组件级历史、设计与实现差距；Git 文本差异很少直接回答系统意义 | 单项目、少组件、改动不频繁，或作者与读者基本是同一人时通常足够 | 保留为所有方案的底座；小项目直接采用，不强制升级 |
| 继续使用 R2 Architecture Explorer | 首页整体拓扑、节点和关系选择、同图运行路径；已有真实浏览器比较 | 原有重点是系统解释；需要机制内容、实现锚点、架构修订、证据时效及差异关联 | 可以复用阅读顺序和经过验证的交互；把全部新语义继续硬编码进 UI 会增加维护 | 复用其已证明的阅读方式，不把本轮做成 R3 美化 |
| CAT-TRACE 式按模块 HTML / PDF 演进文档 | 公式与算法说明自然，模块职责、原案、审查、修改、撤销与 blocker 放在同一位置 | 组件间影响、源码当前观察、多版本关系比较仍需手工查阅；PDF 不适合持续导航 | 少量深度科研模块、用于汇报和长期归档时十分有效 | 保留为正文与导出方式，借鉴模块组织；不强制固定四张历史卡片 [5] |
| LikeC4 + Markdown / ADR | 成熟分层模型、多视图、关系导航、动态视图、源码链接、静态发布；基本图形与下钻不用重写 | 当前实现与证据适用性、永久因果记录、跨类型实现锚点仍需约定；主干新 diff 尚不能按稳定版能力采纳 | 当日常工作就是交互建模、多视图设计或已有 `.c4` 模型时很有吸引力 | 最强现成替代；首版不作为第二份人工权威模型，后续可单向输出到它 |
| Structurizr + Site Generatr | C4 模型、图、文档、ADR 和指定 Git 分支可以一同生成静态站点 | 科研与 Skill 对象需要适配；分支切换不自动等于有意义的架构差异；实现证据仍需补充 | 已有 C4 / Structurizr 资产的团队可直接复用；当前跨三类项目引入 DSL 与构建链的收益较小 | 不新引入；不否认现有 C4 项目采用这条路线的价值 |
| 小型元数据 + Markdown + Graphviz 静态阅读器 | 自有语义保持克制；正文继续使用合适的表达；图布局复用成熟工具；构建产物可离线阅读 | 需要实现薄层引用检查、明确字段的差异、视图适配与交互；不能自动读懂整个仓库 | 适合精选几十个架构对象、只读浏览、来源分散而无需协同在线编辑的当前情况 | **唯一推荐的小试点路线** |
| Backstage 等重型门户 | 软件目录、组织级发现、插件、集中服务整合和开发者入口 | 本任务的设计因果、冻结责任和科学算法语义仍需自行设计 | 目录运营、后台和集成会形成独立工程；多个项目本身不足以证明需要它 | 当前不建设 |

开源项目的实际维护、许可、版本边界和一手资料见 [OPEN_SOURCE_RESEARCH.md](OPEN_SOURCE_RESEARCH.md)。其中 Structurizr 按“官方项目 + 社区 Site Generatr”的较强组合比较，LikeC4 也按当前真实能力比较，而非选一个弱替代来证明自建合理。[3]

### R2 的结果支持什么，不支持什么

既有 A/B 比较使用本地静态服务器、Microsoft Edge 和 Playwright，先操作真实页面再核对文档。两份候选都通过首页完整架构和中文表达门槛；A 的 14 个节点、16 条连接和 19 个情境步骤更利于保持整体定位，关键连接同时支持指针和键盘。B 的状态表达和数据分离有价值，但关键连接的指针点击会被上层元素截获，手机比较表存在内部横向滚动。[1][2]

这些结果支持复用“整体先出现、关系可选择、运行路径留在同一拓扑”的体验，并要求新增机制与历史面板继续接受真实浏览器检查。它们没有比较长期维护成本、实现映射正确率或设计遗漏减少情况，也没有证明 DA 生产接线成立。因此，本轮不会把既有分数当作选择新数据模型的量化依据。

### 为什么不直接停在 LikeC4

如果需求主要是“系统图、机制图和文档链接”，应优先考虑 LikeC4。它已经提供很多容易低估的基础能力，使用它可以减少自己维护图形交互和 DSL 的负担。未来如果用户转向浏览器建模、多层视图探索或需要它的完整编辑生态，应先尝试替换视图层，而非把轻量阅读器扩建成另一个 LikeC4。[3]

本轮选择薄层静态阅读器，是因为最核心的新工作发生在来源与变更语义：设计、实现、证据分别对应哪个版本；变化由什么触发；旧路线为何撤销；源码修改是否已经满足新设计。无论采用 LikeC4 还是自有 SVG，这些关系都需要明确。当前只读、少量精选视图和离线交付的范围允许把页面做得很薄；若这层后来越来越像通用图形编辑器，就应停止自建并重新选择现成工具。

不能把未来 LikeC4 的 diff 视作已经解决永久历史。2026-10-27 核查的主干有具名模型差异与同布局切换，但稳定 `v1.60.0` 的完整树不包含这些新路径；文档还说明应用差异后会删除其标题和说明。因此，即使以后采用这项功能，修改原因仍应保留在本仓库的版本化记录中。[3]

## 2. 用户和三类执行者实际操作什么

用户需要一个稳定入口，不需要知道构建器的内部结构。日常打开离线 `index.html`，或由现有开发环境提供的本地只读页面，先看当前架构，再点进机制和来源。离线页面包含本次选入的图、正文与版本数据；点击 GitHub 源码仍需要网络和原仓库访问权限。页面显示所对应的提交与核对时间，不承诺打开时自动获取最新远端内容。

| 参与者 | 日常工作对象 | 写入什么 | 不能由其代替的判断 |
|---|---|---|---|
| 用户 | 静态阅读器和需要决定的产品取舍 | 必要的目标、范围及批准 | 不承担逐字段录入、查来源和分派审查者的日常工作 |
| Chat | 原仓库中的当前设计、组件与关系语义、重要修订 | 用户能力、边界、关键机制、变更理由、冻结范围、对反例的处置 | 不能以图形完整代替机制设计，也不能把核心空白留给实现者 |
| GPT Work | 原始目标、真实场景、候选设计、证据及差异 | 独立问题、反例、证据解释和审查结论 | 发现问题不自动获得最终架构决定权 |
| Codex | 已冻结任务、对应源码、测试与允许更新的映射 | 实现提交、实际文件及符号、运行观察、明确规则下的机械定位 | 不能补核心算法、发明产品机制、降低要求或静默采用重要默认值 |
| 构建工具 | 上述只读输入 | SVG、派生索引、差异摘要、校验结果、离线页面 | 不创造修改原因、不批准设计、不把测试定义变成测试通过 |

在这个分工中，架构方法比页面更先成立。即使本次最终不建设阅读器，Chat 仍应给关键关系明确传递对象，给关键组件写出可执行机制，给返修留下原因和影响范围。阅读器把这些内容放到容易检查的位置；结构检查阻止明确矛盾，Work 和领域审查承担不能机械判断的专业问题。已有工作流研究也将独立场景调查、技术事实核查和陌生实现者接手区分开来，没有要求每次任务都运行两套完整架构竞赛。[4]

## 3. 首版技术范围

### 仓库保存设计与来源，构建产物可以删除后重建

原有 Markdown 仍保存机制、公式、状态与决策解释。小型元数据保存稳定对象身份、关系含义、正文位置、修订关联和来源指向。实现文件、测试和实验产物留在各自原仓库，按固定提交链接。页面中的索引、图形位置、行号展示和变更摘要属于派生结果，不作为另一份手工编辑的权威内容。

本轮原型使用 JSON 夹具承载已经核查的三个项目片段，便于验证共用模型与真实交互。它不意味着未来必须维护一份巨大 JSON，也不意味着已实现从全部 canonical Markdown 自动抽取正文。正式试点首先要证明“一个事实只改一处”：能从原文提取的内容就构建时读取，必须人工判断的语义才进入元数据。若做不到，应先修输入边界，不能靠要求作者同步改两份来维持一致。

### 图形用构建时 Graphviz，阅读页面保持原生

推荐锁定本轮已实际运行的 `@viz-js/viz 3.25.0` 作为构建依赖，生成 SVG 后嵌入静态 HTML。浏览器中的原生 JavaScript 处理选择、详情切换、历史展开与来源导航，不加载图布局 WASM，也不依赖数据库、服务端、账户系统、向量库或 AI agent runtime。

比较两版本时，先对相关节点和边求并集，只布局一次；版本切换复用坐标，改变显隐与样式。这样避免两张独立重排图让用户难以辨认变化。普通当前视图仍突出当前关系，撤销路线只在比较或历史中出现。Graphviz 只负责位置和 SVG，哪些变化有架构意义、为什么变、哪些证据适用仍由语义记录决定。本地四节点试验验证了中文文本、自定义 id、URL、差异 class 和同输入重复输出一致性，没有证明所有规模和浏览器的排版都合格。[3]

唯一推荐不是“自研一种图形库”。布局借用 Graphviz，源码显示借用原仓库，历史存储借用 Git，正文借用 Markdown。需要自行实现的核心只有语义连接、针对所选字段的版本比较和克制的阅读界面。

### 本轮能展示与以后才增加的能力

| 范围 | 本轮原型要能实际核查的行为 | 尚未完成、不可宣称具备的推广能力 |
|---|---|---|
| 三种项目 | 同一核心模型读取 DA、Mica、CAT-TRACE 的代表片段 | 自动导入各项目完整架构 |
| 实现导航 | 已核查固定提交的真实文件、函数、选择器、测试或设计章节链接 | 跨仓自动同步、通用 AST 符号解析、任意重命名自动修复 |
| 版本比较 | 比较已声明的对象和关系，呈现变化、理由、触发来源及实现差距 | 从任意 Git 提交自动推断架构版本与产品意义 |
| 一致性检查 | 对当前小型模型执行明确结构规则，例如失效引用、实现声明缺锚点、变更缺原因 | 自动证明设计完整、统计正确、代码行为符合架构 |
| 验证 | 本地浏览器操作核心路径，检查节点、边、来源入口、版本切换和未实现状态 | 生产 CI 门禁、全平台可访问性认证、真实产品运行验证 |
| 编辑与协作 | 在 Git 文件中修改后重新构建 | 浏览器写界面、在线协作、权限管理和自动跨应用调度 |

本表说明实现范围，不提前宣称所有检查通过；最终完成状态以原型的实际构建记录与浏览器证据为准。对未实现能力的描述可以保留在技术方案中，但不得在页面用一个“自动同步”按钮伪装成现成功能。

## 4. 从原型到试点的最短路径

当前研究应交付可阅读的方案、共用模型、三个具体案例和真实交互原型。它能证明这种表示是否自然、核心跳转是否成立、差异能否说清楚；它还不能证明长期更新省时。下一步只需要一个真实变更周期，先不做通用扫描器。

### 第一阶段：选一个真实返修，记录维护成本

在已经授权实施的项目任务中，选择 3–5 个代表组件、一项会影响机制或关系的真实修改，以及修改前后两个有意义版本。Mica 的事件触发和恢复机制适合检验来源定位；CAT-TRACE 的算法返修适合检验因果记录；DA 的设计调整适合检验没有代码时的表达。首次试点只选其中一个，不同时录入三个完整项目。

作者在开始前用原来的 Markdown + Git 工作方式完成一组基准查找：找到当前机制、对应实现、修改理由、触发证据和未跟上的部分。试点后用结构与难度相近、尚未阅读的对象做相同任务，记录实际用时和误判，不把反复看同一问题后变熟悉的收益全部归给工具。

每次修改记录三类成本：正常设计和实现本来就要花的时间；为元数据与阅读器额外维护的时间；查找、解释和修复错链节省的时间。这样才知道收益来自更好的设计方法，还是来自阅读界面，或者只来自多写了一份说明。

### 第二阶段：只解决试点中重复发生的一项痛点

只有第一阶段证明有收益，才增加一个自动化：例如从固定提交解析所选符号位置，或检测已绑定片段变化。优先处理实际发生过的文件移动、重命名或证据过期，不预先开发所有语言适配器。解析结果出现多个候选时展示歧义，语义归属由 Chat 决定，不能以自动修复链接之名改掉组件责任。

这一步仍可使用本地构建命令，CI 只是未来可选执行位置。没有稳定、可解释的规则之前，不建立会阻止所有提交的架构门禁。

### 第三阶段：以第二个不同类型项目检查是否值得通用化

通过第二类项目的一次真实更新，检查核心语义能否保持相同、机制正文能否自然选择公式或状态图、适配工作是否局限于来源定位与展示方式。可以有不同渲染器，但不能为每个项目复制整套页面和数据模型。

若第二个项目需要大量特例，先缩小公共模型，保留项目自己的正文和机制表示。若仍必须重新开发一套产品，就停止宣称通用；按项目使用 Markdown、LikeC4 或 CAT-TRACE 式模块文档可能更合适。

## 5. 如何决定继续、回退或停止

继续建设需要同时满足三个条件：用户能够更快找到可靠答案；作者没有为同一事实重复维护；实现者在接手时更少需要补设计。可记录以下观察，但不合并成一个总分。

| 观察 | 要记录的真实事实 | 不能拿来替代它的数字 |
|---|---|---|
| 阅读是否更省力 | 找到机制、源码、原因和证据所需时间；找错版本或误判实现状态的次数 | 页数、卡片数、图节点数、点击总量 |
| 更新是否可持续 | 每次返修额外维护分钟数；需要重复修改的事实数；错链及其修复成本 | 一次生成成功或 schema 通过率 |
| 设计是否更完整 | 冻结前发现的具体缺口；Codex 接手后必须返回设计的核心空白；是否因此避免了后续返工 | “架构完整度”自评分或 Work 的一句 PASS |
| 语义是否跨项目成立 | 第二类项目新增了哪些必要适配；原有对象和修订含义是否保持一致 | 三份页面看起来有同样的布局 |
| 历史是否可信 | 是否能从当前组件追回旧路线、触发证据和当时实现；新证据是否被错误套用到旧版本 | Git 提交数量或时间线长度 |

若两次连续更新的额外维护时间都不低于旧文档方式，同时没有明显减少查找时间、误判或设计空白，先停止增加功能，回到 Markdown 工作流。两次只是触发复查的试点规则，不足以支持统计显著性结论。

若频繁出现“为通过检查而编造锚点”“代码已变但页面被当成实时真相”“Chat 不写机制却让 Codex 自动补字段”，应立即修正流程或暂停该能力。形式上的完整数据会制造错误确信，其危害高于少一个可视化入口。

如果用户基本只看一份线性科研报告，或一年只有少量重大变更，继续使用按模块 HTML / PDF 与版本化决策记录就足够。如果项目已有稳定 LikeC4 / Structurizr 模型，也应优先给现有工作方式补来源和因果记录，而非迁移到本原型。

## 6. 成本怎样估计才诚实

本轮没有完成长期维护的工时测量，不能从原型文件数量推导正式建设预算。可以先设一个条件性投入区间，用来限制试点规模，而不是给出交付承诺。

| 后续工作 | 条件性预算建议 | 前提与不包括的部分 |
|---|---|---|
| 把本轮原型用于一个真实返修周期 | 2–4 个工程工作日，另安排一次集中设计与证据核对 | 复用现有构建和阅读界面；来源已可读取；仅 3–5 个组件；不含项目本身的产品开发和算法研究 |
| 增加一个有明确用途的来源检查器 | 2–4 个工程工作日 | 只支持已选语言或文档格式；规则可解释；不做通用重命名恢复或跨仓认证 |
| 接入第二类项目并评估收益 | 1–2 个工程工作日，加该项目正常的领域审查 | 先前核心模型无需大改；若需要独立页面系统，停止扩大而不是追加预算 |

这些区间是规划假设，没有真实实施样本支持精确估计，也不构成默认授权。进入下一阶段前先用上一阶段实际成本修正它们。AI 研究与执行的总消耗、用户协调时间和日历等待分别记录；并行工作可能减少等待，但不能把各条研究的总成本算成零。

预算最先用于核对高影响事实、做好一次真实更新和修复阅读阻碍，而非扩大组件目录、迁移全部历史或构建通用框架。Graphviz 构建依赖及其上游许可信息应跟随锁定版本记录；本轮阅读产物不分发布局 WASM。固定提交链接仍遵循原仓库访问权限，离线页面不携带令牌。[3]

## 7. 架构方法与工具各自应证明什么

这项研究的价值可以有两种结果。第一种是表示与阅读器都值得保留：组件机制更清楚，来源定位更快，重要返修能直接回到相关组件，维护成本可接受。第二种是方法有效而阅读器收益有限：结构化交接、独立反例、按模块保存演进和固定来源链接已经解决主要问题，继续使用现有文档即可。

两种结果都比建设一个没人持续更新的架构平台更有用。真正需要验证的是，Chat 是否在冻结前解决了跨组件机制，Work 是否发现了能改变设计的反例，Codex 是否能在不补核心设计的前提下实施，以及用户能否在下一次返修时迅速知道“现在是什么、为什么变、代码是否跟上”。界面只有在持续帮助这些任务时才值得留下。
