# 产品与信息架构：让架构、实现和修改原因回到同一个对象

## 1. 最终形态

推荐建立一份 **Git 原生架构工作集**：原项目继续保存正式设计、代码、规则、实验和审查；少量结构化文件连接这些来源；构建器生成可以离线打开的只读阅读器。阅读器是日常入口，工作集才是可维护的产品。重新生成页面不会丢失决定；删除页面也不会损失源文件中的架构历史。

它服务两类直接用户。项目负责人需要尽快理解当前系统、追问局部机制、核对真实实现与返修原因；参与设计和实施的 AI 需要一份可定位、可交接、不会把关键设计空白藏进高层框图的合同。审查者使用同一份对象和来源，独立判断结论是否成立。

本产品不接管项目管理、任务调度、科研运行或代码编辑。用户仍在原来的 Chat、Work、Codex 和 Git 中工作。新增的日常动作应很少：打开当前工作集；选择组件；需要时打开原始来源；在一次有意义的改变后登记决定及其对象范围。

本轮原型是这个阅读与比较合同的可运行切片。三个项目使用同一个渲染器和同一套结构校验，模型有 22 个当前组件、90 个固定来源。实例范围有意受限，尤其历史只重建有证据的部分；这些数量不是完整项目覆盖率。[原型模型](prototype/model/data.json)记录实际范围。

## 2. 从 R2 继承什么，新增什么

既有 R2 已具备系统拓扑、组件与关系选择、路径高亮、外部来源链接及结构化模型。真实 A/B 中 A 得到 86 分、B 得到 82 分；两者都通过整体架构表达，差异集中在扫描顺序、细节深度、命中区域与移动布局。不能将 R2 描述成“没有源码链接”，再把链接本身作为本轮创新。[R2 比较](https://github.com/YuukiAS/AI_Research_Toolkit/blob/515c66acd5aa0c972ef5b0e97e336894d1932a8c/docs/research/complex-system-showcase-20261026/r2/comparison/COMPARISON.md)

本轮增加的是三种连续关系：

1. **职责与机制相连。** 组件不仅有摘要，还能解释真实事件、状态、数据变换、算法或规则如何发生作用。
2. **机制与实现相连。** 每个关键步骤可定位准确版本的函数、选择器、规则段落、公式或测试；没有实现时如实保留设计。
3. **当前与改变原因相连。** 修改回到稳定组件身份；旧方案、触发依据、决定、实现跟进和未变部分可以按需展开。

R2 的图仍有价值。新的系统将图作为一个阅读视角，不让它承担全部信息结构。

## 3. 用户平时怎么读

### 当前工作集优先

首页先回答系统做什么、边界在哪里、哪些部分相互依赖。标题下只放影响判断的当前范围，例如“运行代码为 0.1.7，规格已更新但尚未迁移”。来源提交可以随时打开，但不会占据主要阅读位置。

左侧选择项目，中央查看系统，右侧阅读选中对象。所有历史默认收起。页面不展示一排项目完成率，不把组件变成相同大小的状态卡，也不让内部角色编号替代职责名称。

系统图使用少量线型区分已定位的关系与设计关系。正常路径、失败和恢复、已有能力保护在同一拓扑上高亮，避免读者在多张互不对应的图之间寻找对象。路径说明必须带版本范围；旧 DA 路径不能被新职责说明解释。

### 组件内是机制正文

选择 Mica 的连接器连续显示，可以看到：共享事件如何进入有界观察，哪些结构变化只检查存在，哪些变化刷新快照，何时允许显示只读副本，以及恢复和超时怎样清理。选择旧草稿恢复，先看状态转移与新输入取消，再看有限恢复和安静窗口。选择 CAT 的参考引擎，则先说明消元改变了哪项条件依赖，再展开迭代顺序。[Mica 真实映射与 CAT 演进](THREE_PROJECT_STRESS_TEST.md)

这些内容不要求统一填“为什么需要、输入什么、输出什么、去掉以后”四个框。共同要求是能解释实际机制及其边界；形式由对象决定。

### 实现和证据各有入口

机制中的来源按钮进入实现页，突出刚才点击的准确锚点。条目包含真实路径、符号或规则标题、固定提交、行范围和外链。源码预览只是固定提交的只读缓存；打开原仓库才回到事实来源。

实现页同时解释证据的范围。测试文件存在、历史报告声称通过、本轮真正运行过、真实产品表现已观察，不能合并成一个绿色状态。CAT 私有源只显示本任务必要的摘要和权限控制链接；页面没有令牌和私有源码摘录。

设计态组件仍有完整机制页。DA 的新插件显示“尚无实现锚点”，下方列出设计来源和待验证的接点；拟议目录或函数名不能排在真实源码列表中。Mica 的统一适配层则同时保留“规格已获准”和“当前代码未迁移”。

### 需要时展开演进

组件的“演进”页展示与它有关的少量有意义记录：以前是什么、为什么改变、依据是什么、哪些保持不变、实现是否跟上。读者不必先浏览整个项目的时间线。

跨版本比较回答改了哪些组件、关系、机制和实现绑定。图只承担定位，正文承担原因；前后关系使用同一坐标，撤销路线不会因重新排版而消失。两个不同来源的历史材料不能拼成未经证明的旧全景，详见[版本与演进模型](VERSION_AND_EVOLUTION_MODEL.md)。

### 窄屏采用另一种阅读方式

手机上默认展示完整组件列表和可展开的关系列表，保持可点文字的正常字号；架构图可以单独展开横向查看。选中组件后滚动到机制，提供返回概览入口。这是同一模型的另一种视图，没有另写一份移动架构数据。桌面上保留全图与详情并排。

## 4. 六种共享语义对象

核心模型只增加六种对象。用户能力、要求、问题、角色和测试标准优先引用原项目正式来源，不先建立六个新数据库。

| 对象 | 必须回答什么 | 适合保存的内容 | 不应复制进来 |
| --- | --- | --- | --- |
| 组件 | 这是谁，负责什么，机制在哪里？ | 稳定 ID、职责、机制内容引用、设计依据、实现绑定 | 整份源码、已有正式设计的第二份全文 |
| 关系 | 谁在什么点把什么交给谁？ | 稳定 ID、两端、传递对象或依赖语义、交互点、来源 | 仅写“调用”“数据”的无意义箭头 |
| 来源锚点 | 当时的真实材料在哪里？ | 仓库、固定提交、路径、符号／章节／片段定位、检查结果 | 可变分支假装固定版本、虚构函数 |
| 证据 | 哪个观察支持什么结论？ | 结论范围、来源类型、原始记录、适用绑定和限制 | 由文件存在推导的“全部通过” |
| 变更记录 | 为什么对这些对象作出改变？ | 前后修订、影响对象、理由、触发依据、决定、不变项、跟进 | 用提交日期替代理由、只说“优化” |
| 修订 | 读者正在比较哪一个有意义的截面？ | 范围、父修订或比较基线、设计来源、实现观察、证据引用 | 把每个 Git commit 都变成新架构版本 |

一个组件可以是程序模块、算法模块、规则集或边界服务。稳定身份表示它在系统中的职责连续性，不取决于当前文件名；拆分、合并或职责彻底更换要留下显式继承关系。原型只演示简单稳定身份，正式支持拆分、合并时仍用上述对象和变更，不再增加一个“迁移平台”。

关系既可表示运行数据和控制，也可表示尚未接通的设计依赖。对于科研系统，“参考后验用于核对近似结果”不是生产调用；对于 Skill，“规则被安装”不是运行时实际读取。这些语义要写在关系中，不靠箭头颜色猜测。

### 字段应按阶段出现

开始设计时，组件可以只有身份、职责、机制草稿和来源；代码锚点为空是合法情况。宣称已有实现时，才必须有真实实现绑定。形成运行结论时，才必须补充相应候选、标准、执行与观察范围。

不同机制采用带类型的内容块：简短正文、步骤、时序、状态、数据合同和公式。每种类型只有自己需要的字段。原型中的六种阅读形式共用来源按钮和历史索引，没有任何 `if project === Mica` 的组件模板。

## 5. 三个维度，不设总完成状态

### 设计：这是哪种决定

设计仅需区分候选、已采纳、已撤销。没有找到独立设计决定、只依据源码重建机制时，明确标为“据源码回建”，不借代码存在推定设计已冻结。

这几个词只描述相应范围内的决定。旧 DA 设计曾有通过记录，不代表新的职责候选也获准。Mica 新规格已获准，不代表该规格已有运行实现。

### 实现：在选定源码观察中找到了什么

实现绑定区分尚未核对、尚无实现、局部实现、源码已定位。边界服务另标“外部边界”，这不是第五个成熟度阶段。局部实现必须说清覆盖范围；找到了函数还要核对真实入口和消费方。

因此不在节点上直接写一个没有定义的 `implemented=true`。CAT 的旧 helper 仍存在于文件中，但当前正常迭代已不再调用它；仅凭符号查找会误报当前架构。[C04 案例](THREE_PROJECT_STRESS_TEST.md)

### 证据：哪项判断成立到什么范围

证据保存类型和适用范围，不再增加一个横跨科研、UI、规则的十级成熟度。读者可以看到“源码已核对”“有测试定义”“历史记录报告通过”“真实运行尚未复核”等准确句子。只有具体声明的证据满足其绑定和标准，才可形成该声明的验证结论。

三者并列，使同一页可以自然呈现：设计已采纳、代码仍旧、某项证据待更新。它还允许一个完整算法候选尚无代码，或一个已有参考实现尚未通过正式可靠性门槛。

## 6. 存储与构建边界

推荐先在每个正式项目原仓库中保存如下最小组织。没有既有文档时才创建机制正文，已有文档优先直接引用。

```text
architecture/
  model.json                 组件身份、关系和来源引用
  changes/<change-id>.json    有原因的不可变修订记录
  revisions/<revision>.json   有范围的冻结截面和版本向量
  observations/<id>.json      已核对的来源锚点与证据引用
docs/...                     原有正式设计与模块机制
source / tests / results/... 原有实现与原始证据
```

这里的 observations 是文件归组方式，不是第七种业务对象，也不成为新的项目状态机。正式项目可以沿用已有 `docs/architecture`、`decisions`、`results` 路径；文件夹名字不具有审批权。

生成过程为：读取已选择的正式源 → 检查引用与记录 → 生成索引和局部依赖 → 在构建时生成 SVG → 输出可离线打开的 HTML。生成结果可以缓存或发布，但不能反向覆盖权威设计。跨项目入口只聚合获准公开的投影；不会把私有项目材料默默同步到公开仓库。

原型为了独立复现，把三个小范围实例收敛成一份 `prototype/model/data.json`，其中包含本轮人工核实的机制摘要和两版切片。这是研究夹具，不意味着未来要求用户把整份产品设计再复制到一个 JSON 中。生产接入应把相同字段改为正式内容的定位或生成结果；不要把“自动提取尚未实现”藏起来。

## 7. 谁更新什么

| 参与者 | 日常操作 | 不能由该操作推出什么 |
| --- | --- | --- |
| 用户／Chat | 决定目标、能力、机制、接口、取舍与冻结范围；接受返修后的新设计 | 一段自称批准的 JSON 不能替代真实决定来源 |
| GPT Work | 独立查证、找遗漏和反例、审复杂结果；保存可定位发现 | 发现问题不等于取得最终设计权 |
| Codex | 按已明确任务实施；登记真实文件、符号、调用事实和测试运行 | 找到文件或测试通过不能自行补产品机制、降低需求 |
| 构建器 | 解析引用、生成布局与索引、比对已声明结构、暴露缺失 | 结构合法不代表设计正确、证据充分或系统可用 |

设计文件与观察文件可设置不同审查路径，使实现事实容易更新、设计含义不能被无声改变。但文件权限、Git 审批与实际参与者身份才是控制手段；写下 `author: Chat` 并不能阻止越权。小型试点先用既有 Git 审查，不增加权限服务。

## 8. 怎么防止失真

来源按完整提交定位；当前解析结果和历史引用分开。文件移动、函数改名、一个规则拆成两处或同名函数出现时，自动化只提供有依据的候选，不自动宣布职责相同。

意义上的变更必须有对象范围和理由。原型校验会拒绝不存在的范围对象、缺来源的已有实现、没有传递对象的关系，以及缺记录或记录未覆盖的修改。局部历史中的上下文若发生意外改变，也会报错。

构建器可以使用 `--baseline` 对比已冻结基线，拒绝覆盖旧修订、原因、来源锚点与触发证据；纠正旧记录要追加更正。该能力已在本地实现，尚未配置远端 CI。源码存在性仍来自本轮实际读取固定源；构建器没有假装再次扫描所有远端仓库。详见[实现绑定方案](SOURCE_OF_TRUTH_AND_IMPLEMENTATION_BINDING.md)和[验证记录](prototype/QA.md)。

## 9. 何时这份产品设计失败

如果日常维护需要重复填写已经在源码或正式设计中存在的大段事实，方案失败。若每次普通修复都需要开新页面、填一串状态、发动两轮模型审查，也失败。若读者点进组件后仍只能看到抽象职责，或“当前源码”无法打开准确版本，阅读器没有达到本轮目标。

应先在一次真实返修中观察三个任务：找到当前机制及实现；解释一次改变的原因和未变部分；定位实现尚未跟上新设计的范围。再与现有 Markdown、Git 和 CAT 模块文档实际比较查找时间、遗漏与维护时间。只有收益超过记录负担，才扩展事实提取和更多项目。这些收益本轮未作用户实验测量，不能用原型截图代替。
