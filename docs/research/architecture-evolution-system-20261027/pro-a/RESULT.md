# 最终建议：Git 原生架构工作集与可重建阅读器

**推荐建设一层很薄的架构工作集，而不新建后台平台。** 正式设计、代码、Skill、科研材料和原始证据继续留在原仓库；少量结构化信息连接组件、机制、实现与修改原因；构建时生成可以离线打开的只读阅读器。用户日常打开阅读器，Chat 在正式来源中作设计决定，Work 独立审查，Codex 实施并回填事实。

它的核心是：**同一个稳定组件身份，承载当前机制、真实实现、证据边界和有因果的历史。** 图是入口，Git 中的设计合同和来源关系才是长期资产。

## 2. 为什么适合三种项目

| 项目 | 工作集表达的重点 | 原型已具体做到的部分 |
| --- | --- | --- |
| Delivery Assurance | 设计可以完整，新增实现仍不存在 | 比较旧共享规则与新职责候选；显示 DA、workflow-core、Bridge 的分工与失败回传；实现页明确尚无锚点 |
| Mica | 从真实事件和状态一直读到代码 | 三个代表组件下钻到 TypeScript、函数、DOM selector、消费点和测试；准确比较连接器 0.1.6 → 0.1.7 |
| CAT-TRACE | 科学机制、实现与可靠性分别演进 | C01 数值修订、C04 真实实现版本、零槽位路线撤销与 blocker；保留未完成的生产与正式可靠性边界 |

三者没有使用三套网站模板。共享的是组件、关系、来源锚点、证据、变更与修订；机制内容可以选择步骤、状态、时序、公式、数据合同或简短正文。

Mica 与 CAT 的历史仅重建已核实的局部范围。其余当前节点标为上下文，既不冒充旧全系统，也不被算作历史未变。Mica 的新适配层和回答模型同时显示“规格已获准、实现尚未迁移”；CAT 的旧函数仍在源码中，但正常迭代已经换用新函数。它们直接证明单一 `implemented/verified` 状态不够用。[具体证据](THREE_PROJECT_STRESS_TEST.md)

## 3. 架构设计与展示怎样结合

Chat 从用户能力和已有保护出发，确定对象、责任、关系和关键机制，再沿正常、失败、恢复路径走查。实现范围内的核心机制若仍需要 Codex 临时发明，就不能冻结该部分。

工作集把这些设计内容变成可阅读、可定位的合同，也提供有限结构检查：缺来源的已有实现、没有传递对象的关系、无原因或未覆盖对象的修改、超出局部历史范围的改变都会暴露。它不能证明需求完整、科学正确或产品好用；这些判断仍需要直接事实、场景、实验和适当的独立审查。

第二位独立 Pro 用于确有多条竞争路线、重大投入或强相关盲点的任务；Work 用于独立遗漏、反例和复杂验收。事实和标准清楚的局部工作由一个 Chat 与原实现流程即可完成，不引入固定 Planner–Critic 循环。冻结、返修决定和最终架构权始终属于 Chat。

## 4. 版本和返修怎样留下来

不把每个 Git commit 都包装成架构版本。职责、关键机制、接口、产品要求和重要路线发生变化时，建立有范围的修订；普通实现推进只更新其来源观察。

每次重要变更连接触发证据、设计决定、组件或关系、实现跟进和不变项。默认页面显示当前；组件内展开相关历史；跨版本比较给出结构化差异和图上定位；源码细节仍回到各自固定提交。撤销路线保留原因，纠正旧事实追加更正，不覆盖历史。

原型的差异计算来自作者声明的结构字段，不能自动推断任意代码变化的架构意义。按前后关系并集得到的影响范围只是候选检查范围，不是实际损坏清单或全量测试命令。

## 5. 采用和暂不采用的成熟能力

本轮实际采用 **Git 的版本与永久链接、构建期 Graphviz／@viz-js/viz、原生 HTML/CSS/JavaScript、SVG、Markdown，以及 ADR 保留旧决定的原则**。运行页面没有框架、WASM、后端或外部网络依赖。Graphviz 只生成布局；语义模型、来源关系与因果记录是本任务需要补充的薄层。

调查覆盖 12 组能力、13 个仓库。LikeC4 是最强现成替代：已经支持多层视图、关系探索、动态视图、来源链接和静态发布，不能把它当成只能画框图。当前主干也有模型差异功能，但本轮核查的稳定版尚未包含；永久保留变更原因和证据仍需独立记录。Structurizr 与 Site Generatr 的文档、ADR、多分支能力也纳入完整比较。[开源证据](OPEN_SOURCE_RESEARCH.md)

Tree-sitter、SCIP、dependency-cruiser、Difftastic 是后续按需求采用的工具，本轮没有假称已集成。Cytoscape、ELK 留作更复杂图交互的替代；VitePress 可以承载已有文档站；Backstage 的集中门户和后端超过当前需要。

## 6. 是否值得继续建设

值得先做一个小试点，不值得直接建立新产品团队和基础设施。若只有系统图与文档链接，LikeC4 或现有 R2 已足够；若主要按模块阅读历史，CAT 式高质量文档也可能更省维护。

继续建设的理由必须来自一次真实返修：查找当前机制与实现是否更快，错误历史或过期证据是否更容易发现，维护新增记录所花时间是否低于它节约的理解与返工成本。本轮未作用户实验，不能宣称已节约某个百分比的时间或覆盖 80–90% 需求。

建议先手工维护最小工作集，经历一次真实设计、实现和返修；只自动化其中最重复的事实定位。若仍需大量重复文档、读者继续回到聊天才能理解、或收益没有超过维护成本，就停在 Markdown／Git／现有工具组合。退出时所有设计、来源与历史仍在普通文件中，不被专有数据库锁住。

## 7. 本轮完成了什么，尚未证明什么

本轮交付完整产品模型、设计方法、版本与来源方案、成熟替代调查、三个真实项目映射，以及可运行的高保真原型。原型当前包括 22 个组件、90 个固定来源；13 项模型反例检查与 14 项有限浏览器交互检查的具体结果、环境和文件摘要记录在 [QA.md](prototype/QA.md) 与机器报告中。

源文件和测试定义经过实际查阅；没有运行 DA 生产接线，没有操作真实 ChatGPT 验证 Mica，也没有重跑 CAT 科研计算。页面和模型校验不替这些产品或科研结果作证。

本地构建支持显式传入冻结基线，检查旧修订、来源与原因是否被覆盖；尚未接入远端 CI。运行证据适用性是有反例测试的规则演示，源码自动发现与跨语言解析属于后续可选工作。原型的三项目数据由本轮人工核实整理，未伪装成自动提取系统。
