# 架构与真实来源怎样保持一致

推荐方案把架构含义保留在仓库内的设计说明，把代码事实交给源码，把验证结论交给对应运行证据；少量结构化元数据只负责连接这些来源。静态阅读器读取构建结果，提供下钻和比较，不承担第二套事实维护。这样既能完整描述尚未实施的架构，也能在实施后继续追到真实调用点，同时保留“新设计已确定、旧代码尚未跟上”的差距。

本文给出本轮推荐的绑定规则与更新责任，属于产品研究方案。文中的 Mica 实例已经按固定提交核查；锚点解析、漂移检查和权限隔离的完整实现仍是未来建设范围，不因本轮原型可点击而视为已经具备。

## 1. 每类事实只维护在适合的位置

仓库已经拥有源代码、设计说明、测试和历史，不应再要求逐项抄到一份大型清单。新增元数据只需要给组件和关系稳定身份，指出设计说明、实现位置与证据，并标识有意义的修订。组件内部的算法、状态转换、公式或文字解释仍写在对应 Markdown 章节；渲染时按章节提取，不维护另一份用于网站的改写版本。

| 信息 | 权威来源 | 主要更新方式 |
|---|---|---|
| 用户能力、系统边界、职责、关键取舍 | 当前批准的设计说明与决策记录 | Chat 修改并冻结；用户决定仍由用户作出 |
| 组件及关系身份、机制章节、修订关联 | 仓库内少量架构元数据 | Chat 定义语义；机械格式与引用可由工具生成 |
| 文件、符号、依赖、配置和测试定义 | 对应提交的源代码、配置及依赖锁文件 | 构建时解析；Codex 提交实际实现后更新观察 |
| 调用关系、事件发布与消费点 | 源码中的调用或装配位置；必要时运行轨迹 | 自动提取候选，核对实际入口及适用条件 |
| 已验证的行为、性能或科研结论 | 绑定候选版本与条件的运行报告、实验产物 | 执行者提供事实；独立判断由 Work 或既有审查者作出 |
| 为什么改变、替代哪条路线、哪些保持不变 | 修订记录及其引用的反馈、审查或实验 | Chat 决定；工具仅汇总变化候选 |
| 图形布局、索引、搜索与比较页面 | 上述材料的构建结果 | 自动生成，可以删除后重建 |

阅读器中的“当前”应明确为某次来源观察所对应的版本。用户打开一个离线页面，不能因此得到仓库已经同步到最新提交的暗示。页面可显示最近核对时间和固定版本；构建时有访问权限才比较指定分支的新提交。未能取得新来源时保留上次观察，标明尚未更新，不把旧信息悄悄换成猜测。

## 2. 锚点定位一个对象，也说明它证明什么

一个实现锚点至少包含仓库、固定提交、路径及定位方法。定位方法可以是函数或类、配置键、选择器常量、Markdown 稳定章节标识、规则块，或者一个明确的行区间。解析器再产出行号与内容摘要值，供读者点击、供后续检测变化。GitHub 官方永久链接支持在固定提交中定位文件或行区间；分支链接会随分支前进而改变内容，因此只适合“查看最新”，不适合作为历史结论的唯一出处。[1]

**稳定身份、物理位置和内容摘要值分别解决不同问题。** 组件身份表示它在系统里承担什么职责，不能随文件改名而改变；路径和符号表示本次观察时它在哪里；摘要值表示所定位内容是否变化。摘要相同不能证明行为相同，因为被调用依赖、配置或环境可能已变化；摘要改变也不自动代表架构改变，注释调整或机械移动可能没有语义影响。

为了避免普通换行格式变化淹没结果，建议保留原始文件对象标识，并为所选片段计算约定规范下的摘要。规范必须固定，包括是否统一换行、选取哪些字节、是否包含注释。第一版使用明确的文本片段摘要即可，不把复杂语法规范化当作必备条件。所有摘要都应自动计算；作者不手工填写一个“已核对”的字符串。

行号由固定版本解析得到，不能承担跨版本身份。对于简单脚本，可以用“文件＋完整符号名＋所在作用域”定位；对于 Markdown，可以使用稳定章节标识，再附章节内容摘要。正文标题更自然地改写时，稳定标识可保持不变。若一个文件中有多个同名函数、多个相同段落或多个候选章节，解析结果必须呈现歧义，不能选择第一个匹配项。

实现锚点还要标明用途。例如它证明“定义存在”“入口装配”“事件发布”“事件消费”“配置生效路径”或“测试定义”。这些用途不必变成大量界面徽章，却必须在数据中区分；用户打开详情时应知道当前链接究竟支持哪一层结论。

## 3. 有符号不等于普通入口会使用它

从系统组件下钻到函数只是第一步。要声称组件已经进入正常路径，还需要找到加载、导入或注册位置，以及至少一个真实消费点。没有消费者可能是未接入代码、研究原型、历史残留，也可能是由外部框架或反射调用；系统应列出待核对原因，而不是直接判为无用或自动补一条关系。

Mica 的连接器连续显示提供了具体例子。0.1.7 中，`attachListeners` 监听共享的 `mica-connector-lifecycle-latched` 事件，`handleSharedConnectorLifecycle` 读取事件携带的上下文，再启动初始快照和有界观察。内部 `handleMutations` 在输入框结构改变时调度存在检查，连接器结构改变时另调度快照刷新，分别合并到下一帧。这里可以绑定发布点、监听注册、处理函数、视觉副本和清理函数，说明事件如何实际传到消费者；只有一个 `refreshSnapshot` 函数名并不足以说明这条机制已经接通。[2]

同一组件还消费发送恢复和旧草稿清除的状态。当发送或清除正在进行时，`continuitySkipReason` 阻止显示缓存副本。这条关系传递的是互斥条件，应在图上解释为“恢复期间禁止临时显示”，不宜画成模糊的组件依赖。[3] 代码导入图和设计关系图因此可以共享定位信息，却不能互相替代：导入只能说明程序引用，无法自行推导责任、数据含义或用户影响。

对于动态注册、浏览器 DOM、外部 API 和科学计算例程，静态分析往往只能提供候选关系。需要运行证据时，记录实际场景、候选版本和观察对象；未能观测不等于没有调用，观察一次也不证明所有路径都会调用。

## 4. 设计、实现和验证分别前进

同一个组件可以设计已经确定、实现尚未接入、验证还未开始。也可能旧实现仍在运行，新设计已批准替换它。以单一“完成度”覆盖这些状态，会把最需要用户知道的差距隐藏掉。

Mica 当前固定提交 `7059c0dc24b908b57bd0e1f475142ba4f4520621` 同时包含 0.1.7 运行实现和 2026-10-12 的重建规格。规格约定统一 `extension/src/platform/chatgpt/` 适配层，并要求只有适配层生成共享 `AnswerDocument`；实际读取的目录树没有这些对应实现，选择器仍分布在现有内容脚本与可靠性模块。第二轮审查明确只是设计准入，不能证明代码、界面、性能或发布产物。[4][5] 阅读器应显示“设计已冻结，尚无对应实现”，允许继续查看完整设计；实现入口保持为空，不虚构函数名，也不拿旧代码冒充已迁移的新组件。

已存在的运行实现则必须带自己的观察版本。当前 0.1.7 源码可证明热路径修复已经写入仓库；存在输入回归脚本可证明检查项已经定义。后者并不证明脚本在当前候选上成功执行，更不能证明当下 ChatGPT 界面兼容。Mica 自身版本规则要求运行代码、构建目录、清单与诊断版本一致，因此正式行为证据应绑定用户实际加载的构建，而不能只绑定源文件。[6][7]

对仍无代码的科研模块，同样可以绑定模型公式、假设、算法步骤、数据合同和已有反例。实现位置为空是一种完整、诚实的表达。若已经有参考实现而尚无生产实现，两个对象分别绑定，不能因参考例程存在就把整个模块标成已经落地。

## 5. 文件移动、函数改名与语义重绑定

跨版本解析先查当前精确位置，再查明确的迁移记录和唯一内容匹配，最后才给出基于差分或名称相似性的候选。Git 的重命名检测本身依赖相似性阈值，适合提供线索，不能单独决定“两个文件承担同一架构职责”。[8]

| 遇到的变化 | 可以自动处理的事实 | 必须保留的判断边界 |
|---|---|---|
| 仅移动文件，目标唯一且内容不变 | 记录旧位置到新位置的解析结果，重建点击链接 | 不改组件职责和历史版本 |
| 符号改名，声明及引用由同一修改同步更新 | 报告新名称与调用点，提出绑定更新 | 原有行为是否保持需结合调用及测试确认 |
| 函数拆分、合并或出现多个相似实现 | 列出候选与差分 | 不自动决定哪一个继承原组件身份 |
| 文件删除，替代实现已接入 | 记录删除及替代候选 | 由 Chat 决定撤销、迁移还是职责拆分 |
| 函数保留但已无入口调用 | 显示仍有定义、普通路径未证实 | 不继续沿用“已接入”结论 |
| 无权限访问目标仓库或提交 | 记录本次无法读取 | 不解释为文件不存在或设计删除 |

Codex 可以在已经明确的映射规则内更新机械事实，例如同一符号的无歧义文件移动、行号和摘要。涉及职责重新分配、多个候选选择、旧机制由新机制替代时，应提交观察和建议，由 Chat 决定语义重绑定。自动化不应借“修复坏链接”之名完成一次未经设计的架构迁移。

历史锚点始终保留原提交与原位置。新位置只影响新观察，不能回写旧版本，把读者带到今天的实现后再解释过去的判断。若历史对象已无法从远端取得，应报告缺失；可使用经过授权保留的归档来源，但需保留其原版本身份。

## 6. 两个方向的漂移都要检查

**设计变了、代码未跟上**时，系统比较新设计对应的机制和关系，与最新代码观察中的绑定及证据。未实现的新关系、仍然保留的旧入口、尚未迁移的选择器都应集中到相关组件。这里只报告具体差距，不自动创建十几个状态或把整个项目判为失败；一个已批准的分阶段迁移本来就允许这种差距存在。

**代码变了、设计未更新**时，构建根据受监测的实现路径、符号和关键依赖找出受影响组件。维护者需要判断这是保持语义的实现调整，还是改变了接口、机制、恢复路径或用户能力。第一种更新实现观察即可；第二种生成待设计决定的变化，不能只把架构图重新生成便宣布一致。

Mica 0.1.6 到 0.1.7 的修复说明了这种区分。原实现同时监听共享生命周期事件和六类普通输入事件；连接器上下文锁存后，普通输入可重复建立视觉快照，并通过 60 毫秒定时器检查输入框。修复保留已有共享信号入口，删除普通输入到重型快照的调用链和固定轮询，增加有界 DOM 结构观察、合帧排程与输入性能回归。[9] 它没有改变“短暂连续显示”这一功能名称，却改变关键触发关系与资源消耗，因此应有一条机制修订记录。差异视图应把共享信号关系列为保留，不能误报新增；副本不可交互、发送与清除互斥、缺少安全条件时保持原生等约束也保持不变。

为控制维护量，第一版只监测已绑定组件的实现及明确声明的关键依赖。扫描整个仓库只能发现“还有未映射代码”，无法可靠证明架构遗漏。自动生成的调用图、依赖图和修改文件清单应作为调查入口；只有被选为系统责任对象的部分进入主架构模型。

## 7. Skill 与提示词要绑定到实际控制行为的文本

Skill 的规则身份可由文件、稳定章节或规则标识和内容摘要共同确定。涉及“哪几句话控制行为”时，锚点应缩小到对应规则块，并保留前提与例外；只链接整份 `SKILL.md` 会使读者无法判断究竟哪条规则发生变化。标题、描述和触发条件可能位于不同位置，需要分别引用，不能用一段正文代表完整触发机制。

源码规则、安装产物和本次调用实际加载的内容属于三个观察对象。插件生成可能改变目录和包装，安装缓存可能停留在旧版，平台也可能没有触发对应能力。因此记录源码提交、安装或分发版本、生成产物摘要，以及能够获得的实际加载证据。平台若不暴露加载内容或调用记录，就明确停留在“安装内容已核对”或“触发未证实”；不能从配置清单推导“本次已使用”。

当规则改写后意思保持不变，Chat 可保留其规则身份并更新版本；当一条规则拆成多条、适用范围变化或例外增加，应该记录继承与替代关系。Codex 可以提取文本和计算摘要，也可以报告生成产物不一致，但不能自行决定规则语义未变。用于验证自然语言效果的最终产物必须另有证据，关键词或规则文件存在检查只证明机械属性。

## 8. 证据按结论和适用条件绑定

验证证据至少要能回答：验证哪个行为，针对哪个设计与实现版本，在什么环境和数据条件下执行，实际结果在哪里，由谁或什么程序作出判断。可以引用既有测试和实验报告，不必为每次执行复制整套描述。构建结果可提取摘要，但原始证据仍位于原仓库或受控产物存储中。

一条测试通过只支持其覆盖范围。Mica 的输入回归检查 DOM 复制、样式读取和计数增长，生命周期测试检查关闭、快照过期、重新挂载和互斥条件；这些测试对机制有价值，仍不能替代真实低内存设备上的收益和当前线上结构确认。[6] 架构节点默认显示最接近当前问题的结论，详细证据条件按需展开，不能把测试数量或历史通过次数转换成总体可信分数。

设计或实现修改后，旧证据仍然可看，但需要重新判断是否适用。能确定输入、被测实现或关键依赖变化时，标出受影响的结论；无法确定时显示待核对。不能通过更新时间戳让证据恢复有效，也不应因任何不相关文件变化而使所有历史验证失效。

## 9. 构建检查的能力边界

持续集成适合做可重复、可解释的机械检查：元数据格式与引用完整性，组件和关系身份是否唯一，固定提交能否读取，锚点是否唯一解析，内容摘要有无变化，声称有实现的对象是否绑定来源，修订是否指向真实触发材料，以及静态页面能否构建和完成主要交互。

这些检查可以阻止明显失真，例如实现节点无源码、未知组件被引用、历史被静默覆盖。它们不能证明设计完整、算法正确、失败路径足够、图形容易理解，或冻结方案已经覆盖用户需要。应向 Work 提供具体缺口和受影响机制，而不是用一个通过状态替代独立判断。

本方案的第一版不自动执行引用仓库中的任意命令。绑定测试定义只解析内容；需要运行测试时仍使用目标项目既有入口和授权范围。构建器也不因 Markdown 中出现脚本、插件配置或下载指令而执行它们。Graphviz 只接收程序从校验后的关系模型生成的图描述，不接收文档作者任意注入的构建命令。

## 10. 公开页面与受控来源

源链接并不会自动授予仓库权限。静态页面可公开呈现经过授权的机制概述，并把受限细节链接回原仓库；浏览器是否能打开由来源系统决定。页面不携带 GitHub 令牌，不代理私有仓库读取，也不将一次有权限的研究会话读到的内容无条件打包成公共搜索索引。

私有来源的文件名、章节名、路径、摘要、公式和截图也可能泄露信息，不能只排除整段源码。发布构建应使用明确选择的公开材料集合；未获公开授权的内容保留在受控项目中。公共页面可以只说明该组件依赖受限来源，并显示经允许的入口。跨项目索引只聚合各项目主动公开的最小摘要，避免因搭建统一入口扩大数据可见范围。

Markdown、证据标题、外部链接和图形标签都应按不可信内容处理。默认关闭原始 HTML，链接只允许明确支持的协议，拒绝路径越界和任意文件包含；代码片段以文本渲染。若确有富文本需求，使用成熟净化器并限制允许标签和属性。DOMPurify 支持 HTML、SVG 和 MathML 净化，其文档同时强调后续修改已净化内容可能破坏安全保证；不能把“用了净化库”当作允许任意嵌入的理由。[10]

图形构建也使用固定属性集合：用户文本进入标签而非脚本，来源链接由经过校验的结构化地址生成，输出 SVG 不保留事件处理器、外部脚本或任意外部资源。可通过站点内容安全策略进一步约束加载范围。所有安全选择都服务于同一个产品边界：阅读器负责查看已有材料，不变成执行材料、读取其他仓库或上传项目内容的入口。
