# 版本与演进：比较系统意义，保留改变的原因

## 1. 版本是一段有范围的决定，不是一条 Git 提交

Git 保存全部文件变化；架构修订选择值得以后理解的系统变化。两者有关联，但不要求一一对应。一个架构决定可能跨几个实现提交逐步落地，一个 bug 修复也可能只改变某个内部机制，而不改变系统职责图。

推荐同时保留三条相互关联的线：**设计修订、实现观察、证据记录**。它们通过组件、关系和来源身份连接，不被压成一个“当前版本已完成”。用户首先打开当前工作集，需要时切换其中一段有意义的设计或机制历史。

CAT 的身份与版本文档本来就区分算法、实现和任务等身份；本方案借鉴这种分离，但不把该项目的全部版本术语复制成跨项目模板。[CAT 版本语义来源](https://github.com/YuukiAS/CAT-TRACE/blob/0d829fb17c458a076a15ec51893e917960107c21/docs/decisions/2026-09-22_cat_trace_implementation_identity_versioning.md#L27-L91)

## 2. 哪些改变值得成为可选修订

| 变化类型 | 是否产生架构修订 | 必须留下的内容 |
| --- | --- | --- |
| 职责、边界、关键关系或接口改变 | 通常需要 | 前后对象、原因、决定、影响、实现跟进与不变项 |
| 实现提交推进同一设计 | 通常只更新实现观察 | 对应设计范围、真实提交与消费点、缺口、测试记录 |
| 修复改变关键状态、数值路径或失败机制 | 建立局部机制修订；是否提升系统版本另判断 | 触发缺陷、前后机制、保留能力和相关回归 |
| 设计纠正 | 对受影响范围建立新修订 | 旧假设为何失效、反例或审查、替代机制与边界 |
| 路线撤销 | 保留撤销决定；新路线尚未确定也合法 | 撤销对象、依据、仍保留目标、当前 blocker |
| 实验发现 | 先登记证据；不自动改变架构 | 观察范围、结论与限制，随后哪个决定消费了它 |
| 用户能力或产品要求改变 | 新的设计范围与决定 | 原要求、新要求、谁决定、哪些保护继续有效 |
| 文件移动、函数改名、布局或措辞调整 | 通常不创建架构修订 | 更新来源观察或展示；有语义影响时说明理由 |

内部重构也可能有架构意义，例如隔离一个跨模块依赖、改变扩展边界或解除已测性能瓶颈；不能因为用户界面不变就一律排除。反过来，也不能为了每个提交都能显示漂亮差异而强行编造用户收益。判据是以后是否需要理解这次系统决定，以及它是否改变责任、合同、关键机制、约束或维护风险。

## 3. 修订的最小内容

一个修订记录应说明：身份、比较基线、范围、设计来源、实现观察与相关变更。设计和实现可能来自不同仓库，因此记录的是版本向量，而非一个可以覆盖全部事实的 commit。

示意如下；这里的提交值和 ID 是格式说明，实际实例使用原型模型中的完整真实提交。

```json
{
  "id": "connector-observation-r2",
  "parent": "connector-observation-r1",
  "scope": ["connector-continuity"],
  "designRef": "approved-design-source",
  "implementationRefs": ["observed-code-commit"],
  "changes": ["typing-hotpath-correction"],
  "contextRef": "current-workset"
}
```

冻结时引用确切源版本，不依赖会继续移动的分支名。生成文件自身无需写入自己的最终 Git commit，避免为了更新自身提交号而无限再提交；冻结清单可以引用父基线、内容摘要和已有源提交，最终提交身份由 Git 提供。

当前入口只是一组指针。正式修订、来源观察和变更原因一旦冻结就不可原地覆盖；新实现、新实验和修正决定使用新身份。原型使用易读 ID，构建基线检查确保同 ID 的旧来源不会被重新指向其他提交。正式实现可以自动生成带内容身份的锚点 ID，用户界面仍显示清楚名称。

## 4. 局部历史必须和全系统历史分开

本轮 Mica 实际核对了连接器 0.1.6 与 0.1.7 的机制；没有重建旧版本每个组件。因此选择旧版本时，只替换连接器及其相关边，其他组件沿用当前上下文。它们在比较结果中标为 `context`，不算作“历史保持不变”。CAT 的 C04 也采用同样处理。

这一规则避免把 C01 的早期设计、C04 后来的实现版本、零槽位另一时期的提案拼成一个从未存在的“V1 全系统”。C01 和零槽位的原案保存在各自演进记录中，仍能完整说明原因，不必伪造共同时间截面。

局部历史若要比较范围之外的变化，需要扩展范围并补证据；不能仅修改旁边的节点，然后继续声称它只是当前上下文。原型会拒绝这种 `CONTEXT_DIVERGED`。如果以后确实得到完整历史模型，才提供真正的全系统前后视图。

## 5. 变更记录是因果链的连接点

一条变更需要连接：

**触发依据 → 设计决定 → 受影响对象 → 实现跟进 → 验证边界。**

触发依据可以是用户反馈、独立 GPT 研究、Work 审查、实验、真实故障、API 变化、性能测量或产品决定。产品判断不一定有一个实验附件，但必须有真实决定来源和理由；不能为了通过字段检查捏造证据。

记录的表达随内容变化。算法撤销可以先解释反例，再保留原目标与未闭合问题；性能修复可以围绕事件频率与关键路径；职责迁移可以围绕所有权和消费方。不会强制所有项目填“原始 Planner／Critic／最终方案”四个固定卡片。

旧决定可被后续决定取代，却不能无声消失。这个原则与 ADR 保留旧记录、标记替代关系的方法一致；本系统额外把记录连回组件、关系和实现。[ADR 原始方法](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)

### 三个真实变化说明不同的因果

**Mica：关键热路径修复。** 0.1.6 已有共享生命周期入口，同时还直接监听普通输入并使用固定轮询。0.1.7 保留共享入口，撤销普通输入直接触发与轮询，新增有界结构观察和合帧处理。组件的用户职责没有改变；调用关系和运行成本风险发生了重要变化。原型明确区分仓库修复记录、源码核查和未重新测量的真站性能。[旧实现](https://github.com/YuukiAS/Mica-for-ChatGPT/blob/9f56ea8d23a0895ddbb3f1e95ee207bd049b62c0/extension/src/reliability/connector-continuity.ts#L56-L108) · [修复提交](https://github.com/YuukiAS/Mica-for-ChatGPT/commit/aa4ce52581fff2e207d1f93600becbb3018b0efc)

**CAT C04：科学机制与实现修订。** 最后组成更新从以当前潜变量为条件，变为使用消去潜变量后的观测似然。模型、先验、科学目标和对外接口保持。旧 helper 仍保留，正常迭代已采用新函数。正确性证据与正式可靠性边界分别呈现，不把这次修订写成全系统验收通过。[冻结修订方案](https://github.com/YuukiAS/CAT-TRACE/blob/0d829fb17c458a076a15ec51893e917960107c21/docs/implementation/C04_REF_V0_1_2_Z_COLLAPSED_COMPOSITION_PLAN.md#L313-L372)

**DA：职责方案修改。** 旧共享规则库、新 DA 独立职责、workflow-core 编排与 Bridge 递送的划分发生改变。旧设计的通过记录不自动迁移给新的 `PROPOSAL`。图可以完整表示新方案，但所有新接线仍未实现。[新职责来源](https://github.com/YuukiAS/AI_Skills_Collection/blob/fd6916ad5fdd5fb905544b6a127f9b0d31a737e1/docs/design/ai-reliability-architecture/ARCHITECTURE_ZH.md#L74-L106)

## 6. 差异如何计算与展示

### 计算基于已声明的含义

原型按稳定 ID 对齐组件和关系。组件比较职责、归属、设计状态、机制以及实现绑定；关系比较两端、传递对象、交互点、类型与接通状态。对象数组顺序、坐标和颜色不形成变化。字段的新增、删除和修改能回到具体组件或关系，因而比几百行 Git 文本差异更接近用户问题。

这仍是**作者声明的结构化差异**。它不会从任意代码自动推断产品意义；机制正文改写也可能产生变化，不能宣称程序已经解决了自然语言语义等价。Chat 负责挑选有意义的修订、解释差异和保持项；以后有必要时再把易变正文与少量稳定合同字段分开。不要为了消除几处编辑噪声先引入 AI 推断服务。

### 展示分四层

1. **图上定位。** 标明变动节点、撤销关系和改接的消费方；当前阅读不显示已撤销路线。
2. **结构化摘要。** 列出职责、机制、归属或实现绑定哪些字段改变，不仅给出新增删除行数。
3. **因果解释。** 打开变更，看到触发、决定、具体改变、保留项与当前实现状态。
4. **真实源码比较。** 通过各自固定提交打开文件；必要时再使用 Git 或语法差异工具。代码语法差异不替代架构原因。[Difftastic 等工具的边界](OPEN_SOURCE_RESEARCH.md)

前后图用节点与关系的并集布局一次，再切换显隐与样式。位置稳定来自复用该布局，并非布局引擎能够自动理解历史。端点改变的一条关系在比较图中有两个实例，点击旧实例必须显示旧消费方及旧来源；历史视图中端点未变，也不能错误取当前来源。

不是每种改变都适合叠加。大范围重组、拆分合并或公式替换可以用局部前后说明，并引用共同身份或显式继承关系。总时间线只适合作为查找入口，不成为默认阅读顺序。

## 7. 影响传播使用前后并集，并保留未知

从修改对象和改接关系的参与者出发，沿改动前后的关系并集查找可能消费者。删除旧边不能导致旧消费者的检查责任随之消失。出现环时记录已访问集合，避免无限遍历。

结果只是声明关系中的候选检查范围。它不是实际运行因果证明，也不是必须全跑的测试清单。DOM 边界、共享状态或中心模块的改动可能使候选范围很宽；工具应说明原因，而不是把所有下游涂红并声称损坏。

界面将直接修改对象与推导的下游分开，排除种子自身。找不到下游也不能推出没有影响：关系尚未调查、动态事件、反射或跨仓库消费都可能构成未知。冻结和重要返修需要对这种未知作有范围的人工检查。

## 8. 实现是否跟上新架构

判断必须落到组件和合同范围。一个工作集可以显示：设计 D5，组件 A 仍实现 D4，组件 B 已跟进 D5，组件 C 仅有候选机制。不能用仓库最新提交时间把整图自动升级为已实现。

实现跟进应包含真实锚点、入口或消费方、与新设计的对应范围，以及未验证部分。新的实现可能完全保留旧接口，却替换内部算法；这种情况仍需要更新机制与证据。新的文件虽然存在但没有正常消费者，不能据此宣称接通。

证据适用性依赖候选、标准、输入与条件、执行器和观察者等身份。页面排版调整不应使数值实验失效；目标函数或关键调用改变则可能使相应旧证据不再适用。影响应按声明范围判断，不用一个最新时间戳统一替代。

原型包含拒绝把源码检查／测试定义当作运行证明的规则演示及反例测试；它没有接管真实产品测试执行或自动判断科研证据有效性。当前三项目记录均明确本轮没有重跑产品或科研验证。

## 9. 更正、回滚、合并和旧来源不可达

**更正旧事实。** 冻结前可以修正草稿；冻结后追加更正，指向旧记录，说明哪个事实错误、新证据是什么、当前采用哪个解释。旧材料继续可见，默认页面采用明确决定后的当前解释。

**回滚实现。** 回到旧源码不自动撤销新设计。工作集应显示新设计与回滚实现的差距，保留回滚原因和证据。若决定同时撤销新设计，也应有单独决定。旧测试能否复用仍需范围核对。

**并行修改。** 普通 Git 合并保留各自记录；同一职责、接口或决定存在冲突时，由 Chat 解决含义，不让 JSON 合并顺序决定架构。记录基线和父修订可以保留分歧来源，不另建分支管理服务。

**组件拆分或合并。** 保留旧身份的墓碑和显式继承关系；把实现绑定、历史原因和消费者逐项重新归属。不要通过复用旧 ID 把完全不同职责包装为连续历史。本轮没有实现通用拆分／合并编辑器。

**源码不可达。** 固定提交比可变分支可靠，但访问权限、仓库删除和对象清理仍可能使旧来源不可用。显示不可达原因，保留原身份；长期归档应在原项目授权边界内维护可达引用或保存获准快照，不能把私有源复制到公开阅读器来“修复链接”。

## 10. 本轮可运行的边界

原型已实现同一模型的两版切换、组件与关系差异、局部历史范围、并集布局、前后并集影响查询、按组件查看因果记录，以及本地结构校验。`build.mjs --baseline <已冻结模型>` 会拒绝旧变更、来源锚点、证据和修订被原地改写；普通构建不凭空知道冻结基线，远端 CI 尚未配置。

它没有实现跨仓库自动发现、语言语义解析、事实自动批准、任意版本图谱或交互写回。所演示的真实版本由本轮实际查阅来源后整理。选择这种边界是为了先检验最难的阅读、交接和历史意义，再决定哪些自动化值得建设。
