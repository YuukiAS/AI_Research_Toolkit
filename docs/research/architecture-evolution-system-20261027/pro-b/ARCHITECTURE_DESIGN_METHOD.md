# AI 架构设计与冻结方法

## 1. 目标

该方法解决的不是“怎样画完整架构图”，而是怎样让 Chat 在交付实现前完成足够具体的产品与机制设计，并把可机械验证的部分固化为架构合同。它避免两个极端：无限 Planner–Critic 循环，以及只给 Codex 一张高层图让其自行发明产品。

## 2. 八步设计路径

### 第一步：固定用户能力与边界

先回答用户最终获得什么能力、哪些对象在系统内、哪些外部依赖不由本系统控制、哪些历史能力必须保护。若能力本身还在争论，不应开始组件拆分。

交付：能力清单、非目标、成功与失败语义。

### 第二步：识别核心系统对象

寻找具有稳定身份和责任的对象，不以现有目录或预想页面为起点。组件数量应足以解释系统，又不把每个函数提升为架构组件。

交付：组件、责任、边界和依赖。

### 第三步：设计关系和真实载荷

对每条关键边说明：谁产生什么，谁在何处消费，载荷或约束是什么，失败时发生什么。无法回答载荷的边不能视为已设计接口。

交付：关系、数据/控制/状态类型、输入输出和失败语义。

### 第四步：展开关键机制

对决定用户能力、失败恢复、科学正确性或实现复杂度的组件，选择状态机、时序、算法、公式、数据合同或子图展开。至少覆盖正常路径和一个主要失败路径。

交付：机制步骤、不变量、异常处理和开放问题。

### 第五步：分配实现责任

说明哪些机制已经存在，哪些应由 Codex 实现，哪些仍需技术事实调查或科研决策。设计态对象只记录预期责任，不虚构源码锚点。

交付：三轴状态、实现边界、预期锚点类型。

### 第六步：定义验证

对每项重要能力说明什么证据能支持它。结构文件、单元测试、浏览器行为、统计 oracle 和用户验收不能互相替代。

交付：证据计划、失败判据、关键测试和审查对象。

### 第七步：运行完整性检查与独立审查

机械检查先发现引用、锚点和状态矛盾；GPT Work 再寻找产品遗漏、反例、过度复杂度、证据错配和实现不可行性。审查 finding 必须绑定具体对象，不能只留下散文意见。

### 第八步：冻结修订和实现包

只有核心机制、接口、失败处理、验证和开放边界都已明确，才冻结 `Revision`。Codex 接收的是当前修订、目标对象、允许修改的范围、真实仓库定位、成功/失败判据和必须回报的实现事实。

## 3. 什么时候只需要一个 Chat

下列情况通常不需要第二个 Pro 或 GPT Work：

- 局部、可逆、边界清楚的组件修改；
- 只补充已冻结设计的实现锚点；
- 不改变用户能力的内部重构；
- 已有成熟模式且风险低的文档更新；
- 机械漂移修复。

一个 Chat 仍应完成结构检查，但无需人为增加审查轮次。

## 4. 什么时候需要第二个独立 GPT Pro

第二个 Pro 的价值在于独立探索方向，而不是给同一方案盖章。适用情形：

- 产品形态和技术路线仍有多个可行范式；
- 设计会长期影响多个仓库；
- 需要大量外部方法研究和替代方案比较；
- 第一方案可能受既有架构路径依赖；
- 用户明确需要真正独立的研究候选。

两个 Pro 必须从共同基线独立工作，不能读取彼此中间成果。最终比较应由单独的综合步骤完成。

## 5. 什么时候 GPT Work 有额外价值

GPT Work 适合需要独立高智力判断但不拥有最终设计权的工作：

- 搜索遗漏和矛盾；
- 构造反例；
- 核查真实实现与设计是否一致；
- 评估复杂产品体验；
- 检查科学、统计或数值证据；
- 对最终候选执行高成本验收。

Work 的 finding 进入 `Evidence` 或 `Issue`，由 Chat 决定是否形成新修订。若 finding 已证明设计不成立，Chat 必须返回设计，而不是让 Codex修补。

## 6. 什么时候做技术事实调查

当设计依赖以下事实时，先调查再冻结：

- 外部 API、平台或浏览器行为；
- 当前源码结构和可复用实现；
- 性能、资源或规模假设；
- 数值算法的稳定性；
- 开源库维护、许可和能力边界；
- 真实用户路径或错误复现。

调查结果进入 Evidence，不直接变成架构决定。决定仍需说明如何解释这些事实。

## 7. Freeze 条件

一个架构修订可冻结，至少满足：

1. 用户能力、边界和非目标明确；
2. 核心组件责任不重叠且没有关键孤岛；
3. 关键关系有真实载荷和消费者；
4. 关键组件可展开到机制层；
5. 失败和恢复路径足以指导实现；
6. 实现责任和允许的空白明确；
7. 验证证据与能力相匹配；
8. 重要取舍有原因和证据；
9. 开放问题不会被 Codex 被迫自行决定；
10. 语义模型通过完整性检查。

“有完整页面”“画了所有箭头”或“Critic 没再提问题”都不是 freeze 条件。

## 8. 必须返回设计的条件

- Codex 需要发明核心机制或接口；
- 已接受组件无法说明内部如何工作；
- 一条关键边不知道传递什么；
- 实验或真实故障否定当前机制；
- 新需求改变用户能力或系统边界；
- 实现只能通过降低需求才能完成；
- 关键证据与修订结论冲突；
- 一个 blocker 影响了冻结范围。

普通实现缺陷、命名变化和局部代码错误不需要重新设计，只需在同一任务修复并更新锚点。

## 9. Codex 接手包

最小实现包应包含：

- 固定的架构修订标识和绑定提交；
- 本次目标组件与关系；
- 机制、接口、状态和失败行为；
- 不允许改变的用户能力和既有行为；
- 允许修改的目录或文件范围；
- 实现前仍需核对的事实；
- 成功测试、失败测试和真实入口；
- 需要写回的 anchor、evidence、issue 和实现提交；
- 遇到设计空白时的停止条件。

Codex 可以提出 implementation observation，但 observation 不能自动改写设计。若实现发现某个冻结机制不可行，应创建阻断证据并返回 Chat。

## 10. 返修流程

```text
故障或 finding
→ 绑定组件/关系/机制
→ 判断是实现缺陷还是设计缺陷
→ 实现缺陷：同修订修复并更新证据
→ 设计缺陷：Chat 创建新 Revision
→ 记录 before/after、原因、证据、影响和不变项
→ Codex 跟进实现
→ 验证实现是否追上新架构
```

这样返修不会退化成“再写一份文档”，也不会因为每次发现问题都重启完整治理循环。
