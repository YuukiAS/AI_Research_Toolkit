# 正式建设方案比较与推荐路线

## 1. 备选方案

### 方案 A：继续高质量 Markdown + Git history

优点：零新运行时、作者熟悉、可长期保存。缺点：跨文档连接弱；实现锚点和状态难机械检查；系统意义差异仍需人工重写；整体、机制和实现容易分散。

适合：小型、变化少、只有一个主要读者的项目。

### 方案 B：扩展现有 R2 Architecture Explorer

优点：已有整体拓扑和路径交互；视觉方向已验证。缺点：若只继续增加页面内容，会把语义埋在前端数据中；版本、证据和 source of truth 仍未解决。

适合：作为阅读器和视觉原型底座，不适合作为最终数据模型。

### 方案 C：CAT-TRACE 式高质量 HTML/PDF 演进文档

优点：因果叙事强、当前模块与历史结合自然、易分享。缺点：跨项目复用和机械检查有限；真实实现锚点、组件关系和版本切换需要人工维护；规模扩大后难保持一致。

适合：重要设计修订的正式叙事导出，不作为唯一系统。

### 方案 D：采用成熟架构平台或开发者门户

候选如 Structurizr、Backstage、Ilograph 等。优点：已有模型或门户能力。缺点：不能完整表达本任务独特的三轴状态、因果返修和跨软件/Skill/科研锚点；重平台带来运维和适配成本。

适合：组织已有相同平台时集成，不建议为本需求新建。

### 方案 E：结构化 manifest + 静态交互阅读器

优点：Git 原生、可机械检查、可生成多种展示、无后台、可链接真实来源；能自然支持语义差异和设计/实现共存。缺点：需要定义小型模型、生成器和维护规则。

适合：当前多项目、长期演进、AI 参与设计和实现的场景。

### 方案 F：图数据库 + 后台服务 + 在线编辑器

优点：复杂查询和多人实时协作潜力。缺点：部署、迁移、账户、权限、备份和同步成本大；引入第二事实库；当前规模没有必要。

不推荐。

## 2. 唯一推荐

选择方案 E，并把方案 B 的视觉经验、方案 C 的因果叙事、方案 A 的 Markdown 可读性组合进去：

```text
Git 仓库
├── architecture/ledger/*.json|yaml
├── architecture/narratives/*.md
├── source code / skills / formulas / tests
└── generated architecture site
```

核心事实存储不依赖前端框架。静态阅读器只是生成目标之一，还可导出 Markdown 或 PDF 摘要。

## 3. 推荐技术栈

### 数据与校验

- JSON 或 YAML；一期示例使用 JSON；
- JSON Schema Draft 2020-12；
- Ajv；
- TypeScript 自定义跨引用检查；
- Git permanent links。

### 生成与前端

- Node.js 静态生成器；
- 简单 TypeScript/HTML/CSS；
- Cytoscape.js；
- ELK.js；
- Mermaid 按需；
- 无数据库、无登录、无常驻服务。

### 可选源码索引

- 默认：路径 + 固定提交 + 符号 + 指纹；
- 需要时：tree-sitter；
- 已有生态时：SCIP；
- 不统一部署代码搜索服务器。

## 4. 阶段 0：保持现状并验证维护成本

在正式开发前，用本研究的 schema 和三个样例再录入一个真实新修订。验证：

- Chat 是否能直接形成结构化记录；
- Codex 是否能可靠补锚点；
- 用户是否真的使用语义差异；
- 维护一项变更需要多少额外工作。

若每次更新仍需大量手工复制，先修作者体验，不扩张功能。

## 5. 阶段 1：最小可用账本

交付：

1. schema 与示例；
2. 跨引用/状态检查器；
3. 静态生成器；
4. 三项目切换；
5. 系统拓扑；
6. 组件机制和实现锚点；
7. 父修订语义差异；
8. 完整性报告；
9. GitHub Pages 或本地静态打开。

不实现在线编辑、全文搜索或自动源码索引。

## 6. 阶段 2：真实维护增强

只有阶段 1 出现真实痛点后选择性加入：

- tree-sitter 锚点扫描；
- rename/move 迁移建议；
- 依赖图和影响候选；
- 多仓库 source snapshot；
- Markdown/PDF 导出；
- 组件历史聚合；
- CI 漂移报告。

## 7. 阶段 3：是否需要平台化

只有出现下列证据才讨论后台：

- 数十个活跃项目、静态构建明显过慢；
- 多人需要并发写入和权限；
- 跨仓库查询无法在构建时完成；
- 需要组织级目录和服务所有权；
- Git PR 工作流成为可测量瓶颈。

即使如此，Git 仍应保留权威修订，后台只能缓存和索引。

## 8. 数据布局建议

小项目可用单文件：

```text
architecture/ledger.json
```

中型项目可分片：

```text
architecture/
  project.json
  revisions/
  components/
  mechanisms/
  decisions/
  evidence/
```

生成器将其合并为物化快照。不要过早拆成几十个小文件；分片只为减少冲突和提升可读性。

## 9. CI 建议

每个 PR 运行：

1. schema 校验；
2. 跨引用检查；
3. 固定提交/路径可达性；
4. linked/validated 状态一致性；
5. 重大变更原因与证据；
6. 静态站点构建；
7. 少量浏览器交互测试；
8. 视觉截图回归仅用于显著布局变化。

不要把“检查通过”包装为架构正确。报告名称应是结构完整性与锚点健康度。

## 10. 成本控制

一期预期只有一个小型前端和一组构建脚本，依赖均为本地开发依赖。可部署到 GitHub Pages，也可完全离线打开。每个修订的人工维护应集中在原因、机制和证据，不重复录入自动可得的文件树和 commit 信息。

## 11. 退出条件

若试点表明以下任一情况成立，应停止正式建设并退回 Markdown + 现有 Explorer：

- 结构化录入成本持续高于理解收益；
- 用户只使用最终 PDF，从不使用下钻与差异；
- 锚点漂移噪声过高且无法降低；
- 三项目需要完全不同的数据模型；
- 生成器开始复制项目管理或代码搜索平台。

当前原型和压力测试未出现这些失败，因而推荐继续轻量试点，而不是直接建设平台。
