# 产品与信息架构

## 1. 产品定义

Architecture Ledger 是面向复杂软件、科研方法和 AI 能力系统的 Git 原生架构合同与阅读器。它同时服务两个方向：

- 对人：快速理解当前系统、内部机制、真实实现、变化原因和开放问题；
- 对 AI：要求架构在交给实现前达到足以展开、足以绑定、足以验证的完整度。

它不是新的项目管理器，也不接管代码、设计文档、测试或论文。它保存的是这些事实之间稳定、可检查的语义连接。

主要用户只有四类：项目负责人、负责设计的 Chat、独立审查的 GPT Work、负责实施的 Codex。外部读者可以使用只读生成站点，但不参与权限模型。

## 2. 用户平时打开什么

用户通常打开项目仓库生成的静态站点。首页先回答“当前系统是什么”，而不是先显示历史、任务列表或内部角色。推荐阅读顺序为：

1. 当前架构拓扑；
2. 正常、失败或恢复路径；
3. 点击组件查看机制；
4. 在需要时查看实现锚点；
5. 切换修订或打开语义差异；
6. 查看原因、证据、下游影响和实现是否追上；
7. 打开完整性检查，只看当前需要处理的缺口。

默认页面不显示所有字段。设计状态、实现状态和证据状态以克制的文字和小标记表达；历史、审查和实现列表按需展开。

## 3. 信息分层

### 3.1 系统层

系统层由项目边界、核心组件、外部依赖、关系和路径构成。它必须能表达：

- 数据流、控制流、状态和约束；
- 正常路径、失败路径、恢复路径；
- 已有能力保护；
- 当前修订和开放边界。

关系不是无语义箭头。每条重要关系至少说明载荷或约束、生产者、消费者，以及发生在哪个机制步骤。

### 3.2 机制层

机制层没有统一页面模板。组件可选择最合适的内容表示：

- 状态机：例如 Mica stale composer 恢复；
- 时序：例如事件、观察器和恢复器的交互；
- 算法步骤和公式：例如 CAT-TRACE C01、C04；
- 数据结构或接口合同；
- 关系子图；
- 简短正文与关键不变量。

机制层的验收标准是：另一个实现者无需发明核心产品或算法决定，即可理解“什么时候发生什么、输入输出是什么、失败怎样处理、状态怎样改变”。

### 3.3 实现层

实现层只记录真实存在且可定位的对象：

- 软件：package、目录、模块、文件、类、函数、API、selector、schema、config、hook、test、validator；
- AI Skill：Skill 文件、section、rule、prompt block、validator 和控制行为的具体语句；
- 科研方法：模型公式、数值 routine、数据合同、simulation、reference implementation、oracle 和测试。

锚点必须包含仓库、固定提交、路径、锚点类型和可选符号或行范围。分支链接只适合“当前浏览”，不能作为历史修订的永久证据。

## 4. 页面结构

### 4.1 顶栏

顶栏只保留项目切换、当前修订、与父修订比较和完整性检查。版本名称应表达系统意义，如“零槽位积分路线撤销”，而不是原始 commit 哈希。

### 4.2 左栏：组件目录

组件按系统责任分组，而不是按文件夹平铺。每项只显示名称和必要的三轴摘要。目录支持搜索和定位差异对象。

### 4.3 中央：上下文视图

中央区域根据所选内容在以下视图间切换：

- 当前架构；
- 正常、失败、恢复路径；
- 关系上下文；
- 修订差异。

拓扑节点密度应克制。过多内部细节应在组件机制中呈现，而不是把整个系统画成无法阅读的巨图。

### 4.4 右栏或移动端底部面板：详情

详情分为“机制、实现、演进”三类，不使用固定的“为什么需要、输入什么、去掉以后”模板。

- 机制：内容专用视图；
- 实现：当前锚点、行为事实、测试与证据；
- 演进：当前决定、被撤销路线、证据链、受影响对象和历史修订。

移动端用底部面板承载详情，保持拓扑仍可平移查看。

## 5. 写入与生成流程

```text
Chat 冻结架构语义
        ↓
提交 ledger + 必要正文 + source anchors
        ↓
结构校验 / 引用校验 / 状态一致性检查
        ↓
Codex 实现并补真实 anchor、commit、test evidence
        ↓
漂移检查与 GPT Work 独立审查
        ↓
生成静态交互站点
```

静态站点是构建产物，不是事实来源。它可以部署到 GitHub Pages，也可以直接从仓库打开。

## 6. 设计态与实施态共存

同一组件可以先以设计态存在。此时应有：

- 稳定责任与边界；
- 关系和载荷；
- 机制或明确的开放设计问题；
- `implementation = none`；
- 不得出现虚构的文件、函数或测试。

实施后，不创建另一个“实现组件”替代原组件，而是为当前组件增加实现锚点、实现提交、测试和证据。若代码偏离已接受设计，则形成 `Issue` 或新 `Revision`，而不是悄悄修改说明。

## 7. 当前优先、历史按需

每个对象都有当前投影和历史事件。默认页面只渲染当前修订有效的对象与关系。用户展开“演进”时，按因果链显示：

```text
旧设计
→ 触发证据
→ 决定
→ 新设计
→ 实现变化
→ 验证结果
```

这避免 CAT-TRACE 式高质量演进内容退化成日期流水账，也避免几十轮历史淹没当前架构。

## 8. 权限与责任

### Chat

拥有产品目标、组件责任、关键机制、接口、失败处理、取舍和修订冻结权。Chat 可以更新设计语义和决策，但不能把未验证实现写成事实。

### GPT Work

独立检查遗漏、反例、产品质量、因果证据和复杂验证。它可以新增 finding/evidence，建议 `REVISE`，但不默认覆盖当前设计。

### Codex

只实现冻结任务，记录真实代码事实、运行结果、锚点和实现观察。若需要自行发明核心机制，应停止并创建设计缺口，而不是采用“合理默认”。

### 自动化

只负责可机械判断的事情：模式校验、引用完整性、锚点存在性、符号候选、提交可达性、状态矛盾和生成站点。它不宣称产品正确或科学结论成立。

## 9. 视觉原则

- 以当前系统和内容为中心，不以内部流程为中心；
- 使用留白、细边界和层级排版，不依赖大量彩色卡片；
- 状态主要用文字与少量低饱和强调；
- 关系标签短而具体；
- 复杂内容按需展开；
- 同一组件的三层内容保持上下文，不把用户送到多个独立页面迷路；
- 历史差异使用增、改、撤销三种稳定语义，不模拟 Git 补丁界面。

## 10. 非目标

一期不建设：多人实时编辑、账户权限、在线数据库、跨组织目录、全文语义搜索、代理运行时、自动架构生成、自动科学审查或代码编辑器。需要这些能力时，应先证明静态 Git 原生路线已成为真实瓶颈。
