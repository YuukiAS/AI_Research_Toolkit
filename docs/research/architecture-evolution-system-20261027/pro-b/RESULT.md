# Architecture Ledger：最终推荐

## 核心判断

最合适的最终形态不是新的架构后台平台，也不是继续维护一组互不相连的静态文档，而是一套轻量、Git 原生的“架构演进账本”：

> **少量结构化语义记录 + 指向真实来源的锚点 + 有意义修订的不可变历史 + 自动生成的静态交互阅读器 + 可执行的完整性与漂移检查。**

用户平时打开的是一个静态交互阅读器；Chat 设计时维护的是同仓库内的语义记录和必要正文；GPT Work 审查语义完整性、因果链和证据边界；Codex 只更新实现事实、真实锚点和验证结果。Git 仍然是版本与审计基础，源码、设计文档、测试和提交仍然各自保留事实主权。

这不是“再做一个架构展示网站”。阅读器只是同一份架构合同的投影。真正的新能力是把当前设计、内部机制、真实实现、证据状态和变化原因放进同一个可验证模型，并让架构设计过程本身必须填满这些关键连接。

## 为什么不选更重的系统

本任务最强的替代方案是高质量 Markdown、Git 历史和现有 R2 Architecture Explorer。它们已经能完成整体解释和一部分交互展示，但共同缺少四项能力：

1. 架构对象与真实实现之间可检查的绑定；
2. 设计状态、实现状态、证据状态彼此独立；
3. 面向系统意义的版本差异，而不是文本差异；
4. 变化原因、触发证据和下游影响形成可追溯因果链。

因此值得建设的是这一小层语义与检查能力，而不是账户、数据库、在线编辑器、云服务或代理运行时。若一期实现超过一个静态生成器、一个模式校验器、一个浏览器端阅读器和少量提取器，基本说明范围已经偏离。

## 最小充分结构

Architecture Ledger 只保存九类对象：

- `Project`：项目边界、事实来源和当前修订；
- `Revision`：一次有系统意义的架构修订；
- `Component`：具有稳定责任的系统对象；
- `Relation`：组件间传递的真实对象、控制或约束；
- `Mechanism`：组件内部真正发生的步骤、状态、算法或公式；
- `Anchor`：指向文件、符号、规则、公式、测试或提交的真实定位；
- `Decision`：采用、修改或撤销某条路线的理由；
- `Evidence`：审查、实验、测试、故障、用户反馈或外部变化；
- `Issue`：尚未闭合的缺口、阻断项或已知漂移。

这些对象不是页面卡片模板。展示层根据内容选择拓扑、时序、状态机、算法步骤、公式、数据结构、正文或代码锚点。通用性来自底层语义，不来自所有项目画同一种图。

## 三个状态轴必须分开

一个组件不能只用一个“状态”概括。最小且足够的表示是三条独立轴：

- 设计：`proposed / accepted / open / superseded`；
- 实现：`none / partial / linked`；
- 证据：`none / checked / validated`。

这样 Delivery Assurance 可以诚实显示“设计已接受、实现尚无”；Mica 可以显示“设计已接受、实现已绑定、关键路径已检查”；CAT-TRACE 的 C03 可以显示“设计部分接受、实现为空、核心计算仍开放”。系统不需要十几个生命周期状态，也不会把“存在代码”误写成“能力已验证”。

## 有意义版本与返修

Architecture Ledger 不把每个 Git commit 都升级为架构版本。只有下列变化至少满足一项时才创建 `Revision`：

- 用户能力、系统边界或组件责任改变；
- 组件或关系新增、删除、拆分、合并或重定向；
- 机制、算法、状态机、接口合同或失败处理改变；
- 一条路线被证据撤销；
- 设计与实现的对齐状态发生重要变化；
- 新证据改变了系统应如何理解或验证。

纯重命名、格式调整和不改变系统意义的内部重构继续留在普通 Git 历史。每个架构修订必须明确：变化对象、变化类型、旧值、新值、原因、触发证据、影响范围、实现是否跟上、保留不变项。默认界面只显示当前状态；历史从组件或关系上按需展开。

## 设计与展示是一件事的两个投影

Chat 设计时不是先写一份自由散文，再由另一个工具“画图”。它直接形成可冻结的架构记录：

1. 用户能力和边界；
2. 核心对象与责任；
3. 关系及其真实载荷；
4. 每个关键组件的内部机制；
5. 实现责任与允许的空白；
6. 正常、失败和恢复路径；
7. 验证方法与开放问题；
8. 冻结修订。

同一份记录随后生成整体拓扑、组件详情、机制视图、实现锚点和语义差异。因此“展示不清楚”会反向暴露设计缺口：一条边说不清传什么，接口尚未设计；一个组件无法展开机制，责任仍过度抽象；声称实现却没有真实锚点，状态不成立；修改没有证据或理由，不允许静默覆盖。

它可以承担部分架构完整性检查，但不应冒充自动架构评审。检查器适合发现结构性矛盾、缺失引用、状态不一致和可疑漂移；产品取舍、科学正确性、视觉质量和复杂失败链仍需要 Chat 或 GPT Work 判断。

## 对三个真实项目为何成立

### Delivery Assurance

它最需要的是诚实的设计态表达。账本可以记录推荐组件、责任、关系、假设和开放验证，同时将实现轴设为 `none` 或 `partial`。界面不会生成不存在的 package、function 或测试。设计修订仍可比较，旧研究和新职责划分也可形成有原因的变更记录。

### Mica

它证明账本可以穿过三层：系统层的 ChatGPT DOM、长线程扫描和恢复机制；机制层的 stale composer 有限恢复状态机与 connector continuity 生命周期；实现层固定到 `content.ts`、`stale-composer-recovery.ts`、`connector-continuity.ts`、真实 selector、函数和端到端测试。文件移动或符号改名可由锚点检查发现，而不是靠人工发现文档失真。

### CAT-TRACE

它证明同一模型可以容纳数学和软件共同演进。C01 可绑定公式、数值原语、C++ routine 和稳定性测试；C04 可绑定 Albert–Chib 算法、R reference engine 和诊断证据；匿名零槽位可以记录原始 local Laplace、Critic 的确定性反例、撤销决定、当前替代方向、被阻断的下游模块和“尚无实现”的真实状态。

## 推荐采用的成熟能力

- 采用 C4/Structurizr 的层级与责任思维，但不强制所有对象遵循 C4 页面模板；
- 用 Cytoscape.js 渲染交互拓扑，ELK.js 在需要时计算布局；
- 用 Mermaid 处理适合文本表达的时序、状态和小型流程；
- 用 JSON Schema 与 Ajv 校验语义记录；
- 借鉴 MADR 与 Log4brains 的决策历史组织；
- 对源码符号锚点，可选用 tree-sitter 或 SCIP 生成辅助索引；
- GumTree 只用于实现考古，不作为架构语义差异核心。

不推荐把 Backstage、图数据库、React Flow 编辑器、D2 服务端渲染、账户系统或向量数据库放进核心路径。

## 推荐建设范围

一期只需要：

1. `architecture/ledger.json` 或少量分片 YAML/JSON；
2. JSON Schema 与跨引用检查；
3. 静态站点生成器；
4. 浏览器端拓扑、详情和差异阅读器；
5. GitHub 源码永久链接生成；
6. 设计、实现、证据三轴检查；
7. 少量项目适配规则。

二期只有真实维护痛点出现后再加入符号索引、自动锚点迁移建议和变更影响提示。任何后台服务都必须由实际规模或协作需求证明，而不是预先建设。

## 最终评价

这套系统值得建设，但只值得建设“最小充分层”。它能减少用户反复重读散文和 Git diff 的成本，也能让 Chat 更难把关键机制留给 Codex 自行决定。它不能替代设计判断、代码审查或科学验证；它的价值在于把这些判断的对象、因果和证据连接起来，并且始终能回到真实 source of truth。
