# 事实来源与实现绑定

## 1. 基本原则

Architecture Ledger 不成为第二套人工维护的事实数据库。每类事实继续由最合适的来源拥有：

| 事实 | 主要来源 | 账本保存什么 |
|---|---|---|
| 当前代码 | Git 仓库和固定提交 | 锚点、符号、责任映射 |
| 架构决定 | 冻结设计文档或结构化修订 | 对象、关系、原因、状态 |
| 代码历史 | Git commit / tag | 有意义修订的绑定与实现变化 |
| 测试结果 | 测试代码、CI、结果文件 | 证据引用与能力范围 |
| 审查 finding | GPT Work/独立审查产物 | Evidence、Issue、受影响对象 |
| 用户反馈 | 原始反馈或批准记录 | 触发证据和决策解释 |
| 科学结论 | 原始推导、实验、论文或结果 | 公式/结论锚点与证据强度 |
| 外部工具事实 | 官方文档、源码、版本 | 采用记录和版本边界 |

生成站点从不反向成为事实来源。

## 2. 锚点格式

建议最小格式：

```json
{
  "id": "mica-stale-attempt-recovery",
  "kind": "symbol",
  "repo": "YuukiAS/Mica-for-ChatGPT",
  "commit": "7059c0dc24b908b57bd0e1f475142ba4f4520621",
  "path": "extension/src/reliability/stale-composer-recovery.ts",
  "symbol": "attemptRecovery",
  "required": true,
  "summary": "对匹配旧载荷执行有限次数原生清空并进入验证"
}
```

固定提交保证历史可复现；`symbol` 帮助当前导航；行范围仅作辅助，因为文件插入会使行号漂移。

## 3. 软件锚点

优先级为：

1. 稳定符号或 schema 标识；
2. 固定提交下的文件路径；
3. 可选 AST/SCIP 符号标识；
4. 行范围和文本指纹；
5. 测试或结果锚点。

selector、配置键和事件名也是一等实现对象。例如 Mica 的 `TURN_SELECTOR`、`COMPOSER_SELECTOR`、`SURFACE_SELECTOR` 和 `CONNECTOR_PILL_SELECTOR` 应作为 selector anchor，而不是埋在描述文字中。

## 4. AI Skill 与 Prompt 锚点

Skill 行为可能由几行自然语言控制，不能只链接整个文件。推荐组合：

- 固定提交与 Skill 文件路径；
- section 标题或显式 rule id；
- 关键规则的规范化文本指纹；
- validator 或触发测试；
- 行为说明和适用边界。

若规则没有稳定标题，正式能力修改时应先增加稳定 `rule_id` 或 section anchor。文本指纹用于发现变化，不作为唯一身份。

## 5. 科研算法锚点

科研对象可能没有单一源码入口。一个算法组件可同时绑定：

- 模型公式或定理章节；
- 数值算法说明；
- routine；
- 数据合同；
- simulation 场景；
- reference implementation；
- 高精度 oracle；
- test 与结果文件。

例如 CAT-TRACE C01 的“已实现”不能只靠 `ct_math.cpp`；至少还需稳定性测试或 oracle 证据。C04 的“reference”也必须受 MCMC 诊断边界约束。

## 6. 自动发现、半自动生成与人工冻结

### 可自动发现

- 文件和固定提交是否存在；
- 简单符号、selector、schema key 和测试名；
- import/dependency 关系；
- Git rename 候选；
- 失败锚点和未解析引用；
- 当前代码与上次索引的变化。

### 适合半自动建议

- 文件移动后的锚点迁移；
- 函数改名候选；
- 新测试与组件的可能关联；
- 代码依赖变化对应的受影响组件；
- 普通 Git diff 中可能具有架构意义的变化。

### 必须由 Chat 或人工冻结

- 组件责任和系统边界；
- 关系的业务/科学语义；
- 机制和失败处理；
- 变化原因与不变量；
- 证据是否足以支持状态提升；
- 是否构成架构修订。

Codex 可以更新已验证实现事实，但不能自动把代码结构提升为产品架构。

## 7. 文件改名和移动

固定历史锚点不会失效；当前锚点检查会发现旧路径在新提交中不存在。工具可用 Git rename、blob 相似度、符号指纹或 AST 候选建议迁移。最终更新应记录：旧锚点、新锚点、迁移提交和“机制是否改变”。

若只是移动文件，不创建架构修订；若移动伴随责任拆分或接口改变，则创建修订。

## 8. 函数改名

函数名不是唯一身份。推荐同时保存：固定提交、路径、符号种类、局部签名/文本指纹和可选 SCIP/AST 标识。检查器发现原符号缺失后给出候选，不自动确认。若行为未变，只更新锚点；若签名或机制改变，评估语义差异。

## 9. 架构先变、实现未跟上

新设计冻结后，组件仍保留旧实现锚点，但修订对齐状态为 `behind`，界面明确显示“当前代码仍对应父修订”。不得删除旧锚点后假装 `none`，也不得把预期文件路径写成真实实现。

Codex 完成后追加 implementation commit、当前 anchors 和验证 evidence，再改为 `aligned`。

## 10. 代码先变、架构未更新

漂移检查比较：

- 关键锚点内容变化；
- 组件相关文件和依赖图变化；
- selector/schema/rule 指纹变化；
- 测试覆盖变化；
- 受保护行为的真实入口结果。

检查器只报告候选漂移。Chat 判断这是等价重构、实现缺陷，还是未记录架构变化。禁止自动重写架构图来“追随代码”，否则代码偶然结构会取代产品设计。

## 11. 证据绑定

Evidence 必须说明：对象、来源、时间、提交、方法、结果和结论边界。例：

- 单元测试通过只支持局部逻辑；
- 浏览器端到端测试支持真实交互路径；
- 模式校验支持数据结构，不支持专业正确性；
- MCMC 诊断通过支持该场景的参考链质量，不支持生产可扩展性；
- 用户反馈可以触发产品修订，但不自动证明根因。

## 12. 历史回看

旧修订使用固定提交链接和当时的物化快照。若仓库重写历史或私有来源不可访问，页面标记“来源不可达”，不以当前内容填补。重要长期产物可在同仓库保存小型证据摘要，但不复制大段源码或结果。

## 13. 完整性与漂移报告

报告分三类：

- **阻断**：已声称 linked 却没有锚点、重大变更无原因、关键关系无载荷；
- **需复核**：符号疑似移动、测试证据过期、实现落后设计；
- **诚实边界**：设计明确为 open/none，不是错误。

检查器帮助暴露事实边界，不替代产品或科学判断。
