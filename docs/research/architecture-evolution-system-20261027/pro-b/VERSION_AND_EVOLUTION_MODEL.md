# 版本、返修与演进模型

## 1. 为什么 Git commit 不等于架构版本

Git commit 是代码与文件变更的可靠历史，但粒度由开发活动决定。一次架构修订可能跨越多个 commit，一个 commit 也可能同时包含格式调整、测试修复和实现改动。若把全部 commit 放进架构时间线，用户仍然无法快速回答“系统意义上变了什么”。

Architecture Ledger 因此保留两层历史：

- Git 历史：完整、不可替代的文件事实；
- Architecture Revision：经过解释的系统语义变化。

每个架构修订绑定一个或多个提交，但不复制 Git diff。

## 2. 何时创建架构修订

满足以下任一条件，通常需要新修订：

1. 用户能力、系统边界或非目标改变；
2. 组件或关系新增、删除、拆分、合并或改变责任；
3. 关键机制、接口、状态机、算法、公式或失败恢复改变；
4. 一条设计路线被审查、反例、故障或用户反馈撤销；
5. 实施事实暴露设计不可能或信息不足；
6. 一个开放 blocker 被关闭或新出现，并改变下游可实施范围；
7. 外部 API 或平台变化要求架构响应；
8. 实现正式追上先前已冻结的设计，并形成新的可用能力边界。

下列变化通常不创建架构修订：排版、注释、变量重命名、等价重构、普通依赖升级、测试速度优化、无行为变化的文件移动。它们仍可更新实现锚点和 Git 历史。

## 3. 修订结构

每个 `Revision` 至少记录：

- 稳定标识、标题和父修订；
- 作用范围；
- 修订原因和触发证据；
- 冻结日期与绑定提交；
- 语义变更集合；
- 仍然有效的不变量；
- 实现对齐状态；
- 新增或关闭的问题。

标题应表达变化，例如“撤销匿名零槽位普通局部 Laplace”，而不是“R4”或“2026-09-16 更新”。内部审查轮次可以作为证据标签，但不承担用户理解任务。

## 4. 语义差异

### 4.1 组件差异

显示新增、修改、撤销和未变组件。修改必须说明责任、机制、边界或状态中哪一项改变。纯实现重构不应伪装成组件变化。

### 4.2 关系差异

显示新增、删除、改向、载荷改变和失败语义改变。关系差异应能回答接口是否真的变化，而不是只说明一条线颜色不同。

### 4.3 机制差异

对状态机显示状态/转换变化；对算法显示步骤、公式、近似或容错变化；对数据合同显示字段和不变量变化；对正文显示经过整理的前后语义，而非整段文本 patch。

### 4.4 实现差异

显示锚点新增、移动、失效、替代和测试变化。实现差异与架构差异并列，但不互相冒充：架构未变时可以只有实现差异；设计改变但尚未实施时也可以没有实现差异。

### 4.5 因果与影响

每个重要变化必须链接触发证据，并说明：

- 为什么旧路线不再成立；
- 新路线解决了什么；
- 哪些下游组件、关系、测试或用户能力受影响；
- 哪些不变量保持不变；
- 当前代码是否跟上。

## 5. 当前优先、历史按需

默认页面加载当前修订，不把时间线放在首页中心。历史入口有三种：

1. 在顶部选择另一个有意义修订；
2. 选择“与父修订比较”；
3. 在组件或关系的“演进”面板查看对象历史。

对象历史按因果链组织，不按消息时间排序。一个典型条目如下：

```text
原设计：匿名全零列使用普通 local Laplace
触发：Critic 确定性反例显示远尾质量被局部模式近似遗漏
决定：撤销该正式积分器
当前：保留有限截断模型，研究 discovery complement 积分
影响：C03、C05、C06、C10 阻断；C01、synthetic C02、C04 不受阻
实现：无正式实现，不允许 Codex 自行选择求积
```

## 6. 被撤销路线

撤销不是删除历史。`superseded` 对象仍保留：旧设计、当时依据、撤销证据、替代方案和影响。默认拓扑不渲染旧对象；差异和演进视图可显示。

若旧路线已经实现，锚点仍固定到历史提交。当前实现若已移除，则记录移除提交。这样可以区分“从未实现”“曾实现后撤销”和“代码仍残留但设计已撤销”。

## 7. 实现追赶

设计修订和实现修订可以分开。新的设计修订冻结后，各组件拥有对齐状态：

- `not_applicable`：纯设计对象或无需代码；
- `behind`：实现仍对应旧设计；
- `partial`：部分锚点已更新；
- `aligned`：实现和验证与当前修订一致；
- `drifted`：代码发生未解释变化。

这不是第四个通用生命周期轴，而是修订差异中的实现对齐判断。

## 8. 返修归因

返修先判断问题发生在哪一层：

- 需求变化：创建产品修订；
- 设计遗漏或反例：创建架构修订；
- 实现缺陷：在同一架构修订内修复；
- 证据不足：更新证据状态或创建验证任务；
- 外部依赖变化：记录外部证据并评估是否需架构修订；
- 仅文档失真：修复锚点/说明并记录漂移。

避免看到任何失败就重新设计，也避免把设计失败伪装成普通 bug。

## 9. 版本切换的阅读规则

切换旧版本时，页面必须使用该修订绑定的源锚点和状态，不能把当前代码套到历史架构上。若历史提交不可达，明确标记证据缺失。对当前版本，分支链接可辅助浏览，但永久链接仍以 commit 为准。

## 10. 版本冻结检查

一个新修订发布前至少检查：

- 父修订和差异闭合；
- 所有重大变化有原因和证据；
- 被影响对象可追溯；
- 设计与实现对齐状态明确；
- 撤销路线未被静默删除；
- 当前状态没有引用不存在的未来实现；
- 展示层能回答“哪里变了、为什么、代码是否跟上”。
