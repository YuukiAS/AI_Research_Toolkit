# Asteria：把完整性合同放进设计过程

Asteria 应承担 **Architecture Completeness Contract + Freeze Gate 的表达与检查**，而不只在设计结束后展示图。这里推荐的是一种生产合同，不声称当前 Asteria 已经实现全部检查，也不要求先开发新平台才采用方法。主设计者可以立即在现有 Git 文档中执行同一合同。

## 1. 现有产品、历史原型和本轮建议分别是什么

| 对象 | 已查到的实际能力 | 本研究不能声称的能力 |
|---|---|---|
| Asteria 当前固定提交 `60ba27a...`，2.0.0-rc.19 | 统计语义图、Architecture／Lineage／Evidence 视图；B0/B1/B2 的只读仓库桥接合同及固定合成 fixture；布局和交互结果记录 | 实时 GitHub ingestion 已上线；所有软件架构都可直接导入；自动完成本报告全部 Freeze 判断 |
| architecture-evolution 历史原型 A，`c733aa0...` | 机制、来源、关系、修订等模型检查；对运行证据的范围和绑定作结构约束 | 运行记录内容必真，或检查通过足以证明产品完整 |
| architecture-evolution 历史原型 B，`4322881...` | Git 账本、三轴状态、验证引用等检查 | 一个有效引用等于真实验证；原型已接入所有项目 |

## 2. 合同里的对象必须回答什么

不为每个对象堆同样字段。先判断它对用户承诺是否关键，再要求相应内容；无适用项要给理由，不能用 `N/A` 逃避关键问题。

| 对象 | 必须可追踪的内容 | 不能冻结的例子 |
|---|---|---|
| 用户能力 | 原始来源、正常入口、结果接收者、旧能力保护、验收；被排除时的明确产品决定 | “主动报告”只连接到一个工具函数，没有定时调用者 |
| 组件 | 唯一责任、内部机制、输入输出、持久状态与数据 owner、权限、失败和恢复 | accepted 的 guard 只有一句“保证安全” |
| 关系 | 实际 payload、schema／身份、生产者、consumer、触发时机、顺序或并发、错误传播 | 写出 JSON 就认定已通知，无法找到实际读取者 |
| 关键决定 | 可行替代、选择原因、被否决条件、不可逆影响、允许实施者选择的自由度 | “Codex 选最合适算法” |
| 外部假设 | 具体主张、依赖它的承诺、版本与环境、现有证据、反证结果、隔离或退出方法 | “Hook 安装成功，因此异常时也会阻断” |
| 实现绑定 | 确切仓库、版本、路径／符号、存在还是计划新建、绑定身份 | 声称 linked 却只有仓库首页或未来文件名 |
| 验证 | 输入、oracle、观察入口、正常及代表失败路径、实际结果、证据身份与局限 | validated 的依据仍是一个待执行测试计划 |
| 修订 | 改变哪个决定、原因、原能力去向、新旧依赖影响、失效证据、需复验范围 | 删除 notifier 后没有说明机器级配置由谁承接 |
| 未决项 | 是否阻塞当前范围、负责对象、取得什么信息即可裁定、下一执行者 | “实施时再看”仍涉及核心行为或恢复语义 |

状态分为 design、implementation、evidence 三条独立轴。设计 accepted 不推出代码 implemented；有代码不推出运行 validated；某条路径 validated 不推出整个组件或产品已验证。设计冻结也不把计划中的实现绑定伪造为现有源码。

## 3. 从空字段检查进到主张与证据的对应

Bridge 和 Slurm 表明，缺的未必是更多表格。Slurm 10 月 13 日 v0.3 已写出 Hook 失败放行、真实入口、普通命令保护等 G1–G6 要求；后续依然发生晚验证。因此新合同的实质要求是：**未证的关键依赖不能在状态传播中被已经通过的文档或模拟测试覆盖掉。** 详见[Slurm 分析](SLURM_ROUTING_AND_CANCEL_FAILURE_ANALYSIS.md)。

一条证据至少绑定：主张 ID、候选／源码身份、实际环境与入口、测试输入及故障条件、观察对象、结果、原始记录定位、明确未覆盖范围。若其中任何决定主张是否成立的维度变化，就使对应证据变为待重新确认，而非自动失效所有产品。

例：安装器能找到 Python 解释器，只支持“该路径在安装环境存在”；`Hook trusted` 只支持信任状态；fake scheduler 支持保护算法的部分语义。三者合并仍不能推出“Desktop app-server 启动 Hook 失败时，原 Bash 不会运行”。该主张需要实际宿主入口、失败注入和下游未启动的直接观察。机器检查能发现证据类别不够，不能代替实验。

另一个例子是 CAT-TRACE：一份 grouped／explicit 对照均使用同一 Laplace 近似，不能互相充当近似正确性的独立 oracle。结构合同应记录参照来源及共享假设，随后路由到独立推导或数值对照，不能只数通过了几种实现。

## 4. 哪些外部未知阻止 Freeze

同时满足以下三个条件时，未知阻止依赖它的范围冻结：用户承诺依赖该前提；前提错误会改变核心机制、产生不可逆后果或使一大片实现失去意义；现有证据未覆盖实际入口和关键失败行为。直接证据不一定是昂贵全功能实验，源码与接口已足够时无需运行；但加载、调度、会话生命周期、故障阻断和重要数值行为通常不能只靠文档推断。

有两个合法出口。取得相称证据；或者改变边界，使失败确实被局部吸收且承诺仍成立。写“以后可替换 adapter”不算隔离。若需要用户接受降级，必须作为产品决定，不以结构通过暗中批准。

若环境暂不可得，允许独立范围有界冻结。冻结记录仍保留完整目标、未证能力和禁止越过的依赖，明确下一步取证。CAT 的有限数值研究和 STAT5060 的三路代码包属于合理边界，不应被一个全有或全无的 gate 阻止。

## 5. 与独立智能判断的分工

| 问题 | 结构检查 | 仍需谁判断／取证 |
|---|---|---|
| 已列组件缺机制、关系缺 consumer、引用缺身份 | 可以确定发现 | 原架构师补设计，Codex核实来源 |
| 整个用户场景没有进入对象集 | 不能保证 | 独立 Work 从原需求和事故提出问题 |
| 同 UID 的确认文件可被伪造 | 可要求写权限主体，不能保证识别语义漏洞 | 独立权限分析；必要时无副作用实验 |
| 两套方案共有错误宿主假设 | 只能显示尚未证实 | 真实 runtime probe |
| 科学模型／算法错误 | 只能检查推导和参照是否存在 | 独立推导、数值反例、领域审查 |
| 产品根本不需要专用线程或另一层治理 | 不能从图的完整性判断 | 主架构师与独立产品反例；真正偏好交用户 |
| 某条恢复路径是否真的可运行 | 图可表示，不能证明执行 | 陌生实施者冷读和代表性实验 |

结构检查减少早期 Critic 寻找显性洞的工作，使独立判断集中在语义、盲区与证据适用性。它不会消灭后者。

## 6. 低维护成本和局部修订

合同由主设计负责维护，从现有目标和来源建立引用，不复制全文。相同决定只有一个规范位置，摘要和视图引用它。只为有意义的架构变化记录修订；单纯格式、注释和代码内部实现不产生新产品版本。

内部完整性不能直接变成用户界面的全部字段。complex-system-showcase 的两个候选曾共同通过早期检查，后续仍被发现每卡强塞字段、重复解释和阅读负担；[编辑审计](https://github.com/YuukiAS/AI_Research_Toolkit/blob/ce8442b799e0096b79367da701289255bfa23bd3/docs/research/complex-system-showcase-20261026/r2/editorial-audit/EDITORIAL_AND_CURATION_AUDIT.md)支持把完整数据与按需呈现分开。它没有证明某个 UI 布局普遍最优。

成本也必须进校准：记录新增维护分钟、自动检查误阻塞、来源陈旧率、作者自行关闭的重大结构缺口，以及最终用户是否少读和少搬运。如果结构化只增加表格、不改变取证时点和返修边界，就不应继续扩展它。当前推荐先用最小合同；生产工具是否实现由单独获准任务决定。
