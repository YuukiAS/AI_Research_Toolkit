# 下一位执行者选择器

每个阶段结束时，架构负责人必须给出一个明确的 `NEXT_ACTION`，或一个已经排好依赖的并行批次及其唯一汇合负责人。用户只需要把准备好的任务交给指定对象；系统不能输出“你可以考虑找 Pro、Work 或 Codex”让用户重新判断。

选择器的依据是**当前仍未解决的具体问题及其证据类型**。它不从模型名字推测能力，也不使用未经校准的风险分数制造精确排名。任务分级决定初始投入，实际问题决定增减与停止。

## 1. 先建立可审查的判断输入

负责人每次只更新发生变化的内容：当前目标与版本、冻结范围、未决事项、证据身份及适用环境、当前依赖、已取得授权、已用预算和可用执行者。每个未决事项必须指向某项能力或决定，并说明关闭条件。没有充分事实支持的严重度标为推断，不伪装成已观察事故。

未决事项分为：核心设计未定／被反证、可只读核查的事实、必须运行才知道的事实、可行核心路线竞争、原需求盲区、冻结范围内的代码缺陷、真正产品决定。新需求另外保留来源；其后可产生上述某类具体任务。只写“风险很高”而不能说明缺什么，先由当前负责人澄清，不自动加模型。

事实足够但需要判断的题归 Chat；观点已经一致但缺实际行为证据的题归 Codex；整个问题空间可能遗漏的题归 Work。角色边界贯穿全过程。

## 2. 选择优先级和冲突消解

先停止与已证严重问题相关的危险动作，保留不依赖它的合法工作。随后选择可以立即产生决定性信息的事项，按以下顺序处理；同层先处理不可逆、影响范围大且阻塞更多后继的事项，再比较取得证据的成本。未知成本只作范围判断，不能虚构数值期望。

| 当前状态 | 唯一主动作 | 接收者与实际交付 |
|---|---|---|
| 用户已有明确决定延后关键实证，并授权具体候选代码范围 | `APPLY_EXISTING_USER_DECISION` | 当前Chat直接应用原授权、形成指定Codex任务；不追加模型、不重问用户、不把未知证据改成通过 |
| 新事实已经否定核心决定，或接手者仍必须发明机制 | `RETURN_TO_ARCHITECT` | 原 Chat／Pro；裁定受影响决定与局部修订，不重写无关部分 |
| 路线关键事实未证，且已有文档／源码不能回答 | `CODEX_MINIMAL_PROBE` | Codex；按已定义输入、观察与结果分支取得真实证据 |
| 可从源码、实际接口或既有记录回答的事实未知 | `CODEX_FACT_CHECK` | Codex；只读返回 source anchor 与明确局限。当前负责人能直接查到时就直接完成 |
| 至少两条尚可行路线改变核心 ownership／算法／迁移成本，且证据不足 | `SECOND_INDEPENDENT_DESIGN` | 第二 Pro；相同原始输入，候选隔离，先核心决定；必要时完整展开 |
| 需求来源多、全场景遗漏风险高，尚无独立原始问题调查 | `WORK_BLINDSPOT_AUDIT` | Work；先不看候选，固定问题集，再核对候选 |
| 合同明确，当前代码偏离合同，可在原边界内修复 | `LOCAL_CODEX_FIX` | 原 Codex；修缺陷及相邻失效分支，报告实际验证 |
| 用户价值／风险接受／产品范围无法由已有材料决定，事实调查与具体选项已备齐 | `USER_PRODUCT_DECISION` | 用户；负责人给推荐、备选及影响，只问真正未授权的取舍 |
| 结构、前提和发现已闭合，但必要接手检查未做 | `CODEX_READINESS_CHALLENGE` | 未参与设计的 Codex；只读拆解，报告核心未决项 |
| 设计闭合、接手通过，用户请求并已授权实施 | `FREEZE_AND_IMPLEMENT` | Codex；带精确冻结版本和自由度的正式交接 |
| 设计任务已完成，未请求实施 | `FREEZE_AND_END` | 当前 Chat 结束并交付，不为流程再启动模型 |
| 完整实施包已准备好，只有新的实际执行权限尚未取得 | `USER_EXECUTION_AUTHORIZATION` | 用户；批准的是具体可审查范围，不再询问已授权动作 |
| 已实施，冻结的验证尚未完成 | `CODEX_VERIFY` | Codex；实际同候选测试，不能改标准 |
| 实施验证成立，但仍需要独立产品／科学／黑箱判断 | `WORK_FINAL_ACCEPTANCE` | Work；从原目标核验实际成品与关键反例 |
| 本次交付和必要验收都完成，无阻断项 | `CLOSE_TASK` | 当前 Chat 总结并停止 |

表不是每个角色都要走一次的清单。如果只缺 runtime 事实，不先安排第二 Pro；如果只缺核心决定，不让接手 Codex 用 probe 名义顺便选产品机制；如果普通 bug 已有规范答案，不把它升级为路线竞争。

当多个事项同时存在，主动作是当前最影响裁决的事项，其余**输入已齐且互不依赖**的工作组成同批并行任务。举例：两个原始路线确实不同，同时存在独立站点事实，可以让第二 Pro、Work 和事实调查并行；最终架构裁决必须在相关结果后进行。需要某项实验结果才能定义的实验、修改同一共享文件的任务和依赖冻结合同的正式实施不得为了凑并行同时开始。

若两个路线唯一差异正好可由一个接口事实判定，先事实调查，暂停第二份完整设计。若用户偏好必须先决定整个目标，则只推进仍对两种选择都有用的证据。没有可执行后继时，记录具体等待对象、已有结果和恢复条件，不能自行制造新的审查轮。

## 3. 模型投入怎样动态增加和减少

默认 L 是一个 Pro＋一个 Work 的初始并行批次。负责人在初始材料已看到路线竞争或关键运行未知时，可同批追加第二 Pro或Codex；不必等待完整首稿。风险稍后才显露时按事实追加，保留已完成的有效部分。

Work 已提交覆盖当前范围的独立问题集、没有新来源和高影响变化时，不再重启一轮盲查。Pro 的路线被事实淘汰后，停止深化落选方案。Probe 已取得决定性证据时，不为“更保险”重复同条件运行；只有结果不确定、环境改变或代表故障未覆盖才补测。

第三 Pro 必须带一个前两位未覆盖的路线或专业问题。不同角色名、不同模型商标或多一次多数投票本身不算独立信息。若模型不可用，负责人可以换同等能力的独立执行者并记录局限；不能把同一上下文继续写当成已经完成独立调查。

## 4. 下一动作消息的固定内容

消息只包含执行所必需的信息：

```json
{
  "next_action": "CODEX_MINIMAL_PROBE",
  "recipient": "Codex",
  "why_now": "A-RUNTIME-01 是当前路线成立的必要条件，现有证据仅到模拟层",
  "inputs": ["实际冻结文档链接和ref", "真实入口与现有证据定位"],
  "allowed_scope": "已明确授权的只读或隔离实验范围",
  "deliverable": "能区分路线的观察、原始证据定位及未覆盖条件",
  "result_routes": {
    "supported": "原架构负责人应用已定方案并检查剩余门",
    "refuted": "RETURN_TO_ARCHITECT，只重开受影响决定",
    "unavailable": "保留UNKNOWN，冻结独立范围或取得缺少的条件"
  },
  "stop_condition": "取得区分性结果或触及已定边界即停止"
}
```

上例说明消息形状，不能原样发出占位符。真实接力必须填入实际路径、身份、输入、预算与权限；这些已知材料由负责人整理。若平台支持且已获授权，负责人直接调用；否则给用户一条已经填好的消息与接收者。自动选下一位不等于当前已经部署跨应用自动启动。

## 5. 历史判别题：同一种“失败”不能同一路由

| 情境 | 此刻动作 | 不能误走的路线 |
|---|---|---|
| Bridge v0.8：reader isolation 从未在所选 runtime 证明 | `CODEX_MINIMAL_PROBE` | 第三个 Pro重复猜测；直接大规模接线 |
| Bridge scope recovery：周期 producer／caller 没 owner | `RETURN_TO_ARCHITECT`；需要独立查旧目标时并行 Work | 让 Codex新建核心 daemon |
| Slurm confirmed-file：同 UID shell 可伪造 authority | `RETURN_TO_ARCHITECT`，独立权限反例已有决定性信息 | 仅把文件权限改一改就假定安全 |
| Slurm v2.1 Phase0：已计划的宿主 probe 尚未执行 | `CODEX_MINIMAL_PROBE` | 把 execution PASS 当成探针已通过 |
| Slurm timezone 或 native schema 不符合已定合同 | `LOCAL_CODEX_FIX` | 完整 Planner–Critic再写路线 |
| CAT 两个近似实现相互一致，但没有独立参照 | `CODEX_MINIMAL_PROBE`／独立推导，由架构师选具体问题 | 多数同意即认为科学正确 |
| STAT 合格输入到不了既定状态 | `LOCAL_CODEX_FIX` | 让 Codex降低“合格”含义 |
| Clear Writing 中疑似插件错误，原稿证据没读 | `CODEX_FACT_CHECK`或当前负责人直接核源 | 无来源先改插件／否定整个版本 |
| Asteria 结构完整但所有 UI 卡片重复相同信息 | `WORK_FINAL_ACCEPTANCE`，若只改呈现则局部实施 | 再加 completeness 字段解决阅读问题 |

这些动作分别限定在问题已知的时点；不能把后来的问题当成当时模型已经知道的事实。具体 cutoff 与反事实限度见[benchmark](HISTORICAL_BENCHMARK.md)。

## 6. 停止、重复与例外

已闭合的决定不因普通追问重开。新证据、真实新需求、来源纠正、关键环境变化或原先约定的失败条件触发重审。对同一问题，一次定向复核后仍没有新信息，换能区分答案的证据来源；不能继续同一文本循环，也不能强行签 PASS。

预算不足或环境不可得时，停止相关动作并保留恢复点，推进独立工作。用户请求只交付设计时应结束，不默认创建实施任务。现行项目合同仍要求某种独立审批的，在采用新协议前照原合同执行；本研究的参考选择器只作研究和未来采用后的规则演示，不具有更改治理的权力。

## 7. 可执行演示与其严格边界

[analysis/routing_selector.py](analysis/routing_selector.py)把上表的确定性路由写成一个无网络、无产品写入的纯函数；[analysis/routing_scenarios.json](analysis/routing_scenarios.json)含危险 runtime、未决核心决定、普通 bug、冷读、冻结和停止等判别场景。输入中的能力闭合、证据质量、授权和问题分类**仍须由负责 AI 根据实际来源判断**，脚本不伪装成能自动理解任意项目的智能审核器。

演示用来检查相同判断输入是否产生稳定下一步，并防止缺字段或未处理问题意外放行。依赖必须显式给出，确定没有依赖才用空列表。用户明确延期验证属于需要原指令语义的例外：演示识别后交当前Chat立即应用已获授权，不把它误路由为强制现在probe或再次索要许可；具体候选实施由原指令决定，证据保持UNKNOWN。这里的Chat动作在当前工作内完成，不增加一位模型或让用户转交一次。脚本通过不证明整套方法已能自治运行，也不是实测历史检出率。校准真正要测的是上游判断是否准确、调用是否带来信息，以及用户是否减少协调。
