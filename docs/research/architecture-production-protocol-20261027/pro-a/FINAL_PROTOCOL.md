# 证据驱动的并行架构收敛协议

本研究推荐用**一个架构负责人统合设计，按未解决问题并行取得证据，达到有范围的冻结条件即交给 Codex**，替代复杂任务固定往返的 Planner–Critic 顺序。默认复杂任务先启动一个 Pro 和一个独立 Work；第二个完整设计者、技术调查和运行探针分别由明确风险触发。架构负责人对最终设计和下一执行者负责，用户只处理无法从目标与材料推导的产品取舍及真正新增的授权。

这是 `RUN_ID=pro-a` 的完整方法候选，研究日期为 2026-10-27。本文是唯一推荐的规范正文，其他文件解释证据、参数与具体合同。本轮只交付研究，不修改现行角色合同、插件、Bridge、Asteria 或项目运行机制。后续是否采用由本轮总体裁决决定。历史回溯支持若干关键机制，但尚没有前瞻对照证明整套协议的真实效果。

## 1. 为什么改变固定顺序

固定 Planner–Critic 的独立反对意见有价值，历史默认顺序的问题在于**下一步容易由角色轮次决定，未稳定优先取得当前缺少的证据**。现行 1.7 合同已允许事实路由和局部修复，不能把旧流程的全部问题归给它。审查者即使仔细，也不能通过继续阅读方案确认某个宿主是否会在 Hook 崩溃后阻断命令；增加完整架构师也不会自动获得真实浏览器样本。另一方面，像 STAT5060 的普通接线缺陷，重新设计只能增加等待。[历史基线](BASELINE_PLANNER_CRITIC.md)和[回放](HISTORICAL_BENCHMARK.md)分别保留这些正反证据。

因此，保留独立审查的能力，取消“所有任务固定由同一类 Critic 反复放行”的默认安排。批评必须指出具体能力、反例、来源、影响和关闭条件。结构检查、事实调查、算法论证、产品验收各自取得自己能提供的证据，不互相替代。

## 2. 责任与最小工作材料

Chat／Pro 确定目标、架构、关键算法、接口、状态、不变量、失败与恢复语义、技术取舍、冻结及返修。Work 独立调查遗漏、构造反例、核查复杂证据和成品；它可以提出足以否定设计的证据，最终架构决定仍由负责人作出。Codex 调查技术事实、执行范围明确的实验、实施冻结设计、测试并报告观察；不能替设计者选择核心产品或科研机制。

正式材料尽量复用项目已有文档，只保留三个逻辑对象：一份当前架构、其引用的原始证据、当前唯一下一动作。原始需求、代码和实验保留各自权威；不复制一套平行事实库，不新建后台调度平台。复杂项目可使用 Asteria 连接组件、机制、来源和修订；没有 Asteria 时，同一合同可用现有 Markdown 与 Git 表达。工具建设不成为项目开工的前置条件。

每次架构修订都说明改了哪个决定、依据是什么、哪些能力和接口保持不变。普通实现提交不升级为架构修订。冻结范围之外的研究仍可开放，但完整产品目标继续保留，不能借分阶段静默删减承诺。

## 3. 先判断未知问题，再安排第一批工作

负责人读取原始目标、已有需求、关键源码和历史失败，形成**短的风险判断**：有哪些不可轻易撤回的决定；哪些外部前提一旦不成立会推翻核心承诺；哪些跨功能使用情境可能漏掉；哪些事情已经有可靠证据。资料已经能回答的事实，负责人直接核查，不为工具分工额外开一个模型。

| 档位 | 判定依据 | 默认启动安排 | 追加条件 |
|---|---|---|---|
| S | 局部可逆，不改变组件间合同、科学目标或外部副作用 | 当前 Chat 或原 Codex 直接处理 | 发现越出边界的实质未知才升级 |
| M | 跨组件，但路线成熟、影响可局部控制 | 一个设计负责人；结构闭合与接手检查按改变的接口开展 | 需求来源复杂时加 Work；事实缺失时加调查 |
| L | 长期、多能力共享状态，后期返工昂贵 | 一个 Pro 与一个 Work 并行；Work 初始不看候选 | 技术根前提未证则加 Codex 调查／探针；存在可行互斥路线则加第二 Pro |
| XL | 不可逆投入、强外部运行依赖、跨仓责任或关键科研路线 | 以 L 为起点，同时启动所有**已有明确问题**的独立证据任务 | 第二 Pro 与运行探针可同批；绝不因 XL 标签固定凑足角色 |

“复杂任务默认两个模型”指第一批两个独立任务，不表示设计到交付全程只调用两次。后续陌生实施者接手、必要运行验证与成品验收另计；模型数量、模型调用和串行波次必须分别记录。

## 4. 第一批并行工作如何产生增量

**主设计**从用户能力、状态所有权、数据身份和正常流程出发，比较可行路线，展开关键机制。它必须自行完成双向闭合：每项已知能力能追到输入、数据来源、组件、接口、权限、状态、失败、恢复和验证；每项关键输出能追到真实消费者或有理由的终点。没有接收者的文件不能被当成已接通的功能。

**独立 Work**先只读原需求、历史事故、实际使用方式、待办和外部限制，写出会影响任何候选的情境与反例，并固定这份初始观察。随后才能看候选。这样独立性主要来自问题形成过程，而非给同一种模型换角色名。重点检查整个场景被遗漏、用户负担被转嫁、职责错置、共同错误前提和产品实际需要；不重复检查已经能机械发现的空字段。

**技术事实任务**随关键假设出现而启动。先读官方接口、源码和已有真实记录；不能回答时才做最小实验。探针必须预先说明：它区分哪项架构决定，观察什么，什么结果否定哪条路线，允许什么副作用，以及失败或取不到证据时怎么办。不得等完整方案和实施包都写完才第一次检查决定路线的运行前提。

**第二个独立 Pro**仅在以下条件同时成立时进入：存在至少两条与用户目标一致、尚未被事实排除的路线；它们改变核心职责、数据所有权、算法或长期迁移成本；主设计的选择还没有足够证据。先各自形成不可逆决定及一条跨组件主链，再由证据决定是否值得把两条路线都深化成完整方案。若风险来自全局交互，完整独立设计有必要；若一个接口事实就能排除路线，先获取事实。第三位完整设计者只用于尚未覆盖的实质第三路线或独立专业论证，不用于打破二比一投票。

## 5. 汇合后由一个负责人裁决

独立结果可异步进入，不等所有支路写长报告。负责人先解决来源冲突，再作技术选择；不能按票数合并互相矛盾的设计，也不能把多个报告拼成接口仍不一致的“综合方案”。

每个高影响发现有四种处理：以证据接受并修改；给出可核查的反证；识别为真正新增需求并确认其产品影响；确认是普通实现问题并交回 Codex。无法裁定时应指出缺少的**可观察事实**，选择能取得它的下一任务。对于同一问题，如果一次定向复核仍只重复原意见，停止同样的文字往返，转取证、专业推导或真正的用户产品决定。不能用次数上限把未解决风险强行变成通过。

独立审查最有价值的场合包括：重要路线之间存在实质取舍、科学论证需要独立推导、证据与结论不匹配、成品质量无法由开发者自评。对已经确定的字段、引用、源码位置和普通缺陷，用机械检查或原实施者即可。

## 6. 冻结前做一次陌生实施者接手

对新增或改变关键接口的 M，以及 L／XL，安排一位没有参与设计的 Codex 只读当前完整架构和授权读取的源码。它需要实际指出：改哪些模块、从哪个入口进入、每条关键状态怎样变化、错误交给谁、依赖在哪里、如何证明完成。未存在的模块应说明创建位置，不能伪装成已有代码。

接手者给出一份简短的实施顺序和**未决定事项**。仅影响局部命名、内部数据结构等已允许自由度的问题可自行选择。若还需要决定用户看到什么、哪个组件拥有状态、采用哪个科研算法、失败是否阻断、如何恢复、验收标准或数据从哪里取得，立即 `RETURN_TO_ARCHITECT`。这个阶段不顺便补设计，不启动正式开发。[详细接手合同](IMPLEMENTATION_READINESS_CHALLENGE.md)。

接手检查必须覆盖关键成功链、最高影响失败链、恢复链和一个应保持不变的旧能力；不是逐页复述方案。重复检查只限修订影响的依赖范围。重大的跨组件重划可以触发更大检查，但须说明为什么局部检查不足。

## 7. 什么证据使冻结成立

冻结是“本范围的核心决定已经完成且关键前提获得相称支持”，不是产品已实现。必须同时满足以下条件：

1. 已知用户能力、旧能力保护和范围具有明确来源，不能用本轮发现清单替代全部承诺。
2. 关键组件有内部机制，关系有载荷、消费者和失败语义，状态与数据有唯一责任归属。
3. 正常、失败、恢复和应保持不变的路径能够连贯走通；验证标准、代表输入及观察入口已确定。
4. 会推翻核心承诺的外部前提有直接证据，或已被一个**确实保持承诺、可验证的边界**隔离。只写“可替换适配器”不构成隔离。
5. 所有高影响独立发现已经处理，现有重大争议有可审查裁定；实现者没有未解决的核心设计决定。
6. 本次冻结版本、实施范围、自由度、返回条件和证据适用范围可准确定位。

结构完整、Critic PASS、接手清楚、真实探针分别支持不同条件；任何一个都不能单独替代全部条件。针对安全阻断、跨进程确认、线程投递、宿主生命周期和关键数值近似，直接运行证据应覆盖可能推翻承诺的失败路径。终端中的 Python 正常、模拟调度器测试通过或 UI 原型可点击，都不能替真实宿主与数据条件作证。[冻结与交接](FREEZE_AND_HANDOFF.md)。

若核心前提取证暂不可得，可以冻结与它独立且不会因其结果作废的范围，明确保留未解决能力及后续取证任务；不能宣称整个产品架构就绪。用户选择延后真实验收时，授权改变实施顺序，不改变证据强度。

## 8. 同时降低迟发现的影响

对于每个高影响未知，负责人还必须问：即使遗漏，能否局部换掉它？关键外部边界应具有稳定输入输出、明确配置与数据所有权、可注入的故障语义和受控依赖。更换运行适配器时，不应同时推翻产品目标、进度语义和通知配置；保护检查失败时，不应连带封锁无关命令。

每次新事实出现，先确定它否定了哪个决定，再沿新旧依赖的并集检查受影响消费者。数据写入、权限和不变量改变必须追到边界，不能只按文件修改列表缩小验证。依赖闭合后不受影响的实现继续；只有全局不变量失效才整体重开。已冻结承诺内的普通运行环境修复、加载错误和接线缺陷仍由 Codex 修复；关键是能否在原合同内修好，而非错误名字是否叫“runtime”。

## 9. 下一位执行者由协议决定

每次完成一项工作，都更新一个唯一动作，包含负责对象、原因、输入定位、可运行范围、预期证据、结果分支与停止条件。若有可并行工作，输出一个已排好的任务批次和一个汇合负责人，而不是让用户选择菜单。[选择器](DYNAMIC_ROUTING_POLICY.md)给出优先级、冲突消解与可运行的纯决策演示。

典型路由如下：资料可回答的事实去 `CODEX_FACT_CHECK` 或由当前负责人直接核查；关键运行事实未证去 `CODEX_MINIMAL_PROBE`；竞争路线未裁定去 `SECOND_INDEPENDENT_DESIGN`；整个需求空间可能有洞去 `WORK_BLINDSPOT_AUDIT`；机制缺失去 `RETURN_TO_ARCHITECT`；普通实现缺陷去 `LOCAL_CODEX_FIX`；冻结条件齐全去 `FREEZE_AND_IMPLEMENT`；实际成品需要独立质量判断去 `WORK_FINAL_ACCEPTANCE`。没有新信息需求时，停止设计。

自动选择与自动启动分开。当前平台已有且获授权的调用入口可以启动任务；否则负责人提供填好所有已知参数的短消息及接收者。不能声称跨 Chat、Work、Codex 的自动接力已经部署。本研究不会引入守护进程、消息队列、授权数据库或另一套持久状态机。

## 10. 停止标准与改变推荐的条件

满足冻结条件即停止一般审查；不要求模型再也找不出任何建议。非阻断建议留给常规改进，不增加本轮串行依赖。仍有重大缺口时继续取得能改变决定的信息，不能以“再审一次更放心”重跑同样输入。若下一动作既不能区分路线，也不能验证承诺或减少可解释的返工风险，就不安排。

本推荐可被证伪：真实对照若显示同等成本的 Planner–Critic 更少遗漏和返工；独立 Work 长期主要产生无关发现；第二 Pro 没有提供路线或风险增量；结构化维护持续比它节省的时间更贵；探针频繁使团队过早锁死错误路线；或 Bridge／Slurm 类问题在符合本协议的任务中仍因同样证据缺口反复发生，都应修改对应机制。普通追问只触发核查已有决定与证据；只有新需求、反证、来源纠正或已预先定义的适用条件变化，才改变架构。

校准时优先记录人工时间、必须串行的波次、冻结后重大缺口、实施返回设计、作废代码与核心决定转嫁，而不统计报告数量或 PASS 数量。[校准计划](CALIBRATION_PLAN.md)给出对照方法及明确预测。
