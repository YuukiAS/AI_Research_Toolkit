# 真正的 Architecture Freeze 与实施交接

Architecture Freeze 是架构负责人对**一个明确范围**作出的可追踪决定：核心行为已经选定，危险前提获得相称证据，实施者只需实施和验证。它不表示产品已实现、已验收或已发布，也不禁止新事实导致局部修订。

## 1. 各种“通过”究竟证明什么

| 证据 | 能支持的结论 | 不能推出的结论 |
|---|---|---|
| 文档完整 | 所选对象和问题已被表达，信息可以交接 | 对象集包含全部用户场景；机制可行 |
| Critic PASS | 独立审查者在其实际阅读范围内未发现阻断项／接受裁定 | 没有未知缺口；真实宿主行为已验证 |
| Asteria completeness | 编码过的结构、不变量、引用、状态与影响关系满足规则 | 科学论证正确、产品路线正确、证据内容可信 |
| implementation handoff dry-run | 陌生实施者能定位实际工作，未发现自己须补的核心决定 | 未来代码无缺陷，运行条件成立 |
| 真实技术 probe | 特定版本、入口、环境、输入下某个技术事实可观察成立 | 全产品正确、所有环境成立、长期不会变 |
| representative failure-path probe | 已选关键故障下的拒绝、恢复、隔离或数值误差行为成立 | 所有故障已穷尽、无并发竞态、无限尺度稳定 |
| 最终产品验收 | 同一实际候选在约定能力与输入下满足标准 | 未覆盖的能力已交付；旧版本证据可签新版本 |

Bridge v0.8 与 Slurm 的多种 PASS 穿过的正是这些边界。另一方面，CAT-TRACE 的有限研究、STAT5060 的三路代码允许、Delivery Assurance 的设计 PROCEED 都明确保留未证明范围，不能被误判成“假全局冻结”。[历史回放](HISTORICAL_BENCHMARK.md)分别记录。

## 2. 六项冻结条件与检查责任

**能力闭合。** 每项已知用户能力和旧保护都有来源、正常入口、结果、owner 与验收；范围排除有产品依据。设计者完成双向追踪，独立 Work 针对可能遗漏的整个场景提出问题。

**机制闭合。** 关键组件展开到行为、状态、数据、权限和失败恢复；关系具有真实载荷、consumer 和触发。核心算法与可观察语义已经由 Chat 决定。

**路径闭合。** 正常、失败、恢复、取消／不确定结果及保留旧能力的关键轨迹连贯；验证 oracle 与观察点明确。涉及科学近似时，参照与候选的共享假设被识别；涉及强制阻断时，真正阻断 owner 明确。

**前提闭合。** 可能推翻核心承诺的外部事实已在相关入口和条件下验证，或者其不成立能被一个已经说明且可验证的边界局部吸收。UNKNOWN 不能因其他字段通过而自动变为 TRUE。

**接手闭合。** 高影响独立发现均有证据处理；必要冷读已经完成；Codex 剩余选择属于明确授权的内部实现自由度。任何未决核心机制都禁止当前相关范围冻结。

**版本与范围闭合。** 明确规范版本、原始来源、实施范围、尚未交付范围、外部证据适用条件、允许自由度和返回条件。正式修改需要的权限由已有授权决定；架构冻结本身不扩大权限。

前三项不能只由“已检查”复选框代替。至少保留能让陌生读者重建判断的关系和具体路径；无需额外复制整份报告。

## 3. 未经运行验证的前提什么时候一定阻塞

判据不是“凡 external 都跑实验”。已有精确源码、官方接口和同条件运行记录足以支持的事实可以复用。必须提前实测的典型情形是：选择路线依赖宿主实际加载、会话身份、进程故障传播、授权消费、线程材料化或数值行为；该事实错误将损害核心承诺；而现有证据只来自假环境、相邻层或未覆盖的成功路径。

对于强制保护，至少区分“检查程序决定拒绝”“宿主收到合法拒绝”“原始操作确实未启动”。检查程序崩溃或未启动时，谁完成阻断必须得到直接支持。对于正常能力，同一实验还要证明合理正例可以继续；全盘拒绝不能冒充保护成功。

Bridge 的 early reader probe 应在真实选定运行身份上观察 instructionSources 与接口实际行为；不需要先完成所有通知接线。Slurm 的早期失败 probe 应穿过真实 host／loader，用无害 marker 观察原操作启动数；单独运行 Python 或 mock scancel 不够。这是对历史的反事实建议，本研究没有执行这些真实环境试验，也不预报必然检出率。

## 4. 有界冻结和实验包如何避免假 Freeze

允许以下几种明确结论：

| 结论 | 可以做什么 | 必须仍保留什么 |
|---|---|---|
| `PROBE_READY` | 运行已经决定目的、输入、观察、范围和结果分支的最小实验 | 主产品相关未知；不把探针代码自动纳入产品 |
| `FROZEN_WITHIN_SCOPE` | 实施不会因未决事实而失去意义的独立部分 | 完整目标、剩余能力及依赖阻塞；没有暗中延期或删除 |
| `FROZEN_FOR_IMPLEMENTATION` | 在已授权范围内正式实施全部当前设计 | 未实施、未验收与未发布状态；证据环境限制 |
| `RETURN_TO_ARCHITECT` | 修订被事实否定或仍未决定的架构部分 | 不受影响的既有设计、实现和证据继续有效 |
| `PRODUCT_ACCEPTED_WITHIN_SCOPE` | 关闭已经完成且验收的当前交付 | 未覆盖环境、能力和后续阶段不代签 |

这些是报告用结论，不要求建一套新运行状态机。不能为了减少 architecture reset，把所有事情都叫“实验”，却投入完整生产实现。实验包需要可判定的有限假设和预算；有界代码冻结则必须说明独立性，依赖未知前提的大量接线不满足它。

用户可明确选择延后真实验证。此时可以依法按其选择实施，但报告须写“按用户决定承担待验证前提的实施风险”，不得重新命名为已证明的全局 Freeze。能够安全并行推进的独立工作继续，依赖事实的成功主张保持未证。协议既不越过用户，也不改变证据含义。

## 5. 发给 Codex 的最小完整交接

交接直接引用当前架构，不另写一套可能漂移的长方案。至少含以下内容：

1. 用户目标、当前交付边界、保留能力及明确不在本次完成的事项。
2. 规范版本与关键决定；仓库、分支和可写范围；真实已有模块与计划新建模块。
3. 入口、状态／数据 owner、接口载荷、权限、失败与恢复、并发／幂等要求。
4. 算法与实现自由度；Codex 可以选择什么，哪些改变必须返回 Chat。
5. 已有技术证据及其适用环境；哪些验证必须在本次实现后完成。
6. 实施依赖图和可并行子任务；共享合同先固定，不能各分支独自改变数据语义。
7. 验收输入、独立 oracle、成功／失败／恢复和旧保护；观察实际入口与候选身份。
8. 停止、局部修复、架构返回、取证和最终验收的路由；输出必须包含唯一下一执行者。

若项目已有 Goal／Kickoff／Plan 规定，使用其原路径和合同。不要为了新协议再建一套平行任务体系。当前现行强制审查或许可仍然有效；本研究并不绕开它们。

## 6. 实施中发现问题时怎样保持冻结有效

先问“能否在不改变冻结承诺和机制的前提下修好”。能，则 `LOCAL_CODEX_FIX`，包括普通接线、配置、已选 runtime 的加载修复、CI 和数值实现 bug。不能，则定位受否定的决定，`RETURN_TO_ARCHITECT`；科研模型、目标函数、近似方法或接受误差不能由 Codex静默更换。

新增需求记录为新要求，不倒算历史遗漏。外部变化记录为事实版本变化；原始事实本来未证则标证据缺口。实现报告与事实冲突时先核来源和实际观察，避免 Clear Writing 式错误归因。

影响范围沿变更前后依赖的并集检查。语义、数据 owner、权限、持久格式和全局不变量变化需要追到真实消费者；若边界合同与消费者观察不变，允许局部重新绑定证据。不能用“只改一个文件”来缩小实际影响，也不能让任意变化使全仓已通过证据一律作废。

Bridge 可把表达／transport 与运行事实拆开；Slurm 可把 launcher／native question／session 与 partition policy、一次性取消事务拆开。但 authority owner 被证伪时涉及核心机制，不能假装只是替换 adapter。

## 7. 冻结后的停止条件

六项条件成立、当前范围无需额外高价值信息，就停止一般设计审查。正式实施后按冻结标准测试；只在结果需要独立产品或科学判断时安排 Work。实际完成、证据覆盖当前交付、没有未处理阻断项时关闭任务。

停止不要求所有建议消失。保留不阻塞建议及未覆盖范围，不强迫用户读完所有发现；用户最终看到的是结论、重大取舍、剩余限制和一个明确接收者。后续普通追问只解释已有决定；新需求、反证、来源纠正或范围变化才触发再设计。
