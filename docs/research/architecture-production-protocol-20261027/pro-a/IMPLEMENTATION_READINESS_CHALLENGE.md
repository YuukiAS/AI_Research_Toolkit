# 冻结前的陌生实施者接手检查

目标是发现“实现者仍被迫做核心设计”的地方，并把它留在设计阶段解决。检查由未参与当前设计的 Codex 执行，只有只读调查权；它不获得补设计、启动正式开发或改变验收标准的权力。对改变关键接口的 M 和所有 L／XL 使用一次；S 可由原实施者直接检查局部变更，无需额外模型。

## 1. 输入与独立性

输入为当前完整架构、原始能力与旧能力保护、精确源版本、已取证的外部条件、验证标准和已批准实施范围。不给它 Planner 自评“已经完整”的结论作为答案，也不把上一位实现者的任务列表当唯一入口。它可以只读源码确认真实入口和依赖；已经知道源不足时应返回具体事实问题，不能猜一个存在的模块。

这是冷读检查，不要求隐藏原始需求，也不要求对候选盲读。盲区调查在更早阶段保持候选隔离；接手检查必须看到候选，才能验证交接是否充分。两者不要混用独立性定义。

## 2. 必须实际给出的答案

| 检查项 | 有用的回答 | 不合格的回答 |
|---|---|---|
| 修改位置 | 已存在的路径／符号，或明确新建位置；每项对应冻结决定 | “按最佳实践新增合适模块” |
| 正常入口 | 谁调用谁、实际输入来自哪里、谁接收结果 | “添加 helper 并写测试” |
| 状态与数据 | 初态、事件、转移、持久化 owner、身份、并发与幂等约束 | “实现可靠状态机” |
| 失败与恢复 | 超时、部分成功、取消、失联、不确定结果的 owner 与合法动作 | “失败时重试” |
| 技术依赖 | 真实版本／接口／安装和会话身份；哪些事实已经验证 | “SDK 应该支持” |
| 验证与完成 | 输入、oracle、观察点、正常和危险路径、旧能力保护 | “单元测试全绿即完成” |
| 自由度 | 不影响合同的内部命名、局部数据结构、等价实现可自行选择 | 让 Codex 决定用户体验、状态所有权或科研算法 |
| 接手后的第一步 | 一个可执行的调查或实施批次及明确停止条件 | 留给用户在多个 next steps 中选择 |

至少演练四条轨迹：一条主要成功链、一个最高影响失败链、一个恢复／取消／不确定结果链、一个不能被改坏的旧能力。若有多种互不等价的宿主、权限或科学对象，按风险覆盖差异，不用简单“四条”数字声称全覆盖。

输出可以很短：实际改动定位、轨迹与不变量、未决定事项、唯一结论。不要复述整份架构。

## 3. 结论与下一位执行者

| 接手结果 | 结论 | 下一位 |
|---|---|---|
| 需要选择核心机制、产品结果、算法、owner、失败政策、恢复语义或验收标准 | `RETURN_TO_ARCHITECT` | 原 Chat／Pro；指出缺的决定及其受影响能力 |
| 核心决定已定，只缺可查询技术事实 | `CODEX_FACT_CHECK` | Codex；限定只读问题和来源 |
| 文档无法证明关键运行／数值前提 | `CODEX_MINIMAL_PROBE` | Codex；由负责人先写清实验及结果分支 |
| 未知来自用户价值取舍且证据已足够 | `USER_PRODUCT_DECISION` | 负责人整理具体选项、推荐与影响，用户只做取舍 |
| 所有核心决定已定，存在不阻塞的内部实现自由度 | `READY_WITHIN_SCOPE` | 由架构负责人核对其余门，签署有范围冻结 |

接手者没有最终架构裁决权。它可以提供备选修复的技术事实，但不能把自己选定的方案填回文档后自报 READY。主设计也不能通过把缺口改叫“实施细节”逃过检查：凡会改变外部可观察行为、共享合同、科研含义、权限、恢复或验收，都属于设计决定。

## 4. 历史样例如何检验这道门

Bridge 的主动报告如果没有周期 owner，陌生实施者应回答不了“改哪个正常入口、谁维持周期”；它只能退回，不得顺手新建 daemon。v0.8 reader 则不是缺少文件位置，而是 runtime 能力未证，下一步应该是探针。Slurm 的同 UID confirmed-file 要求独立权限分析；仅能列出 binder 和 guard 文件不足以 READY。具体证据见[Bridge](BRIDGE_KIT_011_FAILURE_ANALYSIS.md)与[Slurm](SLURM_ROUTING_AND_CANCEL_FAILURE_ANALYSIS.md)。

STAT5060 的正向状态聚合缺陷发生在后来的代码里；冷读不能保证预知未来编码错误。它可以要求明确“全部合格输入应到达哪些可用状态”，由独立 oracle 在实施后发现接线错误。CAT-TRACE 的同近似对照，也不能由能列任务的 Codex证明算法正确；需要独立参照与数值实验。[跨项目分析](CROSS_PROJECT_CASES.md)。

## 5. 如何防止它变成另一轮完整 Critic

问题必须定位到“我需要替你做的决定”或“当前不能确认的技术前提”。一般代码风格、偏好重命名、不影响合同的内部实现不是阻塞。首次完成后，只复核实质修订影响的轨迹和依赖；源未变、事实未变、范围未变时不重开全量检查。

如果同一缺口一次定向修订后仍争论，应说明缺事实、缺产品决定还是表达仍有歧义，按该类型换取证方式。不能无限进行“再读一遍、再写一遍”。也不能因预算到期把真实缺口改为通过。

这道门证明的是**没有在限定冷读中发现未决核心设计，且能形成实际实施定位**。它不证明代码未来没有 bug，不证明外部环境永久稳定，不替代成品验收，也不保证整个需求空间没有遗漏。收益需要用冷读捕获的核心决定数、误阻塞数以及之后的 D_codex／G_gap 校准。

## 6. 可直接复用的接手指令

> 你是未参与本设计的 Codex 接手者。只读所给架构与指定源码，不写产品代码。按原始能力检查当前冻结候选，实际列出修改入口、状态和数据 owner、失败／恢复、真实依赖、验证与完成条件。演练主要成功、最高影响失败、恢复和旧能力保护。明确哪些问题仍迫使你选择核心产品机制、算法、接口或验收；这些一律 RETURN_TO_ARCHITECT，不代为补齐。事实不足时指出最低成本的只读核查或最小探针。允许的局部实现自由度无需升级。输出最小实施次序、带来源的阻塞项、唯一下一执行者；所有结论限定于当前版本与范围。

负责人发出这条指令前必须把具体文档、源码 ref、权限和范围填入；模板本身不是可直接发给项目实施者的空白执行包。
