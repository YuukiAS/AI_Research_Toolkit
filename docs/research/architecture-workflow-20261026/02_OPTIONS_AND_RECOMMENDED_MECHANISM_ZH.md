# AI 架构团队：工作方式比较与推荐机制

日期：2026-10-26。性质：**研究性推荐方案，尚未通过真实项目的对比实验，也未实现自动跨应用调度**。
用户要求与取舍权威：[01_USER_REQUIREMENTS_ZH.md](01_USER_REQUIREMENTS_ZH.md)。
依据已有工程标准：[复杂系统设计与交付标准](../../../COMPLEX_SYSTEM_DESIGN_GUIDE.md)；[Mica 已发生的设计遗漏](../../examples/MICA_REAL_UI_EVIDENCE_GATE_FAILURE_2026-10-26_ZH.md)。

## 结论先行

**推荐“异构并行调查 → 唯一总架构 → 陌生执行者接手 → 有界定向修订”作为复杂软件的默认路径。** 角色按真实任务能力分派，不依赖未来插件建成：GPT Pro 负责系统模型和最终方案；GPT Work 独立寻找被忽略的用户场景与跨功能缺口（先不看候选方案）；Codex 只读核查现有源码、真实接口和技术可实施条件。前两类研究与代码事实核查可以并行，之后由总架构师结合结果作整体设计，独立执行者再检查是否能依方案动手。

这不是“先 Planner 再 Critic 再 Planner”：**检查所用的场景在候选方案出炉前产生，事实来源独立，最终准入要经过具体跨组件流程与冷启动接手检查。** 只有技术路线真正互斥，才追加独立架构竞赛；只有高风险前提无法靠现有证据解决，才支付 Codex 实验成本。每轮任务负责人指定下一波执行者、完整任务指令和继续/停止原因，用户只复制粘贴或审议真正的产品取舍。

## 一、设计难题真正在哪里

TODO → 模块的表格容易补满，却只检查了“每项功能归谁”。完整架构至少有另一层结构：**共享的数据身份、状态生命周期、跨组件的先后依赖与错误恢复**。逐项正确的局部决策可能在一起互相冲突。还存在不在 TODO 中出现的限制：宿主第三方服务是否真的提供数据、授权与人工操作、实际发布入口、升级和旧行为保护。

成熟架构师一般先确定业务核心对象、不可破坏的系统不变量、最重要的跨功能使用流程，比较少数造成长期锁定的边界决定，然后选择组件与通信方式。接着用安全、性能、兼容、维护等典型场景检验关键取舍，再回到完整 TODO 作覆盖核对。可复用的工程思路包括 SEI 的 ATAM（场景、风险和权衡）、CBAM（经济成本、收益与不确定性）、集合式并行设计（先保持真正不同的选择、再淘汰），但本流程不机械照搬它们的全部会议和报告。

例如 Mica：复制、高亮、PDF、低内存分别找到模块仍不足以证明“同一回答中的跨公式选区，经刷新/虚拟化恢复后，导出为保真 PDF”成立。要解释回答唯一身份、文本与数学表示、保存锚点、数据生命周期和 PDF 坐标之间的共同合同。另一个根本问题是：GPT-6 的真实交互块究竟如何合法取得样本、记录流式变化并验证宿主适配。两者都不会由一张普通功能分配表自动解决。

## 二、三套已经尽量优化的工作方式

| 路线 | 完整工作方式 | 如何减少时间开销 | 主要优势 | 主要失败方式与适用场景 |
| --- | --- | --- | --- | --- |
| **A 单一总架构师 + 一次盲审** | GPT Pro 自主研究并完成架构；Work 独立从原始需求发现风险；总架构师定向修订、冻结、交 Codex | 一个设计主体；不开发第二方案；审查一次只问具体缺口 | 最低 AI 成本与简单交接，对成熟小修改和已稳定产品有效 | 如果架构师和审查者共享同一错误假设，盲点仍在；复杂跨功能系统中不能仅以此宣称完整。与过去的 Planner–Critic **本质差异有限**，只提高独立性和约束轮次 |
| **B 两套完整架构并行竞赛** | 两个独立设计者各读原始需求、不互看，分别形成自洽的完整架构；第三方使用同一组用户目标、跨功能场景和真实约束比较，淘汰一套，继续深化胜出者 | 两套方案同时生成，墙上钟时间约取较慢者；不强行合并冲突路线 | 最适合根本技术路线分歧、不可逆锁定与昂贵迁移；让用户看到真正有价值的取舍 | 两次完整设计消耗大；共享的第三方能力误判可以同时击倒两套；若后来发现基础事实有误，两份设计都浪费。重大新项目/整体重构时采用 |
| **C 异构并行的架构调查与交叉接手（推荐默认）** | 一条设计核心领域模型和少数候选方案，一条**事先独立**研究未知用户场景与失败，一条从已有代码和外部事实核查可行性；总架构师完成唯一架构；另一执行者冷读架构检验接口/流程/证据，发现缺口只修相关决策 | 三条互补调查同步进行；Work 的场景先以文字完成，无需逐个编码；Codex 第一轮只读，实验按需；避免双份完整设计 | 同时覆盖需求盲点、全局架构矛盾、真实接口虚假前提；对 Mica 一类多功能复杂项目更稳健 | 总架构师仍需真正综合冲突，不可把三份文件简单拼接；若出现根本互斥路线，要临时升到 B；若真实接口无法判定，要追加有限实验 |

**三套不必每个项目都组合。** A 是规模小且核心架构稳定时的简化路线；B 是互斥架构的专门路线；C 是本用户多功能软件架构任务的默认路线。C 的核心改变在于**让三个不同问题来源先独立产生，再由单一负责人真正解决它们**。增加三位名称不同、却一起检查同一张 TODO 表的 Critic，不属于 C。

## 三、统一成本模型：包含并行、人工时间和不确定性

设：
- (D)：从需求产生一份完整架构的成本；(R)：开发前的普通局部设计返修成本；(V)：一次独立问题调查/审查；(P)：一次 Codex 定向技术验证；(I)：整体产品开发；(L)：**进入开发后**才发现根本设计错误造成的额外损失。
- (H)：用户亲自协调、选下一轮角色、重复回答、人工检查与返修的时间；(T)：实际日历等待时间；(C)：额外模型调用、工具和实验消耗。
- 对开发前某项检查，(p)：相应重大问题存在的可能性，(q)：该检查发现它的条件概率。为便于比较，暂忽略多项缺陷之间的联系，单次检查相对不检查的预期节省为 (p q(L-R))，只有 (c < p q(L-R)) 才有纯经济价值。多个审查的 (q) **不能假设相互独立**，特别是模型读同一份报告时。

偏好按真实用户要求分层：**先避免安全/权限/核心目标被破坏，再尽可能少消耗用户时间 (H)，随后优化交付日历 (T) 和预期返工，最后优化 AI 资源 (C)**。必要时可写成 (J=lambda H+mu T+C+mathbb E[L])，但 (lambda,mu) 并未测定，不能声称精确数值最优。普通局部修订通常 (R<D<I)，根本推翻时 (R) 可能接近重新设计；真实 Codex 实验往往比阅读/审查昂贵。

**多个任务并行时，总计算量是各支路之和，但该波墙上钟时间约为最慢支路，而非各支路之和。** C 的首轮等待约为 (max(D_{m model},V_{m blind},V_{m reality}))，再加必要汇合与冷读时间；连续 Planner–Critic 更接近多次顺序设计与审查的求和。可同时启动多个 Pro/Work/Codex 是真实可用的优势，但并行重复一模一样的问题不一定创造信息价值。

### 不凭单组自定概率作决定

下表的成本单位与 (p q) 均仅用于**边界敏感性分析，不是模型真实检出率**。取 (D=2,R=0.6,I=20)，将迟发现根本缺陷的额外损失分别设为 (L=6,20,50)。设 C 的额外盲区调查加冷读成本约 (c_C=1.8)；额外生成第二套完整方案并比较为 (c_B=4.0)；Codex 定向技术实验为 (c_P=3.0)。下表给出各项**单独**投资在成本上打平所需的最低 (p q)：

| 潜在额外返工 (L) | C：额外盲查 (c=1.8) | B：多一套架构 (c=4) | Codex 探针 (c=3) |
| --- | ---: | ---: | ---: |
| 6（容易补救） | 33.3% | 74.1% | 55.6% |
| 20（一次相当大的返工） | 9.3% | 20.6% | 15.5% |
| 50（核心方案推翻） | 3.6% | 8.1% | 6.1% |

这些数不能拿来直接对方案排名，因为不同检查针对不同缺陷、检出率不同，且再次检查会改变剩余风险。在 (L=6) 时重型架构竞争通常不划算；在 (L=50) 时，一项有足够机会发现根本错误的并行研究或实验容易值回成本。若 (p q) 只能粗估为 5%、12%、30%，C 在 (L=20) 下的预期毛收益分别为 0.97、2.33、5.82（相对开销 1.8）；低风险时可减配，高风险时应保留。决策依据是**多组条件下选择是否稳定**，而非声称已经知道 (p,q)。

务实规则：新项目启动时 AI 只做定性分档：是否有重大互斥路线、是否有真实来源尚未确认、错误是否会影响多个功能或大量返工。若几档假设下选择一致，直接执行；若选择会翻转，先买成本最小、最能区分路线的信息。安全关键和无法回滚的错误按硬约束处理，不依赖期望成本赌运气。不要求用户估计任何概率。

## 四、推荐 C 的可执行任务组织：一轮是一个并行工作波次

**启动输入：** 用户现有 TODO、产品优先级、已有仓库、不能改变的旧功能及真实使用环境。已有资料由 AI 自己读。总架构师在原项目的现有设计位置维护一份**唯一当前架构**和一个简短的未解问题/证据表；不另建超出项目需要的任务管理平台。

### 波次 1：三项相互独立的调查，可同时运行

| 执行者 | 本轮真正要产生什么 | 对独立性的要求 |
| --- | --- | --- |
| GPT Pro（架构负责人） | 先从整体使用流程找核心领域对象、所有权与状态转换、不变量、共享组件边界；研究成熟可用方案和真正互斥的关键路线，初步提出设计模型 | 忠于原始需求与代码，不提前按某个审查者的文字写答案 |
| GPT Work／另一独立模型（盲区发现） | **只读取原始需求、用户使用方式、历史故障及相关领域事实**；找出 TODO 之外的必要情境、跨功能时间序列、产品隐含约束、典型失败原因，形成按严重性排序的反例及期望输出 | **不要先读候选架构或设计者自报的需求覆盖率**；只提出能改变方案的实际问题。此阶段是研究与文字场景，不要求为每个场景写测试代码 |
| Codex（技术现实调查） | 对现有项目只读核查：真正可用的入口、已有组件和版本、第三方数据/协议来源、权限与宿主能力、已存在的测试、技术风险；区分“已实际证实 / 仅源码存在 / 未证实 / 无合法路径” | 第一轮原则上不实施功能，不做全面 E2E，不接触用户私人登录态；以可定位源码或实际已做过的证据为准 |

若项目极小、无技术路线分歧和重要外部依赖，可由负责人自行完成第一波，不强制启动三路。若有明确互斥路线，**负责人指派另外的独立 GPT Pro 与自己并行设计第二方案**，按 B 的方式先找到最能区分优劣的事实并淘汰劣势路线；此时不把两套互斥架构强行拼接。

### 波次 2：负责人做真正的架构综合

同时读取三份独立结果，先解决它们彼此矛盾的事实。然后形成**同一套内部一致的系统模型**，至少交代：
1. 什么是关键业务对象、唯一身份、生命周期与不变量；
2. 哪些组件拥有/修改状态，组件之间实际怎样调用或传输、上下游如何消费输出；
3. 关键跨功能用户操作从入口、数据和状态变化到最终结果如何贯通；失效、重试、撤销和降级时谁承担责任；
4. TODO 与这些机制的映射：**允许足够长的表**，但要补齐组件间的接口边和必要的新问题；
5. 需要真实外部事实才能成立的承诺，给出证据取得方法、合法执行者、可替代边界及未证状态；
6. 已否决的主要技术路线和决定理由，以及实施的可用功能顺序、保留的旧能力、验收入口。

**主要架构决定应集中在这一步解决。** 如果同一件事有真正不可同时满足的两种产品取舍，给用户一份短比较与推荐，一次集中询问。一般技术选择、证明所需的调查和审查者的协调，由 AI 决定。

### 波次 3：陌生执行者接手与盲区压力测试，并行进行

- **Codex 冷读接手**：只给原始目标与当前完整架构，不让它从作者的聊天补充隐藏设计。检查能否拆出实际开发任务并准确说出每条关键路径的入口、数据、接口、真实消费者、可验证结果和故障恢复。若发现必须自己发明用户承诺、系统不变量、核心协议或验收数据来源，产出**具体缺失的接口/前提及受影响功能**，返回架构负责人；普通类名、文件名和内部函数拆分可以由实施者决定。
- **Work 交叉检验**：使用波次 1 事先冻结、架构师未针对性准备的场景，尤其是跨模块操作、延迟状态变化、宿主变化、旧功能保留和失败恢复；检查设计是否确实有满足它们的机制。要求指出具体链条在哪里断裂，不能只说“需要加强可靠性”。
- **必要时唯一的小探针**：对于会整体推翻设计、目前仍无证据、且从资料无法解答的关键外部前提，才授权 Codex 做最小技术实验。必须先明确“实验结果如何改变哪个架构决定”，否则不要做。实验结论和未证条件归还原架构负责人，不能把实验中的临时实现当作正式用户功能。

若存在阻断问题，**同一位架构负责人仅修订受影响的系统模型、接口、阶段或真实验收办法**，冷读/盲测也只复核受影响依赖。避免每轮从头写一份全新总体设计；新问题出现才有新工作。

### 波次 4：设计退出与开发交接

设计可以结束的具体条件：
- 全部已知高优先级 TODO 有可定位机制和验收入口，跨功能共享规则明确；
- 关键业务对象和状态所有权无自相矛盾的决定；代表性的高风险跨功能流程可完整走通；
- 关键外部输入/权限/样本来源为**已证、明确可取得或明示受限**，绝不把假设写成实测；真正依赖未证前提的功能按范围保留条件，不能谎称已可发布；
- Codex 冷读接手**没有未解决的重大设计决定**；Work 的高影响反例已经被修订或由明确依据解释，重要旧行为不丢；
- 用户尚需决定的只剩真正的产品取舍，最多集中一次提出；没有必要为了凑审查次数延迟交付。

满足条件就冻结已知决策、交给 Codex 按可用功能连续开发。**开发时普通实现错误/单点测试 FAIL 直接在原任务修；只有真实新事实推翻领域模型、核心接口或用户承诺时，才由原架构负责人对涉及的决定局部重新设计**。对外部缺证导致暂时不可验的能力，其他不依赖它的功能继续。每次交付审查都核查最新真实产物，不把纸面架构通过当作产品实现通过。

## 五、每轮怎么交接，怎样避免用户当流程管理员

每一波负责人**必须替用户作出下一波的工具选择**：基于未解决问题的性质决定谁做什么。不可把“要不要再跑一个 Critic、选哪种模型、运行什么提示词”交给用户。操作接口先按现有 Chat/Work/Codex 可用能力实现：由负责人输出同一批可以同时发送的、写明目的、仓库、授权分支、输入、唯一验收结果和写回位置的**完整任务消息**。现有账号/连接无法自动启动另一条会话时，由用户复制粘贴启动；用户无需自行写提示词或决定顺序。后续只有真实证明的自动交接工具才能宣称替代这个操作，不把未来的 Bridge/Skill 设计当作已经接通。

用户每轮只看五件事，通常总共数句话：

> **已解决**：本波关闭哪项架构关键问题、采用了什么决定。  
> **新证据**：最有说服力的源码/真实能力/场景结果是什么。  
> **仍有的问题**：最多三项当前真正影响架构成立的缺口。  
> **下一波**：已替用户分配给哪些 GPT / Work / Codex，分别解决什么；可直接复制的任务提示词附在同一消息或一个明确的 GitHub 位置。  
> **需要你**：默认“无”；若有，呈现候选取舍、成本、推荐和唯一要决定的问题。

不记录无关的研究者角色表演；不让用户查阅几十页过程纪要。详细证据、备选路线否决理由和当前唯一架构放在原项目合适位置，不能只放在单个聊天上下文。工作尚未完成时不能因当前模型回复结束就报告整个设计完成。

## 六、为什么推荐 C，以及怎样验证它真比旧方法好

该用户有丰富 TODO、多功能共享状态和真实第三方依赖；用户允许并行 Pro / Work / Codex，而且对人工协调和后期大返工极其敏感。A 的成本最低但难以主动发现共同盲点；B 适合根本路线竞争，却会在许多已有项目上浪费第二份完整架构；C 把并行 AI 计算量优先用于**三种不同来源的未知问题**，再由唯一负责人作整体权衡，最符合当前偏好。它不把新插件实现设为 Mica 等项目的前置条件。

更强的证据需要真实项目验证，而不靠本文件自己打 PASS。可从已发生过的项目问题做**保留事实的回放评估**：输入同一份原始需求，隐藏已知失败答案，检验新流程在设计冻结前能否主动找出类似“Mica 真实动态 UI 无取证路径”“跨功能状态生命周期冲突”“原生入口未消费实现”等问题；再把普通 Planner–Critic 历史运行作为对照。记录：用户亲自指出重大缺口次数、重大缺口出现阶段、设计返修和开发后返工、从构思到首个可实施版本的日历时间、AI 用量、人工接力次数。**关键指标是重大遗漏是否更早被 AI 自己发现，以及每减少一次重大返工实际花了多少成本。**
