# 把关键行为设计清楚，再冻结实施范围

Asteria 的设计契约帮助 Chat 暴露一个系统还没有想清楚的部分。用户应能沿着能力、责任、消息、机制和证据不断追问，直到关键行为已经有依据，或者看到明确的待决问题。完整性检查负责发现结构矛盾和缺失引用，独立裁决负责判断这套设计是否足够进入实施。

冻结是一份有明确范围的设计契约。它允许范围之外仍有开放研究，也允许范围内的设计尚未有代码。它不能把没有决定的关键行为交给 Codex 临时发明，不能把填完字段、没有结构报错或制作者自查改称架构通过。

本文是本轮候选规格。正式冻结记录采用 [SEMANTIC_MODEL.md](SEMANTIC_MODEL.md) 中的修订和决定实体，不另建 Freeze 数据库；本轮来源重构与原型检查也不冒充原项目已经做过的冻结。

## 从一个用户能力开始建立设计

Chat 可以逐步形成设计，无需先填完一套表单。起点是一个真实的用户能力及其边界，例如“出现验收失败后，原制作任务能够收到具体问题并继续修复”。只有这句话还不够：谁识别失败，失败指向哪个版本，接收者怎样识别原任务，中断后从哪里恢复，都影响实现。

下面的顺序规定推理需要到达的深度，不要求每一步生成一张卡片。已有图、公式或正文已经解释清楚的内容直接引用；只增加读者仍然需要的信息。

| 设计阶段 | 应能回答的问题 | 保存到共同模型的内容 |
|---|---|---|
| 用户能力与边界 | 用户从什么情境开始，得到什么可观察结果？哪些情形明确不在本次范围？ | 要求、场景、边界与来源 |
| 核心对象 | 哪些对象需要稳定身份和版本？一次修改后什么仍算同一个对象？ | 实体、产物组成、候选身份 |
| 组件责任 | 谁负责判断、谁修改、谁消费结果？职责是否遗漏或重叠？ | 组件责任及设计决定 |
| 真实关系 | 具体传递什么，谁以何种方式消费，怎样拒绝不适用的输入？ | 有类型关系、载荷与消费者 |
| 关键机制 | 输入如何成为输出，需要哪些状态、条件、公式或数值步骤？ | 适合内容的机制能力面 |
| 正常、失败与恢复 | 何时成功，怎样失败，哪些状态能恢复，何时应停止？ | 分支、守卫、取消、恢复与终止条件 |
| 已有能力保护 | 新行为不能破坏哪些已接受要求？共享依赖在哪里？ | 保留承诺与影响关系 |
| 实现责任 | 哪一部分由本项目实现，哪一部分依赖外部契约？哪些选择已决定？ | 责任边界；存在实现时才增加绑定 |
| 验证方法 | 什么观察能够支持这项要求，什么仍需专业判断？ | 验证计划、方法来源与实际结果 |
| 开放问题与冻结范围 | 还有什么未知，它阻止哪项能力，什么事实能解除？ | 问题、假设、决定和范围化冻结提案 |

每次下钻都应检验当前设计是否回答了新的具体问题。一个组件名称如果始终只能换成另一句抽象口号，就还没有解释机制。一条箭头如果找不到消费步骤，也没有完成信息流设计。

## 关系要走到消费者，机制要走到可实现的行为

对于信息流关系，Chat 至少需要明确产生者、载荷、触发条件与消费者。消费者可以是目标组件中的一个设计步骤；纯设计系统不要求提前存在函数。实现已经声称接入时，消费点应继续连到真实注册、处理函数或其他源码位置。[1]

Mica 提供了可核对的实例：连接器信号发布 `mica-connector-lifecycle-latched`，载荷包含代次、来源、输入框身份等信息；连续显示模块的 `handleSharedConnectorLifecycle` 读取它并启动对应观察。把这条边写成“同步状态”，会遗漏到底传了什么、如何进入后续机制的重要信息。[2]

机制的充分性随内容而变。状态恢复需要事件、守卫、取消和期限；数值算法需要定义域、误差、停止与失败条件；材料验收需要候选身份、要求、判断范围、发现定位与返修消费。Asteria 使用相同实体和关系，正文分别采用状态图、时序、公式、数值步骤或页面对象阅读，不把所有机制改写成通用流程卡。

说明正常路径之后，至少沿关键边界做一次失败和恢复推演。失败可能是输入版本错误、真实消费者缺失、算法条件不满足、来源不可读、渲染失真或任务中断。恢复不一定是自动重试；它可以是撤销优化、保留人工恢复点、提出研究问题或停止声明结果。必须由设计决定适合的处理方式。

Mica 清空恢复的实现包含明确清空确认、旧内容匹配、新输入取消以及尝试次数和期限。它说明“自动恢复”这个标签远不足以指导安全实施。Next 应让这些关键条件在冻结前可见；它们的正确性仍需对应源码和证据支持。[3]

## 合理的外部契约与未定机制

组件可以依赖一个无需展开内部实现的外部系统，但边界必须明确。`opaque_contract` 至少说明提供方、可观察输入输出、适用条件、失败语义、调用方的恢复责任与验证方式。它不能用“由智能模块处理”代替本产品自身必须作出的关键判断。

`unresolved` 机制表示确实尚无唯一算法或行为方案。它适用于真实研究状态，也能使缺口不被示意图掩盖。若冻结范围承诺的能力必须依赖该算法输出，问题阻止这项能力进入实施契约；若其他数值模块和参考算法已有独立、可验证的边界，可以分别提案冻结这些局部范围。缩小范围必须反映真实责任边界，不能把仍被依赖的未知工作藏到图外。

开放假设也需要说明影响。暂未观测的外部负载上限，可以成为限定适用范围的假设；决定核心算法是否成立的数学条件，则不能仅凭填写“假设成立”跳过科学判断。Asteria 能记录前提和依赖，不能替代证明或领域审查。

## 实现者可以决定什么

冻结应给实现保留合理空间，同时让关键行为的缺口尽早返回设计。判断依据是该选择是否改变用户承诺、跨组件契约、科学含义、失败恢复或已有保证。

| 实施过程中遇到的选择 | 处理方式 |
|---|---|
| 局部变量名、满足约束的内部函数划分、等价且不影响契约的代码整理 | 实现者按工程判断完成 |
| 既定输入输出内的数据结构选择 | 可由实现者选择；若改变复杂度、持久化或行为保证，补对应依据 |
| 关系的真实消费位置尚未确定 | 返回具体设计问题，不能临时把消息接给一个方便的模块 |
| 失败后的重试、取消、回滚或用户提示未决定 | 返回受影响范围与可选取舍，由设计形成决定 |
| 科研算法、近似方法、误差容限或停止条件仍不确定 | 保留研究问题；不能用一段能运行的代码填补科学空白 |
| 验收规则与用户要求发生冲突，或缺少整页、整套产品判断 | 返回对应要求和产物对象，由专业裁决处理 |

实现返回的问题必须能定位到对象、关系或要求，并说明为什么现有契约不足。它可以附带工程建议，但不能自行把建议升级为已接受架构。补正后的重要决定形成新修订，再继续受影响范围的实施。普通实现选择无需制造架构修订或额外审批。

## 机械检查只检查能够证明的条件

检查读取整个选定快照及其声明范围，不能只读取当前画面里的节点。结果给出问题、对象、来源和为什么影响本次提案；不显示完整度百分比，不把字段数量当成设计质量。

| 条件 | 可机械核对的部分 | 结果应怎样使用 |
|---|---|---|
| 冻结范围内已接受组件缺少机制 | 是否存在机制、独立机制引用或具名外部契约；必要路径上的 `unresolved` 不能满足关键行为已定的条件 | 指向受阻能力；机制内容是否充分仍交专业判断 |
| 信息流未说明载荷 | 该关系类型是否需要契约，载荷来源和必要结构是否存在 | 要求补具体契约；不向科研参数关系强塞消息字段 |
| 消费者缺失或不属于目标范围 | 组件、机制、步骤引用是否存在，归属是否符合关系目标 | 防止箭头止于没有接收责任的方框 |
| 声称已接入实现却无来源 | 绑定与锚点是否存在，固定来源是否可定位，声明的粒度是否相符 | 纠正声明或补真实实现；空绑定的纯设计不报此错误 |
| 声称当前已验证却无适用结果 | 实际结果、对象版本、方法和依赖是否匹配；是否过期或不可解析 | 不因测试文件存在或一条支持边就显示已验证 |
| 关键失败或恢复路径没有交代 | 是否声明分支、共用处理或有依据的不适用情形 | 缺失被暴露；分支是否完整仍需推演 |
| 重要变化缺少原因或触发 | 修订是否关联实际问题、观察或决定，原因是否有来源 | 不能自动用提交标题“优化”补全因果 |
| 下游影响没有说明 | 是否记录变化范围、影响关系和待核对项 | 提示缺口；不自动证明未列对象安全 |
| 保留承诺没有对象或检查方法 | 是否引用明确要求和方法，是否混入范围外对象 | 区分希望保留、定义未改和实际复验 |
| 引用悬空、来源歧义或重复身份 | 端点是否存在，锚点能否唯一定位，ID 是否冲突 | 保留具体候选与原因，不静默挑选或合并 |
| 设计与代码存在未解释变化 | 固定前后来源、受绑定对象及依赖是否有变化 | 给出比较范围，不能由提交日期判断对齐 |
| 产品证据指向另一候选 | 文件摘要、页或对象身份、要求版本是否一致 | 旧证据仍保留，当前适用性待重新判断 |
| 受阻问题被放到冻结范围之外但仍在依赖路径上 | 必需依赖是否跨出边界，是否具备明确外部契约 | 重新界定范围，不能靠隐藏节点消除阻塞 |

这些检查采用条件规则。没有实现声明就不要求源码绑定；没有运行结论就不要求运行证据；没有科学公式就不要求符号表。明确不适用必须解释相应边界，不能成为所有字段都填“无”的通用逃生口。

关键性来自本次能力所需的行为与依赖路径。作者可以说明某项细节为何不影响契约，不能靠取消一个 `critical` 标记，让必要的未定机制从冻结检查里消失。

机器可以发现引用和结构缺口，无法仅凭一段非空文字确认其信息质量。短小但精确的契约可以足够；很长的说明仍可能把关键行为留空。未知内容不得由导入器自动补成接受状态。

现有 Asteria 的证据样例按支持边与缺口边计数，校验器也含自然语言 `role` 字段启发式。Next 应迁向严格能力面、真实版本与条件校验，不能沿用这些简化规则产生新的冻结结论。[4]

## 必须交给专业判断的问题

专业审查需要具体对象和依据，而不只是“人工看一下”。判断可以发现整个能力遗漏、职责划分不合理、失败策略不可接受、算法前提不成立或整页视觉失衡；这些问题无法由结构完整性替代。

| 判断主题 | 审查应形成的内容 |
|---|---|
| 产品范围与取舍 | 是否漏掉真实用户场景；代价是否值得；拒绝或延期的能力是否合理 |
| 架构深度 | 机制是否具体到实施无需发明关键行为；外部黑箱边界是否真实可接受 |
| 科学有效性 | 模型、公式、算法和证据是否支持所声称结论；反例与适用范围是否被处理 |
| 实现对应 | 固定代码是否真正实现了设计语义；静态索引未覆盖的动态行为如何判断 |
| 证据充分性 | 方法是否能检测目标失败，结果是否足以支持该能力，环境差异有何限制 |
| 产品与视觉质量 | 页面、对象、整套叙事和交互是否满足要求，信息取舍和阅读顺序是否成熟 |
| 旧能力保护 | 已接受行为是否被完整识别，变更是否需要更广范围的复验 |

每项审查结果保存为有来源的证据或发现，记录判断者、范围、依据与限制。制作者自查、独立审查和用户裁决保持各自身份。检查页可以把尚待判断的事项交给相应审阅者，但不安排代理执行，不自动把判断者名称变成结论可信度。

## 冻结提案如何形成契约

冻结提案使用当前作者文件和结构连接生成快照，选定本次准备实施或接受的能力与对象范围，连同必须依赖的契约一起提交。相关开放问题和已有证据随范围进入提案；原文、机制图和来源可以按需展开，不为“完整”重复打印全部字段。

提案最少要让独立裁决者回答五个问题：本次承诺什么，关键行为怎样发生，什么仍未知，实现者必须遵守什么，以及以后怎样判断完成。问题直接来自设计内容，不由一个总分代替。

机械检查发现的真实矛盾必须处理。对于缺少实现或运行证据但本次只冻结设计的情况，保留相应事实即可；对于仍会迫使实现者发明关键行为的缺口，提案需要返修或调整真实范围。专业审查随后判断设计、边界和证据是否足够，给出接受该范围或继续修改的决定。

独立裁决者通过现有授权确定，可以是负责最终决定的人或独立审查线程。Asteria 只记录其身份、对象与依据，不把系统自身或制作者自查当成独立裁决。只有取得明确的范围化接受决定，真实修订才能记为 `frozen`；机械检查结束只表示检查完成，不自动显示 PASS 或 READY。

冻结记录包含稳定范围、父修订、内容摘要、触发和理由、接受决定、证据引用、已接受假设、开放问题及其影响、保留承诺。它是可继续演进的基线：之后改变契约形成新修订，已经冻结的旧内容仍可回读。[5]

### 哪些开放项影响本次冻结

问题要指向具体能力与解除条件。若它影响本次承诺的必要路径且没有可接受的外部契约，就阻止该范围冻结；若它只影响明确排除的能力，可以继续保留。边界必须与真实依赖一致，裁决理由中说明为何排除仍然成立。

“尚无生产算法”不会阻止独立数值内核的设计审查；但它会阻止把依赖该算法的完整推断引擎交给实现者。没有 DA 宿主接线的运行证据，不妨碍描述完整责任与消息契约；却不能支持“反馈已实际送回并被原任务消费”的声明。没有重新渲染的新 PDF，也不能继续沿用旧候选的视觉通过记录。[6]

## 四个参考项目的冻结边界

| 参考项目 | 可以形成的具体设计提案 | 必须暴露的未定内容与证据限制 |
|---|---|---|
| Delivery Assurance | 正常交付、失败返回原任务、中断恢复、旧能力保护的责任和消息契约 | 新接线可以无实现；宿主身份、反馈接收与实际消费能力必须有明确依赖或 blocker，不能从路径动画推断已运行 |
| Mica | 选定输入、连接器或恢复机制的责任、事件、状态、取消与资源边界 | 真实代码可绑定；本轮输入路径合成证据不等于真实 ChatGPT、全部恢复分支或目标设备验收 |
| CAT-TRACE | 稳定数值模块与具备明确适用范围的参考算法 | 被反例撤销的路线保留历史；生产算法尚未唯一确定时保持受阻，不补假代码 |
| STAT5060 Tutorial | 候选身份、要求、机械证据、专业判断、发现定位与修复后复验的契约 | 原有 validator 不能自动视为正确答案；页面、对象和整套叙事需要对应审查，新候选使哪些旧证据失效必须说明 |

四者都能以共同模型表达设计、实现与证据，但设计冻结不等于软件发布、科学结论成立或成品验收通过。冻结决定必须指明自己接受的是什么。四项目的固定来源与更细阅读路径见 [FOUR_REFERENCE_PROJECTS.md](FOUR_REFERENCE_PROJECTS.md)。

## 交给 Codex 的内容应能直接使用

交接以选定冻结修订和范围为起点，给出目标能力、实际作者来源、关键契约、机制、可自由选择的实现部分、禁止破坏的既有要求、开放问题与验证方法。存在代码时附固定绑定与当前对齐观察；纯设计则明确尚无实现，不列未来函数来装作已有来源。

实现者开始工作后可以沿同一对象继续补绑定、运行证据和发现。新代码改变契约时，返回对应设计问题或提出修订；只是把既定契约实现出来时，更新来源与验证即可。代码先行、设计先行和证据过期的判定遵循 [VERSION_EVOLUTION_AND_DRIFT.md](VERSION_EVOLUTION_AND_DRIFT.md)，不会因为一次提交成功就自动消失。

交接是否足够，应通过一次真实路径推演来检查：从用户要求出发，指出谁处理输入、如何产生结果、失败后谁接手、哪些旧行为仍受保护，以及什么证据能让裁决者接受完成。推演中出现无法回答的关键问题，就把它记录到对应对象并继续设计。Asteria 的作用是让这些问题在实施前可见，决定仍由设计者和相应专业判断作出。

## 本轮消费者核读带来的具体约束

制作方实际核读 Mica 时发现，原型两条关系中的手写消费函数名并不存在，真实源码分别是 `collectConversationTurns` 和 `confirmPendingClear`。名字非空、图上有接收组件、甚至相邻已有真实源码链接，都不足以支持该关系已实现。已在原型修正，并保存[八条关系逐项核读](sources/mica-relation-consumer-audit.md)。

正式实现中，linked 软件关系的消费点必须引用已解析的 source anchor / binding，由定位结果提供符号名；手写文本只能补充用途。解析器能够检查符号是否存在、是否唯一及绑定提交是否匹配，载荷是否在该控制路径中真正被使用仍需代码或运行证据核对。纯设计关系则引用明确的接收机制和预期消费契约，允许尚无源码，但不能借用软件 linked 的状态。

Tutorial 同时保护另一条边界：既有课件或验证器有未修缺陷，可以阻止产品验收；当验收回路的责任、载荷、机制和修复合同已经明确时，缺陷本身不必阻止该设计范围被审阅冻结。设计接受、实现修复和产品验收继续分开。
