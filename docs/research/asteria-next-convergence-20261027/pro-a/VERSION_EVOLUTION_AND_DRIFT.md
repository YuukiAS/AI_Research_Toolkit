# 当前架构与局部演进

Asteria 默认展示当前选定的架构。用户选中一个组件后，可以继续看它曾经怎样工作、什么证据触发了修改、实现改在哪里，以及当前哪些结论仍待验证。历史服务于这个问题，首页不铺满时间线。

本规范沿用 [共同语义模型](SEMANTIC_MODEL.md) 的 `revisions`、`anchors`、`bindings` 和实体关系。变更列表、历史视图、影响范围与对齐状态都由这些来源计算，作者只补原因、取舍和承诺，不再维护一份平行的 Change 数据库。本文规定最终候选的实现目标；演示原型只覆盖其中的选定案例。

## 不同版本回答不同问题

| 概念 | 回答的问题 | 保存的依据 |
|---|---|---|
| Git 提交 | 当时仓库里是什么文件？ | 不可变提交与文件内容 |
| 来源观察 | 本次读取了哪个提交，哪些绑定可以定位？ | 读取提交、内容摘要、解析器版本与定位结果 |
| 架构修订 | 哪项责任、机制、要求或科学判断为什么改变？ | 明确范围、父修订、触发、理由、差异、影响和证据 |
| 产品版本 | 对外发布或称呼的是哪个版本？ | 来源项目实际的版本定义；可关联一个或多个修订 |
| 产品候选 | 这次验收的是哪份文件或构建？ | 文件或构建摘要、组成及产生来源 |
| 模型变体 | 哪些定义需要并存比较？ | `variants` 及其对象范围 |
| 谱系 | 这个方法继承、修改或撤销了什么？ | 有类型的来源关系和对应解释 |

一个架构修订可以跨多个提交逐步实现；一个提交也可能同时修改几个互不相关的机制。只改布局、修正文档排版或升级构建工具，并不自动产生架构修订。代码已经更新而架构解释尚未更新时，先产生来源观察与待核对范围，不能根据提交时间替作者写下新的接受决定。

变体、谱系和时间历史分别保留。Original TRACE 与 CAT-TRACE 的并存比较属于变体；某个算法吸收了另一方法的数值思想属于谱系；同一算法修改停止条件属于修订。DA 在同一拓扑上切换正常、失败和恢复路径，则只是视图选择。[1]

## 什么变化值得进入局部历史

当变化改变读者需要理解或实现者必须遵守的行为时，建立有意义的修订。例如责任转移、消息载荷或消费者改变、关键状态转换修正、科学假设变化、参考算法被反例撤销、验收要求更新，或证据使原先的接受决定需要返修。

源文件移动、符号显示样式和解释文字润色可以作为来源或编辑变化保留，不必挤入默认架构历史。文字看似只改一句但改变了前提或承诺时，仍属于语义变化。是否有意义取决于内容，不能用改动行数或提交标题自动判定。

修订使用稳定 ID，显示名称由项目决定。Mica 的“0.1.6 → 0.1.7”适合做真实产品版本标识；纯设计 DA 可以使用“返修接收责任明确”等自然标题。Asteria 不要求为每次架构调整制造一个新的语义化版本号。

每项重要修订需要让读者理解以下因果关系：哪个问题或观察触发了重新考虑，原做法为什么不够，采用什么决定，哪些对象实际改变，谁可能受影响，以及哪些行为仍需保留。具体内容放在关联的 issue、result、decision 和修订解释中；相同正文只维护一次。[2]

## 修订范围与来源重构

修订范围使用 `SemanticObjectRef`，可以选定实体、关系、符号、变体或绑定。范围中的对象有完整前后定义；相关外部对象作为背景读取。跨出范围的影响可以被发现和列出，但不因出现在画面中就获得“已检查未变”的保证。

局部历史必须显示自己的边界。例如，本轮从 Mica 两个提交重构的是连接器输入路径的机制变化，不能据此把整个 0.1.6 产品画成已完整重建的系统快照。对没有调查的其他组件，界面只显示当前背景及其来源，不制造旧版内容。

历史有三种来源状态：

- `draft`：作者正在形成的解释或未提交变化。
- `frozen`：有明确范围、实际冻结来源和对应裁决的记录。
- `source_reconstruction`：根据历史源码或文档，在后续研究中重构的解释。

本轮原型的历史研究使用第三种状态。后来完成的检查绑定本轮实际运行对象，不能挪到旧版发布日期上；后续裁决若接受这份重构，也应形成新的记录，保留它是后来重构的事实。

快照和来源摘要遵循 [SEMANTIC_MODEL.md](SEMANTIC_MODEL.md) 的规范化规则。修订不在自己的作者文件中写入尚未生成的 Git 提交；源文件清单与语义摘要先固定，导入器读取实际提交后补充读取来源。历史内容不可原地覆盖。

## 通用语义比较如何计算

现有 Asteria 的 `diffOriginalTraceToCatTrace` 返回预写条目，没有使用两个输入。它可以保留为已有解释材料，Next 必须以真实的前后快照计算比较结果。[3]

比较器接受两个快照、一个显式范围和一个 schema 版本。它按稳定身份匹配对象，对范围内对象及相关关系执行规范化比较，再返回新增、删除和修改。不能按标题相似度自动把两个组件合并，也不能把同名函数视为同一架构责任。

| 比较对象 | 纳入语义比较 | 单独呈现或排除的内容 |
|---|---|---|
| 实体 | 责任、定义、边界、接受决定、机制、要求、假设 | 单纯显示名称变化归重命名；坐标、尺寸和选中态排除 |
| 机制 | 步骤顺序、事件、守卫、动作、公式引用、误差与终止条件 | 渲染器排版、代码高亮和折叠状态排除 |
| 关系 | 类型、两端、方向、载荷、消费者、触发、失败与恢复契约 | 路由控制点、线条颜色和标签位置排除 |
| 符号 | 含义、作用域、维度、域及公式绑定 | 字体选择等纯显示属性排除 |
| 绑定 | 服务的实体、作用角色、实现选择及确认依据 | 来源位置变化单独说明；函数行为不能由行号变化推断 |
| 证据与发现 | 结果适用对象、方法、范围、依赖及发现状态 | 导入时间和查看次数排除；过去的原始结果保持不变 |
| 变体 | 并存定义与范围变化 | 当前显示哪个变体属于会话选择 |

规范化必须尊重类型。集合可以排序去重，有序步骤和状态转换不能任意排序；正文空白可按明确规则归一化，公式、代码和要求中的有意义差异必须保留。文字等价、数学等价和行为等价都不能仅由字符串规则证明。比较器可以指出文字或公式发生变化，再由相应审查判断其意义。

差异首先呈现责任和行为的前后变化，原始文本与源码差异按需展开。源码的语法差异可以辅助解释实现变化，但不能代替上述架构对象比较，也不能自行生成触发原因和科学结论。

### 删除对象仍应留下可读的前态

删除后的当前快照没有该节点，但比较视图必须保留旧节点的只读投影、旧来源与旧关系。用户需要知道被移除的东西曾经服务谁。仅在新图上遍历会丢掉这条证据。

比较视图使用前后关系的并集。相同关系 ID 若改变了端点或契约，保留带有前态、后态标识的两个版本；不能先用当前关系覆盖旧关系再计算影响。被删除节点和边以明确的文字或线型标示，深浅主题均不能只依赖红绿色彩。关系详情可直接比较旧载荷、旧消费者和新契约。

例如连续显示模块删掉普通 `input` 触发入口后，旧输入事件节点及其旧连线仍出现在差异范围中，新图显示共享连接器事件与结构观察路径。共享连接器事件原本已经存在，应显示为保留的背景或保留对象，不能因为新机制主要使用它就误标成新增。[4]

## 影响追踪与保留承诺

影响分析从发生实质变化的对象出发，在前后关系并集上按类型追踪可能受影响的对象。信息流沿生产者到消费者传播；`depends_on` 从依赖目标的变化传播到依赖方；产物包含关系按页面重排、组成变化等规则展开；证据支持关系则用于检查证据适用性。所有边一律按箭头方向递归，会把这些含义混在一起。

关系注册表必须声明传播方向、适用的变化种类与停止条件。没有登记传播语义的关系保留为待判断，不能默认等价于安全，也不能默认使全项目失效。循环依赖需要去重，路径长度截断或来源覆盖不足必须展示范围限制。

计算结果是一组可能影响与依据路径。判断某项结果实际过期，需要继续核对该结果的对象、要求、方法和依赖。原则及四类项目的失效案例见 [SOURCE_BINDING_AND_EVIDENCE.md](SOURCE_BINDING_AND_EVIDENCE.md)。

“没有变化”也有不同强度。快照相同，只能说明该项规范内容没有改变；作者希望保留某行为，是设计承诺；通过对应新候选的检查，才产生当前证据。界面分别使用“定义未改”“需要保留”“已在该候选核对”等确切表达，不把它们合成一个安心标签。

保留承诺必须指向具体要求或行为，说明适用范围与检查方法。Mica 两版源码都保留外观层不可交互、关闭功能时清理、创建前检查快照新鲜度的约束；本轮输入性能检查没有覆盖这些行为的全部实际交互分支，不能宣告所有保证已复验。发送与清空恢复的跳过分支只阻止新建外观层，不能把“已有外观层立即消失”写成两版已经提供的保证。[4–5]

## 组件局部历史的阅读顺序

选中组件首先显示当前责任、关键机制和与当前问题有关的开放项。历史入口给出最近一次有意义变化及简短原因；展开后按以下顺序阅读：

1. 当时什么问题促成了修改，证据来自哪里。
2. 机制、关系或要求的前后变化。
3. 对应实现与来源变化。
4. 受影响范围、保留承诺及当前复验情况。

读者可继续选择更早的修订或两个明确端点进行比较。返回当前状态时恢复原来的组件选择与视图位置。已删除组件可以从历史搜索或旧修订进入，打开后标明历史身份，不能像当前组件一样提供修改入口。

桌面允许在原系统图上强调前后变化，并在相邻阅读区呈现解释。手机先显示变化原因和当前结论，再依次阅读前态、后态与证据；完整图作为可展开上下文，不把两张桌面图挤成两列。全项目时间线保留为按需工具，不作为默认导航。

## 双向偏离：设计与代码分别有基线

对齐判断至少记录：选定架构修订、比较范围、设计内容摘要、实际读取的代码提交、相关绑定及定位结果、所用检查或审查证据。提交日期只帮助定位历史，不能证明谁已经跟上谁。

| 情形 | 显示的事实 | 下一步需要什么 |
|---|---|---|
| 纯设计且没有实现声明 | 尚未开始实现；空绑定合法 | 明确实施责任即可继续设计，不制造错误锚点 |
| 已接受机制要求新增行为，现有绑定仍指向旧机制 | 设计先行，列出未实现的具体差异 | 实施后补固定绑定及对应验证 |
| 绑定函数或相关依赖出现可能改变行为的修改，设计尚未解释 | 实现变化待核对 | 比较真实变化；接受后修订设计，或修正实现 |
| 设计与代码都改变，现有证据不能证明含义一致 | 双方变化尚未对齐 | 明确采用哪个契约以及需要修复的部分 |
| 指定范围已通过有依据的对应检查 | 该范围在所示版本上已核对 | 来源更新后重新计算适用性 |
| 绑定失联、索引不完整或来源不可读 | 当前无法判断 | 恢复定位或补充范围，不误报成代码不存在 |

代码更晚但只有格式化或文件移动，不自动成为“代码先行”；设计较新但变化仅在解释文字，也不自动成为“实现落后”。反过来，函数仍能打开、名称保持不变，也不能保证其行为仍符合设计。

设计偏离的处理是有来源的决定。作者可以补正架构以表达真实且被接受的实现，也可以要求实现返回原契约。Asteria 提供差异与证据，不自动把代码当成科学模型或产品要求的新权威。所谓“已核对”必须带范围，未绑定的仓库区域不计入结论。[6]

## 纠正、撤销和回滚

发现历史绑定指错函数、解释误读源码或证据绑定错了候选时，建立纠正记录，指明原记录、错误原因和新依据。原记录在当前阅读中可以被新记录取代，但旧修订仍可回读。旧测试结果不能悄悄改绑到另一个函数或另一份产品。

纠正原因使用决定实体，新解释或新结果通过有类型关系指向被替代记录；涉及契约变化时关联新修订。它不新增另一套纠正对象库，也不新增可以掩盖历史来源的修订状态。

算法路线被反例撤销时，以 `supersedes` 等关系保留旧路线、反例和撤销决定。当前视图默认使用有效路线；局部历史解释为什么旧方法不再适用。旧实现仍存在于仓库，并不使被撤销的科学结论重新有效。

回滚也形成新的修订。代码回退到旧提交时，架构接受决定不会跟着自动倒退；应检查当前设计是否仍要求新行为。设计决定回退时，也应检查代码是否已经回退，以及旧证据在当前环境、要求和输入下能否复用。Git 能恢复文件内容，不能代替这两项判断。

Tutorial 的修复尤其需要保留产品身份：新候选覆盖旧文件名时仍产生新的文件摘要；旧页面判断继续指向旧候选。页面重排、公式修改和渲染器变化分别决定哪些证据需要重新获取，不能凭相同文件名认为已经复验。[2]

## 真实案例：Mica 输入路径返修

固定的前后提交是 `9f56ea8d23a0895ddbb3f1e95ee207bd049b62c0` 与其直接下一提交 `aa4ce52581fff2e207d1f93600becbb3018b0efc`。版本来源分别为 0.1.6 与 0.1.7。旧连续显示路径监听六类输入与交互事件，在连接器上下文或选择动作检查通过后，重复启动重型快照并进行 60 毫秒轮询；新路径消费旧版已有的共享连接器信号，通过短期结构观察与下一帧调度合并刷新，并复用没有变化的快照。观察窗口从 3200 毫秒改为 4200 毫秒，发送互斥条件也有变化，不能因为高层功能名称相同就列为机制未变。[4]

这项修订改变了实现机制，用户能力名称没有变化。修订说明应聚焦普通打字为何不应承担连接器快照开销，再给出删除的触发入口、保留的事件能力和当前实现锚点。

本轮在固定当前提交 `7059c0dc24b908b57bd0e1f475142ba4f4520621` 执行现有输入路径合成检查，13 项原有断言通过；这是后来取得的本轮证据，支持对应本地输入场景。它不能被显示为 0.1.7 发布时已经执行的记录，也不证明真实 ChatGPT 或目标设备的全部表现。[5]

## 正式实现必须守住的回归条件

这些条件用于检验比较和历史机制本身，不作为架构质量计分表。

| 输入变化 | 必须得到的结果 |
|---|---|
| 只移动节点或切换主题 | 语义比较为空，历史不新增架构事件 |
| 修改步骤顺序、消费者或数值停止条件 | 返回对应类型的真实前后差异 |
| 删除节点及其消费边 | 旧节点和旧边仍可阅读，下游影响不会因删除而消失 |
| 同一个关系 ID 改变目标 | 前后端点均参与影响核对，不能被字典覆盖丢失 |
| 两个同名实体各有不同 ID | 保持独立；只有显式合并决定才能建立对应 |
| 局部比较没有覆盖某组件 | 标为背景或待核对，不标为已验证未变 |
| 旧证据通过而对象依赖已改变 | 保留历史结果，当前适用性变为过期或待复核 |
| 一个函数能定位但从未审查语义对应 | 不生成“设计实现对齐”结论 |
| 源码先回滚，设计仍接受新契约 | 显示需要核对的差异，不自动回滚设计 |

原型代码目前计算选定实体、关系和绑定的前后比较，并让旧边参与影响追踪。正式实现仍需补齐符号、变体、严格类型化传播、来源范围和证据适用性规则；原型的简化函数不能直接作为这些契约已经实现的证明。
