# Asteria Next 唯一产品规格

## 1. 产品定义

Asteria Next 是一个 Git 原生的复杂项目架构工作台。它把**当前架构、机制、真实实现、验证证据和有意义修订**连接在同一规范语义图上，使用户可以从整体系统逐步追到可核验的代码、公式、成品对象或验证结果，并在冻结前暴露实施者仍需临时决定的空白。

Asteria 不替代产品判断、科学判断、统计判断、教学判断或视觉判断。它负责保存结构、准备材料、运行可机械检查、显示证据边界，并把专业结论绑定回具体对象和修订。

## 2. 产品边界

Asteria Next 继续演进 `YuukiAS/Asteria`，保留 Asteria 2.0 的 Architecture／Lineage／Evidence 和现有迁移兼容层。新增能力进入 2.x 主线，不恢复 1.x 无限画布，也不另建 Architecture Ledger 产品。

产品内包含：

- 规范语义图及其多种投影；
- 系统、机制、实现、证据、演进与完整性阅读；
- Git 仓库桥接和固定提交源码锚点；
- 有意义修订、语义差异、局部历史和双向漂移；
- Architecture Freeze 的机械检查、专业判断边界和冻结回执；
- 四类项目所需的差异化 renderer；
- 静态本地优先工作方式及可审查导出。

不包含：

- 后端数据库、图数据库、账号、协作云、向量数据库或 agent runtime；
- 自动替代架构设计、科学方法选择或专业验收；
- 全仓库完美调用图；
- 自动把代码变化解释为科学真值；
- PPT／Word／PDF 编辑器；
- 用字段数量计算“架构完整分”。

## 3. 主要用户任务

### 3.1 看清当前系统

用户打开项目后先看到当前架构投影和少量可读路径。节点显示稳定身份和当前主要状态；关系显示方向，选择后再展开载荷、消费者、失败与恢复含义。默认不展示历史时间线、内部编号和所有 schema 字段。

### 3.2 进入机制

节点可下钻到机制。机制按内容选择序列、算法步骤、状态机、公式、数值例程或成品验收循环 renderer。机制必须说明承担者、输入、输出、不变量、失败模式和恢复条件；不强迫所有类型使用同一种卡片。

### 3.3 追到真实实现与证据

实现页签从规范实体进入 repository bridge：固定仓库和提交、相对路径、符号或结构锚点、角色、绑定来源、置信度、测试引用和陈旧状态。证据页签区分候选身份、机械观察、专业判断与最终裁决。设计对象可以没有实现；声称已实现却没有锚点时才形成漂移。

### 3.4 理解为什么改变

对象和关系提供局部历史；演进页只列有意义修订。每个修订给出改变前、当前、触发证据、原因、下游影响、不变保证、实现对齐、被撤销路线和校正／回滚状态。

### 3.5 冻结并交给 Codex

冻结对象是一个明确的 `ArchitectureRevision`。Asteria 先运行结构检查，再要求 ChatGPT、GPT Work 或合资格领域审查完成专业判断。关键机制、关系消费者、失败链、验证方法或权限边界仍为空时不得冻结。开放项只有在影响有限、退出条件清楚且不要求 Codex 决定产品或科学语义时才可保留。

## 4. 信息架构

一级入口固定为四个：

1. **系统**：当前拓扑、路径、节点、关系和对象详情。
2. **机制**：状态、算法、公式、数值例程和流程 renderer。
3. **演进**：有意义修订、语义差异、变化原因、影响和对齐。
4. **检查**：可机械发现的结构空白，以及必须由专业判断处理的边界。

Lineage 与 Evidence 不被删除。Lineage 继续作为跨方法来源投影；Evidence 继续作为以 claim／requirement 为中心的证据投影。它们在产品导航中可按项目类型作为一级或二级入口出现，但底层仍使用同一图。

## 5. 当前优先、历史按需

默认页面只显示当前 accepted／tested／design-only／open／blocked 状态。历史通过三种入口下沉：对象局部历史、修订列表、语义差异。巨型时间线不是默认视图。被撤销路线保留在修订和当前机制的替代路线中，不与当前路线等权占据首页。

## 6. 桌面与手机

桌面系统页使用路径、语义图、对象详情三层布局。手机重新排列为：项目摘要 → 路径选择 → 顺序步骤 → 关系载荷 → 底部详情。手机不显示缩小的桌面图；机制、演进和检查页使用横向索引与单列正文。

## 7. source of truth

唯一真值是受 Git 版本控制的 Asteria 规范语义包：

- `ArchitectureProjectV2` 的 entities、symbols、relations、variants 和 views；
- repository bridge manifest 的实现绑定和状态对象；
- 本规格新增的 revisions、changes 与 evidence records。

UI 坐标、搜索索引、布局缓存、截图、导出文件和自动分析结果都是可再生投影，不得成为第二真值。正式实现应升级现有 schema，而不是引入同义数据库。

## 8. 最小可行发布顺序

1. 模型扩展与迁移：关系合同、修订、变化、证据记录；保证现有 CAT-TRACE 图零语义损失迁移。
2. 当前系统与路径：保留现有 Architecture renderer，增加路径聚焦和关系合同 inspector。
3. 机制 renderer：先覆盖 sequence、algorithm、formula／numerical 和 artifact loop 四种。
4. repository bridge：接入现有 manifest，加入陈旧检测和确认工作流。
5. 演进与 semantic diff：扩展现有 `semanticDiff.ts`，实现局部历史和 meaningful revision。
6. Freeze 与 drift：结构检查、专业判断回执、双向漂移和 Codex handoff 导出。
7. 四个 reference projects 与完整视觉、响应式和真实入口验收。

## 9. 发布完成条件

- 四个参考项目均由同一规范模型加载；
- 四类 renderer 不需要项目专属分叉数据模型；
- P0/P1 和明显 P2 为零；
- 320、390、768、1366、1440、1920 宽度无不可接受溢出或遮挡；
- light/dark 的系统、机制、演进、实现、证据和差异均可读；
- 关键键盘路径、焦点、语义标签和减少动画可用；
- source binding 正负控制、提交漂移和断裂锚点测试通过；
- Architecture Freeze 输出中没有需要 Codex 决定的关键产品、科学或权限语义；
- README、ROADMAP、VERSIONING 和迁移说明与真实产品一致。
