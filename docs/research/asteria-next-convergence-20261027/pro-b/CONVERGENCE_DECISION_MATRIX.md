# 四版裁决矩阵

本矩阵按能力裁决，而不是按整版胜负选一个赢家。当前收敛分支没有读取本轮另一位 Pro 的成果。

| 能力 | R2 GPT-6 保留点 | R2 GPT-5.6 保留点 | 上轮 GPT-6 保留点 | 上轮 GPT-5.6 保留点 | 最终采用 | 其余不采用原因 |
|---|---|---|---|---|---|---|
| 系统整体可读性 | 完整拓扑与主要路径最强；保留首页可见全貌。 | 层级更克制，状态更易扫读。 | 工作集结构完整，但原型的系统第一眼较弱。 | System 层较成熟，但卡片密度偏高。 | 首页只显示当前拓扑、路径入口和最少状态；详细语义下沉。 | 不采用无首页拓扑的工作集，也不采用状态卡铺满全页。 |
| 节点上下游探索 | 选择节点后能看到邻接与路径；保留。 | 选中态与聚焦层级较清楚。 | 稳定组件身份与局部历史可追踪。 | 对象模型和 inspector 信息完整。 | 同一规范图提供上游、下游、路径与局部历史；选择只在一个主要位置表达。 | 不使用另建 ledger 维护邻接，也不重复显示同一选中状态。 |
| 关系／载荷／消费者 | 最明确提出连接实际传递什么；核心保留。 | 关系状态可读，但载荷细节较弱。 | 强调 source anchor 与实现责任。 | Relation 对象完整，但容易字段化。 | 扩展现有 TypedRelation：payload、consumer、failureMeaning、recoveryMeaning；UI 只在选择时展开。 | 不把边当装饰线，也不把全部关系字段常驻画布。 |
| 正常路径 | 同一拓扑切换正常交付最自然。 | 路径信息密度较好。 | 可用工作集保存路径，但阅读不如拓扑直接。 | 可表达流程，视觉容易落成状态机卡片。 | 路径是 ArchitectureProjection 的阅读焦点，不复制节点。 | 不为每条路径生成独立页面或独立图数据。 |
| 失败路径 | 失败返修与正常路径共用拓扑，保留。 | 失败状态表达清晰。 | 原因和影响可进入 revision。 | Issue 与 blocker 模型较完整。 | 失败路径突出触发、实际载荷、消费者和恢复入口。 | 不把‘失败’只做成红色，也不让验证器越权修产品。 |
| 恢复路径 | 恢复与失败路径切换是 R2 GPT-6 的关键优势。 | 手机顺序阅读更适合恢复链。 | 局部历史和漂移有助于解释恢复。 | 可用机制 renderer 说明状态机。 | 桌面同图聚焦，手机按步骤阅读；恢复前提与取消条件属于机制。 | 不单独维护恢复图，不把恢复写成无条件成功。 |
| 旧功能保护 | R2 GPT-6 明确展示旧能力保护。 | 状态和内容层级有助于减少 reassurance。 | unchanged guarantees 与局部历史最有价值。 | Freeze 中可保存保护项。 | 每个 meaningful revision 保存 unchangedGuarantees；验证只展示实际覆盖。 | 不使用一句‘旧功能未受影响’替代回归证据。 |
| 组件机制下钻 | 具备交互入口但机制表达深度有限。 | 内容分层较好。 | 机制与源码、历史的绑定研究扎实。 | System → Mechanism 下钻与 renderer 最强。 | Mechanism 是实体子型；用步骤、序列、公式或状态图投影，不统一成卡片。 | 不建立独立机制数据库，不强迫所有机制填同一字段。 |
| 源码／Skill／科研实现下钻 | 早期版本较弱。 | 数据与样式分离有利于实现。 | source anchor、planned code trace 和 repo workset 最强。 | Implementation 轴明确。 | 复用 repository bridge；固定提交、路径、qualified name、role、来源、置信度、测试和陈旧状态。 | 不把文件树当架构，不让自动推断冒充确认绑定。 |
| source anchor | 未形成完整模型。 | 未形成完整模型。 | 稳定锚点与断裂处理是主要贡献。 | Anchor 被提为对象。 | Anchor 不新增为顶层规范实体；作为 RepositoryBridgeBinding 的结构锚点和值对象。 | 拒绝第二套 Anchor 表和无法随提交校验的行号链接。 |
| design／implementation／evidence | 路径上已有雏形。 | 状态表达较好。 | 三者分离与双向漂移较强。 | 三轴表达最系统。 | 三轴是同一实体的可独立状态与投影，不复制对象；证据不能自动提升实现或设计状态。 | 不采用三份同义对象，也不以一个总状态压平三轴。 |
| revision | 早期仅有路径变化。 | 状态变化可读但语义修订不足。 | meaningful revision 与局部历史最强。 | Revision／Change 作为 ledger 对象较完整。 | 新增 ArchitectureRevision；仅系统语义改变时创建。 | 不把每个 Git commit 或每次保存变成架构修订。 |
| semantic diff | 交互上可比较路径，模型不足。 | 差异层级较克制。 | meaningful diff 与 source change 研究最强。 | before／after renderer 较完整。 | 复用现有 semanticDiff，扩展到组件、关系合同、机制、绑定和证据状态；显示 before／after、原因、影响和不变保证。 | 不显示巨型 JSON diff，也不把文本变动都算语义变化。 |
| 为什么改变 | 未成为一等语义。 | 文字表达较好。 | change causality 最强。 | Decision／Evidence／Issue 链较完整。 | revision 必须绑定 trigger、reason、evidence、downstreamImpact、unchangedGuarantees。 | 不靠提交消息猜原因，不用‘优化’等空泛说明。 |
| 被撤销路线 | 路径可切换但缺少 superseded 语义。 | 状态可读。 | 可用局部历史表达。 | Issue／Decision 模型支持。 | 用实体状态与 revision change 表达 superseded／corrected／rolled_back；保留触发反例。 | 不删除错误路线，也不让撤销路线与当前路线同权常驻首页。 |
| blocker | 失败路径可见。 | 开放／阻塞状态较清楚。 | 双向 drift 和工作集可定位阻塞。 | Issue／Blocker 最完整，但容易状态密集。 | blocker 是实体当前状态或 Issue 子型；必须有影响、退出条件和证据。 | 不把所有未完成项显示为 blocker，不用红色 badge 堆叠。 |
| drift | 未系统建模。 | 可表达状态但缺少双向规则。 | 设计领先代码与代码领先设计最强。 | 三轴可发现不一致。 | drift 是比较设计、绑定、代码指纹和证据后产生的派生 finding；双向且可解释。 | 不新增永久 Drift 实体，不把合法 design-only 当错误。 |
| Architecture Freeze | 路径与旧能力保护提供基础。 | 信息层级适合冻结摘要。 | 冻结前工作集研究较强。 | Freeze contract 最系统。 | Freeze 是对一个 ArchitectureRevision 的报告与状态；结构检查通过、开放项有边界、专业判断完成后才可冻结。 | 不把字段齐全或测试通过等同于冻结。 |
| mobile | 路径阅读思路明确。 | 四版中手机顺序与密度最值得保留。 | 原型手机成熟度较弱。 | mobile 状态较完整但仍接近桌面缩放。 | 手机只显示路径选择、顺序步骤、关系载荷和底部详情；不渲染缩小拓扑。 | 不做横向画布缩放，不在手机同时放全部入口。 |
| large graph | 完整图优势明显，但缺少长期布局策略。 | 层级与筛选有帮助。 | Git 工作集和 stable identity 支持增量。 | renderer 研究较深。 | ELK.js 布局 + semantic lanes + 路径／层／trace 聚焦；视图投影保存人工修正，不复制语义。 | 不依赖手工绝对坐标作为唯一真值，不默认显示全图。 |
| 中文内容 | 关系和路径术语直接。 | 文案相对克制。 | 研究内容扎实但工程术语偏多。 | 原型较美观但报告式说明偏多。 | 面向用户使用自然中文；机器字符串仅在源码、字段与路径处保留；图能表达的内容不重复。 | 不使用报告式自我定义、状态口号和模型化对偶句。 |
| 内容取舍 | 功能覆盖强，仍有重复说明。 | 内容层级和密度最好。 | 研究产物完整但 UI 取舍不足。 | 字段丰富，容易 schema 驱动 UI。 | 每个可见元素先做 KEEP／DELETE／MERGE／RELOCATE／REWRITE；默认只呈现当前任务需要的信息。 | 不因 schema 有字段就显示，不用卡片填空白。 |
| 视觉层级 | 交互清楚但完成度较早。 | 状态、密度和层级值得保留。 | 视觉相对薄弱。 | 上一轮最成熟，但 dashboard 味仍存在。 | 建立 Asteria 专属视觉语法：拓扑为主、表面克制、选中态唯一、状态不靠 badge 泛滥。 | 不沿用任何旧 prototype，不用无语义渐变和几何装饰。 |
| theme | 覆盖有限。 | 层级适合主题化。 | 未形成完整双主题。 | 已有较成熟色彩基础。 | light/dark 各自定义表面、网格、状态、代码、公式和 diff；两套均真实截图验收。 | 不做背景反色，不牺牲暗色关系线或浅色次要文字。 |
| accessibility | 节点／关系选择是良好基础。 | 手机与密度处理有优势。 | 研究不足。 | 部分控制完整。 | 键盘可达、语义按钮、焦点、跳转链接、减少动画、强制色模式和 320px 以上无横溢出。 | 不依赖 hover 或颜色表达唯一信息。 |
| maintainability | 数据／交互／样式分离不足。 | 这方面最值得保留。 | Git 原生工作集与明确边界强。 | 对象丰富但容易扩大维护面。 | 规范模型、投影、renderer、索引器和 UI 分层；四项目共用模型与组件。 | 不建后端、数据库、账号、云服务、向量库或 agent runtime。 |
| source of truth | 拓扑可读但未定义唯一语义源。 | 数据分离有基础。 | Git 原生 source of truth 最强。 | Ledger 方案容易成为第二真值。 | 现有 ArchitectureProjectV2 及 repository bridge manifest 是唯一真值；revision/evidence 作为受版本控制的扩展记录。 | 不让截图、视图坐标、索引缓存或 ledger 成为第二真值。 |
| 证据有效性 | 显示证据，但失效规则不完整。 | 状态表达有帮助。 | source change 与局部历史能触发失效。 | Evidence 轴完整。 | EvidenceRecord 绑定候选、范围、生产者、观察、有效提交和 invalidatedBy；改动只失效受影响证据。 | 不把旧通过结果自动附着到新产物。 |
| 四项目通用性 | DA 路径最强。 | 移动与内容密度通用。 | Mica／CAT-TRACE 的绑定与历史研究强。 | 四项目压力测试最系统。 | 共享实体、关系、修订、绑定、证据；DA/Mica/CAT-TRACE/Tutorial 使用不同 projection 和 renderer。 | 不追求四项目同卡片、同状态机或同首页。 |
| Chat 设计辅助 | 能暴露路径和关系空白。 | 能降低阅读负担。 | 设计—实现—历史链最强。 | Freeze 与 completeness checks 最明确。 | 设计合同按能力→对象→责任→关系载荷→机制→路径→实现→验证→开放项→冻结推进；机械检查只找可证空白。 | 不奖励字段数量，不让 Asteria 替代产品或科学判断。 |
| Codex 交接 | 拓扑与路径可作为实施输入。 | 数据分离利于实现。 | 工作集、锚点和 drift 对交接最有价值。 | Freeze contract 能限制临时决策。 | Codex 只消费冻结 revision、规范图、机制合同、实现责任、验收和开放项；关键语义不得留给实施者发明。 | 不交付多方案，不让 Codex 决定产品边界、科学方法或证据标准。 |

## 总裁决

最终结构以现有 Asteria 2.0 为宿主；交互骨架主要继承 R2 GPT-6，内容层级与手机阅读继承 R2 GPT-5.6，Git／源码／漂移语义继承上一轮 GPT-6，冻结、机制 renderer 和四项目压力测试继承上一轮 GPT-5.6。所有能力都映射回现有规范语义图，不建立平行 ledger。
