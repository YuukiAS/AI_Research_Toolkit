## 1. 真正要交付的东西

你要设计一个用户愿意浏览、专业、克制、视觉成熟、可交互的**复杂系统解释网站产品模板**；以 **Delivery Assurance** 做一份具备真实具体内容的完整样例，并展示它与整个 AI 可靠工作体系的真实关系。

网站必须让一个没有参加之前长篇讨论的用户在适当阅读深度下判断：

1. **系统是什么、为什么值得做**：解决哪些切实发生或高风险的失败，对用户的实际行为产生何种改善。
2. **用户怎样使用、会看见什么**：从正常任务开始，走过成功、故障/返修，以及不应发生退化的旧功能保护情境。
3. **必要部件是什么、分别为什么存在**：每项组件的责任、触发、权威输入、实际产出、消费者、失败处理；移除此组件会让哪个真实能力失效。删不掉的理由讲不明白时，考虑合并设计。
4. **部件如何交互**：特别说明 DA 与当前 Codex、workflow-core、Bridge Kit、领域专业验收器和必要独立审查者之间的**实际/拟议**交接；箭头不能替代消费者、状态和真实运行机制。
5. **凭什么相信这套系统**：真实历史故障、现存源码、已验证能力、研究设计、未实施假设与剩余风险各是什么；哪些验收才能把“理论有效”变成“真实可用”。
6. **为什么选这个架构、投入是否合理**：认真比较最强的现实可行简化路线，解释弃选理由、首个可否决试点和旧 DA 研究估算。
7. **如何复用模板**：相同信息组织和展示组件适用于 Mica、Lucerna、科研方法、AI Skills 等其他复杂系统，而不让所有系统都被硬塞入同一张结构图。

网站设计和实际可见文案**自身必须体现** Artifact Curation 的“内容有无必要”、Clear Writing 的易懂与保真、Reasoned Design 的依据和主动反证。不得因为这是内部设计研究就把角色分工、开发状态码、测试标签、冗余营销话、无关装饰、假想用户训诫和内部审查过程塞进作品。

最终网站**不是说明这份任务提示词怎么写出来的展示馆**。用户面对的是 Delivery Assurance 的能力、机制与证据，以及按需深入的技术内容。

## 3. 独立检索：不要预设展示框架或视觉风格

请**实际检索当前 GitHub 开源项目、官方原始文档及优秀专业技术系统展示案例**。至少研究三类不同解决方式，优选检验约 6–10 个有独立参考价值的项目（允许更少但需说明筛选不足）：

- 专业文档站与内容框架（如 Astro/Starlight、VitePress、Docusaurus、Next.js/React 等只是候选；可以选择其他方案）。
- 复杂系统/数据流/交互式机制解释的组件及模式（系统边界、调用路径、状态切换、证据逐层展开、组件理由/缺失反证）。
- 视觉与交互呈现的成熟案例、设计体系和响应式布局，能处理严肃长内容而不是大堆卡片、长箭头流程图、过量动画。

对真正影响决策的候选核查一手来源：仓库 URL、实际产品/演示、维护与兼容情况、许可证和复用形式。说明看重哪个具体机制/设计做法、为何不采用其余方案；不能只列产品名和标语，也不得自动假定一个框架能包办内容判断和真实证据。

需要**收敛唯一推荐的技术栈、信息架构、视觉体系、交互形式和复用模式**。通用模板应优先使用可维护的静态/文档驱动方案，只有真实交互需求能证明必要时才增加复杂客户端逻辑。必须比较“维护一套小型专用网站”“单仓库 Markdown/静态生成模板”“现成文档框架”等切实可行路线。不要凭个人喜好直接写 Astro 或 React。

两位模型承担**相同完整任务**，没有分配审稿/复核专职，也没有提前指定一位做视觉、一位做技术。可从不同搜索线索开始，但必须跨出起始方向，独立综合。

## 4. 内容优先，视觉必须真的能看

先形成网站**目标读者画像和阅读承诺**：用户打开后在首屏就理解核心价值与实际状态，进入深层后可查关键机制、必要组件、真实证据和设计取舍。规定什么适合在首页出现、什么应该只在需要时揭示、什么没有必要展示。**不以预设页面数、标题数、卡片数来代替内容架构。**

必须形成一份**基于真实材料的 Delivery Assurance 完整样例**，不能只是写“这里放流程图”“这里显示组件列表”“待填内容”。至少有：

- 一段准确易懂的系统引入，明确用户实际损失与预期改变。
- 一个固定有来源的真实案例；一条可验证的正常成功链、一个设计阶段明确标示的失败阻断/同任务返修链、一个旧功能不应改变的情境。不要将假设性交互当作历史实测。
- 关键部件的真正作用：每一项都能回答“为什么非有它不可、由谁启动、交给谁、删除后哪项具体能力损失”。对新目标架构与旧 DA 研究的冲突给出处理。
- 实施/证据状态与代价：设计通过和生产已验证分开；首片、宿主探针及原计划估算如有引用必须保留其非实测身份。
- 用户从样例中应得到的**唯一下一步或可否决验证**，不向读者展示实施过程流水账。

**视觉交付必须可直接审阅**：成熟的字形、排版尺度、留白、层级、密度、间距、色彩和移动端信息顺序，不靠换个框架就说“专业美观”。在自己的 GitHub 研究分支内提交高保真桌面和移动端设计样例，包含真实可见中文文案和至少一个关键机制的展开态。建议用浏览器可打开的只读静态 `prototype/index.html` ＋同目录必要 CSS/JS/图形素材，**仅作为设计原型，不是正式网站实现，也不得连接生产或发布**。若使用 Figma，也要将足够审阅的视觉源/图片与说明提交到 GitHub，不能只给一个外部链接；可以选择其他更合适的设计媒介，但必须说明为什么更易审核且可落地。

原型中可以有**少量确实提升理解的交互**，例如对比“正常候选 / 低配候选 / 旧功能退化”如何受到验收约束，或选择某组件查看实际输入、消费者和移除后果。每个交互必须明确其带来的额外理解价值；不必要时完全可以不设计。禁止装饰性 hover 演出、胡乱动画、按个按钮只把同一段话翻出来、无关图片、格式化自夸文案和虚构实时进度。

**视觉自检不可省略**：若有浏览器/渲染工具，实际打开原型、检查桌面/手机与关键展开态，再附 GitHub 可访问的预览素材及真实观察。如果当前宿主确实不能渲染，诚实保留待验证项；不得凭代码存在就自称完整视觉验收通过。所有原型源码和必要视觉资产最终必须在自己分支的 GitHub 交付目录内。

## 5. 明确模板如何通用，又不会沦为万能流水线

需要交付一套**可扩展但足够薄**的模板设计，包括：
- 一份系统的关键事实以何种简单内容格式/仓库引用描述；哪些为共享展示字段，哪些属于具体项目才有的专业内容；不建立第二个真值数据库。
- 通用视觉容器与必要功能怎样按内容选择，而非所有系统自动生产等量模块和图形。
- DA 实例换成 Mica、Lucerna、研究方法或插件体系时，复用哪个能力，哪些内容必须重新研究而不能套模板。
- 新数据或原系统状态变化后怎样更新网站，如何避免陈旧截图、旧运行证据和“自动更新成功”的假象。
- 如何将原始技术材料、深层证据与简明读者正文分开；关键一手链接、提交版本可在需要时找得到。
- 本次网站如何实际遵守 **Reasoned Design（有依据地作取舍）/ Artifact Curation（有必要才展示）/ Clear Writing（自然且可信）/ workflow-core（真实需要时才组合能力）/ Delivery Assurance（按最终受检候选验收）** 的目标标准。以上是**设计及自检原则**，不伪称未实现插件已自动调用。
- 如何让未来 Codex 严格按用户批准的设计开发，不能私自加页面、功能、图片、装饰控件或弱化重要机制。

## 6. 质量标准：作品真正给用户带来什么？

在设计前冻结可反驳的问题，不要最后靠 PASS 字样自证：

**理解测试**
- 只看网站首页，能否知道 DA 解决哪类真实错误、预期用户变化及当前是否已经可用？
- 在不翻原始研究文档的情况下，能否找到一个真实任务的成功、失败、应保持不变三个路径？
- 选择一个必要组件，能否说明来源/输入、处理、输出/消费者，指出删掉会出现哪项具体故障？
- 是否能区分旧 DA 已审方案、更新中的整体分工、真实运行证据和待验证技术假设？
- 是否能从可视说明理解为什么当前推荐比最有竞争力的简化替代更合适；投入是否值得？

**内容/体验测试**
- 每一个可见标题、文字、图片、卡片、标签、按钮和交互都必须说明其不可替代的信息或操作价值。不能说明就删、合并或留白；**内部删除理由存于研究记录，不出现在用户页面**。
- 用来引导用户的关键例子、公式、事实、风险、成本及证据不可因追求极简而被误删。
- 不能无端出现批评读者、内部审查角色、项目编号堆积、组件自我介绍和重复的否定对照。
- 多种屏宽仍能自然阅读，视觉重要性与信息重要性相符；没有大片空洞占位、巨大无意义徽章或为了交互而交互。
- 原型实际实现应能正确渲染、导航、查看示例与证据；如果仅静态视觉稿，须明示无法验证的交互，不得伪装已测试。

**最低比较**
- 与原 DA 11/12 两张图＋长文说明相比，新设计至少要具体改善：读者找到核心价值、找到组件存在理由、跟随真实故障机制、区分设计与已运行状态、知道下一步应该验证什么。
- 再采用另一个完全不同的复杂系统做简短迁移演练，证明模板没有硬编码 DA 独有的六泳道或七仓术语。

- **`DA_STORY_AND_EVIDENCE.md`**：从已读真实材料提炼的**可直接面向用户呈现的完整样例文案**，含实际证据索引、全部关键责任/机制与状态边界；标出原型呈现层级。

- **`WRITE_ACCESS_CHECK.md`**：开始写入验证及远端回读事实。

可以自行选择合适的补充文件存储原始搜索资料与实现参考，但用户可见网站不得受其篇幅污染。检查路径链接和图像真实存在、源码文件是同一最终研究候选。每次最后提交后从**远端 GitHub**重新读取核心文件并核对引用/产物，报告分支和提交 SHA。禁止把 `file:///...`、本地构建目录、聊天生成附件或尚未提交的 Figma 当正式交付。

## 8. 必须尊重的边界

- 本任务研究**网站解释与可复用展示模板**，不是实施 Delivery Assurance，也不是重新正式批准 DA 的算法架构。
