## 3. 首屏必须有真正的系统架构图

**不可谈判的硬要求：** 首页主要阅读区域直接呈现**准确、清楚、专业的整体架构图**。不是三行流程、一个项目列表、若干职责卡片，也不是深藏在证据附件里的 PNG。网站的第一项核心功能就是让读者从图中把整个系统建立起来。

图中应能清楚辨认：
- 正常使用入口、当前 Codex 执行者及原任务；
- workflow-core 如何选择领域能力与交付检查；
- Bridge Kit 的身份、运行、反馈和合法恢复责任；
- Delivery Assurance 如何把已批准的要求/受影响旧功能交给验收并核对交付证据；
- 项目原有专业验收器及需要时的独立审查，真实结果的下游消费者；
- 成功交付与失败回原 Codex 的两条不同路径；
- Reasoned Design、Artifact Curation、Clear Writing 和领域技能在**更大体系中的按需位置**，通过清晰分组/相邻视图说明它们与 DA 的关系，不能为完整而谎画强制调用。

每条关键连接必须知道**谁调用、传的是什么、谁接收**；确实不了解、尚未开发的边应标为设计或待证，不许画成今天已工作。图形应按职责分组、层次可读、连线不会乱穿文字。设计可以包含不同层级的视图，但**不能为了看全局先让用户浏览冗长文字或点开其它页面**。

**最少的有效交互：**
- 选择组件：该组件及其真实上下游清楚高亮，旁边就地显示“为什么需要它、负责什么、输入/输出、谁真正消费、没有它会怎样、现在做到哪一步”。
- 切换“正常完成 / 错误交回原任务 / 旧功能被改坏”：仍以同一整体图为定位基准，相关连接按实际先后高亮，说明下一位接收者与证据变化。
- 选择关键连接时能看到交付的准确内容或状态；没有真实消费者的箭头必须标记缺口，不能靠“回路已形成”自证。
- 桌面必须能一眼掌握全貌；手机必须重新组织可读层次及联动，不准把宽图缩小成一片看不清的字，也不准用装饰性拖拽/乱动取代解释。

可以用 SVG + 合适的布局工具、成熟关系图组件或其他真实最优方案实现，但要调查并收敛一个选择。**既不能因为嫌流程图“AI 味”就不画真正必要的架构，也不能用漂亮的大图掩盖准确性不足。**

## 4. 自然中文是与架构图并列的否决项

目标：网站上每一句面向读者的话，都应像一名懂软件、能够清楚表达的**中文技术作者**写给真实项目负责人的话。语言可以精确，也可以有专业名词，但不能把内部技术状态、工程计划、报告模板和 AI 口号直接摆给读者。**不能靠“AI 检测器通过”宣称达到人类文风。**

先做**整页内容筛选**，后做**逐句编辑**：

1. 每个可见段落、标题、图内标签、按钮、状态文字、页脚、对照表和折叠详情都问：读者为何需要知道它？重复、空洞或纯装饰就删除、合并或留白。常规状态用普通话说清，不包装成口号/英雄区/多个同义徽章。
2. 再读每一个留下的文字。消除故作深刻的对偶、机械“不是 X 而是 Y / 只有 X 才 Y / 先 X 再 Y”的大量重复、过度第二人称、数据库腔、顾问腔、无用英文、神秘形容词、无因果的主张、迎合审查的自我说明与视觉口号。**这不是机械禁词**；语义确有必要的否定、专业术语、精确字段可以保留。
3. 检查整屏阅读节奏：段落长短是否自然、标题是否确实引导用户理解、邻近元素是否反复说一件事、技术词首次出现是否说明了具体作用、空间是否留给图形而不是文字墙。
4. 执行**全页面文本盘点**：最终浏览器实际可见 DOM（含点击后、情境切换后、折叠打开后、手机显示）的每条独立文字，在内审 \`COPY_EDITORIAL_AUDIT.tsv\` 或 Markdown 表中保留原文、所在页面/状态、**保留/删除/合并/重写**决定与最终可见文案；真正需要专业事实的文字附来源定位。不允许全部填“合格”并结束。改完重新浏览整个页面并与该清单对照，确保 HTML、JS 动态文字和图内标记没有遗漏。
5. **纯文本复检**：把可见中文从设计中抽出来，连续读一遍；去掉 CSS 后如果仍像 GPT 的总结汇报，就继续编辑。如果只是每句单看正确、整体全是平行小标题与名词列表，仍判不合格。
6. 源码、issue 编号、验收协议和来源保留在需要时可追踪的技术层；给用户看的第一屏只说真正必要的事实。不能为了“严谨”把开发状态、角色/工具调用日志、流程 gate 和自我合规声明排满屏幕。

**强制语言对照**：对照 R1 原型和 CUHK Date 的实际坏文案，至少定位旧网站中 8 个具体模型腔短句/可见元素，说明新网站分别是“删掉、合并、改写、移入证据层”的哪一种；处理后的结果必须在**真实网页**中体现。不能提交一份漂亮的审稿表却让 \`prototype/index.html\` 原封不动。

这六项是制作端自己的编辑责任；用户不应被要求代替你一页页挑句子。

## 5. 必须让人理解“为什么这套东西有用而且可信”

围绕一个有原始来源的 Lucerna 状态问题，先解释它造成什么麻烦，再看图上 DA 预计在什么环节识别。至少覆盖：
- 一次正常任务与应成功的候选；
- 故意错误实现（例如掩盖真正故障）：哪个**实际已有或拟议的**验收器识别哪项错误，反馈怎样回到谁；
- 新功能看起来正确、原来正常的入口却退化：哪种旧功能保护会阻止交付；
- 断线、权限、无人接收或证据缺失时诚实怎么办；
- 为什么至少需要该组合，怎样比较“只加强各项目原有测试”等强竞争替代；
- 当前做到了哪一步，以及**最先值得做的真实否决试验**和大致成本身份。

图与机制说明都要准确表达**当前已经有的程序、已经通过审查的设计、下一步拟新增的能力、尚未实测**。读者不应因为漂亮交互误以为 DA 已经在工作。页面如需要一句状态，就用普通中文说明；不要连续重复免责声明。

## 6. 视觉与技术独立研究，最后收敛唯一方案

实际检索当前开源/官方来源中的专业系统关系可视化、信息密集产品/开发者工具设计、SVG/节点边交互、移动端关系图阅读及静态网站框架。挑选有实质借鉴价值的参考，核实维护、许可、功能适配和采用/不采用理由；**不要默认复用 Eleventy 或 Astro，也不用为了展示研究量列十几个无关仓库**。

最终给出一个技术与视觉组合，考虑：
- 清楚、准确、可访问的整体架构图及节点/边交互；
- 有独特性但克制的字体、色彩、疏密、版式和手机布局；尽量少用无意义图标/插图/渐变/卡片；
- 内容与真实 GitHub 来源绑定，不建立第二套产品真值；更新时能指出证据是否过期；
- 模板未来迁移到 Mica、科研方法或其他复杂系统时更换结构数据、必要示例和文本，不强制保留 DA 专有节点及三种失败情境。

先确定**信息和主图**，再选择工具和视觉风格。用户指定的必须可见能力优先于你自己的审美偏好。任何新页面/动画/控件都要能指向一项具体的理解需求；否则省略。
