# 复杂系统展示网站：编辑与内容取舍审查

日期：2026-10-27

对象：GPT‑6 与 GPT‑5.6 两个 R2 候选的独立修订副本

详细逐项记录：[VISIBLE_CONTENT_AUDIT.tsv](VISIBLE_CONTENT_AUDIT.tsv)（720 项）
回归样本：[REGRESSION_CASES.tsv](REGRESSION_CASES.tsv)（26 项）

## 结论

两个网站的技术事实大体可靠，真正拉低成品感的不是某几句“AI 腔”，而是同一种生成倾向渗进了内容架构：每个对象都要有完整字段，每个判断都要再解释一次，每个页面区域都要被填满。结果是单句通常没有硬伤，整页却像一份努力证明自己完整的模型报告。

修订没有重做系统架构，也没有删除责任边界、版本归属、失败回传和旧功能保护。主要动作是删掉没有信息增量的元说明，合并固定字段，下沉方案比较与工时估算，缩短动态步骤，并为手机重新安排阅读入口。默认状态下，GPT‑6 的连续可见文字从 1,258 个非空白字符降到 894（约 −29%），GPT‑5.6 从 1,807 降到 940（约 −48%）。字数变化只是结果；验收重点是三条路径、关键组件、版本边界和失败去向仍然可读。

## 两个网站共同暴露出的五类问题

### 1. 把字段完整当成内容完整

GPT‑6 强制每个组件回答“为什么需要、接收什么、交给谁、去掉以后、目前情况”；GPT‑5.6 又扩成“为什么存在、需要什么、交出什么、谁接收、少了会怎样、当前状态”。这些问题对 Delivery Assurance 有用，却不适用于“用户”“当前成品”“领域技能”等所有对象。

修订后，每个组件先有一句职责摘要；只有确有信息增量时，才保留边界、当前缺口或使用条件。组件可以只有一句话，也可以没有额外字段。

### 2. 图已经表达关系，文字又把关系完整复述

节点、箭头、状态徽标、图例、详情面板和后文反复说明同一件事。尤其是连线详情中的“何时发生”“怎样算接通”，多数只是把箭头动作换一种说法。

修订把连线详情收敛为“传递”“接收与用途”，只有待接线关系再补一条“当前”。

### 3. 内部过程和研究状态占据产品主层

“当前职责调整”“旧方案工作量”“三种架构路线比较”“本原型构造的情境”等内容对研究存档有价值，却不是用户理解系统的第一层。它们被平铺在首页后，网站更像研究交付物或咨询演示，而不是技术产品。

修订保留来源和边界，但把未采用路线、旧估算等下沉到折叠区；对已经由控件和内容说明的“这是推演”类元说明直接删除。

### 4. 状态在多个位置重复出现

“设计已审、尚未接入生产”同时出现在页眉、首屏边注、节点徽标、详情字段、证据区和页脚。每个位置单看都合理，合在一起却形成持续 reassurance。

修订为状态指定一个主位置，其他位置只补充新的边界，例如“普通入口和七仓接线尚未实测”。

### 5. 桌面信息架构被直接搬到手机

GPT‑6 原版在手机上继续呈现 1,710px 高的完整关系图。它并非技术上“坏掉”，但用户要滚动很久才能进入当前路径。GPT‑5.6 原版已有路径列表，这是两套候选中值得保留的做法。

修订后的两个手机版都以当前路径为入口，再提供组件详情；完整关系图仍保留在桌面。响应式在这里是阅读顺序变化，不是缩放。

## 哪些内容根本不该存在

- 对所有组件一律出现的“去掉以后 / 少了会怎样”。真实风险应写成具体事实，不应由模板逼出假设。
- “以下是按方案推演的三种结果”等控件已经表达过的元说明。
- 案例卡片上“历史事实 / 验收反例 / 旧功能保护”这类与标题重复的类别标签。
- 每条连线固定出现的“何时发生”和“怎样算接通”。
- 只是为了证明页面完整而填入的状态、来源或总结槽位。

这些问题属于 Artifact Curation。把句子润色得更自然，仍然会留下错误的信息架构。

## 哪些内容应该保留，但原来不会说

- 版本归属、证据失效、失败回原任务、旧功能保护等关键机制。
- Delivery Assurance、Bridge Kit、workflow-core 等真实组件名。
- “设计已审但尚未接入生产”的实施边界。
- Lucerna 中“未观测保持中性，确认故障仍提示”的事实。

原稿常把这些事实包进报告式标题、对偶句、长串并列项或内部工程过程。修订只改阅读顺序和表达，不改变证据强度。这一层属于 Clear Writing，并受 Writing Fidelity 约束。

## 局部问题与整页问题

局部问题可以在单句上指出，例如“下一位接收者”比“去向”更像内部流程语言，“为什么存在 / 少了会怎样”形成机械对偶，动态步骤一句话塞入四个执行者。

整页问题必须看实际渲染才能发现：标题数量过多、所有区块同等强调、状态重复、空白被解释填满、图和详情互相复述、手机仍沿用桌面结构。两个候选都做过逐句自审，仍同时出现这些问题，说明句子级自然度不能替代整页内容取舍。

## 应进入通用能力的规则

### Clear Writing

- 在内容已经确定后，检查报告式自我定义、机械对偶、过长并列、内部工程角色泄漏和状态口号化。
- 对整页可见文字做一次连续阅读；如果去掉 CSS 后仍像工作总结，应继续消重和改节奏。
- 同一个事实在标题、摘要、详情和状态中重复时，指定一个主表达，其余位置只补充新信息。
- UI 文案必须以控件任务和用户可感知结果为中心，不用内部执行顺序代替结果。

### Artifact Curation

- 对每个可见元素先做 KEEP / DELETE / MERGE / RELOCATE / REWRITE，再进入文案润色。
- 不能因为模板有槽位就强制填满；允许一句摘要、零个详情字段和有意留白。
- 图形已经表达的方向、顺序和分组，不再用文字逐项复述。
- 研究过程、未采用方案、旧估算和来源说明默认下沉，除非它们直接改变当前决策。
- 响应式审查要重新判断手机端的首要任务，不把桌面结构等比缩小。

## 不能机械泛化的部分

- 不能把“为什么存在”“当前状态”列入禁词表。对核心组件或高风险状态，它们仍可能是必要字段。
- 不能设定统一字数、字段数或折叠区数量。三项只是本次结果，不是新的模板。
- 不能因为图已经存在就删除所有文字；屏幕阅读器、复杂边界和证据归属仍需要文本。
- 不能把“更像人”理解为更随意。版本、权限、责任、失败条件和来源必须保真。
- 不能把 GPT‑5.6 的手机路径列表复制成所有网站的固定组件；应先判断手机上的主要任务。

## 怎样减少以后逐页人工审查

建议把检查拆成四道可重复的门，而不是新增一份禁词表：

1. **可见内容清单**：从真实渲染中提取默认、交互、折叠和响应式状态，不能只扫源码字符串。
2. **存在性判定**：要求每项先给 KEEP / DELETE / MERGE / RELOCATE / REWRITE；禁止默认 KEEP。
3. **页面级探针**：统计同义状态重复、字段模板覆盖率、标题密度、图文重复和移动端阅读深度，并把结果交给人或模型复核，而不是自动删文。
4. **回归 replay**：用本轮 26 个案例验证 Clear Writing 是否只改表达、Artifact Curation 是否先做取舍，以及两者是否共同保护事实边界。

自动化可以发现高概率候选，例如“所有节点字段完全相同”“同一状态出现五次”“手机仍显示超长 SVG”；最终 disposition 仍需结合真实任务、风险和读者判断。

## 对现有插件的现实检验

当前 Clear Writing 已能识别自然中文、内部过程泄漏、过度解释、页面级重复和 UI 文案节奏，也明确不替前端决定文字是否应该出现。Frontend Design 已能处理内容层级、响应式阅读顺序、留白和真实渲染验收。两者结合后，首屏标题、动态步骤、手机结构和详情密度都能明显改善。

当前缺口是：没有一个正式能力先枚举所有动态可见内容并强制做 disposition；没有统一的页面级重复与模板覆盖回归；原候选自己的验收合同还把“所有节点字段完整”当成正向指标。因此，本轮证据应补入现有 Clear Writing / Frontend Design TODO，并作为 Artifact Curation 设计样本，不应直接改 production skill 或另造同义规则。
