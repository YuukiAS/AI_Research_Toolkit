Lucerna：未观测不等于故障

两条访问路线可用、另一条仍在检查时，旧逻辑曾把整体状态显示为故障。原因是尚未观测的辅助状态被当成了已确认故障。

修复必须同时守住两条线：未观测保持中性，确认故障仍然提示。历史回归已经通过，但当时没有重建并独立验收新的 Windows 成品。

观察到的情况应有表现
两条路线可用；Tailscale 检查中；辅助状态未观测整体保持可用，未查明的部分单独说明。
已确认次级服务故障提示需要处理；不把故障隐藏为正常。
本次状态修复正确，但原来可用的入口打不开仍需返修，并重新验证受影响的旧入口。

Lucerna 历史修复记录状态处理源码已有状态回归

证据边界

源码解释判断为何改变；运行记录说明当次成品怎样表现。新的 DA 接线仍需从正常任务入口实测。

已有事实

历史修复已把未观测状态排除在确认故障之外，并通过定向回归。它不能证明后来修改过的 Windows 成品已经验收。

检查程序也可能判断错

新补的检查要先能区分正确实现、故意错误、旧功能回归和证据缺失。专业标准由项目确定；涉及新的重要标准或观察方法时，需要独立核对。不能同时放松产品要求和测试答案来获得通过。

原研究：检查与返修实施路线图

先做一条真实链路

用同一个 Lucerna 任务跑四类对照：正确版本、确认故障、旧功能回归和缺少证据。后三类都应拒绝交付，并把失败送回原 Codex；修复后重新验收当前版本。

如果共享层不能减少漏检、催验收或人工搬运报告，就撤去它，只保留项目内有效的回归检查。

旧方案估算：宿主探针 4–8 小时，首个完整试点 40–88 小时，七仓全量 138–332 小时。三个范围逐级包含，不能相加。

这是实施前估算，不是已花工时或当前预算；也不含外部审查、设备、账号和新的科学训练。
