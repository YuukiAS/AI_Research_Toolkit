历史事实

两条路线可用，第三条仍在检查

当 Bridge host 或 VS Code 只有“未观测”证据时，旧逻辑曾把整体状态升级为故障。修复后，只有确认的次级故障才会要求注意。

定向回归已经通过；该回合没有重建 Windows 正式候选，也没有完成新的独立界面验收。

验收反例

不能把确认故障也改成正常

为了消除误报而压低所有告警，会漏掉真实故障。验收程序应同时检查“未观测保持中性”和“确认故障仍然提示”。

这是用于检验架构的故意错误候选，不是 Lucerna 已发生的新故障。

旧功能保护

修好检查态，不能弄坏原有可用路线

如果新状态映射让 Main 或 Backup 从可用变成不可用，即使新增用例通过，也不能交付。旧功能必须进入同一批交付义务。

这也是检验用反例，用来确认回归保护是否实际运行。

方案比较

为什么选择窄交付层

推荐方案复用各项目现有验收程序，不新建中央调度器、数据库或通用评分器。

路线 能解决什么 主要问题 结论
只加固各项目测试 专业标准留在项目内，中央依赖最少。 每个项目重复处理原要求、证据失效和失败回传；普通任务仍可能绕过正式入口。 作为公共层无收益时的退路。
窄交付层 + 现有验收 共享交付义务、候选身份、证据资格和失败递送；专业判断仍由项目负责。 需要一组小接口，并逐个证明正常入口确实消费结果。 推荐。
另建编排平台 运行、重试和长任务管理更完整。 增加账户、持久状态和多主风险，仍不能提供项目要求和专业标准的真值。 不采用。

证据与投入

先用一条真实任务判断这套架构值不值得继续

最早的否决试验

  1. 确认当前 Windows 与命令行入口能绑定原任务、接回失败并停止重复启动。
  2. 在同一 Lucerna 候选中运行正常、确认故障、旧功能退化和缺证据四类对照。
  3. 观察失败是否回到原 Codex，修复后是否重新验收当前候选。

若失败报告仍需用户搬运，或旧功能没有进入检查范围，就撤回公共层，继续使用项目内加固方案。
