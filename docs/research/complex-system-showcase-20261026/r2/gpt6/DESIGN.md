# Delivery Assurance：架构与网站设计

采用原生 HTML/CSS/JavaScript 与 SVG。首页直接展示完整关系，读者在同一张图上选择组件、查看通信内容、追踪正常交付与返修。桌面和手机共用语义模型，分别排版；不接入 Delivery Assurance，也不模拟真实执行成功。

技术比较和原始资料见 [RESEARCH.md](RESEARCH.md)。可见文本、取舍理由及实际出现位置见 [COPY_EDITORIAL_AUDIT.tsv](COPY_EDITORIAL_AUDIT.tsv)。

## 从整体到具体

页面顺序只有四部分：系统架构、Lucerna 状态误报、依据与未验证环节、下一步试验与替代方案。顶部用一句话说明作用、一条状态说明限制。没有营销英雄区、指标卡、英文栏目副标题、装饰插图或单独的“组件合同”页面。

架构在桌面首屏中完整显示。上层是用户、当前执行者、当前成品和项目专业验收；中间是批准的要求、能力安排、DA 与独立审查；底层是 Bridge 和受管交付入口。左下方的四种专业能力按需使用，不连成强制流水线。外侧的返修线回到原 Codex，成功线把相应成品交回用户。分组表示责任关系，不表示新增常驻服务、后台进程或网络部署。

与 R1 的根本差别是阅读对象由“几个阶段的摘要”改为完整系统关系。阶段只负责在同一关系图上指出这一步经过哪些组件、传递什么证据。没有用三条流程替代架构。

手机重新排成纵向结构，节点保持可读字号；并列保留批准要求与独立审查，长距离关系走外侧。情境按钮和当前步骤文字放在图前，方便先知道看哪里。点选就地打开底部详情，关闭后回到刚才的组件或连接。它需要纵向滚动，这是保留完整拓扑与文字可读性的明确代价；不增加缩放、拖拽、小地图或自动播放。

## 架构判断

本图采用 2026-10-26 总体架构中的拟议分工。DA 决定本次应验范围，并根据项目结果判断可以声明哪些完成范围。workflow-core 选择和安排专业能力、明确结果接收者。Bridge 提供身份、运行、权限、反馈与合法恢复。业务是否正确仍由项目自己的标准和验收器判断，必要的独立观察按风险加入。

“批准的要求”和“当前成品”是有版本和来源的资料对象；“受管交付入口”是已有项目交付入口拟增加的末端核验责任。两者都不是本轮新建的产品。图中箭头包括数据依赖和执行安排，不声称每条都是直接 API 调用。尤其项目结果由原 Codex 取得再交 DA；技能由原 Codex 实际读取使用。点击连线会明确中间消费者，不能把箭头当成已经工作的网络连接。

已有项目操作用实线，拟议连接用虚线。颜色只表示当前选择或当前步骤，红色同时配有具体错误文字。节点的现状另有明确说明：已有程序、已有合同、通过研究审查的设计和未实现接线不能合成一个“已完成”标识。全部 14 个节点与 16 条连接的可追溯定义见 [ARCHITECTURE_MODEL.md](ARCHITECTURE_MODEL.md)。

## 交互为何存在

| 操作 | 读者得到的解释 | 行为细节 |
| --- | --- | --- |
| 选择组件 | 为什么需要、输入、实际消费者、删除损失、目前情况 | 全部真实相邻连接和上下游一起高亮；桌面右侧详情，手机底部详情；退出情境高亮，恢复组件观察 |
| 选择连接 | 传什么、谁接收、怎样继续、接通与否 | 直接选择有文字标识的线；方向箭头保留；键盘 Enter/Space 可操作 |
| 切换三种结果 | 同一个任务在不同结果下经过的路径 | 正常 5 步、故意错误 7 步、旧功能回归 7 步；主动前后翻，不自动演示 |
| 全部关系 | 恢复全貌 | 清除情境和选中高亮，不隐藏任何节点 |
| 展开依据 | 某项可信程度的具体限制 | 原生 details；来源外链直达 GitHub，不堆源码编号在首屏 |

没有保存账户、真实任务状态、网络请求、自动修复按钮、模型聊天、后台任务或遥测。原型的交互只改变解释视图。

## 视觉规范

采用清晰的技术图纸风格：浅灰页面、白色主图、深蓝文字，蓝色用于当前关系，砖红色用于错误。页面背景 `#f5f7fa`，正文 `#172a3b`，次要文字 `#526579`，强调 `#245bb7`，错误 `#a33d2f`，分隔线 `#d8e0e9`。主图与详情之间靠细线分区；正文不用卡片包裹。

字体使用系统 Segoe UI / Microsoft YaHei / PingFang SC，无外部字体下载。正文 16px，手机 15px；主标题 30/29px；图节点标题 16px，手机保持约 16px 的 SVG 设计尺寸，关系标签 12px。窄屏通过重排而非缩放桌面图。间距以 4px 为基础，正文行距约 1.9，内容区最大 1080px；主图可用 1480px 页面宽度。边框圆角以 6–8px 为限，不用大面积药丸、投影或发光效果。

组件与边的焦点状态有清楚描边。手机底部详情支持 Escape、明确关闭按钮、焦点限制和关闭后焦点恢复。无 JavaScript 时保留完整图、正文及依据，说明交互不可用。屏幕阅读器有对象名称和按钮角色，但本轮没有实机屏幕阅读器测试，不能宣称完整 WCAG 认证。

## 模板如何迁移

`content.cjs` 保存全部语义与编辑决定；`layout.cjs` 只保存两种坐标；`app.js` 根据节点、边、情境数组工作；`build.cjs` 将模型、样式和交互装入单个离线 HTML。`model.json` 是便于检查的构建产物，不作为第二份手改真值。

换成 Mica、Lucerna 或科研方法时，需要重新回答“对象是什么、关系传什么、哪种观察能否决结果”，而不是换掉 DA 标题。可把节点换成采样器、数据版本、分析程序与质量检查；情境可以是数据污染、重复测量或设备离线，不要求沿用三种 DA 情境。节点字段、证据状态、连接载荷和场景顺序沿用同一内容合同，见 [TEMPLATE.md](TEMPLATE.md)。

这是一套有明确内容合同与样式的展示模板，不是任意图自动排版引擎。当前构建器保留 DA 页的案例段落装配，迁移时需要替换该内容段与两种图坐标；交互控制器不按 DA 节点名称分支。超过约 20 个主要节点或需要用户自由构图时，应重新评估 React Flow/ELK 等方案，不能继续堆手写折线。

## 更新与事实保真

事实源在原仓库。网站保存链接、核对日期和本次读取身份，不能建立第二套“DA 已完成”状态。更新任一事实后，定位受影响节点、边、情境、正文与来源，再重建、逐句复看、重拍实际截图。当前总体架构使用分支链接便于读者查看后续变化，核对时的 blob 身份固定在 RESEARCH；链接变动不自动更新原型主张。

最先值得做的真实试验是一个 Lucerna 正常入口：正确版本能交付、掩盖真故障的版本被拒绝、旧入口坏掉被拒绝、缺证也不能交付；失败必须返回原 Codex 并被实际处理。这只是下一阶段建议，本轮没有执行。若只加固原项目测试就能达到相同效果，共享 DA 又未减少漏检和人工催办，应保留测试并撤去新增层。旧 4–8h / 40–88h / 138–332h 估算逐级包含，既非实耗，也非新分工预算。

正式开发的约束见 [ACCEPTANCE.md](ACCEPTANCE.md)。本轮到可审阅设计和原型为止。
