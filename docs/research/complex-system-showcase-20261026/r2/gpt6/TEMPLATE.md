# 模板内容合同

这套模板用于解释一个有真实关系、真实限制和可核对结果的系统。迁移时先重新取舍内容，再改模型；不复制 DA 的业务名词或成功结论。

| 数据 | 必需字段 | 审查问题 |
| --- | --- | --- |
| 节点 | id、名称、职责、存在理由、输入、输出及消费者、删除损失、目前情况、来源 | 删掉后到底损失什么？是否只是为了凑图？ |
| 连接 | id、from、to、方向、载荷、实际消费者、状态、来源 | 谁发送、谁接收？有没有尚未实现的中间步骤？ |
| 情境 | id、名称、steps[] | 是否说明一个值得理解的结果？不规定情境数量 |
| 步骤 | 标题、解释、nodeIds、edgeIds、普通/错误语义 | 必须引用全图真实节点和边，不能另画一个不同拓扑 |
| 来源 | 链接、读取身份、核对日期、支持的主张及限制 | 源码、设计批准、一次测试与生产能力是否混淆？ |
| 版式 | desktop/mobile 节点矩形、连线路径、标签位置 | 同一语义，在每个屏幕都能读和操作吗？ |

`prototype/model.json` 给出完整实物。对象角色包括执行者、组件、成品/基线和按需能力；不要强制新项目也有四种按需技能。双向关系必须在载荷说明中分别给出两个方向。多段间接消费可以画成明确的逻辑依赖，但详情必须说明中间接收者，不能伪称直接接口。

例如，一个测量分析网站可以只有“测量设备 → 原始记录 → 分析程序 → 结果复核”四个主要节点，另有“已批准的方法”提供标准。正常测量和仪器漂移是两个情境；若没有自动重测能力，就不画自动返回设备的箭头。研究方法的有效性由真实校准或对照证明，不能借用本例的代码测试记录。这是结构迁移示例，不是已调查或已实现的科研系统。

迁移步骤：

1. 从原项目事实源取得标准和真实案例，写出读者首先需要回答的三个问题。
2. 删除没有独立责任的节点，确定关系载荷和消费者；设计或未知边必须写清。
3. 替换 `content.cjs` 的语义、页面案例与来源，再人工编排 `layout.cjs`。案例段落的 HTML 装配也需调整，不能声称当前脚手架可无修改生成任意网站。
4. 保持通用的选择、高亮、步骤控制和详情行为；删除没有解释价值的情境，不保留空按钮。
5. 作者逐句记录取舍，运行浏览器检查，再通读脱离样式的可见文本。若图太复杂，先按用户问题分层，而不是缩小字号。
6. 建立同版代码、截图和原始证据身份后才交付。

无需 CMS、用户账户或网站后台。需要多页面协作编辑、复杂路由或大量依赖时才重新选择构建框架，依据任务变化作新决定。
