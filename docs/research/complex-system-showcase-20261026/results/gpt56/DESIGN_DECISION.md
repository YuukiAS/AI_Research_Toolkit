# 复杂系统展示模板：唯一设计决定

## 核心决定

采用“证据驱动的系统叙事站”，而不是架构图查看器、文档目录或仪表盘。读者首先看到系统解决的真实损失和当前完成边界，随后沿一项真实任务理解正常路径、失败返回和旧功能保护；组件关系与证据层级作为可追查的第二层。最终工程采用自定义 Astro 静态内容站，原型使用无依赖 HTML/CSS/JavaScript。

本轮停止在设计交付，不创建 Delivery Assurance 插件，不连接宿主，不部署网站，不把静态原型称为生产能力。

## 读者要在五分钟内形成的判断

1. 这个系统防止什么真实损失：局部测试绿色、设计文档完整或退出码为零，却没有覆盖原始承诺、真实成品和相邻旧功能。
2. 一项任务怎样被处理：冻结候选，收束义务，运行项目专业验收，取得独立证据，最后按证据强度决定允许声明什么。
3. 失败怎样回到真正能修复它的人：Delivery Assurance 产生具体缺口；workflow-core 找到消费者；Bridge Kit 递送到原任务；原 Codex 修复并产生新候选。
4. 各组件为什么不能互相吞并：判断、路由、运行、专业事实和独立观察分别拥有单一责任。
5. 目前可以相信到哪一步：设计已审、Lucerna 源码与回归存在；宿主接线、同任务回传、正式 Windows 候选复验和七仓启用尚未证明。

## 信息架构

### 第一层：一句价值与真实边界

首屏只回答三个问题：系统解决什么、当前完成到哪一步、下一项真正有价值的证据是什么。不得用“智能、统一、端到端、全链路”等抽象词替代具体损失。

### 第二层：同一任务的三种结果

同一 Lucerna 状态修复提供三个切换结果：

- 正常完成：同一候选覆盖新要求与相邻旧行为，才允许升级交付声明。
- 发现失败：具名缺口被送回原任务，修复后必须重建和重新复核。
- 旧功能保护：新状态规则通过但主要入口、详情或刷新回归，仍阻断交付。

每个结果都使用相同的五阶段骨架：入口登记、义务收束、项目验证、独立复核、交付结论。阶段详情固定显示输入、实际动作、输出与消费者、证伪条件。这样读者比较的是机制差异，不是三张互不相干的图。

### 第三层：组件合同

组件检查器每次只展开一个组件，固定回答：

- 为什么存在；
- 何时触发；
- 权威输入；
- 输出给谁；
- 失败如何处理；
- 删除以后失去什么；
- 明确不负责什么；
- 当前是已有、部分已有、已审设计还是未验证。

### 第四层：证据账本

证据账本不按文件列表组织，而按主张组织。每条主张同时写“支持什么”和“不支持什么”，避免读者把设计评审、源码、确定性回归和真实发布候选混为一层。

### 第五层：唯一架构决定与下一证明

页面最后明确职责收敛、最终技术路线、最强简单替代和停止条件。读者无需从几十页研究报告自行推断推荐方案。

## 对旧 DA 长文与 11/12 图的判断

旧材料有两项价值：它保存了真实问题、角色和失败回路；它也明确标注设计阶段边界。它不适合作为通用展示模板的主入口，原因如下：

1. `11_DELIVERY_ASSURANCE_ARCHITECTURE.svg` 把 workflow-core 写成“检查与旧功能保护”，把 Bridge Kit 写成“最终交付检查”；新总体架构已经把交付判断独立给 Delivery Assurance，因此旧图不能继续作为当前职责真相。
2. 两张 1920×1080 图需要从左到右追大量角色、箭头与回路；移动端只能缩小到不可读，或迫使用户横向平移。
3. 旧图把所有节点放在同一视觉层级，读者难以区分真实存在的运行底层、项目源码、已审设计和未验证接线。
4. 箭头说明“发生什么”，但没有就地回答“输入是什么、谁消费、怎样证伪、删除后失去什么”。
5. 长文信息充分，却要求读者先读完研究过程再形成核心判断；作为评审材料成立，作为系统展示入口成本过高。

本方案保留旧材料的事实，不复制其展示结构。图形退为局部机制；状态、消费者和证伪条件进入可操作详情。

## 视觉系统

### 方向

采用成熟的编辑型技术图谱视觉：暖灰纸面、深墨正文、有限强调色、清晰分隔线。视觉重点由字号、留白、分组与证据色承担，不依赖大面积插画、渐变、玻璃、发光、漂浮卡片或装饰节点。

- 背景：暖灰与近白，降低长时间阅读疲劳。
- 正文：深墨色；次级说明使用中性灰，不用低对比浅灰。
- 已有或真实观察：克制绿色。
- 已审设计或计划：琥珀色。
- 缺证或失败：红褐色。
- 部分已有或独立观察：蓝灰色。
- 圆角只用于分组与控件，默认 4–10 像素；阴影仅用于真正浮起的交互容器。
- 标题采用中文衬线体作为编辑层级，正文使用系统无衬线体；不引入网络字体。

### 桌面与移动

桌面使用最大 1240 像素内容宽度与 12 列逻辑；移动使用单列阅读，五阶段流程转为纵向，组件目录成为局部横向选择器。整页不得横向溢出。移动端不把桌面大图缩小，而是重新安排阅读顺序。

### 无障碍

- 提供跳过链接、语义标题、原生按钮、原生 `details`、明确焦点。
- 触控目标至少约 44 像素。
- 状态不只靠颜色，必须有文字。
- 支持 `prefers-reduced-motion`；本原型没有必要动画。
- JavaScript 只增强切换；默认内容、证据和结论在 HTML 中可读。

## 交互原则

允许的交互只有三类：

1. 比较同一任务的正常、失败、旧功能保护；
2. 逐阶段检查输入、机制、消费者和证伪条件；
3. 逐组件检查存在理由、责任和删除后果。

禁止加入拖拽节点、缩放画布、自动播放、视差、鼠标追随、装饰性悬停、无业务含义的数字动画、主题切换、个性化仪表盘、搜索、登录和编辑器。后续新增交互必须明确减少哪一项理解或判断成本，否则删除。

## 技术选择

### 生产模板

- Astro 静态输出；首版不启用服务端渲染。
- Astro Content Collections 保存系统、场景、组件、证据和决定；模式校验阻止遗漏关键字段。
- MDX 仅用于需要连续论证的证据页，不允许在每个组件里自由堆叠任意 UI。
- 两个局部原生 TypeScript 交互岛：场景浏览器、组件合同浏览器。
- CSS 自定义属性提供设计令牌；不引入大型组件库。
- 原生 `details` 承担证据展开；无需交互运行时。
- 第一版无数据库、账号、搜索、CMS、分析脚本、图编辑器或常驻后端。

### 为什么不是默认文档框架

Starlight、VitePress 和 Docusaurus 都能快速得到成熟侧栏、搜索和文档页面，但这些能力会提前决定读者先看到“目录”，而本任务需要先看到“系统价值、任务链和证据边界”。使用 Astro 自定义页面仍可获得静态输出和内容约束，又无需逆向改造文档主题。

### 为什么不是 React Flow、Mermaid 或 D2 主界面

复杂系统展示的核心不是让读者探索任意拓扑，而是让读者准确回答少数关键问题。节点画布引入缩放、拖拽、边交叉、移动端平移和可达性负担；自动布局则难以保证叙事顺序和证据层级。它们可在工程附录输出一张源码维护图，但不能成为主入口。

## 最强简单替代与停止条件

最强替代是“项目内验收加固 + 一份静态说明”，不建设共享 Delivery Assurance。它减少共享依赖和宿主接线风险，但会重复义务、证据与回传规则，也更容易在项目间漂移。

首个 Lucerna 试点必须实际减少至少一项：漏检、用户催促、报告搬运、候选身份混乱或旧行为回归。若不能减少，删除共享 DA 层，保留项目回归和本展示模板，不用已经投入的设计成本为继续建设辩护。
