交付保障系统 · 第一版完整样例

交付之前，先确认任务真的完成了。

Delivery Assurance 把原始承诺、项目验收和当前候选的证据放在同一条链上。缺证或失败时，它把具体问题交回原任务继续修复；证据不足时，不允许把“测试跑过”写成“产品可用”。

一条真实任务链

同一项修复，必须同时回答三件事

下面使用 Lucerna 的真实历史问题：当主要访问仍可用、次级路线处于检查中或没有观测证据时，整体不应误报不可用；真正次级故障仍应提示；修复也不能破坏已有正常入口。

设计机制

先固定“正在验收哪一个候选”

记录来源提交、构建产物、运行实例和任务承诺。后续任何源码变化都使旧复核失效，避免拿旧截图签发新版本。

进入什么
原任务、确切提交、Windows 发布候选、必须保护的既有行为
实际动作
Bridge 只提供任务身份和合法运行接点；Delivery Assurance 绑定验收对象与承诺
产生什么
同一候选的身份记录，交给项目验证和独立复核消费
怎样证伪
提交、构建、进程或截图来自不同候选；或者身份无法从正常入口取得
→

正常完成：同一发布候选通过项目正常入口和独立复核，证据覆盖新要求与相邻旧行为，才允许写“可交付”。

选择一个组件，查看它为何存在、接收什么、把结果交给谁，以及删除以后会失去什么。状态标签描述当前事实，不描述愿望。

交付判断

Delivery Assurance

拟建插件

把原始承诺转成不可降级的验收义务，判断当前候选还缺什么证据，以及此刻允许作出怎样的交付声明。

何时触发
正式软件交付、重要集成变化、首个真实纵向功能和最终候选
权威输入
用户确认目标、项目正式约定、已接受旧行为、当前候选的项目验收结果
输出给谁
缺口交给原 Codex 继续修复；放行结论交给最终用户说明
失败怎么办
标准不清则返回专业负责人补齐；证据缺失或版本不一致则保持未通过
删除它会怎样

项目可能各自有测试，但没有一方负责证明“所有承诺都被当前候选覆盖”，绿色局部结果仍可被扩大成产品完成。

明确不做

不编写项目领域测试，不接管 Codex，不负责插件路由，也不创建新的常驻调度器。

证据账本

相信到哪一步，只由证据类型决定

同一事实旁边同时写明“能证明什么”和“不能证明什么”。设计评审、源码、确定性回归和真实发布候选分别占据不同层级。

真实观察或现有源码 已审设计 仍待证明
E1真实问题检查中或未观测曾被误写成故障历史事实

支持：Lucerna 的历史修复记录明确说明，次级 MISSING 与恢复动作曾错误提升整体严重度，界面出现中性文案却继承严重状态。

不支持：不能据此证明 Delivery Assurance 已经发现或阻止了该问题；当时修复发生在项目任务内部。

E2源码与回归未观测、检查中和确认故障已有分离规则源码存在

支持：固定提交中的 Rust 聚合逻辑、展示映射和确定性测试可以区分“没有证据”“正在检查”“确认失败”。

不支持：Producer 记录同时声明尚未重建并启动正式 Windows 发布候选，也没有新的独立界面复验。

E3架构评审R3 设计获得继续推进结论设计通过

支持：职责、失败回路、候选身份与证据复用形成了可实施的设计方向。

不支持：PROCEED 和“设计闭合”不等于宿主接线、自动调用或七仓生产启用。

E4生产能力宿主探针、入口接线、回传和七仓启用尚缺未验证

需要看到：受支持宿主的真实能力探针；同一 Lucerna 候选的好例、坏例、旧功能、缺证与绕过测试；失败结果确实回到原任务继续处理。

当前声明：系统仍处设计与试点准备阶段。

E5投入估计宿主探针 4–8 小时，首条纵向 40–88 小时计划估计

支持：用于比较先做小探针还是直接建设完整体系。

不支持：这些是研究阶段估计，不是已经消耗的实际工时，也不是交付日期承诺。

唯一推荐方案

用独立的 Delivery Assurance 守住交付边界，保持路由与运行底层克制

旧 R3 设计把共享判断靠近 workflow-core 与 Bridge。新的总体架构已经明确：workflow-core 只负责能力发现、组合和消费确认；Bridge Kit 只负责身份、权限、运行接点与结果递送；Delivery Assurance 单独拥有验收义务、证据缺口和交付声明。这种拆分更容易独立调用、独立测试，也避免基础设施自我批准。

网站实现Astro 静态内容站 + 结构化内容模式 + 两个局部原生交互岛
首个试点Lucerna：一项真实状态修复、一项相邻旧功能、一个故意坏候选
停止条件若试点不能减少漏检、用户催促和报告搬运，删除共享 DA 层，仅保留项目回归

下一项真正有价值的证据

证明失败能在同一任务里被接住

  1. 冻结一个确切 Windows 发布候选。
  2. 故意保留“检查中误报故障”或破坏相邻旧行为。
  3. 让项目入口与独立复核产生当前候选证据。
  4. 确认 DA 阻止交付并把缺口交回原 Codex。
  5. 修复后重新构建、重新复核，再决定是否放行。

本轮不执行以上产品开发，只交付可审阅设计与静态原型。
