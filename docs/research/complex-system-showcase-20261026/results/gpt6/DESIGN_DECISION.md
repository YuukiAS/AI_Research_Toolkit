# 推荐：用静态“案例—机制—证据”页面解释复杂系统

唯一推荐是 **Eleventy 3.1.7 + Markdown/YAML + Nunjucks + 原生 CSS/JavaScript**。视觉采用浅色编辑式版面；用同一案例的候选对照解释机制，用可展开的责任条目解释组件，用固定版本来源说明证据。没有服务器、账户、数据库、图编辑器或自动发布。这个选择针对解释网站，不是 DA 产品的实现架构。

本轮已经完成可直接审阅的 [视觉原型](prototype/README.md)。原型是普通 HTML/CSS/JS，验证版式与交互；没有把它包装成正式 Eleventy 项目或已上线网站。未来获准开发时才把冻结内容装入所选模板，不能重新发明产品。

## 读者和信息顺序

首要读者是要决定是否值得试点的项目负责人：知道 Codex，但没有参加 DA 历次讨论。第二类读者是实现者，需要核查责任、输入、消费者和证据。阅读承诺是先看懂“替我免去什么损失、现在能不能用”，再理解“为什么这样判断”，最后才进入实现细节。

首页先给交付问题、设计状态和 Lucerna 的 2/3 路线历史切片。它接着呈现同一要求下三种候选：符合要求、掩盖真实故障、破坏旧行为。读者可以在原位比较输入、展示、判断与下一接收者，减少跨页寻找。组件区随后解释六种责任，其中独立审查按风险出现；这不是六个新服务，也不是强迫未来系统拥有六个模块。证据区区分历史、已审设计和当前建议，最后只留下宿主探针与最小试点这一条下一步。

“完整内容”和“默认全展开”不是同一回事。真正损失、状态边界、三条路径和投入应直接出现；详细接口、生命周期、版本引用通过展开及证据链接进入。没有为凑页面数拆页，没有全局文档侧栏。将来多个系统各有自己的解释页；只有独立的读者任务或内容量证明必要时才拆出深层专题。

### 三条现实路线的最终裁决

| 路线 | 得到什么 | 持续成本与放弃理由 |
| --- | --- | --- |
| 小型专用站，手写 HTML/CSS/JS | 当前原型最直接，控制力足，零构建 | 多系统时头尾、来源和组件容易复制漂移；适合作为本轮可携带视觉候选，不作为正式维护结构 |
| **单仓库 Markdown + 静态生成模板** | 普通文件审阅；少量统一容器；静态输出；按需 JS | 自己维护小型内容校验和视觉容器。因为这正是作品独特价值，成本有必要，选择此路 |
| 现成文档框架 | 搜索、侧栏、版本、多语言成熟 | 这些当前没有需求；大量主题覆写后反而维护两套逻辑。不选；若未来主要读者任务变成 API 查阅，再重新评估 |
| React/Next.js 应用式专用站 | 客户端状态、路由、服务集成空间大 | 当前没有账户、实时数据、编辑或多步骤业务；无证据支持增加应用层，不进一步扩大研究或安装 |

选 Eleventy 并不表示模板替人判断内容。它只完成构建，事实、组件必要性和新旧证据仍由作者核查。采用稳定包精确锁定；未来维护先看安全与兼容修订，再在同一原型上回归。运行时只交付 HTML、CSS 和本页少量 JS；无需 Node 服务。

## 冻结视觉方向

名称“系统观察室”表示一组解释材料的阅读入口，不创建新的产品或平台。选择“浅色研究编辑版”：宽窄对照、细分隔线、深绿文字、浅灰绿事实面板、克制的橙红反例面板。历史案例数字直接来自记录，用于解释可用路线与整体误报的矛盾；不展示无依据的 KPI。

| 规则 | 冻结值与用途 |
| --- | --- |
| 页面 | 最大正文宽 1200px；桌面边距至少 48px，手机 20px；大屏继续留白，不拉长段落 |
| 字体 | Segoe UI / Microsoft YaHei / PingFang SC / sans-serif；无字体网络请求。中文实际渲染在本机检查，其他系统需再验 |
| 字号 | 桌面 H1 58px、H2 38px、主引入 18px；手机 H1 42px、H2 29px、正文 16px；密集机制正文 12–14px，来源 11–12px |
| 色彩 | 背景 #f7f8f4；正文 #192f2b；次级 #56655e；结构线 #d5ddd4；正向 #285e45；错误 #973f2d；辅助浅绿 #eaf0e5、浅红 #fbede6 |
| 状态 | 文字明确说明历史/设计/未部署；绿色只表达候选预期，不能暗示实测通过；不只靠颜色传达 |
| 节奏 | 章节 94px 间距，手机 54px；同一因果关系贴近呈现；来源和研究日志不占主叙事 |
| 控件 | 仅内部锚点、三态比较与原生 details；可见焦点，常用触控目标至少 44px；无自动轮播、滚动劫持、装饰 hover 或进度动画 |
| 图形 | 不用插图填空。首屏状态重绘是有来源的解释性视觉，明确不是原应用截图；标记只用于品牌识别或状态，不叠加图标库 |

手机顺序是用途→状态→主要入口→案例→输入→候选→判断→返修。桌面输入与判断并排，手机上下阅读；不缩小整张架构图。不把桌面侧边说明保留为手机冗余段落。

另比较了两个视觉方向：传统文档侧栏适合查找但不适合首次理解；深色控制台容易把设计推演误看成正在运行的系统。选浅色编辑式版面，不以三套未完成截图让用户代做设计选择。

## 交互为何值得存在

- 候选切换保留同一要求，改变输入、错误展示、判定与接收者，让读者识别“画面更绿”与“要求满足”的差别。不是换皮的重复文案。
- 组件展开把“谁启动、权威输入、处理、交给谁、删除损失”并置。默认展开 DA，其他按需读；不开新窗口，也不要求拖拽节点。
- 失败候选直接给展开的返修链；真实接收、重新取证和取消边界同时出现。不存在“运行 DA”按钮。
- 缺证据说明用原生 details 解释与候选通过不同的情况。当前状态边界不藏在 details 内。
- 所有正文已在 HTML 中；JS 只增强单个候选比较。禁用 JS 时三条路径顺序显示，不产生空白站。

## 自我约束及取舍记录

Artifact Curation 原则用于逐元素判断：删除框架徽章、运行指标、复制命令、全局搜索、三列营销卡片、动态图背景、大型总架构图和未获证部署入口；保留真实案例、缺证据处理、成本和停止条件。内部删除理由只留在本文件。

Reasoned Design 原则用于与项目测试补强路线竞争，并设置首片失败即撤公共层的条件。Clear Writing 用于把内部字段转换为读者问题，同时保留固定版本、未实测和新旧所有权。workflow-core 的目标原则体现为只使用本轮需要的研究、写作与浏览器检查；没有假称未实现能力已自动调用。DA 的目标原则体现为原型源码摘要、截图和行为报告对应同一候选；这是作者验收纪律，不是 DA 产品运行证据。

下一步是用户审核本设计。所选技术不需要改变任务范围或增加费用；无待用户补参数的技术决定。真实理解效果仍需后续招募未读源材料的人验证，不能由作者自查宣布已证。
