# 薄模板与冻结开发验收

模板复用的是解释能力：从读者损失进入，用必要的对照讲清机制，让组件责任与来源可查。它不规定每个系统都有六个泳道、七个仓库、三张卡片或固定数量的页面。正式开发必须保留本轮批准后的内容与视觉身份；新功能、删减承诺和更换呈现方式都需要说明实际收益。

## 内容只保存解释，不复制第二份业务真值

未来采用一个仓库内的 Markdown 正文，加少量 YAML front matter；Nunjucks 提供可选的展示容器。业务事实继续属于原仓库的固定提交和原始产物。页面只记录有来源的解释及引用，不同步全部产品状态、不维护运行数据库、不在构建时悄悄请求“最新结果”。

建议目录是 `content/systems/<slug>.md`、`_includes/`、`assets/`。不是本轮实际建立的正式网站。本次 `prototype/` 则是获准的静态设计候选，所有文件都可直接打开，不需要安装框架。

一个最小完整内容实例：

```yaml
---
layout: system.njk
slug: delivery-assurance
title: Delivery Assurance
reader_question: 这次说完成的东西，真的符合原要求吗？
status:
  label: 设计研究，尚未部署
  checked_on: 2026-10-26
  scope: 旧 R3 已审；独立 DA 职责为更新候选
authority:
  - repo: YuukiAS/AI_Research_Toolkit
    revision: ae2766a62b1546048ec6122e01ee95f1904fb73c
    path: docs/research/software-production/22_DELIVERY_ASSURANCE_GLOBAL_WORK_RESEARCH_20261022/WORK_OUTPUT/CURRENT.md
  - repo: YuukiAS/AI_Skills_Collection
    revision: fd6916ad5fdd5fb905544b6a127f9b0d31a737e1
    path: docs/design/ai-reliability-architecture/ARCHITECTURE_ZH.md
presentation:
  comparison: scenarios
  component_disclosure: true
  quantitative_plot: false
next_question: 正常受控入口能否把真实失败交回原任务并完成合法修复？
---
```

正文按读者问题写 Markdown，不要求把每个句子改成 JSON。比较情境若需要模板读取，可用页内数据文件保存 `premise / observed_or_expected / consequence / next_consumer / evidence_ref / evidence_kind`；这些是展示字段，不运行产品判定。`evidence_kind` 至少能区分历史记录、当前实测、设计推演、未验证；不能自动用“有 URL”判为真实运行。

共享约束只有：标题与用途、状态边界、读者损失、机制及其前提、来源、未证范围、下一决定。组件说明和多情境比较按内容出现；某系统没有独立部件、数值数据或返修机制，就不渲染相应容器。来源链接需绑定 revision；观察证据额外说明对象、时间和适用范围。源文件删除或无法访问时显示证据缺口，不退回缓存结果假装当前。

## 容器的最小边界

| 容器 | 何时用 | 何时不用 |
| --- | --- | --- |
| 用途与状态引入 | 所有系统；同时回答价值与当前可用程度 | 不做产品口号、组件数量或成功率仪表盘 |
| 案例切片 | 有能改变判断的具体事故、结果或观察 | 没有来源时写示例身份，不能包装成真实案例 |
| 前提—结果对照 | 两个或多个候选的差异能解释因果 | 只是翻出相同文字时改为普通段落 |
| 组件责任展开 | 有读者需要追问的必要部件 | 不自动从依赖包列表生成组件墙 |
| 证据及边界条目 | 主张强度不同或需要深入核查 | 不展示无意义绿色徽章或测试总数 |
| 数值图 | 数据、尺度和比较问题都真实存在 | DA 当前无效果数据，因此不渲染 Plot |
| 下一验证 | 有一个能否决现推荐的动作 | 不制造开发任务清单，不放“立即启动”假按钮 |

图、表、文字和交互均可选。布局由内容关系选择，不能把每个系统强制映射为节点图。最初只实现本次已验证容器，不开发通用拖拽编辑器或页面搭建器。

## 第二系统迁移：离线并发编辑

已完成 [另一类系统的静态迁移页](prototype/transfer.html)，同样使用 `styles.css`，不用 DA 的交互脚本。机制来源为 [Automerge 一手仓库](https://github.com/automerge/automerge)与[官方冲突语义](https://automerge.org/docs/reference/documents/conflicts/)。它说明同一对象属性被并发写入时，默认值与保留的冲突值不同；这只是机制说明与应用设计，不是本轮运行了 CRDT 同步或实现了笔记软件。

迁移前主问题是“谁证明这次交付”；迁移后是“两个离线修改是否都能找回”。页面不用 DA 的六种责任，换成两端并发输入与同步后读取的对照。缺失反证也换成“库保留了冲突，但界面只展示默认值，用户仍可能丢失对分歧的理解”。旧功能保护是未改正文不变，证据缺口是实际应用重启与同步未测，下一验证是离线双端修改、反向同步顺序、重启后恢复。

| 可直接复用 | 必须重新研究 |
| --- | --- |
| 字体、色彩角色、响应式顺序、前提/结果并列、details、来源强度 | CRDT 对不同数据类型的语义、持久化适配、网络交换、冲突 UI、数据损失风险 |
| 候选状态、来源版本、未证范围的展示语法 | 实际应用的成功/失败判据、合并策略、已接受旧内容和真实用户任务 |
| 源码与截图同候选核查 | 真正产品运行证据；不能拿本页静态结果替代 |

更换为科研方法时，则应围绕研究问题、输入、假设、基线、结果分布与局限，必要时加入真实数值图；不借用软件“自动返修”。更换为 Mica 时，必须重新读取当前正式里程碑、扩展实际加载路径和登录态权限；不能将 DA 文案里的 EXE/PID 改个名字就交付。

## 更新与防陈旧规则

1. 作者先读取原系统新的有效来源，比较与页面引用版本的差异。任何自动工具最多报告漂移，不自动升级事实结论或宣称更新完成。
2. 变化涉及状态、责任、观察对象、标准或现有能力时，改对应解释及引用；旧截图注明旧版本或重新取得，不把截图时间改成今天。
3. 对已改变内容做保真、必要性及读者复读；渲染与交互检查必须针对新候选。正文没变但 CSS 改了，视觉证据也要更新。
4. 提交原稿、模板、截图、检查记录的同一候选；远端回读核对 SHA/文件摘要。网页的 `checked_on` 只代表完成这次核查，不代表上游从此永远最新。
5. 部署属于另行授权阶段；本模板没有后台监控、定时抓取或自动发布。

## 给后续 Codex 的冻结开发合同

批准权威为用户选定的本目录提交及其 `prototype/index.html`、CSS、交互、全部中文内容、截图和本文件。用户批准以后，在原任务记录中绑定该准确提交，不允许用分支不断移动的 HEAD 模糊设计基准。以下是未来开发应履行的验收，不能称本轮已全部生产验收。

### 必须保留

- 首屏用途、用户损失、未部署状态、历史案例身份及出处。
- 三种候选的输入、可见结果、判断、具名消费者；坏候选的同任务返修和新候选取证。
- 独立 DA / workflow-core / Bridge 新旧分工差异、旧设计通过不等于运行证明。
- 缺证据、错候选、未知覆盖、独立审查必要性、取消及无活跃 owner 的边界。
- 旧功能保护、专业标准所有权及验收器校准，不以极简为由删去。
- 三个旧估算及包含关系、非实测身份、未含成本；只给一个可否决下一步。
- 普通 HTML 可读正文，禁用 JS 后仍可读所有情境；完整键盘路径和手机单列顺序。
- 全部有效来源及其固定版本；链接坏了必须修复或标缺证，不能静默删除不利事实。

### 绝不自行增加

账户、聊天助手、搜索、反馈表单、订阅、CMS、远程配置、数据库、遥测、后台定时任务、自动部署、运行 DA 的按钮；无证数据图、成功率、虚构实时日志、动画进度、随机图片、装饰卡片、图编辑器、无信息增量的控件；将研究角色、内部编号、状态枚举、开发日志放进用户主界面。

不能仅因后续开发方便更换为 React/Next、引入 UI 组件全集、修改原任务完成含义、删除组件理由、改变真故障或旧行为的预期。必要变更须写明读者收益、受影响状态与兼容代价，并取得适用的用户决定；样式小修在冻结语义下可自行完成。

### 可实际否决的验收

| 检查 | 判定依据及失败条件 |
| --- | --- |
| 首屏理解 | 未参与讨论的读者不翻源材料，能回答用途、用户变化与目前是否部署；将设计误认成可用产品即失败 |
| 三条路径 | 能找到正确、故意掩盖故障与旧行为退化；说清实际/预期与谁接失败；找不到或只会复述组件名即失败 |
| 组件必要性 | 任取一项，说清权威输入、处理、输出、消费者和删除损失；有明显重复职责则返修 |
| 证据强度 | 能区分旧已审方案、新候选、历史修复、本轮原型渲染和未做产品实测；任一混淆不能靠免责声明掩盖 |
| 取舍 | 能指出“只补强项目测试”何时足够、何时薄 DA 才值得，以及试点失败如何退出 |
| 阅读测试方法 | 后续用至少 3 位未读源材料的目标读者分别完成前五项，不提前解释；逐题记录原话、找到的位置和误解；若任一人误认已部署或错认模拟为实测，必须修复；其余题至少 2/3 独立答对。这是未来小样本可用性门槛，不代表统计推广 |
| 视觉 | 320、390、768、1024、1440、1920px 不横向溢出；页面无标题切字、遮挡、图例误导；正常、坏候选、组件展开和底部都实看 |
| 行为 | 锚点准确；三个候选恰好一个被选，内容真实变化；Enter/Space 可操作；details 开合正确；关闭 JS 不失去三路径；外部网络请求为零（用户主动点来源除外） |
| 可访问性 | 普通文字对比至少 4.5:1；大字至少 3:1；焦点可见、语义标题连续；状态不只用颜色；常用触控目标≥44px；200% 缩放无内容丢失。最终目标浏览器及屏幕阅读器仍须实际检查 |
| 范围与身份 | 只改获准的网站目录；记录源码摘要、构建输出、截图对应关系；截图后源码变化必须重拍受影响状态；不能用旧截图验收新候选 |
| 审核边界 | 作者自查不称独立审查；浏览器渲染不称读者理解；模板构建不称 DA 产品完成；部署另行授权 |

原型当前的作者行为检查见 [browser-checks.json](prototype/browser-checks.json)，实际观察与局限见 [视觉核查](VISUAL_QA.md)。本轮没有招募读者，不声称理解测试已经通过。

## 与旧两图加长文的可检查改进

| 阅读问题 | 旧 11/12 形式的负担 | 本方案具体变化 | 本轮能证明什么 |
| --- | --- | --- | --- |
| 找用途与状态 | 图和长文需要寻找限定句 | 首屏放用途与“尚未部署” | 已渲染可见；尚无读者用时测量 |
| 找组件必要性 | 泳道显示角色，但删除后果需跨段推理 | 每项责任旁写输入、消费者与缺失损失 | 内容存在且可展开；不宣称独立理解效果 |
| 跟随失败 | 从主链跨多泳道寻找回路 | 同一要求原位对照，失败下直接展开接收与重验 | 点击改变内容，接收者与边界可见 |
| 区分证据 | 设计图容易被读成运行状态 | 历史、旧设计、新建议分栏，推演就近标明 | 三种强度在页面上可区分 |
| 知道下一步 | 读完整研究才找到首片和成本 | 页尾只给可否决试点，成本说明包含关系 | 完整内容已呈现；试点本身未执行 |

原图有保留价值：它适合已经理解系统的人核对全链拓扑。本方案不宣称图永远无用，只把首次理解的入口改成可读案例；深层证据仍能回到原研究。新增复杂图须证明它回答了文字和对照无法回答的问题。
