这里观察的是“哪些状态会被当成故障”。不能因为有一个未知项，就把整台系统标成不可用。

交付判断 / 条件成立时

证据齐全，才可交付

  • 正确与错误状态均通过对照
  • 受影响的旧连接、状态展示不退化
  • 本次 EXE 与真实窗口观察一致
  • 必要的独立审查属于同一候选

项目验收程序提供观察，DA 核对必需项及版本；原工作流消费结论后，才向用户报告相应范围已完成。

正确结果应是“需要注意”，同时保留可用连接。验收要同时检查误报与漏报，不能只看画面是否变绿。

交付判断 / 推演预期

拒绝这个候选

真实故障没有被提醒，原始要求尚未满足。

失败证据
确认故障的输入、窗口实际展示、预期状态与候选身份
下一位接收者
原 Codex 任务，修复状态映射并重新验收
不得替代
删除这个坏例、放松标准，或拿旧截图证明新版本
失败怎样回到原任务，而不是留下一份报告？
  1. 项目验收 → DA

    原运行器返回实际与预期、原始观察和候选身份；DA 判定哪项承诺没有满足。

  2. workflow-core → Bridge → 原 Codex

    路由到原任务的活跃执行者；Bridge 传递准确身份和反馈。必须观察到接收与后续处理，写出文件不算送达。

  3. 修复后的候选 → 重新验收

    Codex 修映射，重跑正例、坏例与受影响旧行为。新 EXE 重新观察，过期截图和独立意见失效。

只在已证明支持的入口和原预算内续修。用户取消、权限不足或没有活跃接收者时，保存原任务恢复点；不承诺后台自行唤醒。

修改共享状态逻辑时，要沿入口与依赖找回受影响的旧行为。只跑新增测试，会漏掉这个错误。

交付判断 / 推演预期

旧功能也是交付条件

检查从哪里来
已接受的版本、正式产品合同，以及本次改动的反向消费者
失败交给谁
原 Codex 修共享映射；重新运行受影响回归与当前窗口观察
范围未知时
保留覆盖缺口；全跑现有测试也不能把未知改成通过
如果测试全绿，却没有本次应用的观察呢？

仍不能证明真实交付。源码测试、构建产物、实际 EXE、运行实例和窗口观察必须对应。缺少当前观察时明确“尚未证明”，不把缺测算作成功。检查程序自身还须用正确、错误、缺证据和旧行为四类对照校准；有重要专业判断时，由既有独立权威批准适用版本。

本页采用的目标分工

核查各层证据 ↗
Delivery Assurance确定这次能否交付
由谁启动
受控开发入口中，由 workflow-core／原工作流调用；完成时再次检查。
权威输入
批准目标、正式领域标准、已接受旧行为、当前候选与专业结果。
怎样处理
核对义务覆盖与证据资格，识别缺测、过期、错候选；不自创专业阈值。
交给谁
将可声明范围或具体失败交给原工作流；失败再回原 Codex。

少了它：各项测试可能分别通过，却没有人核对它们是否共同证明了这次承诺。

项目专业验收观察真实成品
由谁启动
当前 Codex 按所选义务，调用项目已有运行器。
权威输入
冻结的专业标准、当前应用、合法环境、可靠的对照及观察方式。
怎样处理
运行适用测试，检查当前窗口或最终产物，记录原始观察。缺权限就是缺证。
交给谁
原始结果交 DA；采集器错误交采集负责人，产品错误交原 Codex。

少了它：只剩报告里的“通过”，无法发现数据与实际画面互相矛盾。

当前 Codex实现并继续修复
由谁启动
用户照常提出目标，或原工作流将合法反馈送回当前任务。
权威输入
原请求、项目约定、所需专业能力、实际与预期的失败证据。
怎样处理
实现产品；标准已定而缺程序时补验收器。不能为通过而降低目标。
交给谁
候选交项目运行器；新证据回 DA。标准冲突交原专业负责人。

少了它：失败被识别后停在报告里，用户仍得重新组织一次修复。

workflow-core组合能力，安排接收者
由谁启动
复杂任务进入现有执行流程时；简单问答无需完整编排。
权威输入
当前宿主实际可用的能力、任务依赖和原工作流。
怎样处理
选择需要的插件与顺序，核实输出被下游消费；缺失能力不能只登记为已调用。
交给谁
能力与行动交当前 Codex；DA 失败路由给具名接收者。

少了它：复杂任务容易遗漏应使用的专业能力，或生成无人接收的检查意见。单领域小任务可直接调用。

Bridge Kit保持身份与合法恢复
由谁启动
既有受管入口或已验证的宿主接点调用。
权威输入
原任务身份、工作目录、授权、预算、候选标识与反馈引用。
怎样处理
在原边界内递送和恢复；取消、身份不明或预算耗尽时不再启动。
交给谁
精确反馈交存活的原执行回合，运行及消费回执交原工作流。

少了它：需要退出后恢复的受管路径可能找不到正确任务，或重复执行。已有等价项目入口可以复用，不为 DA 增建常驻服务。

必要的独立审查制止产品和标准一起放宽
何时需要
重要专业判断、新验收定义或项目合同明确要求时；不因修改了 UI 就一律触发。
权威输入
原始要求、先于候选冻结的标准、当前完整产物与原始证据。
怎样处理
沿已有合法角色核对；审查者不能修改产品、标准或受保护答案。
交给谁
准确版本的意见回原任务负责人，由 DA 核对其适用性；无通道则保留未证。

在需要时少了它：实现者可以把测试和产品同时改松，自行证明错误结果正确。

它与整个 AI 可靠工作体系怎样配合？

Reasoned Design
在需要重大判断或完整方案时，研究目标、替代路线与遗漏。它形成有依据的方案，DA 核对已经批准的承诺。

Artifact Curation
判断成品元素是否值得保留，由领域制作端实施取舍。它不能以简洁为由删掉已承诺能力。

Clear Writing
把核实后的机制、结果与边界说清楚。语言润色不能升级证据或把设计写成可用产品。

这些能力按任务需要组合，不要求每次经过全部组件。新跨插件自动调用仍需真实入口验证；本页没有调用尚未实现的 DA 或 Artifact Curation 插件。

历史修复是有来源的证据；上方三个候选是为解释判定规则而构造的情境。它们没有连接真实应用，也没有运行产品测试。

值得增加这一层吗

先和“只补强项目测试”竞争。

直接补强已有运行器最便宜，也能修掉已知缺陷。如果问题只是某个项目少一条回归，应优先这样做。

DA 只有在跨任务反复出现“漏验承诺、用错版本、失败没人接”时才有额外价值。首个试点若没有减少其中任何一种真实损失，就退回项目测试路线。

唯一下一步

先证明一次失败，
真的回到了原任务。

先验证目标宿主的接入与恢复，再用 Lucerna 的一个冻结小任务检验最薄判定链。不要从七仓铺开。

查看可否决的首个试点
  1. 正确候选能交付，真故障被掩盖和旧功能退化必须被拒绝。
  2. 漏跑、空结果、错候选与旧截图不能获得正式完成结论。
  3. 原 Codex 实际收到失败并修复；新候选重新取证后才能接受。
  4. 取消后不再启动；无活跃接收者时只保存恢复点。
  5. 记录误拦、增量耗时和用户提醒／搬运次数；只多了回执却没减少真实损失，就否决推广。
