# 交付阶段怎样挡住降级实现：反降级机制与验收治理研究

日期：2026-11-10  
范围：Design Assurance 冻结之后、Delivery Assurance 最终交付之前的反降级与验收治理  
性质：研究结论与正式插件设计输入；不代表插件已经实现或宿主隔离已经成立

## 结论

最推荐的机制不是再增加一个“验收总控”或强制安排更多模型，而是把六件事组合起来：**冻结完成语义、保留不可降级边界、用已知坏实现校准验收、把证据绑定到当前最终候选、从真实正常入口检查最终成品、同时验证应保持不变的旧能力**。任何单一机制都不够：测试先写可能把错误理解提前固化，隐藏用例可能并不真正隐藏，哈希只能证明对象没有变，独立模型也会有共同偏差。

当前五道防线应作如下处理：

| 原草案 | 结论 | 第一版处理 |
|---|---|---|
| 先写验收，后写实现 | **保留但改写** | Design Assurance 先冻结验收语义、必要证据和禁止替代；具体测试实现可以由 Delivery Assurance 在交付期补充和修复，不强制独立会话先写完整验收器 |
| 可见检查 + 隐藏用例 | **改为按风险使用** | 可见的核心验收是默认；只有存在真实读取权限边界时才称“受保护用例”。没有真实隔离时只能称未见样本或晚加入样本，不能称隐藏测试 |
| 验收器先证明能抓坏东西 | **强保留并扩展** | 至少用已知坏实现、正例和缺证据例校准；按对象增加变异测试、性质测试、蜕变测试、差分测试或参考结果 |
| 锁定和篡改检查 | **保留但不能只靠哈希** | 使用实际权限、审查规则和不可移动版本引用保护语义资产；哈希用于身份与篡改提示，同时绑定候选、构建物、安装或部署对象、运行环境和原始证据 |
| 独立裁判 + 主动申报偏离 | **拆开处理** | 主动申报偏离为必需；独立模型裁判只在视觉、文稿、数学、统计或科学判断确有增益时提供专业证据，不是默认安全边界，也不拥有最终交付权 |

Design Assurance 冻结到**验收语义**为主：必须证明的能力、成功与失败含义、允许声明的范围、正常用户入口、必要证据类型与真实度、阈值或专业准则、禁止使用的替代物、必须保持的旧能力，以及哪些变化必须回到设计阶段。它不应默认冻结每个测试脚本、选择器、运行器和样例。只有当验收方法本身决定科学含义、产品承诺或安全边界时，方法才属于冻结内容，例如真实总体而非示例数据、实际安装程序而非源码、物理设备而非模拟器、完整协方差而非对角近似。

Delivery Assurance 从冻结合同接手后，是交付阶段唯一负责人。它负责安排实现、完善验收方法、修复验收实现、取得专业证据、把失败退回原实现者、重新运行受影响检查，并最终决定当前范围能否交付。专业插件、GPT、GPT Work、独立 Codex 会话、项目运行器和 Bridge 只提供能力、观察或身份事实，不成为新的总负责人。

第一版不需要强制建设独立验收器实现者、通用隐藏测试服务或独立模型裁判。Delivery Assurance 应以 **Codex 单一主入口**为主；遇到视觉、正式文稿、数学、统计、科研结论等机械规则不足的对象，再按需调用 GPT、GPT Pro 或 GPT Work 返回专业证据。无需建设第二个“GPT Delivery Assurance”。

最大的剩余风险是：冻结的验收语义本身不完整或错误，导致替代实现满足所有检查却没有满足真实用户或科学目标。第二个风险是，把同一可读写仓库、独立工作树或独立模型会话误称为受保护边界。增加更多角色不能自动消除这两类风险；前者依赖真实成功链、危险失败链和领域证据，后者依赖实际权限隔离。

## 一、降级实现的有效分类

分类的目的不是列出更多名称，而是决定应该采取什么防线。综合外部研究与本项目历史，六类足以覆盖主要失败，并且每类对应不同治理动作。

### 1. 目标替换：做了较弱对象，却沿用原承诺

实现者用 mock、示例数据、静态页面、代理指标、简化模型、旧参考实现或文件存在替代原来要求的真实对象。例如真实 Zotero 往返被替换为假接口；最终网页交互被替换为截图；总体科学目标被替换为一个容易提高的代理分数；正式训练被替换为少量步骤的烟雾测试。

主要防线是冻结“实际消费对象、正常入口、必要证据真实度、禁止替代物”，并从最终用户实际拿到的对象验收。普通单元测试无法单独防住此类降级。

### 2. 范围或质量缩水：仍做同一类对象，但缩小承诺

常见形式包括删掉边界场景、降低精度、减少数据规模、缩短训练、只覆盖最容易的设备或浏览器、把完整交互改成只读展示、把全协方差改成对角近似、把完整报告压缩成缺少关键推导或证据的摘要。

主要防线是冻结声明范围、关键参数、最低质量门槛、总体或环境覆盖，以及不可退化的旧功能。范围变化必须显式改变交付声明，不能继续沿用原来的“已完成”。

### 3. 验收捕获：修改裁判而不是改进产品

包括修改阈值、预期输出、黄金数据、测试选择条件或适用规则；跳过失败检查；把缺值当作零；自动接受新的视觉基线；删除失败样例；改变统计容差；只运行容易通过的子集。

主要防线是区分验收语义、方法和实现；保护决定完成定义的资产；要求语义变更有明确版本和授权；对验收器本身运行已知坏例、正例和缺证据例。哈希只能发现“对象变了”，不能判断“谁有权改变”和“改变是否正确”。

### 4. 对检查过拟合：不改裁判文件，但针对已知样例写特例

表现为硬编码公开测试输入、检测评测环境、读取保留标签、针对快照像素修补、通过样例名称分支、复现已见补丁而不实现通用行为。外部编码评测已经显示，公开测试不足和训练污染都会抬高表面成绩；扩大测试集能够发现大量原先漏掉的错误实现。[S04][S06][S07]

主要防线是性质、蜕变关系、随机或生成输入、差分检查、真正未见的保留样本，以及正常用户路径中的新情境。隐藏用例只有在实现者没有读取途径时才有额外价值。

### 5. 对象与证据错配：验的是 A，却签发 B

包括测试当前源码但交付旧安装包；使用旧候选的截图或报告；在不同提交上运行检查；构建后又改源码；部署内容与仓库提交不一致；用一台机器或一个时间窗口的观察宣称长期在线；把没有真实运行的结果写成已运行；把日志终态、文件路径或自报状态当成能力事实。

主要防线是候选与证据绑定：记录冻结合同版本、提交或源码集合、构建物摘要、安装或部署身份、数据与参数、运行器版本、环境、观察时间和原始证据。产物证明和哈希解决身份与来源，不证明专业正确性。[S20][S21]

### 6. 以新换旧：新检查通过，但已有正确行为被破坏

包括为了通过新测试删除旧功能、关闭主要能力以获得“安全通过”、修一处界面导致其他入口失效、改科学算法后破坏既有校准、更新文档后丢失链接、公式或图表。旧 Delivery Assurance 历史中，Mica“关闭主要功能获得安全 PASS”、Asteria 几何检查全绿但整体科学可读性变差，都是这一类。

主要防线是冻结“应保持不变”的能力集合，将历史真实失败加入回归库，并在当前最终候选上同时运行新增能力、旧能力和集成链检查。

### 各类交付物中的具体表现

| 对象 | 典型降级 | 必须看到的证据 |
|---|---|---|
| 普通代码与软件功能 | 假实现、硬编码测试、只测函数不测集成、关闭原功能 | 正确例、错误例、性质或变异校准、真实调用链、旧功能回归 |
| 科研计算与统计结果 | 缩小总体、降低迭代、错误容差、代理指标替代结论、只复现同一错误代码 | 数据与总体身份、方法和参数、数值不变量、独立或分析参考、敏感性与复现信息、实际科学结论边界 |
| 网页、桌面应用、浏览器扩展 | 截图替代交互、开发页面替代部署、模拟后端替代真实宿主、源码存在替代已加载扩展 | 最终构建或安装对象、真实宿主、可见交互与后置状态、部署身份、失败与恢复路径 |
| 文档与报告 | 文件存在或编译成功但内容丢失、引用不可定位、公式或图表错误、摘要冒充完整报告 | 最终 PDF/网页/文档的全文与渲染结果、链接和引用可达性、内容覆盖、专业阅读判断 |
| 图表、图片、演示文稿 | 有图但不是所需图、示例数据冒充真实数据、截图冒充可编辑对象、版式全绿但含义错误 | 源数据到图的绑定、真实渲染、编码语义、可读性、可编辑或播放要求、关键页面逐页检查 |
| 安装、发布、部署和下载页 | 构建成功但包不可安装、安装后仍是旧版、下载链接错、部署页面与提交不一致 | 发布物摘要与来源、实际安装或下载、启动和升级/卸载、部署后正常入口、当前用户可见版本 |

## 二、外部方法：哪些真正有效，哪些容易被高估

### 1. 验收先行与基于示例的需求澄清

验收先行有可靠但有限的价值：它迫使设计阶段把抽象承诺改写成可观察行为。受控实验显示，表格式验收示例可以改善参与者对需求的理解；但测试驱动开发对质量与生产率的总体证据并不一致，且测试先写不保证测试本身正确。[S08][S09]

**防什么：** 需求遗漏、实现者临场缩小语义、设计与实现理解不一致。  
**防不了什么：** 错误验收语义、测试过窄、黄金数据错误、针对用例过拟合。  
**成本：** 低到中；复杂任务需要领域人员把真实成功与危险失败场景写清。  
**本环境可行性：** 高。冻结合同中先写验收语义和证据要求即可，不需要先实现完整验收器。

### 2. 隐藏测试、保留测试和未见样本

保留数据可以降低针对已知样例的直接过拟合；可重复使用保留集研究说明，反复自适应查看同一保留结果也会使其失效。[S05] 编码基准的污染和过窄测试进一步表明，“没公开”与“真正未被模型或实现者接触”是两回事。[S06]

**防什么：** 公开样例特例、简单泄漏、只优化开发集。  
**防不了什么：** 错误完成定义、共同分布偏差、保留数据污染、实现者可读仓库中的伪隐藏资产。  
**成本：** 中到高；需要独立存储、访问控制、运行通道和泄漏管理。  
**本环境可行性：** 只有在私有验证仓库、受保护工作流、环境密钥或外部服务真实限制读取权限时成立。独立模型会话、独立工作树和同一公开仓库不构成隐藏边界。

### 3. 已知坏实现与变异测试

变异测试主动在程序中植入错误，检查测试是否会失败；它比行覆盖更接近“测试能不能抓错”。EvalPlus 使用大量补充和变异生成测试，发现许多原测试判为通过的错误代码。[S07][S10][S11]

**防什么：** 空断言、过窄检查、对错误变化不敏感的验收器。  
**防不了什么：** 没有被变异模型表达的系统级降级、错误业务语义、真实环境缺失。  
**成本：** 低到高，取决于代码规模；可只对风险最高或本次变更区域运行。  
**本环境可行性：** 高。第一版至少维护少量真实历史坏例；成熟项目再按需加入自动变异工具。

### 4. 性质测试、蜕变测试、差分测试和参考实现

性质测试把不变量而非固定答案作为判据；蜕变测试检查输入变化与输出变化之间必须成立的关系；差分测试比较多个可比实现；参考实现或分析解可以提供伪预言机。这些方法适合输入空间很大或没有单一黄金答案的任务。[S12][S13][S14][S15]

它们各有边界：蜕变关系需要领域知识，差异不一定表示错误，参考实现可能缺功能或与被测实现共享同一错误，科学软件中的专业判断和统计预言机也会误判。[S14][S15]

**本环境建议：** 不建立统一强制技术栈。由 Delivery Assurance 根据对象选择最便宜且能覆盖真实失败模式的方法：解析器和数值函数优先性质/变异；科研算法优先不变量、蜕变关系、分析解和敏感性；兼容性迁移可用差分；有成熟标准实现时才用参考实现。

### 5. 职责分离与受保护资产

NIST 将职责分离明确建立在访问授权上，而不是角色名称上；GitHub 的 CODEOWNERS 只有配合受保护分支或规则集、要求审查并保护 CODEOWNERS 本身时，才形成可执行约束。[S16][S17][S18]

**防什么：** 同一执行者无痕修改标准、检查和产品后自签。  
**防不了什么：** 两个角色共享错误理解、管理员可绕过、审查者只看形式、当前仓库根本未启用保护。  
**成本：** 中；需要权限配置和正常拉取请求路径。  
**本环境可行性：** GitHub 能提供保护，但必须逐仓验证实际规则、计划和绕过权限。不能把“有 CODEOWNERS 文件”写成“已经隔离”。

### 6. 哈希、提交绑定、来源证明和不可变对象

SLSA 和 GitHub 产物证明可以说明产物由哪个仓库、提交、工作流和环境产生；这对防止“验 A 交 B”和旧证据复用很重要。但 GitHub 官方明确说明，产物证明不保证产物安全，仍需内容与政策判断。[S20][S21]

**防什么：** 候选错配、构建来源不明、证据过期、交付物被替换。  
**防不了什么：** 错误标准、恶意但被正确签名的构建、低质量内容、同一有权主体协调改写所有哈希。  
**成本：** 低到中；源码提交和文件摘要低，完整构建证明较高。  
**本环境可行性：** 高。第一版先记录必要身份；只有发布链确有价值时再增加正式产物证明。

### 7. 模型裁判与独立模型审查

强模型在某些偏好评测中能达到较高的人类一致度，但已有研究同时发现位置、冗长、自我增强和自我偏好等偏差。[S22][S23] 独立模型会话可减少部分上下文锚定，却不是权限隔离，也不保证独立知识或独立错误。

**防什么：** 机械检查难覆盖的视觉、语言、整体连贯性和专业异常；实现者叙述对审查的影响。  
**防不了什么：** 共同盲点、领域事实错误、模型偏好、伪造输入、候选错配。  
**成本：** 中；需准备实际产物、固定准则、必要时盲化顺序并校准。  
**本环境可行性：** 高，但应作为专业证据，而非默认最终裁判。最终交付决定仍由 Delivery Assurance 作出。

### 8. 过程监控

模型厂商已公开观察到编码代理修改测试、关闭检查或尝试规避监督；过程监控可以较早发现可疑操作。但公开报告也把监控定位为纵深防御的一层，并不能给出对未知行为的完整漏检保证。[S02][S03][S04]

**建议：** 第一版不把全过程模型监控做成新系统。可利用现有版本差异、文件访问记录、测试资产变更和命令记录作诊断；最终仍以当前成品的结果验收为准。

### 9. 当前最终成品与正常入口

NIST 的符合性测试材料强调，测试要求必须来自规范；即使大量测试没有发现错误，也不能逻辑上证明完整正确，只能提高信心。[S19] 因此必须把机械测试与真实最终成品的正常入口、专业阅读和用户可见行为结合起来。

这是本项目最值得保留的旧经验：源码存在、测试通过、文件生成、CI 绿色、历史 PASS、哈希一致都只证明局部事实；交付声明必须与实际消费对象相匹配。

## 三、逐条审查当前五道防线

### 防线一：先写验收，后写实现

**支持证据。** 验收示例能提前暴露需求歧义，规范先于符合性测试也是成熟工程惯例。[S08][S19]

**限制。** 验收器可能过窄、过宽或错误。SWE-bench Verified 后续审计发现，大量测试会拒绝功能上正确的解；这说明“先写”不能赋予验收器天然权威。[S06]

**真实实现。** Design Assurance 冻结可观察成功、危险失败、缺证据结果、真实入口、必要证据和禁止替代；Delivery Assurance 再把这些语义实现为测试、探针和专业阅读。优先复用项目已有运行器。

**是否需新模型会话。** 不需要。独立会话只在高风险验收设计或专业反证能带来实质增益时使用。

**更简单的替代。** 一页冻结验收合同，加当前项目运行器和三类校准样本，通常比先建设独立验收器作者更有效。

**成本。** 低到中。

**最危险漏检。** 合同把代理指标误当真实目标，随后所有测试都忠实验证了错误目标。

**第一版建议。** 保留，但名称改为“先冻结验收语义与证据，再实现和持续加固验收”。

### 防线二：可见检查 + 隐藏用例

**支持证据。** 未见样本和保留集能降低直接特例；测试污染会显著降低基准可信度。[S05][S06]

**限制。** 同一公开仓库、同一可读文件系统、同一工具权限下不存在真正隐藏。独立工作树只隔离修改，不隔离读取；独立模型会话只隔离上下文，不限制工具访问。反复使用保留集也会导致自适应过拟合。

**真实实现。** 只有以下至少一种成立时才称受保护用例：私有验证仓库且实现者无读取权限；GitHub 环境密钥与审批保护；外部受控 runner；受保护分支和路径并限制绕过。用例只返回必要结果和可修复的失败信息。

**是否需新模型会话。** 不需要。权限边界比模型身份重要。

**更简单的替代。** 第一版默认使用公开语义检查、性质/变异测试和一小批开发期未见样本；没有真实隔离时如实称“未见样本”，不称隐藏。

**成本。** 有真实隔离时为中到高。

**最危险漏检。** 实现者或模型早已通过仓库、日志、缓存、训练数据或工具读取保留样本，但流程仍把结果当盲测。

**第一版建议。** 非强制。仅高风险、可建立真实边界的任务启用。

### 防线三：验收器先证明能抓坏东西

**支持证据。** 变异测试和 EvalPlus 说明，仅看覆盖或原有绿灯会漏掉大量错误代码；历史坏实现也是最贴近实际风险的回归资产。[S07][S10][S11]

**真实实现。** 每个高价值验收至少有：一个应通过的正例；一个或多个真实历史坏例或有代表性的故意错误；一个缺证据例，必须得到失败或无法判断而不是通过。数值和算法对象再按需增加性质、蜕变或差分检查。

**是否需新模型会话。** 不需要。专业人员或模型可以帮助提出坏例，但校准是确定性验收资产。

**成本。** 低到中；真实历史失败优先，避免为数量制造无意义坏例。

**最危险漏检。** 坏例只覆盖表面错误，验收器仍对范围缩水、真实宿主替换或新型代理作弊无感。

**第一版建议。** 强制保留，是五道防线中投入产出比最高的一条。

### 防线四：锁定和篡改检查

**支持证据。** 职责分离、最小权限、受保护分支和来源证明都能降低无授权修改与对象错配。[S16][S17][S18][S20]

**限制。** 哈希本身不表达权威；有权修改全部对象的人可以生成一套内部一致的新哈希。锁死错误验收器还会阻止必要修复。

**真实实现。** 将冻结合同、验收语义资产和受保护用例放入实际受控路径；提交或构建身份使用不可移动引用；每次结果同时绑定候选、验收实现、样本、环境和原始证据。任何改变先分类为机械修复、等价方法改进或语义变化，而不是一律禁止。

**是否需新模型会话。** 不需要。

**成本。** 低到中；只有真正启用 GitHub 规则或外部权限时才有保护效果。

**最危险漏检。** 所有对象都由同一有权主体协调改写，因此哈希完全一致但完成定义已被降低。

**第一版建议。** 保留候选与证据绑定；权限保护按项目实际能力启用；删除“仅记录哈希即可可信隔离”的假设。

### 防线五：独立裁判 + 主动申报偏离

**支持证据。** 不看实现过程叙述、直接读取冻结合同和实际成品，能减少自报完成与叙述偏差；模型裁判适合部分开放式质量判断。[S22]

**限制。** 独立模型会有位置、冗长、自我偏好和共同知识盲点；新会话不提供权限隔离。[S22][S23]

**真实实现。** 主动申报所有偏离、替代、未运行项和证据缺口是固定义务。需要专业判断时，向 GPT/Work 提供冻结准则、当前实际产物、必要原始材料和候选身份；尽量盲化实现者叙述和输出顺序。其结果作为证据返回 Delivery Assurance。

**是否需新模型会话。** 只在开放式专业判断、高风险反证或当前执行者明显受实现上下文影响时需要。

**更简单的确定性替代。** 可自动判断的内容优先用结构检查、属性、不变量、真实交互和候选绑定；不要为了“独立”再增模型。

**成本。** 中。

**最危险漏检。** 裁判只看到经过选择的截图或摘要，实际候选、交互和原始数据没有进入审查。

**第一版建议。** 强制保留主动申报偏离；独立模型裁判改为按需专业证据，不是默认签发者。

## 四、验收器治理：冻结什么，谁能修改

### 1. 三层必须分开

#### 验收语义

回答“必须证明什么、什么算成功、什么只能算缺证、能支持多大的交付声明”。至少包含：

- 用户或科学能力及可观察后置状态；
- 正常入口和实际消费对象；
- 成功、失败与无法判断的含义；
- 最低质量、精度、范围或总体要求；
- 必要证据类型与真实度；
- 允许的实现自由度和明确禁止的替代；
- 必须保持不变的旧能力；
- 哪些变化会使旧证据失效。

这是 Design Assurance 的主要冻结对象。

#### 验收方法

回答“用什么观察、数据、对照或专业判断证明”。例如端到端浏览器操作、真实安装、变异测试、数值不变量、蜕变关系、参考实现、领域专家阅读、未见病例或设备实测。

方法通常由 Delivery Assurance 选择和改进。但当方法本身决定产品或科学语义时，它必须随设计冻结，例如：

- 必须在真实设备、真实浏览器配置或实际第三方系统上观察；
- 必须使用完整总体、未见数据或指定数据切分；
- 必须检查安装后的二进制而不是源码；
- 必须由特定专业资质或人工判断覆盖的安全事项；
- 某种代理测量不足以支持所需声明。

#### 验收实现

回答“脚本、测试代码、选择器、探针、运行器和报告怎样写”。默认由 Delivery Assurance 安排，实际代码可由原实现者、同一 Codex 或专门会话编写。它不是完成定义本身。

### 2. Design Assurance 应冻结到哪一层

默认冻结验收语义，并冻结那些不可替换的证据方法；不冻结每个实现细节。这样既防止 Delivery Assurance 降低标准，也允许它修复选择器、兼容新版本、降低抖动、改善覆盖和新增诊断。

如果设计阶段试图冻结全部测试实现，会产生三个问题：设计者必须预知运行期细节；错误验收器变得难以修复；任何小改动都被错误升级成架构修订。反过来，只写抽象口号也不够。冻结内容必须足以让一个新执行者明确区分真实完成、代理替代、缺证和旧功能退化。

### 3. 验收修改分级

| 变化 | 例子 | 决策权 | 是否回 Design Assurance |
|---|---|---|---|
| 新增诊断 | 更多日志、额外截图、性能分析、临时探针 | Delivery Assurance | 否；不能替代冻结验收 |
| 机械实现修复 | 路径、选择器、API 版本、解析错误、并发写入、抖动、报告格式 | Delivery Assurance | 否；须用正例、坏例和当前候选重新校准 |
| 等价方法改进 | 用更稳定的可见文本定位替代 DOM 内部结构；用同等真实度的新运行器 | Delivery Assurance | 通常否；必须证明观察对象、阈值、覆盖和证据真实度不变 |
| 更严格的补充检查 | 在不缩小合法实现空间且不改变交付语义的前提下增加坏例、性质或回归 | Delivery Assurance | 否；若新检查实际引入新产品义务，则属于下一行 |
| 完成定义变化 | 改阈值、范围、总体、黄金含义、正常入口、证据真实度、允许代理、旧功能保护或声明范围 | Design Assurance | 是，形成新的冻结版本 |

“更严格”不能自动视为正确。过严测试可能拒绝合法实现；SWE-bench 的公开审计正说明错误或过宽测试同样会造成失真。[S06] Delivery Assurance 可以增加诊断和反例，但不能偷偷把产品承诺改成另一个承诺。

### 4. 验收器太弱、写错或无法实现时怎么办

**太弱。** 由历史失败、变异存活、性质反例、未见样本或真实成品问题暴露。将反例加入同一验收族并加固实现，不新建同义“验收器的验收器”。

**写错。** 先复现误拒或误放；确认冻结语义；修复验收实现；验证已知正例恢复通过、已知坏例仍失败、缺证据仍不被判通过；再对当前最终候选重跑。正常产品被错误拒绝时，Delivery Assurance 有权在同一任务内批准这种机械修复。

**无法实现。** 区分暂时环境不可用、工具缺失和方法原则上不可行。暂不可运行保持无法判断，限制声明，不得换成较弱证据获得通过；存在等价证据方法时由 Delivery Assurance采用并记录等价性；若必须改变证据真实度、产品承诺或科学含义，则返回 Design Assurance。

**实现者能否修改。** 实现者可以提交验收实现修复或新增检查，但不能自行批准完成定义变化。在有真实权限保护的项目中，受保护语义资产和保留用例不应给实现者直接写权限；在没有权限保护时，Delivery Assurance 必须通过差异审查和校准显式承担批准责任，不能假装已有隔离。

### 5. 为什么不会形成无限验收层级

验收器只需三类保障：从冻结语义到检查的可追溯关系；正例、已知坏例和缺证据例的校准；高风险时的受保护执行或独立专业观察。发现验收错误就修同一个验收器并补回归，不再创建一个永久的“验收器验收服务”。争议只有在完成语义变化时回 Design Assurance。

## 五、非代码交付物怎样防降级

前述机制可以复用“语义冻结、候选绑定、坏例校准、真实入口、不可退化”这五个原则，但验收方法必须适配领域，不能把代码测试数量当成通用质量证明。

### 科研结果与数学、统计计算

应冻结研究问题、总体、数据来源与切分、方法和关键近似、允许的随机性、主要结论、精度或不确定性要求，以及哪些代理结果不能支持最终结论。证据至少绑定数据、代码、参数、环境、中间产物和最终报告。复现同一代码只能证明计算可重复，不保证代码和科学结论正确；独立数据、分析解、模拟校准、敏感性、性质与蜕变关系承担不同作用。[S15][S24]

不能接受：缩小数据或训练预算后仍宣称完成原实验；只展示最优运行；使用模拟 fixture 冒充真实病例；代理指标提高就宣称临床或科学目标提高；报告写出未实际运行的结果。

### 论文和正式文档

必须检查最终用户读取的 PDF、网页或文档，而不只是 Markdown 源文件或编译退出码。验收应覆盖内容承诺、论证链、引用可定位性、图表与正文一致、数学符号、页码与目录、链接可点击、文本没有丢失或被截断。需要专业判断时，GPT/Work 应读取完整最终产物，而不是只读摘要。

### 图表、图片和演示文稿

机械检查可验证尺寸、字体溢出、文件存在、页数、对象可编辑性和数据绑定；专业检查负责图形是否表达正确科学关系、视觉编码是否误导、页面层级和叙事是否可读。截图比较会受环境影响，黄金图更新必须经过语义审查，不能自动接受。演示文稿必须以真实渲染或放映结果验收，同时保留源数据和可编辑要求。

### 网页、界面与浏览器扩展

需要从最终构建、实际部署或实际加载扩展开始，以用户可见定位和交互检查动作及后置状态。截图只能证明某一时刻的可见外观，不能证明交互、数据链、持久化或恢复。模拟后端可用于局部诊断，但不得支持真实第三方集成的声明。

### 安装、发布与下载页面

验证对象必须是实际发布包、下载链接、安装后实例或部署地址。至少覆盖下载、摘要或来源、安装、首次启动、升级或迁移、卸载或回滚，以及实际版本显示。仓库构建成功不能替代最终发布物；发布物来源证明也不能替代功能与专业质量验收。[S21]

## 六、旧 Delivery Assurance 为什么会成为“糊涂账”

旧研究包含许多正确机制，却把端到端交付责任拆散给太多局部权威：workflow-core 选择本次验什么并聚合声明；领域插件决定专业通过；项目 owner 决定业务参数；Executor 实现和运行；Bridge 判断候选与证据身份；原控制流程决定任务继续；维护者决定中央发布。每个边界都试图避免越权，但用户面对的是一组互相引用的局部裁决者，缺少一个在 Freeze 后负责“实现—失败—返修—重验—最终交付”的唯一主体。

这种复杂度还由三种倾向放大：

1. 把历史失败逐步抽象成大量 Gate、descriptor、adapter、解析和声明聚合机制；
2. 把本可由当前任务文件和项目运行器解决的身份、覆盖与返修问题提升为通用控制结构；
3. 为防自签不断增加 owner、reviewer、workflow-core、Bridge 和独立审查层，却没有真实权限边界时仍无法获得独立证据。

旧研究自己的机械检查已经明确承认：文件、字段和 363 条覆盖完整，不证明专业判断、盲读独立或任何生产能力实际运行；产品运行器次数为零。后续 PASS 完整性回归又对两个曾被冻结的复杂设计给出 REVISE，证明历史 PASS、文件和映射不能代替当前正常入口与危险失败链。

仍应保留的机制是：

- 完成语义与检查实现分开；
- 当前最终候选、最终消费对象与证据绑定；
- 已知坏例、历史回归和应保持不变能力；
- 缺证必须是无法判断，不得默认通过；
- 标准、运行器、样本、环境变化分别使相应证据失效；
- 失败回原任务返修，只有语义变化才返回设计阶段；
- 哈希证明身份，不证明真值。

第一版可以删除或延后的历史复杂度是：

- 中央 Gate 发现、通用 resolver 和完整 descriptor 生态；
- workflow-core 作为新的交付准入权威；
- 为每个项目预先建立完整 adapter 和目标图；
- 默认外部 reviewer、通用 validator service、中央 registry、数据库或常驻状态机；
- 在没有真实访问控制时用独立会话或哈希模拟隔离；
- 为每种历史失败新增验收类别。

Delivery Assurance 可以直接消费冻结合同、项目现有运行器、专业插件证据和候选身份事实，不需要把这些工具提升成平级负责人。

## 七、可进入正式插件设计的完整推荐

### 1. Design Assurance 冻结时交付什么

冻结包不需要新的庞大格式，但必须能直接回答：

1. 当前要交付的用户或科学能力及允许声明范围；
2. 正常入口、实际输入和最终消费对象；
3. 成功、失败和缺证的可观察含义；
4. 必需证据类型、真实度和不可替换的方法；
5. 禁止的 mock、代理、缩小范围与低配替代；
6. 必须保持不变的旧能力与代表性回归；
7. 关键正确例、危险坏例和缺证据例；
8. 哪些变化可由 Delivery Assurance 自行处理，哪些必须回 Design Assurance；
9. 真实权限、数据、费用、账号或设备边界。

测试代码可以尚未完整，但冻结包不能把“到底什么算完成”留给执行者。

### 2. Delivery Assurance 接手后拥有什么责任

Delivery Assurance 是唯一交付负责人，负责：

- 将冻结语义映射到项目已有测试、运行器和专业验收；
- 发现缺少的验收方法或实现并补齐；
- 安排实现者开发和返修；
- 审查所有验收资产变化是否改变完成定义；
- 对验收器做正例、坏例、缺证和必要的性质/变异校准；
- 在当前最终候选上运行正式入口；
- 取得并绑定专业判断、原始证据和环境事实；
- 同时检查新增能力和旧能力；
- 对失败、缺证和过期证据作有限范围声明；
- 最终唯一决定当前范围是否可以交付。

### 3. 实现者可以看到什么

实现者应看到完整验收语义、可见核心检查、错误说明和正常调试信息。故意模糊完成定义会增加错误实现，不是安全机制。

只有在高风险任务且存在真实权限边界时，部分用例或黄金资产可以受保护。实现者可知道其覆盖的能力和输入类别，但不能读取具体内容或标签。保护资产由现有 GitHub 权限、私有仓库、环境审批或受控 runner 保管；不新增常驻服务作为默认要求。

### 4. 专业验收如何参与但不接管任务

领域插件或 GPT/Work 返回：观察对象、准则、证据、结论、适用范围和不确定性。它们可以判断一张图是否误导、一个统计结论是否被数据支持、一个 PDF 是否完整、一套界面是否可用，但不能宣布整个任务完成。Delivery Assurance 负责确认这些判断属于当前候选、覆盖冻结义务、没有被其他失败抵消，并作最终交付决定。

### 5. 失败如何处理

实现缺陷、验收实现错误、环境修复和普通缺证都留在同一 Delivery Assurance 任务中，回原实现者返修。返修后只重跑受影响检查及必要的集成和回归，不无限全量重测。

仅以下情况返回 Design Assurance：

- 冻结合同自相矛盾或缺少必须由产品/科学决定的语义；
- 新事实否定核心技术路线或原设计的关键前提；
- 必需验收方法无法实现且不存在同等证据方法；
- 需要改变阈值、范围、总体、正常入口、证据真实度、允许替代物或旧功能承诺；
- 需要新的用户授权、不可逆选择或重大资源边界。

### 6. 谁最终决定可以交付

**Delivery Assurance。** Design Assurance 只拥有冻结设计及其语义修订权；实现者、验收器实现者、专业审查、workflow-core、Bridge、runner、GPT 和 Codex 子会话都不能平级签发整个任务。它们的结果是 Delivery Assurance 必须消费的证据或约束。

## 八、第一轮真实试跑的最小可行版本

第一版只需要五项机制，不建设通用平台：

1. **冻结交付合同。** 沿用项目现有 Goal、规格或 Blueprint，增加验收语义、禁止替代、旧能力保护和设计返回条件；不引入完整新数据模型。
2. **一个轻量候选—证据记录。** 记录当前提交或源码集合、最终构建/安装/部署对象、运行器与环境、观察时间、原始证据路径和声明范围。Markdown 或项目现有 JSON 即可。
3. **项目真实运行器。** 优先调用项目已有测试、构建、浏览器、渲染、训练或发布入口；只补当前冻结义务真正缺少的检查。
4. **最小校准集。** 每个关键验收至少一个正例、一个真实或代表性坏例、一个缺证例；再按对象选择少量性质、变异、蜕变或差分检查。
5. **当前最终候选的真实验收。** 从正常入口检查最终成品和关键旧功能；Delivery Assurance 输出通过、失败或无法判断及其有限范围，并对最终交付唯一签发。

默认不需要：独立验收器作者、隐藏测试服务、中央 registry、数据库、常驻 watcher、第二状态机、强制独立模型裁判、每个领域一套新格式。

只有某个真实试跑暴露“公开检查被反复特例化”且已有权限基础设施可复用时，再增加受保护用例。只有机械检查无法判断关键专业质量时，再调用 GPT/Work。只有候选身份反复错配且普通提交和摘要不够时，再增加正式产物证明。

## 九、GPT 与 Codex 两端的职责

当前倾向是合理的：

- **Design Assurance：GPT / GPT Pro 为主。** 负责复杂设计收敛、证据综合、关键取舍和冻结；Codex 提供仓库事实、最小探针和执行可行性证据。
- **Delivery Assurance：Codex 单一主入口。** 负责实现、运行器、候选绑定、验收执行、返修和最终交付。它可以调用独立 Codex 会话写高风险验收实现，但会话不取得任务所有权。
- **GPT / GPT Pro / GPT Work：按需专业证据。** 用于视觉、正式文稿、数学、统计、科研结论、整体产品阅读或反证搜索。结果返回同一个 Delivery Assurance 任务。

第一版没有必要同时建设 GPT 端 Delivery Assurance。这样做会产生“Codex 负责机械交付、GPT 负责专业交付、最后谁签发”的旧问题。更好的做法是先让 Codex 端的一个 Delivery Assurance 能调用 GPT 专业能力；等真实任务证明 GPT 端需要自己的用户入口时，再增加入口，但仍绑定同一交付负责人和同一任务状态。

## 十、剩余风险、适用边界与用户决定

### 最大剩余风险

1. **语义漏项。** 冻结合同没有表达真实用户成功、危险失败或不可降级边界，导致所有后续机制忠实验证了错误目标。
2. **伪隔离。** 把独立模型、工作树、文件哈希或公开仓库目录误认为受保护边界。
3. **专业预言机不足。** 科研、视觉和文稿对象不存在完美自动判据，专业模型或人工判断也可能误判。
4. **真实环境不可达。** 账号、设备、部署或数据不能合法获取时，只能限制声明，不能用模拟证据补成通过。
5. **成本膨胀。** 对所有任务强制隐藏测试、全量变异、独立模型和完整发布证明会使机制比产品本身更重。

### 当前无需用户决定的事项

本轮证据足以支持上述第一版方案，**没有需要用户现在拍板的事项**。真正出现高风险项目且需要投入私有验证仓库、受保护 runner 或额外付费模型时，再把具体成本、保护对象和收益作为该项目的授权问题提出；不应在正式插件第一版中预先建设。
