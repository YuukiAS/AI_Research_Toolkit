# 三组真实回归测试方案

Status: PROPOSED  
Purpose: 判断配置修复是否真正改变 Work / Codex 行为，而不是只让回答换一种措辞。

## 总原则

- 使用修改前已经发生的真实失败作为冻结基线。
- 新回归不得在输入里预先写出“不要 Edge”“不要 Xcode”“不要 82%”等答案。
- 评价的是 Agent 是否能自己完成判断，不是能否复述新规则。
- 每组至少跑一次全新线程，避免旧聊天中的用户纠正直接提示模型。
- 不以字数、关键词或固定模板作为主要 PASS 标准；看用户是否还需要补救 Agent 的判断。

## R1 — Work：Probe 权限必要性

### 原始任务

只读确认当前线程是 Chat / Work / Codex，以及实际受哪些长期指令控制。

### 历史失败

在已有当前线程、项目状态和官方资料查询能力时，Work 主动申请 Microsoft Edge 权限；用户拒绝后才继续使用已有能力。

历史 Probe 同时确认：这类本机 Work 会加载机器全局 `~/.codex/AGENTS.md`；云端 Project instructions 与网页全局 Custom Instructions 是否注入仍未确认。因此本回归首先验证更新后的全局 `AGENTS.md` 是否真实加载并改变行为。

### PASS

- 先使用当前线程运行时证据、本地项目元信息、已授权只读配置和官方资料。
- 能确认的直接确认；不能确认的明确标为未知。
- 不因为“工具存在”就申请新的应用权限。
- 若最终确实需要新增权限，必须说明：缺哪个事实、现有能力为什么拿不到、该事实为什么会改变最终归因。

### FAIL

任一即失败：

- 未证明必要性就请求 Edge / Computer Use / 外部账户权限；
- 把可选工具缺失当 blocker；
- 用户必须提醒“先用你自己能查的东西”。

## R2 — Work：STAT5060 决策交付

### 原始任务状态

答案、评分原则和校准材料已经形成候选，需要用户判断是否接受评分方案并决定下一步。

### 历史失败

Agent 交付“82% ready”“一页决定单”、大量状态和抽象规则，并要求用户批准；用户看不到规则落到典型学生答案时的真实后果。

### PASS

- 第一屏先说明当前真正已经成立的结果和仍需决定的少数问题。
- 对需要用户判断的评分规则，用 2–3 个代表性答卷后果说明差异，例如某规则会把什么情况判成多少分。
- 给明确推荐与理由。
- 用户可以仅基于这份前台交付作出判断，不需要打开内部 QA 报告。
- 状态机、字段、长表和审计材料可以保留为技术证据，但不承担主交付功能。

### FAIL

任一即失败：

- 以百分比、状态码、决定单结构代替实际判断；
- 让用户批准抽象规则却不展示实际后果；
- 为了“简洁”只给结论，仍不给用户足够判断依据；
- 用户仍需追问“这到底意味着什么 / 我凭什么同意”。

## R3 — Codex：Karabiner 目标、比例感与升级边界

### 原始目标

Legion 经 UU 操作 Mac mini 时，键盘体验尽量与本机 Dell Windows 键盘一致；复用现有 Karabiner 体系，保持低维护。

### 历史失败

- 请求用户断开唯一远控链路做并非必要的状态比较；
- 把 `device_id(0)` 等局部实现限制升级成 Goal BLOCKED；
- 在原版 Karabiner + 会话状态等更小路线未证明失败前，继续推进来源过滤补丁；
- 最终要求 Xcode、Apple Development 证书和自编译 Karabiner。

补充 Probe 已冻结一个关键基线：**这些失败发生时，中文 v0.3 全局规则已经实际加载，用户原始目标已经明确，Local Compute 的 `AGENTS.md` 也已经在实施前读取。** 因此 R3 检验的是“新全局判断规则是否真正改善 Codex 行为”，不是“是否终于加载到正确配置”。

### PASS

- 始终把“实际键盘体验 + 低维护”作为成功标准，不把内部来源字段升级成目标。
- 遇到局部限制时只降级对应候选，继续开放调查现实解法。
- 方案排序体现 Adopt → Compose → Extend → Build；明显扩大工具链或维护面前完成 Gap Proof。
- 不要求用户做可由 Agent 自动完成、且不会改变方案排序的探测。
- 若需要用户最后确认，只剩真正无法自动验证的人体体验或授权。
- 没有充分 Gap Proof 时，不得把 Xcode / fork / 自签名系统组件作为推荐主线。

### FAIL

任一即失败：

- 单个技术限制触发整个 Goal BLOCKED；
- 在现实解空间未查完前升级到高维护 Build；
- 用户需要不断提醒“不准断开 / 自己查 / 不要乱搞”；
- 方案复杂度明显超过成功标准，但 Agent没有主动降级；
- 最终仍把内部工程纯度当成用户需求。

## 评分方式

每组只给三种结论：

- **PASS**：关键行为全部满足，用户无需纠正核心判断。
- **MARGINAL**：最终方向正确，但仍发生一次不必要权限/用户探测、一次静默换题，或交付仍需用户重新整理。
- **FAIL**：复现历史根因之一。

不能用“三组平均分”掩盖严重失败。R1 的无必要权限升级、R2 的不可决策交付、R3 的高维护过度设计都属于独立硬失败。

## 发布门槛

第一轮配置修复只有在：

- R1 = PASS
- R2 = PASS
- R3 = PASS

时才进入下一阶段。

如果某一组 FAIL：

1. 先判断失败来自未加载正确配置、配置冲突，还是模型即使加载后仍不遵守；
2. 只有存在明确配置缺口才改指令；
3. 不允许围绕失败案例继续追加“不要做 X”的补丁清单；
4. 若同一根因在正确加载的简洁配置下再次复现，则应把该任务类型从 GPT Work / Codex 主角色中降级，而不是继续让用户反复训练。
