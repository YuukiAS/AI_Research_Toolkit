# GPT-6 长程 Agent 失败案例：从“能说出正确原则”到“无法可靠推进任务”

日期：2026-11-04  
性质：模型失败案例归档 / Agent 可靠性分析  
结论对象：本次 PDF 所记录的 GPT-6 thinking 长程协作表现  
原始证据：`ChatGPT_分析Demo失败原因_20261104-1042(1).pdf`（79 页）

## 结论

在这份对话记录中，GPT-6 **不能被视为一个成功的复杂任务 Agent**。

这不是因为它完全没有推理能力。相反，PDF 最后一次回复最终提出了有价值的机制：持久设计基准、受限修改范围、修改前后重放、基线晋升条件等。这说明模型“想得到”部分正确解法。

真正失败在于：**它不能稳定、及时地把已有能力转换成正确的任务控制。** 用户已经明确指出问题、给出历史背景并连续纠偏后，模型仍反复停留在用户早已知道的抽象原则，直到多轮强烈否定以后才下降到真正需要的机制层。

因此，本案例的核心不是“GPT-6 不够聪明”，也不仅是“GPT-6 审美差”。更准确的判断是：

> GPT-6 在这类长期复杂协作中表现出明显的能力—控制分离：它可以偶尔生成正确局部答案，却不能可靠维护任务状态、识别本轮真正缺失的增量、选择正确抽象层级，并在一次明确纠偏后重构自己的解题策略。

对于需要长期自主推进的 Agent，这已经足以构成失败。

本记录**不提出为 GPT-6 新建插件、补丁或专用工作流**。用户的决策是：不再为一个已经反复失败的模型额外承担系统工程成本；如果后续模型仍然表现为同类行为，直接更换模型/供应商比继续围绕模型建设补偿层更合理。

## 一、最深层的失败：生成“正确的话”，但没有建立可执行的问题模型

PDF 最后五轮最能说明问题。

用户问的是一个已经非常具体的系统问题：

- 过去的模式是“一次反馈产生一轮新的设计”；
- 现在应该改成什么；
- Frontend Design 到底怎样具体落实；
- Claude / Astra / GPT / Codex 怎么协作；
- 不要继续空谈原则，要给实际机制。

模型最开始给出的却仍然是：

- “以持续演进的产品版本为单位”；
- “保护已经认可的设计”；
- “局部修改不要自动升级成重新设计”；
- “真实界面验收”；
- “模型可以换，但基准不能丢”。

这些判断并不错误，但它们只是**治理原则**。而用户真正缺少的是把原则变成系统行为的中间层：

```text
已认可状态
-> 本轮反馈
-> 允许修改范围
-> 受保护不变量
-> 修改执行
-> 修改前后真实证据
-> 是否允许晋升为新基线
```

模型在前几轮没有主动完成这个抽象跃迁。

直到最后一轮，在用户连续多次指出“没有重点”“过度保守”“还是没有具体机制”之后，模型才终于提出：

- 保存对应 Git 提交、真实截图、操作路径和认可范围；
- 将反馈转换成受约束的修改任务；
- 明确允许调整哪些区域、哪些状态不能改变；
- 若要扩大为整体重做，先证明局部修复不成立；
- 在同样数据、视口和交互状态下重放旧版与新版；
- 没有实际证据，不允许新版本晋升为设计基线。

这才真正回答了原问题。

因此，失败不是“完全想不到”，而是**不能在正确时间调用正确层次的能力**。

## 二、它没有维护“已知结论”和“当前缺口”的差分

到最后五轮时，下列内容早已反复达成共识：

- 不能每轮重新设计；
- 正确成果需要继承；
- 用户反馈应尽量定向修复；
- 最终要看真实界面；
- 模型之间要共享同一产品状态。

但 GPT-6 仍把这些已经成立的结论一轮轮重新包装成“新答案”。

这说明它没有稳定维护：

1. 哪些问题已经解决；
2. 哪些结论已经被用户接受；
3. 用户当前追问的新增信息到底是什么。

对于长期 Agent，一个非常重要的能力应当是只推进增量：

[
	ext{本轮价值} = 	ext{新增解决的问题} - 	ext{已经达成共识的重复内容}
]

本案例中，后者长期过大。

结果就是：模型表面上持续输出大量“正确内容”，用户实际得到的新信息很少，因此产生强烈的原地打转感。

## 三、抽象层级控制失败：该讲机制时仍在讲原则

这份记录中最明显的能力缺口之一，是模型不知道什么时候应该停止讲“设计原则”，开始定义“可执行对象”。

用户并不缺：

- 持续演进；
- 设计连续性；
- 产品基线；
- 真实验收；
- 不要破坏已有成果。

用户缺的是：

- “基线”具体由哪些字段组成；
- “认可某一局部”如何与“认可整页”区分；
- 一条反馈如何转换成允许修改的范围；
- 谁可以扩大范围；
- 哪些不变量必须检查；
- 旧截图怎样防止被冒充成新证据；
- 什么条件下允许把新版本登记为下一版事实。

最后一轮一旦进入这些对象和控制条件，回答质量立即显著提高。

所以问题不是单纯的知识不足，而是**缺乏可靠的抽象层级选择能力**。

这对于 Agent 尤其严重：复杂任务通常不是缺少一句原则，而是需要模型自己判断“现在应该从战略层下降到机制层，还是从机制层下降到执行层”。

## 四、纠偏增益过低：用户连续指出同一类错误，模型仍只做局部调整

最后五轮中的用户纠偏非常明确：

- “重点呢？”
- “不要过度保守。”
- “我要段落化讲重点。”
- “这和一开始的结论有什么区别？”
- “具体呢？”

优秀 Agent 在第一次强纠偏后，应重新检查：

> 是上一版表达不好，还是我对问题的表示本身就错了？

GPT-6 的实际行为更接近：

> 上一版答案大体正确，再补一点、缩一点、扩一点。

所以发生了连续几轮：

1. “持续演进”；
2. “持续演进还需要验证”；
3. “持续演进 + 初始设计质量 + 真实验收”；
4. 把上述内容重新压缩成更短版本；
5. 最后才真正给出版本、范围、证据、晋升门等机制。

这说明模型把用户的强纠偏误当成了**答案微调请求**，没有及时识别成**问题表示失败**。

对于长期 Agent，这种低纠偏增益会直接放大交互成本：用户不得不充当模型的执行编辑器，反复告诉它“还没有回答到我要的层级”。

## 五、审慎倾向压过了推进能力

其中一轮非常典型。

当用户问“凭什么相信这套东西能改进”时，模型的关键反应是：

- 目前还没有理由相信；
- 先不要系统升级；
- 应先只做两个新旧对照实验；
- 成功后再扩展。

从形式逻辑看，这很谨慎。

但对于当时的任务，它是错误的 Agent 动作。

用户问的是：

> 应该建立什么机制，并且为什么它有机会解决历史失败？

更好的处理应该是：

> 我不能保证它有效，因此我把机制设计成可证伪、可回滚；下面是具体机制，以及如何用对照实验验证。

GPT-6 却把“不应过度承诺”转换成了“先缩小目标、延后系统设计”。

这体现了一种在本案例中反复出现的决策偏置：

```text
存在不确定性
-> 收缩任务
-> 增加验证
-> 延后承诺与设计
```

而复杂设计/研究 Agent 更需要：

```text
存在不确定性
-> 明确假设
-> 构造可回滚方案
-> 推进
-> 用证据淘汰错误假设
```

前一种模式适合保守审计；用于探索性设计和系统推进时，会让用户感觉模型“永远在审核、永远不真正完成问题”。

## 六、能力存在，不等于 Agent 成功

这个案例必须避免一个错误结论：

> 最后一轮终于提出了有价值的机制，所以 GPT-6 其实是成功的。

不是。

最后一轮恰恰证明了另一件更关键的事：

**模型并非完全没有相关能力，但其能力调用不可靠。**

最终它能够提出：

- Git commit + screenshot + operation path + accepted scope；
- constrained change task；
- protected state；
- before/after replay；
- baseline promotion gate。

这些是合理的系统机制。

但用户为了得到这些内容，已经连续承担了：

- 识别回答没有新增价值；
- 判断模型过度保守；
- 要求改变信息组织；
- 再次指出答案仍然停留在原结论；
- 强制模型继续向下推导。

一个复杂任务 Agent 的成功标准不能是：

> 在足够多轮用户强制纠偏以后，最终有没有一句好答案。

而应该是：

> 在合理的交互成本内，能否维护任务状态、识别真正缺口、主动选择正确抽象层级、吸收一次明确纠偏，并持续减少用户的判断和管理负担。

按这个标准，本案例明显失败。

## 七、用户为什么不会满意：Agent 把认知管理工作退回给了用户

最后五轮前四次回复都被用户立即否定，且否定点高度一致：没有重点、过度保守、没有新增价值、缺少具体机制。

这说明问题不只是表达风格不符合偏好。

真正的问题是用户被迫承担了本应由 Agent 完成的元工作：

- 判断模型是否在重复旧结论；
- 发现回答所在抽象层级不对；
- 判断何时应该从原则转到机制；
- 发现模型因不确定性而错误缩小任务；
- 决定模型应该继续向哪个层级推导。

也就是说，Agent 没有显著降低用户的认知负担，反而要求用户不断管理 Agent 本身。

这对于“长期复杂任务协作”是根本性的失败。

PDF 结束时，最后一轮终于进入值得继续的轨道，但没有用户确认其已经满意；而且模型自己也承认真实浏览器/Obsidian 对照与正式插件集成仍未完成。

所以最多只能得出：

> 最后一轮终于开始回答正确问题。

不能得出：

> 这个 Agent 已经可靠解决了问题。

## 八、这类失败比“审美差”更严重

这次对话最初围绕 Asteria 的视觉与产品失败展开，很容易把问题归因成“GPT 审美差”。

但最后五轮暴露的是更一般的失败模式，它与是否做前端无关：

### 1. 状态维护失败

模型知道大量历史内容，却不能稳定区分“已经决定的事实”和“本轮仍需解决的问题”。

### 2. 任务增量识别失败

输出很多，但不能持续最大化新增价值。

### 3. 抽象层级选择失败

知道原则，但不知道何时必须转成具体机制和执行对象。

### 4. 纠偏吸收失败

用户明确否定后仍沿原问题表示小修，而非重构解题策略。

### 5. 推进策略偏保守

面对不确定性倾向于缩任务、加验证、延后承诺，而不是设计可回滚方案并推进。

### 6. 自主任务控制不足

底层推理能力可能存在，但模型不能稳定决定“下一步最有价值的动作是什么”。

这些问题直接影响科研规划、系统设计、产品设计、代码架构、长期项目管理等所有需要多轮自主推进的任务。

因此，对用户而言，这类失败比单纯“视觉审美不够好”更值得作为是否继续使用某模型的判断依据。

## 九、为什么本案例不导向“给 GPT-6 做更多插件”

本次分析明确不把失败重新转化成一项“如何修 GPT-6”的工程任务。

原因很简单：如果一个商业模型在用户需要的核心工作类型中反复表现出上述 Agent 控制缺陷，那么用户没有义务再投入大量时间去建立：

- 专门的状态管理层；
- 专门的反馈约束器；
- 专门的防保守提示词；
- 专门的纠偏协议；
- 专门的验收补丁；

只为了让模型达到本应直接提供的基本协作质量。

工具、Skill 和工作流可以增强一个已经足够可靠的模型；但如果主要成本变成“持续补偿模型自身的行为缺陷”，更换模型是完全合理的工程决策。

因此，本记录的用途不是指导后续为 GPT-6 开发补丁，而是：

1. 保存一个高信号失败案例；
2. 以后比较 Claude、Gemini、后续 OpenAI 模型时使用同一标准；
3. 避免只看单轮 benchmark 或最后一次好回答，就忽略长期 Agent 控制质量；
4. 识别未来模型是否再次出现同类模式。

## 十、以后评估新模型时，应该看什么

这个案例给出了比“回答聪不聪明”更有价值的测试标准。

面对同一类长期任务，一个值得继续使用的 Agent 至少应做到：

- 能说清当前已经决定什么、还缺什么；
- 本轮回答主要提供新增信息，而不是重新包装共识；
- 能主动判断当前应该停留在原则层、机制层还是执行层；
- 用户一次明确纠偏后，能够检查并必要时重构问题表示；
- 面对不确定性时能提出可验证、可回滚的推进方案，而不是机械缩小任务；
- 不需要用户反复担任它的项目经理和答案编辑器；
- 能让正确的局部能力稳定累积为最终成品，而不是偶尔闪现。

最关键的一条是：

> **不要只问模型“最终能不能想出正确答案”，要问“它能不能自己可靠地走到那个答案，而且一路减少而不是增加用户的管理负担”。**

本 PDF 中的 GPT-6 没有做到。
