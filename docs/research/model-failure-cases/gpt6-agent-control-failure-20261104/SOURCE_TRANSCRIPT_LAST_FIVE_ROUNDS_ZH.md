一、以后不再让一个 GPT 对话同时承担四种职责

过去的模式是：一个 GPT 对话长期统筹，用户反馈后，它自己解释问题、决定是否重新设计、撰写下一轮提示词，再让其他模型或 Codex 实施。下一轮又由这个对话根据新结果重新裁决。

这个模式有两个根本缺陷。

首先，模型既是方案提出者，又是返修决策者，容易用自己的新理解覆盖此前的决定。其次，重要产品状态实际上保存在对话上下文里，而不是一个所有模型都能准确读取、共同维护的设计基准。

我建议以后改成：

产品仓库保存当前设计事实，设计模型负责提出具体改动，Codex 负责实施，独立审查按风险触发，用户只做真正影响产品方向的决定。

这里特别要区分：持续负责人不等于永远使用同一个模型。

Claude、GPT Astra、GPT 极高都可以承担高价值的设计判断，但接手时必须继承相同的用户决定、视觉基线和已接受的交互。不能因为换了模型，就获得重新设计整个产品的权力。

这样 Claude 额度用完，可以换 GPT Astra；GPT Astra 处理不好某个高价值视觉问题，也可以交 Claude 独立判断。换人不再等于换产品。

关键不是多模型相互监督，而是所有模型都受到同一份已确认设计的约束。

二、最重要的改造：每次反馈先判断“改什么”，而不是先决定“下一轮怎么设计”

Frontend Design 收到反馈后，首先应检查当前产品、已确认的设计、实际画面和用户这次指出的问题。

随后只允许进入三种处理方式。

第一种是局部修复。 例如字号太小、图例不清楚、节点重叠、点击后无法返回。这些问题不需要新设计候选。模型定位问题，明确哪些部分不能改变，Codex 修复并重新渲染。如果只是 CSS、事件处理或布局错误，甚至不需要重新调用昂贵的设计模型。

第二种是有限范围的设计调整。 例如 Atlas 的论文局部关系图不够清楚，需要改变论文节点、边和详情之间的信息组织。设计模型只调整相关视图及受到影响的相邻状态，不重新设计整个知识库。

第三种才是方向级重新设计。 只有当原有信息架构确实无法支持核心用户任务时，才允许提出新方向。模型必须指出原架构为什么不能通过局部修改解决，并给出可比较的替代方案。用户确认之前，不得开始整体重做。

这三种不是简单按照修改文件数量分类，而是按照产品语义改变了多少分类。

例如你说“Atlas 这里的线太多”，默认应该先定位哪些边缺少科学意义，而不是直接删除所有关系。

反过来，如果用户明确说“这个产品方向全部不要了”，也不应机械阻止重新设计。

这个区别恰恰是过去没有稳定做到的。

过去 Asteria 的灾难暴露了三个根本缺陷：第一次设计经常判断错，后续返修又破坏正确的部分，最后验收还会错误宣布成功。 只解决其中一个，确实不够。我前面把改造范围收得太窄了。

一、真正应该改变的是整个设计工作方式

以前是：

一个 GPT 对话统筹 → 提出设计 → Codex 实现 → 用户指出问题 → GPT 重新规划 → 再交 Codex。

新的模式应该是：

产品需求 → 确认设计方向 → 建立可运行基线 → 持续定向改进 → 真实界面验收 → 更新基线。

核心变化是：不再以一次 GPT 对话或一次设计任务作为工作单位，而是以一个持续演进的产品作为工作单位。

对话可以结束，模型可以换，设计负责人可以从 GPT Astra 换成 Claude，但产品已经确认的部分、当前画面、用户反馈、交互行为和版本历史不能丢。

二、Frontend Design 应该一次性补齐三种能力

第一，真正提高初始设计质量。

现在的插件已经会讨论字体、配色、布局和视觉方向，但过去证明，“避免普通仪表盘”“保持信息层级”这类原则远远不够。

改进后，设计模型必须先理解用户究竟在操作什么对象、需要理解什么关系、为什么使用图而不是表格、哪些信息应该同时可见。

对于复杂产品，不能让模型直接根据文字生成整套界面。应该先使用真实内容完成一两个关键场景的视觉探索，必要时给你两种有实质差异的方向。

这里要保留设计创造力。 不能因为过去出现过卡片，就机械禁止所有卡片；不能因为出现过无意义连线，就减少一切图形关系。

模型要解释的是：为什么这种表现形式适合这个用户任务，并用实际画面证明。

第二，让每一次返修都继承已经正确的设计。

这是最大的改造点。

每个产品只需要维护一份权威的当前设计基准，记录当前版本、已确认的界面和交互、关键截图、尚未解决的问题。

以后你说“这里太密了”，AI 先读取这个基准，再决定具体怎么调整。默认保护已经正确的部分，而不是重新设计整个产品。

例如 Blueprint 实现台已经被你局部认可，后续修改系统图时，Codex 就不能顺手把实现台改回普通开发界面。

如果确实需要整体重设计，也完全允许。但必须是明确的产品决策，而不是模型为了修一个问题擅自换方向。

第三，让真实产品成为验收依据。

设计模型不能再用“我已经修复”“视觉审查通过”证明任务完成。

Codex 实施后，必须打开真实界面，执行本次涉及的用户操作，保存修改前后的画面，并检查原有正确功能有没有被破坏。
