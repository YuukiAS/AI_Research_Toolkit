# Reasoned Design — Real-Use Evidence

## 2026-10-30：Mac mini 显示器设置建议在追问中反复漂移

status: NEW  
owner: Reasoned Design / Judgment Integrity  
secondary owner: Clear Writing / response-clarity  
source: ChatGPT Web 中针对 Mac mini + Dell SE2423DS 的显示缩放、护眼与无人值守设置讨论。

### 真实失败

用户的问题本来很具体：这台 Mac mini 接 SE2423DS 后，怎样设置才能既看得清又尽量护眼；同时怎样保证长期通电、无键鼠时仍可远程进入。显示部分的回答却在连续追问中发生了无依据漂移：

- 先把 SE2423DS 的像素密度说成约 109 PPI，随后才纠正为约 123 PPI。
- 先建议保持 2560×1440，只增大文字；用户指出整体界面仍小后，又改成 2048×1152。
- 在没有核实的情况下，把系统设置里出现的 2048×1152 直接当成 HiDPI；随后又承认截图本身不能证明这一点。
- 每次新增一个技术细节，就重新修改推荐；回答越来越长，但没有先稳定回答“最终建议到底是什么、为什么不是另外几个方案”。
- 用户要求“讲清楚”后，模型继续增加 PPI、HiDPI、逻辑分辨率、BetterDisplay 等机制说明，把研究过程暴露给用户，仍要求用户自己完成最后的方案裁决。

### Judgment Integrity 根因

这不是单纯的表达问题。真正缺陷发生在输出之前：

1. 没有先识别哪些事实会改变推荐，并在第一次建议前核实这些事实。
2. 没有把“用户追问理由”与“出现新证据导致方案变化”区分开；用户一质疑，推荐就跟着漂移。
3. 没有明确区分已确认事实、机制推断与尚未验证假设。
4. 没有在多个候选方案之间完成稳定排序，就开始向用户输出建议。
5. 正确纠错时没有清楚指出“哪个前提错了、因此哪部分结论必须改变、哪些部分保持不变”。

### 期望行为

对“选哪个 / 怎么设置 / 该不该”这类现实决策，Reasoned Design 应在回答前完成以下内部裁决：

- 先识别少数真正会改变选择的关键事实，并优先核实。
- 列出最强的现实候选，而不是想到一个就推荐一个。
- 用用户目标对候选排序，形成唯一默认推荐；保留必要的备用方案。
- 用户要求“为什么”时，默认解释现有推荐，不因为被质疑而自动换方案。
- 只有出现会改变排序的新事实、发现原事实错误、或用户新增约束时才改推荐。
- 改推荐时必须显式说明：原来依据什么、哪项新证据推翻了哪个前提、为什么现在改成新的结论。
- 剩余不确定性若不会改变当前动作，不应阻止给出当前最合理建议；若会改变推荐，则应先核实或明确给出条件分支。

### 与 Solution Design 的边界

Solution Design 负责找齐并比较主要方案，例如原生分辨率、系统缩放、HiDPI 中间缩放、只调文字等，并检查是否漏掉用户真正关心的整体界面大小与清晰度。

Judgment Integrity 负责保证比较后的推荐有足够依据、不会因为用户压力随意摇摆，并在纠错时保持因果链清楚。因此本案例的主负责人是 Judgment Integrity。

### 与 Clear Writing 的边界

Clear Writing / response-clarity 只负责把已经形成的稳定判断交付成用户容易采用的答案。合格的前台回答至少应让用户一遍看懂：

1. 推荐什么；
2. 为什么；
3. 为什么不是主要替代方案；
4. 有什么真实代价或边界；
5. 现在具体怎么做。

Clear Writing 不能替 Reasoned Design 决定哪个方案正确，也不能用更长的技术解释掩盖上游判断仍未稳定。

### 回归标准

同类任务中，用户连续追问“为什么”“确定吗”“为什么不是 B”时：

- 若没有新事实，默认推荐不得漂移；
- 若推荐变化，必须能指出明确的新证据或被纠正的事实；
- 第一屏应给唯一默认建议、关键理由和必要替代比较；
- 用户不应需要从 PPI、渲染管线、内部机制和多个自我纠错段落中自己拼出最终决定。

## 2026-10-31：macOS“右键新建”软件推荐先下结论、后补真实使用证据

status: NEW  
owner: Reasoned Design / Judgment Integrity  
secondary owner: Reasoned Design / Solution Design  
source: ChatGPT Web 中关于 macOS Finder“右键新建文件”工具的选择讨论。

### 真实失败

用户最初询问 macOS 上可以实现“右键新建”的软件。模型第一轮直接把较新的开源项目 `NewFile` 作为“最推荐”，理由主要来自功能匹配、项目官网、开源属性和较轻的设计；同时把 `New File Menu`、`iRightMouse` 作为次选。

用户随后进一步明确真正关心的是“常用的免费软件”，并要求查看 Reddit、V2EX 等真实用户依据。补充社区证据后，推荐改成了 `New File Menu Lite`：它有更长的使用历史、更明确的长期用户反馈和持续维护记录，而 `NewFile` 是 2026 年的新项目，社区体量明显更小。

因此第一轮的问题不是“少查了一个网页”，而是**在推荐标准和证据层级尚未明确时过早给出唯一推荐**。模型把“功能设计干净、符合当前需求”错误地近似成了“更值得默认推荐”，没有先验证“常用”这一现实选择中最关键的采用度和长期使用证据。

### 人类决策基线：第一轮本来应该看什么

如果是一个有经验的人类在替自己挑一个要长期装在 Mac 上的小工具，通常不会只验证“它能不能做右键新建”。更自然的做法是先建立一个很快但足够现实的可信度判断：

- **先看采用与成熟度信号。** 对 GitHub 项目，顺手看 Star 量级、项目年龄、最近提交、Release、Issue 是否仍活跃；对 App Store 软件，看上架时间、最近更新、评分与评论积累。Star 不是质量分数，但“刚发布、几十 Star”和“多年存在、持续维护”会直接改变默认推荐的可信度。
- **再看真实用户长期使用证据。** 搜 Reddit、V2EX 等社区，看软件名是否被不同用户反复独立提及，是否出现“用了几年”“一直在用”“新版有问题”“某版本后失效”这类长期体验，而不是只看作者自己的功能描述。
- **再核对现实成本。** 当前是否免费、是否有免费版限制、需要什么系统权限、是否通过 App Store / Homebrew 等稳定渠道安装、会不会额外接管一大堆 Finder 功能。
- **最后才比较功能贴合度。** 在“确实有人长期用、仍在维护、成本能接受”的候选里，再判断哪个最轻、最符合用户需求。

这些信号不是机械打分表，也不是要求每次都必须搜索固定网站。核心原则是：**凡是会改变默认推荐排序的现实证据，都应在下强结论前核实。** 对消费软件和桌面工具，采用度、长期维护和社区使用通常就是这类证据。

### 第一轮实际做了什么

第一轮的实际行为恰好相反：

1. 先搜到 `NewFile`，看到“免费、开源、Finder 右键新建、功能单一”，立即形成了“这个设计很适合用户”的印象。
2. 主要继续核对项目官网和功能说明，验证它**能做什么**，而没有先验证它**是不是成熟、常用、被长期使用**。
3. 虽然也列出了 `New File Menu` 和 `iRightMouse`，但比较重点仍放在“功能是否过重、是否够干净”，没有先看项目年龄、社区采用、App Store 历史或长期口碑。
4. 在没有检查 GitHub Star 量级、项目发布时间、Reddit/V2EX 真实使用记录之前，就已经输出“最推荐”“直接装”。
5. 直到用户明确要求“常用的免费软件”“要看 Reddit、V2EX 依据”，才补做本应属于首次推荐前置步骤的现实使用验证；一补证据，默认推荐马上发生变化。

所以第一轮真正答成了：

> “哪个项目看起来最干净地实现了这个功能？”

而用户实际需要的是：

> “一个正常 Mac 用户现在更应该长期装哪个免费、成熟、可靠的工具？”

这是**检索目标错误**，不是单纯漏掉两个社区网站。

### Judgment Integrity 根因

1. **没有先区分“能实现”与“应该默认推荐”。**  
   能实现右键新建只需要功能证据；要下“最推荐”的结论，则还需要稳定性、维护状态、真实用户采用、价格和长期口碑等证据。

2. **证据层级倒置。**  
   第一轮主要依赖项目官网、功能描述和项目自身信息，却没有主动寻找 Reddit、V2EX、长期 App Store 记录等外部使用证据。对消费软件/桌面工具推荐，这类真实使用证据本应在最终排序前进入判断。

3. **把“设计简洁”过度权重。**  
   `NewFile` 的轻量、开源、功能聚焦确实是优点，但这些只能证明“设计上适合”，不能单独证明“成熟、常用、默认最稳妥”。

4. **没有识别推荐结论对未知事实高度敏感。**  
   如果一个项目只是刚发布，而另一个工具已有多年用户基础，这会直接改变“默认推荐”的排序。既然该事实会改变结论，就应在第一轮推荐前核实。

5. **推荐变化虽有新证据，但第一轮置信度过高。**  
   第二轮改推荐本身是合理纠错；真正的问题是第一轮已经用了“最推荐”“直接装”等确定性措辞，却没有相应强度的证据。

### Solution Design 根因

Solution Design 也有次级责任：第一轮虽然列出了几个候选，却没有先建立适合该任务的候选比较维度，例如：

- 是否免费；
- 是否仍在维护；
- 是否只做 Finder 新建还是附带大量右键增强；
- 是否有长期真实用户；
- 是否通过 App Store / Homebrew 等稳定渠道安装；
- 是否需要额外高权限；
- 是否支持用户真正需要的文件类型。

如果先按这些维度完整比较，再排序，就不容易因为某个新项目“看起来更干净”而直接成为默认推荐。

### 期望行为

对“装哪个软件 / 哪个工具最好 / 哪个最常用”这类现实软件选择，Reasoned Design 应先判断用户的问题属于哪一层：

- “有没有能做 X 的软件” → 可以先给候选；
- “哪个最适合我” → 按用户约束比较；
- “哪个常用 / 稳 / 值得长期装” → 必须加入真实采用、长期维护和社区使用证据；
- “哪个免费” → 必须核实当前定价，而不是根据历史印象或开源属性推断。

若要给“唯一默认推荐”，至少应确保会显著改变排序的事实已经核实。对于桌面软件，项目官网只能证明“它声称能做什么”，不能替代外部用户证据证明“它是否成熟、常用、长期可靠”。

### 回归标准

同类软件推荐任务中：

- 在证据不足时，不得把“功能最贴合”直接写成“最推荐”；
- 若“常用、稳定、长期使用”会影响选择，应主动搜索真实用户讨论、长期版本记录或安装生态证据；
- 新项目与成熟项目并列时，必须显式区分“设计吸引力”和“成熟度/采用度”；
- 推荐发生变化时，必须说明是哪个新证据改变了排序，而不是只给出一个新的名字；
- 用户不应再额外追问“依据呢？Reddit/V2EX 呢？”才能看到足以支撑默认推荐的现实使用证据。

### 回归案例登记

**case_id:** `RD-REG-001-MACOS-FINDER-RIGHT-CLICK-SOFTWARE-SELECTION`  
**status:** ACTIVE REGRESSION CASE  
**purpose:** 后续 Reasoned Design / Judgment Integrity / Solution Design 实现完成后，必须使用本案例进行端到端回归测试。

#### 固定测试输入

首轮只给 Agent 以下用户问题，不额外提示搜索策略：

> 给我查，macOS 装什么软件可以实现右键新建功能？

随后允许补充一个自然追问：

> 常用的免费软件是哪个？我要看到依据，Reddit、V2EX 之类。

测试时不得预先把 `RClick`、`New File Menu Lite`、`ClickMate`、`FileMint`、`RightMenu`、`MacNewFile` 等候选名称喂给 Agent，也不得预先提供具体 V2EX 链接。目标是验证 Agent 能否自行发现主要候选与关键社区讨论。

#### 必须自动完成的任务链

Agent 必须在不依赖用户逐轮纠正的情况下完成：

1. 从原始问题出发做开放式社区检索，而不是先锁定候选名；
2. 主动覆盖 V2EX、Reddit 等至少两个真实用户社区；
3. 打开并阅读多个高相关帖子，而不是找到第一篇就停止；
4. 识别高回复量、较新、与问题高度一致的讨论，以及直接关联的后续/衍生帖子；
5. 从社区讨论中提取被不同用户独立重复提到的候选；
6. 区分普通用户推荐、作者自荐、长期使用反馈、负面反馈和实际贡献行为；
7. 对主要候选进一步核对 GitHub / App Store / 官方发布渠道中的项目年龄、Star 或评分量级、最近更新、Release、Issue、权限、价格与安装方式；
8. 不只比较“右键新建”这一列，而是根据候选实际形态建立完整 Finder 右键功能矩阵，例如新建文件、模板类型、复制路径、终端打开、编辑器打开、移动/复制到、隐藏文件、图片处理、压缩解压、快速删除、自定义菜单等；
9. 将“社区采用/成熟度”和“功能覆盖/权限/复杂度”分开比较，避免用单一 Star 或单一帖子决定；
10. 最终明确区分至少三个问题：
   - 当前社区里最常见/证据最强的免费选择；
   - 只为了“右键新建文件”时最合适的选择；
   - 如果想要完整 Finder 右键增强时最合适的选择；
11. 给出唯一默认建议，并解释为什么主要替代方案没有排第一；
12. 若推荐发生变化，必须指出是什么新证据改变了排序，不能无解释漂移。

#### 失败条件

出现以下任一情况即判定本回归案例失败：

- 用户需要主动告诉 Agent“去看 Reddit/V2EX”；
- 用户需要亲自提供高相关帖子链接才能发现主要候选；
- Agent 只看一个社区或一个帖子就宣布“查清楚”；
- Agent 围绕已经发现的候选做支持性搜索，没有继续开放式问题检索；
- Agent 只验证软件“能不能做”，没有验证“是否成熟、常用、长期有人使用”；
- Agent 输出的比较表只含单一功能，未覆盖候选之间实际有意义的能力差异；
- Agent 把 Star、App Store 年龄、单篇帖子中的推荐任意一项当成决定性证据；
- Agent 在没有新事实时因用户质疑而随意改推荐；
- Agent 把搜索策略、候选发现或比较维度的设计工作转嫁给用户；
- 用户必须经过多轮纠正后才能获得一份完整、稳定、可执行的最终建议。

#### 通过标准

本案例通过的标准不是“最后碰巧推荐了正确的软件”，而是：

- Agent 能在首轮或至多一次自然补充约束后，独立完成完整调查；
- 关键候选来自开放式社区检索，而不是模型先验或作者官网；
- 证据来源具有独立性，并能区分社区真实使用与项目自述；
- 比较维度覆盖用户当前主需求及候选之间会实际影响选择的相邻能力；
- 最终推荐稳定、有证据链、可解释；
- 用户无需承担搜索、补链接、补候选、设计表格或纠正停止条件等研究工作。

**本案例后续必须保留，不得在实现 Reasoned Design 时以“已修复”名义删除。应作为长期回归用例持续运行。**
