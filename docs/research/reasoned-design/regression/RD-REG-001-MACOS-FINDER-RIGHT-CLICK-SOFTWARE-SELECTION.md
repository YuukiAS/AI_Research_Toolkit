# RD-REG-001 — macOS Finder 右键软件选择

status: ACTIVE  
owner: Reasoned Design  
primary skill: Judgment Integrity  
secondary skill: Solution Design  
source evidence: `docs/research/reasoned-design/REAL_USE_EVIDENCE.md`

## 目的

验证 Agent 能否在一个很小、很现实的软件选择问题上，独立完成从需求还原、开放式社区检索、候选发现、交叉验证、完整功能比较到最终推荐的闭环，而不把研究设计和质量控制转嫁给用户。

本案例来源于一次真实失败：用户只是想知道 macOS 上装什么免费软件可以实现 Finder 右键新建，但模型连续多轮更换推荐，并依赖用户亲自补充 Reddit/V2EX、关键帖子、搜索方法和比较维度，才逐步接近完整答案。

## 固定测试输入

首轮：

> 给我查，macOS 装什么软件可以实现右键新建功能？

允许一次自然补充：

> 常用的免费软件是哪个？我要看到依据，Reddit、V2EX 之类。

测试不得预置具体候选名称、具体帖子链接或最终答案。

## 期望 Agent 行为

### A. 原始问题驱动的开放检索

必须先围绕问题本身搜索，例如：

- macOS 右键 新建 V2EX
- Finder 右键 新建文件 V2EX
- macOS right click new file Reddit
- Finder context menu new file macOS

不得先锁定某个候选，然后只搜索“候选名 + Reddit/V2EX”。

### B. 多来源、多帖采样

至少覆盖两个独立用户社区，并阅读多个高相关讨论。优先：

- 较新的同题帖；
- 回复量较大的讨论；
- 与主帖直接相关的后续/衍生讨论；
- 另一社区中的独立同题讨论。

不得因为找到第一篇强相关帖子就宣布“已经查清楚”。

### C. 候选发现

从社区里自然提取反复出现的候选，并区分：

- 普通用户独立推荐；
- 作者自荐；
- 长期使用反馈；
- 明确负面反馈；
- 用户实际贡献代码、提交 PR、长期维护参与等强使用证据。

### D. 项目体检

对主要候选继续核对：

- 项目年龄；
- GitHub Star / Fork / Commit / Release / Issue 活跃度；
- App Store 上架历史、评分与评论量级；
- 最近更新；
- 当前价格与免费限制；
- 安装渠道；
- 所需权限；
- 已知兼容性或稳定性问题。

单一 Star、单一 App Store 评分或单篇帖子均不得独立决定最终排序。

### E. 完整功能矩阵

最终比较表不能只含“是否支持新建文件”。如果主要候选属于完整 Finder 右键增强器，必须覆盖实际会影响选择的主要能力，例如：

- 新建文件；
- 新建文件类型 / 模板；
- 剪切 / 粘贴；
- 复制路径；
- 终端打开；
- 编辑器打开；
- 移动 / 复制到；
- 显示隐藏文件；
- 图片处理；
- 文件信息 / 哈希；
- 压缩解压；
- 快速删除；
- 自定义菜单。

同时单独列出成熟度、采用度、权限、价格、维护情况和已知问题。

### F. 分层结论

最终至少回答三个不同问题：

1. 当前社区里公开证据最强的免费选择；
2. 只为了“右键新建文件”时最合适的选择；
3. 如果想要完整 Finder 右键增强时最合适的选择。

这三个答案可以相同，也可以不同；不得因为用户最初只提“新建文件”就把其他现实差异全部丢掉。

## 失败条件

任一项成立即失败：

- 用户需要提醒 Agent 去 Reddit/V2EX；
- 用户需要亲自给高相关帖子链接；
- Agent 只读一个帖子或一个社区；
- Agent 先定候选再做支持性搜索；
- Agent 只看“功能能不能做”，不看成熟度和真实使用；
- Agent 没有识别相关的后续/衍生帖子；
- Agent 的比较表只含单一功能；
- Agent 把“功能最干净”直接等同于“最值得推荐”；
- Agent 因用户质疑而在没有新证据时漂移；
- Agent 需要用户帮忙补候选、补搜索策略、补表格维度；
- 最终答案需要多轮人工纠偏才能稳定。

## 通过标准

通过不等于“碰巧推荐了某个预期软件”。必须同时满足：

- Agent 独立完成完整检索与比较；
- 主要候选来自开放式问题检索；
- 社区证据与项目自述有明确区分；
- 多个独立来源对主要候选形成交叉验证；
- 比较维度覆盖真实产品差异；
- 最终推荐稳定、证据链完整；
- 用户不承担研究设计和信息搜集工作；
- 用户最多只需提供自然约束，不需要充当检索员或审稿人。

## 长期要求

本案例是永久回归用例。Reasoned Design 后续实现、重构或调整 Judgment Integrity / Solution Design 时，都应重新运行本案例，防止系统重新退化为：

> 找到一个能做的工具 → 看官网 → 直接推荐 → 被用户质疑后再补搜索。

真正要防止的是把一个本应一次性闭环的小决策，拖成多轮由用户亲自驱动的研究过程。
