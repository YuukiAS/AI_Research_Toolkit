# 研工台：可运行的软件生产合同与信任边界 v0.1

> 状态：拟议接口，**未实现、未经独立 Critic 审查、未获实施授权**。
> 日期：2026-10-13；与 00_ARCHITECTURE_DECISION_V0_1.md 共同构成一个版本的待审对象。
> 目标不是统一文件结构，而是：现有 Codex、Bridge、GitHub、产品测试与领域评审必须能从同一已批准目标完成一次可恢复、可验收、可交付的正常开发任务。

## 1. 面向用户的最小产品合同

产品名称暂定“研工台”；名称不指向既存程序，也不锁定未来仓库。用户只需要四类自然指令：

- “继续 <产品> 的 <当前任务>”：解析**唯一活动任务**，核对真实运行事实，若多个活动目标有实质歧义才问一次；不自动创建重复任务。
- “修复这个问题”：定位真实版本、复现入口与已接受行为；若既有目标允许局部修复则继续，若需改变产品方向、权限或设计则返回 Planner。
- “发布已经验收的版本”：首先核对签名、安装或部署目标现状。若已生效则不执行副作用；未获发布权时只给准确阻塞。
- “进度如何”：读取 Git、任务、运行和审核来源，报告**获得的用户能力、当前阻塞、唯一下一步和是否需要用户操作**，而不是汇总模型长日志。

首版用户界面可依靠 ChatGPT/Codex 对话与 GitHub 任务/拉取请求/检查记录；但“自然语句自动驱动远端执行”不是已存在的保证。必须通过已安装、实际登录和已授权的调用入口才能运行。若没有执行主机则只可恢复，不得说任务正在后台继续。

## 2. 系统权威与信任边界

四个不能混淆的权威：

| 权威事实 | 拥有者/存储位置 | 不得据此推断 |
|---|---|---|
| 产品目标、已接受功能、设计来源、批准的任务范围 | 目标产品仓库的现有规范、任务和明确用户决定 | 聊天摘要或者自报 PASS 能改写目标 |
| 任务工作树、执行许可、会话/持久运行、已发生副作用 | Bridge/目标主机/实际 Git 和运行环境 | 读取到文件就证明已加载或已授权 |
| 可信的验收要求、验证器身份、产品实际运行证据 | 与候选写权限隔离的验收身份、已批准基线和隔离运行环境 | 候选自己提交的 JSON、截图或测试退出码可以作为最终裁决 |
| 正式集成、发布、目标安装或部署 | 受限发布身份及目标实际状态 | 本地编译完成等于已经交付 |

AI_Skills_Collection 继续拥有 workflow-core 的执行指导、Frontend Design 的专业设计/渲染检查及平台领域能力，但**不默认拥有软件生产流程的全部生命周期**。Bridge 不变成产品质量裁判；项目已有测试脚本仍在项目仓库中。第三方成熟工具若被采用，应把固定版本、许可、运行条件和替换范围写入执行包，不复制低配替代。

开发身份、可信验收身份、发布身份必须通过实际账户/凭据/受保护运行位置隔离。两个名字不同但使用同一高权限 GitHub 账户的代理并不独立。可信环境不能执行带发布密钥的候选构建脚本；不可信构建产物的元数据和归档内容均视为不可信输入。不得在具有密钥的高权限工作流中直接运行来自 PR 的代码；尤其需核查 GitHub pull_request_target、workflow_run、缓存与工件的边界。官方依据：
- https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target
- https://docs.github.com/en/actions/reference/security/secure-use
- https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets

个人账户和私有仓库能否启用特定保护、是否允许绕过、执行者与管理者是否拥有同样权限，均**需要在目标账户实测**。未具备此信任域时，只能提供独立验收建议和有人批准的交付；禁止把它表述为强制阻断已生效。

## 3. 最小代码组成：只开发当前工具无法提供的部分

首轮不预设新仓库或程序语言。下面是**可按模块实现的职责合同**；当现有工具确实已经实现某部分，应直接消费而不是重写。

| 模块合同 | 主要输入 | 输出和拒绝条件 | 首选复用来源 |
|---|---|---|---|
| 任务定位/准入 | 用户任务、目标仓库、当前既有产品来源、授权 | 唯一任务；增量要求、旧行为、交付目标；缺身份/权限则停相应步骤 | GitHub Issue、项目任务、Spec Kit 轻量模式 |
| 产品切片/变更影响 | 已接受行为、设计来源、任务规模、预计修改的共享模块 | 用户操作—真实结果—错误恢复闭环、不可变项、最小验证集合；只列组件不算完整需求 | 现有产品合同、workflow-core、领域技能 |
| 实施适配 | 批准的执行位置、任务标识、工作树、Codex/Bridge 当前版本、预算 | 真正启动/恢复的执行 run、源码提交和日志；无法证明入口/授权时不运行危险动作 | Bridge 已有 Lite/Reviewed/Persistent Run；Codex 当前正常入口 |
| 候选与证据 | 源码/构建输入、应用包、宿主/设备身份、验收合同、执行记录 | 候选摘要、实际行为结果和缺失覆盖；不能仅用退出码或报告字段判断 | 项目现有测试、平台原生检查 |
| 专业审查路由 | 冻结设计、最终候选、完整渲染和交互证据 | 有材料的独立审查；缺完整产物/错候选/主观核心缺陷则不放行 | Frontend Design、领域能力、必要的 GPT Work |
| 恢复/去重 | 原任务、基准与当前提交、工作树、运行进程、外部目标、授权 | 安全下一步/暂停/原任务返修；不以新提交清零重试，不重复外部副作用 | Bridge 当前工作树与运行恢复、Git/GitHub |
| 发布/晋升 | 可信结果、当前获准目标、最终包、外部平台状态 | 已交付、未交付、已经满足无需操作、阻塞；不拿候选自报作为放行依据 | 项目发布程序、受保护 GitHub 入口、平台 installer/deploy |

重要约束：模块合同不意味着需要七个 Python 包或七个进程，更不意味着新增七个模型。研工台核心仅是确定性程序，所有复杂智能规划继续使用对应合法角色。若同一需求可以由一条现有调用直接完成，不需要包装一道虚假的新“控制层”。

## 4. 角色与独立权限

| 职责 | 人/模型/执行者 | 可写对象和可作决策 | 不得控制 |
|---|---|---|---|
| 产品负责人 | 用户 | 产品目标/关键取舍/数据、服务商、费用、外部副作用授权 | 不负责重复调试或第一轮 QA |
| Planner | 独立的 GPT Chat 规划线程 | 明确任务/设计、必要外部研究、风险与专业验收方案 | 不能自批重大架构、伪造实现通过 |
| Critic | 与 Planner 区分的独立审查线程 | 对明确版本的重大设计和执行/权限方案作 PASS/REVISE | 不改变被审方案、产品代码或候选验收口径 |
| 产品设计负责人 | 有产品设计授权的领域模型或人 | 产品结构、Figma/当前设计规范、关键状态与整体原型 | 不能用静态稿宣称真实应用完成 |
| Executor/开发者自检 | Codex | 获准的源代码/开发测试、真实内部自检和候选准备 | 不能修改冻结正式标准后自己批准自己 |
| 任务协调（程序） | 有界确定性控制器 | 读取有效权威、派发已授权动作、保存恢复事实/冻结候选 | 不能批准费用、改变需求、扩大权限或捏造实际运行 |
| 专业 Reviewer | GPT Work 或独立只读审查者 | 观察绑定候选的完整产物、提出结构/体验/学科意见 | 不改源代码、正式评分器或发布凭据 |
| 可信验收器 | 与开发写权限隔离的程序 | 冻结合同、真实测试驱动、正确证据裁决 | 不信 Codex 自报，不将环境未覆盖记 PASS |
| 集成/发布执行器 | 受限身份/授权工作流 | 在指定目标与版本上执行已批准发布及后置核验 | 不执行不可信候选中的任意发布命令，不越权重试 |
| 失败归因/恢复 | Planner 作语义归因，确定性程序保存恢复事实，Executor 修实现 | 从证据返回正确责任方、检查权限和同类失败预算 | 不把新模型会话当作原运行进程已恢复 |

普通小改无需把所有角色都实例化；Executor 与内部开发自检合一是正常做法。但 Planner 与正式 Critic、实现者与正式验收器、候选构建与发布凭据三组分离不能仅靠角色文字保证。

## 5. 最小任务合同与来源选择

任务合同可以是从既有任务文件及批准记录解析得到的机器视图，**不是在每个产品复制新的需求数据库**。例如：

~~~yaml
schema: software-production/task-v0-draft
task_id: "mica--highlight-persistence"
repository: "YuukiAS/Mica-for-ChatGPT"
source_task: "docs/tasks/<exact-current-goal>"
base_commit: "<verified-sha>"
ownership:
  branch_policy: "respect-target-repo"
  worktree: "<verified-canonical-or-authorized>"
authority:
  approval_locator: "<actual-approved-scope>"
  allowed_effects: ["repo-code-edit", "local-deterministic-tests"]
  external_effects: "none"
product:
  claims:
    - "选择真实答案文本后保留高亮并能重新加载恢复"
  protected_behaviors:
    - "宿主 ChatGPT 原生编辑和操作不能受损"
  excluded:
    - "不将未知宿主结构猜测成可用答案"
  delivery_target: "browser-extension-candidate"
checks:
  cheap: ["targeted-logic-regression"]
  platform: ["isolated-real-extension", "host-page-compatibility"]
  qualitative: "required-if-product-surface-changed"
runtime:
  max_parallel_actions: 1
  retry_policy: "bounded-by-task-and-failure-mechanism"
~~~

这里的字段是设计样例，不代表 Mica 现有任务已批准这些精确值。目标是让每项真实的完整功能有：从哪里进入、输入/输出是什么、错误如何表现、哪些旧能力不可丢、正式用户拿到的是什么。若新增能力的重要验收标准尚未被批准，则只能进行开发自检，不能进入独立的最终通过。

**任务从哪里读取：**
1. 用户当前指令与授权；
2. 目标 repo 当前分支/工作树的 AGENTS、产品/设计和既有 Goal；
3. 实际实现/测试和已接受真实行为；
4. 已批准的适用能力文档或外部成熟工具；
5. 最新机器/权限/环境事实。

Bobbio 可以沿 develop 里程碑提交，不强制一任务一分支；其他仓库按各自正式开发与发布规则。控制器不能自动把所有软件统一为 PR 工作流。

## 6. 阶段推进：真正由事实决定，不另造第二套状态机

阶段用用户结果与已发生事实表示：
- 目标待明确：现有批准要求不足，负责者 Planner/用户。
- 设计/方案有效：已按风险选择是否独立 Critic，真正重要的设计来源已消费。
- 实施进行中：有真实 Codex 执行者、合法工作树和授权。
- 开发候选存在：有可识别的最终源码/构建产物，内部质量检查结果独立标注。
- 正式验证进行中：机器与实际平台/专业审查分开记录；有缺口就不能晋升对应声明。
- 待交付：有当前候选的有效全部适用结果和已批准发布权限。
- 已实际交付：目标分支、安装/部署/商店或用户机器状态已被核实。

暂停不是等于失败。阻塞原因另行分类：产品、设计、基础设施、权限、没有独立材料、外部服务、报告/证据与规范冲突。已经通过的独立成果在修复无关原因时保持真实有效，只有受影响结果需重验。

控制器每次执行下一步（拟议函数，无现存实现）：
~~~python
def reconcile_and_advance(task_id):
    task = resolve_canonical_task(task_id)
    facts = reobserve_git_process_artifact_environment_target(task)
    require_consistent_repository_worktree_and_granted_effects(task, facts)
    require_unique_current_candidate_or_explicit_resolution(task, facts)
    checks = derive_required_checks_from_approved_claims_and_change_impact(task, facts)
    if missing_design_or_authority(task, facts):
        return WAIT_FOR_REAL_OWNER
    if implementation_missing_or_failed(task, facts):
        return CONTINUE_OR_REPAIR_SAME_TASK
    if missing_or_invalid_internal_checks(checks, facts):
        return RUN_BOUNDED_DEVELOPER_QA
    if missing_or_invalid_trusted_checks(checks, facts):
        return VERIFY_EXACT_CANDIDATE
    if professional_review_required(checks) and not reviewed_exact_artifact(facts):
        return WAIT_FOR_INDEPENDENT_REVIEW
    if requested_delivery_already_true(facts):
        return NO_OP_ALREADY_DELIVERED
    return BOUNDED_AUTHORIZED_PROMOTION
~~~

这个函数只允许跳到既有合同指定的动作，不从任务正文中接受任意 shell。若发现真实现状与记录冲突，必须停下复核而不是默默“修正”工作树。

## 7. 风险裁剪：全面是覆盖风险，不是强制所有检查

### 分流依据

将变更影响映射到：已接受行为、共享模块、用户可见界面、外部服务、数据/持久化、权限、原生平台、构建与安装、发布。一个单文件修改如果涉及共享状态就可能是广影响；新增很多文件如果仅为孤立文档则可能是低风险。

| 实际任务 | 设计/审查 | 内部验收 | 独立候选门槛 |
|---|---|---|---|
| 改明确的普通文案 | 不重新规划；按现有视觉规范 | 文案及关联界面排版 | 非正式发布一般不需 GPT Work |
| 可复现单点逻辑修复 | 最小旧坏新好证据 | 对应测试及邻接/应不改变 | 若只交付源码，按仓库边界；正式用户能力需实际入口 |
| 新增完整用户功能 | 定义纵向切片，设计权威按需读 | 输入、动作、持久化、故障和相关回归 | 必须按平台验证实际产品 |
| 整体设计重构 | 产品系统与关键状态，独立 Critic | 设计对照与完整交互 | 独立整体视觉/体验审查 |
| 生产服务/凭据/数据模型变动 | 权限、费用、迁移/回退特别审查 | 真实接口/隔离替身、旧数据 | 真实服务证据或明确未验证；不可超权 |
| 正式桌面/网页/移动发布 | 只复用已经批准的设计 | 构建/打包/相邻回归 | 精确最终产物、平台验证、发布后置结果 |

**昂贵检查在稳定候选后做**。开发期允许重复目标回归；进入正式候选后不“跑到绿”为止，也不拼接不同候选的结果。发现项目内现有检查器漏检，应修已有检查入口，不自动增建第 N 套审核器。

## 8. 可信验收合同：防降级、防作弊、防错包

### 必需身份链

同一个真实候选的身份至少包含：

~~~text
repository + source_ref/base_commit + candidate_commit + trusted_contract_revision
+ verifier_revision + build_provenance + final_artifact_sha256
+ target_platform + actual_run_environment + check_run_identity
+ evidence_hashes + reviewer_artifact_binding(if required)
+ requested_delivery_target + effective_authority_scope
~~~

最终发行对象必须按真实流程决定：源码候选与后附证据提交可以不同；安装包签名/重新包装若改变字节，实际正式发行的最终包必须受到对应的安装验证，不得拿未签名开发 EXE 的截图证明签名后的 NSIS 安装升级正确。静态网页的 URL 应绑定实际部署的不可含混身份；移动包则核对 APK、签名及运行安装身份。

### 实施者不能决定验收标准

1. 产品能力的冻结声明来自用户批准和当前产品仓库的真正既有基线；新增重要要求在本轮正式验收前单独冻结。
2. Codex 可以修开发测试；但**正式验收所使用的旧行为集合、评分要求、检查器和历史有效基线不受候选同轮修改影响**。
3. 可信验证器应从固定批准的来源取得本次必要场景，并对精确候选产物执行。修改正式评分器必须单独审查；评分器修复后旧通过不能自动继承。
4. 机器门槛仅判断可计算的状态和行为；完整用户界面、读者语言、产品层级、数学/科研语义等由看过完整实际产物的独立审查者判断。
5. 只有生成真实因果后置条件的证据才证明能力；截图、HTTP 200、测试文件和退出码仅证明其自身范围。
6. 外部主服务能力可受限测试，但模拟/夹具不能被说成真实服务。没有真服务账号时该功能保持未验证，并可完成无关边界。
7. 一个未经保护的自建 runner、GitHub workflow 或模型自报不能被称为可信发布硬门槛。

### 信任检查的故意反面用例

同样走正式入口：删除旧功能及测试、把服务响应改固定、修改验收脚本为直接 PASS、用旧截图、错版本安装包、撤掉真实界面动作、伪造环境通过、Reviewer 拿不到原始材料。任何一项若被承认为真正用户可用，**设计本身不得通过**；参考 02 中的反证矩阵。

## 9. 中断/失败恢复与不重复外部动作

- 原任务不因重连或新 Codex 会话重建。任务唯一标识来自现有源任务/经授权的实际 Issue；GitHub 事实和本地任务结果可重新索引。
- 持久化信息只记**无法从 Git 或外部平台重建的最小事实**，例如被批准的任务目标/权限依据、已执行外部效果的意图与实际执行结果；不重复保存整套 Git 历史。
- 若已有运行进程，必须识别它的宿主身份、PID 与启动时间；即使进程丢失，也不假装在后台运行。
- 外部动作（安装/删除/远端发布/付费请求）使用意图键与受控目标，必要时先记录意图，执行一次，恢复时查询外部后置状态；未知结果时停止，而非直接重发。
- 失败指纹绑定任务目标、故障机制、操作/证据环境；**变更源码 SHA 不能自动擦除同一根因的连续失败次数**。第一次定位，第二次无新证据暂停根因复核；可配置策略，但不能无限自动模型调用。
- 故障归因必须区分：目标错误、方案设计、代码实现、测试工具、权限、基础设施、专业评审误判、发布目标和外部服务。
- 返回 Planner 只处理真正的方向性争议；已有批准范围内的修复由 Executor 完成。
- 同一个资源只允许一个拥有正确授权的执行者控制，原生桌面/安卓模拟器/发布目标各自有资源租约。租约失效必须核对进程和外部动作后再恢复。

## 10. 实际产品验收的最低接口

拟议接口，平台负责人实现行为，中央核心只作契约解析、身份检查与归类：

~~~python
class ProductVerifierAdapter:
    def describe_capabilities(self) -> dict: ...
    def inspect_artifact(self, artifact_bytes, context) -> dict: ...
    def verify_behavior(self, artifact, approved_scenario, environment) -> dict: ...
    def verify_delivery_target(self, target, expected_identity) -> dict: ...
~~~

返回结构必须包含：执行对象摘要、受控环境、真实操作或服务输入、实际后置结果、原始证据定位、被该证据**直接证明**的能力与未覆盖项、错误类别、检查器版本。不得只输出 PASS 字段。每个项目可以用现有脚本适配为这一接口，而不是把它们迁移成中央统一测试框架。

Lucerna 的 development-acceptance 是已经存在的自检入口，不是外部独立裁判；governance-regression 的退出码 0 仍可能存在环境 GAP。任何可信调用者必须解析结果语义，检查实际隔离与正式发布约束。Windows 候选不可操作用户正式桌面；隔离不足时可继续无危险的代码/后台验证，但原生验收不升级为已通过。

SeminarArc 的运行入口可使用固定 APK 的现有黑盒脚本；Mica 当前对用户真实登录 ChatGPT 的操作有明确人工边界；Bobbio 的隔离 Zotero 与 develop 分支策略不能被新的统一工具覆盖；Asteria 与 CUHK Date 的外部托管状态不能被静态配置检查替代。

## 11. 当验证器还没有正式安全执行位置时

必须诚实区分两种强度：

- **审计型模式**：可以运行不可变候选检查、独立审查和用户批准的交付，但如果执行者仍能改写 GitHub 保护/验证器/发布密钥，就不声称不能绕过。
- **强制型模式**：已用负面实测证明受限实现身份不能修改批准合同、正式裁判、可信检查状态或未授权使用发布凭据；正式交付操作无法跳过有效门槛。

转换只能由真实权限测试、实际候选行为及发布负例证明，不依赖 Repo 目录或规则文件数量。原生 GUI 工具仅是“手”，独立可恢复的虚拟机/专用机器及其权限隔离才是测试边界。

## 12. 谁保管软件生产控制程序、是否要独立仓库？

本文件**不以目录位置替代产品/信任决策**。先评估现有：
- Bridge 已有执行/恢复，不能重复实现工作树交换和授权传递；
- VibeResearch 已有 kernel、daemon、adapter schema、reliability checkpoint、next_action、codex_adapter 等实码，但其现有状态语义显式面向科研与 Slurm，若移植需证明正常软件任务不触发科研周期和大量文件；
- Spec Kit Lean 有低仪式需求/计划/任务流程，可参考或作为独立前置，但它的指令不能代替独立质量权威；
- GitHub 已存任务/提交/检查事实，可作为可靠显示与部分持久事实。

首轮允许只在 Lucerna 安全试点实施必要的独立验收模块；当另一个平台消费者确认需要同一稳定模块，再决定正式代码库/分发方式。**评审资料暂存 AI_Research_Toolkit 只因用户暂时允许，不构成未来控制代码属于此仓库的决定。**

## 13. 必须经独立 Critic 关闭的关键设计风险

1. 怎样在私有个人 GitHub 账号和当前执行身份下保证裁决独立？具体计划/规则/绕过边界可用吗？
2. 已存在的项目任务如何承载新增功能的验收要求，而不产生两份互相竞争的事实？
3. 控制器是否又复制 Bridge/VibeResearch 状态机？最小无法替代的新能力是什么？
4. 用户同时进行多个任务时如何保证资源锁、工作树和正确进度身份？
5. Windows 验收是否已经实际安全？如何阻止正常开发路径触碰用户原生桌面？
6. 从自检到真实功能、专业审查和正式发布，哪一步依赖模型自报而缺独立可观测性？
7. 普通修复和大重构分流能否被绕过？共享模块影响范围由什么真实来源发现？
8. 同一根因反复返修时是否有有界停止和明确人工/设计出口？
9. 第二个平台加入后，哪些代码可完全复用？哪些平台特化留在产品本地？
10. 缺少正式强制权限时，审计型模式能否诚实产出价值，还是会诱导用户误信？
