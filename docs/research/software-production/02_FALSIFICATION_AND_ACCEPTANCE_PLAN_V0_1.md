# 研工台：真实能力、降级与全生命周期反证计划 v0.1

> 状态：**待审测试计划；没有执行任何候选、设备、外部服务、付费实验或生产发布**。
> 与 00/01 一同交独立 Critic 审查。每个反例都必须经过同一普通执行/验收入口，而不是在测试里为该反例增加专用拒绝关键词。
> 核心问题：在普通软件开发中，新体系能否实际减少用户首次发现的缺陷、旧能力退化、虚假交付、重复返修与中断损失，并且不拖垮小任务？

## 1. 可信路线的阶段和可以相信的结论

| 阶段 | 真正对象 | 需要的独立可观测证据 | 允许宣称什么 | 不能宣称什么 |
|---|---|---|---|---|

| P1 单平台机制成立 | Lucerna 现有 Windows 候选或范围明确真实任务 | 正常功能实际交付链 + 阻断旧功能删除、虚假证据、错包、越权/错误恢复的负例 | **对已实测的 Lucerna 范围具有可重复能力** | 已覆盖其他平台或所有 Windows 情况 |

若 P0 REVISE，只修真正阻塞项；若 P1/P2 失败，先修归因机制，不得通过多添一套标准补绿。若 P3 不能减少返工/人工成本或使普通任务显著变重，则收缩或停止“独立研工台”路线，只保留证明有用的项目与中央局部修复。

## 2. 全生命周期失败模式：从最早发现点而不是最终报告组织

每一项至少绑定一个可执行观察入口；没有实际执行入口时如实标记 OPEN，不得以“规范有此条款”记 PASS。以下分别标注负责者（Planner/设计/Codex/可信验收/Bridge/发布）；专业问题的人工或模型审查不能由机械检查的结果替代。

| 类别/问题编号 | 具体失效与直接后果 | 最早防护/实际观测 | 失败后的责任方 |
|---|---|---|---|
| 需求 R01 | 只实现要求的一个组件，完整功能缺失 | 任务合同绑定用户入口、业务结果、后置状态和错误处理；单功能实际操作失败 | Planner 核对范围，Codex 补实现 |
| 需求 R02 | 已实现旧能力从新的任务要求中消失 | 与已接受基线对比，应保留能力必须有对应旧场景 | Planner，既有验收保持有效 |
| 需求 R03 | 顺手扩大功能、偷加服务商或收费路径 | 变更 diff、真实外部动作与已授权效果比对 | Planner／用户决定是否改范围 |
| 需求 R04 | 重复做仓库已实现的功能 | 先在当前源码及实测路径确认，已达目标直接继续缺失验收 | Planner 纠错 |
| 需求 R05 | 小修复被规划成大型项目 | 风险与影响范围对应本轮必要检查，跟踪新增步骤/总耗时 | 协调器收缩路线 |
| 设计 D01 | 忽视 Figma 或产品系统，结果全屏不协调 | 编码前读取设计权威；关键用户状态与完整页面审查 | 设计负责人/Planner |
| 设计 D02 | 一直修边距/箭头而方向根本错误 | 真正的完整视觉评审发现同机制复发，返回设计而非第 N 次微修 | 设计负责人/Planner |
| 设计 D03 | 正常、空、错、未知、鉴权状态缺页或误导 | 受影响状态矩阵的实际渲染和操作 | 设计负责人/Codex |
| 设计 D04 | 只看默认画面，忽略缩放、无障碍、触控与键盘 | 代表性实际平台/尺寸/焦点/系统交互观测 | 领域质量负责人 |
| 技术 A01 | 重造低配现有依赖或未经调查替换架构 | 方案给出现有成熟实现与选择/拒绝证据，真实功能/性能对照 | Planner/领域专家 |
| 技术 A02 | 先建设控制器而产品任务不前进 | 跟踪每阶段新增真实产品能力；仅增长文件/机制不算成果 | Planner/Critic 停止扩项 |
| 技术 A03 | 平台语义泄漏进中央核心，扩展时到处改分支 | 第二平台用相同 core contract，平台实现保持 adapter 本地 | 架构 Planner |
| 技术 A04 | 新依赖不稳定、许可/实际运行与预期不符 | 读取真实源码/官方材料，受控接入及替代/回退条件 | 平台负责人 |
| 执行 E01 | 选择错误仓库、工作树、分支，污染其他任务 | Bridge+Git 当前状态、脏文件归属、进程及租约核对；与 Goal 不符停止 | Bridge/Executor |
| 执行 E02 | 规则没有真正加载或 AGENTS 被截断 | 运行时实际读取/插件身份和上下文检查；真实行为仍单独验收 | 执行环境负责人 |
| 执行 E03 | 使用测试借口触碰用户桌面、个人资料或正式进程 | 独立机/虚拟机的访问负例；跨界立即停止原生测试 | 环境/安全负责人 |
| 执行 E04 | 重复向用户索要已批准同范围权限 | 绑定任务—效果—用途—授权，恢复时复用而非新任务重问 | Bridge/协调器 |

| 实现 I01 | 按钮有 UI 无真实操作 | 实际从可见入口操作并核对真实后置状态，不能只检查 handler | Codex |
| 实现 I02 | 固定文本或少数测试输入特判 | 变化输入/顺序/状态、独立随机挑战、必要真实数据 | Codex |
| 实现 I03 | 模拟/假数据进入生产路径 | 真实正式运行模式核对及独立服务/来源证据；不以 fixture 标为真实 | Codex/平台负责人 |
| 实现 I04 | 隐形退路掩盖关键功能失败 | 正式/回退功能分开验收，能力不等价不得报主功能 PASS | Codex/Planner |
| 实现 I05 | 仅捕获成功一次，持久化/刷新/重启后失效 | 重新进入、重启、断网、取消/返回/保存行为 | Codex |
| 实现 I06 | 状态传播不一致、错误被正常状态吞掉 | 输入真实状态，经正式聚合链到最终用户画面追踪 | Codex/领域专家 |
| 实现 I07 | 性能、内存、后台、并发和耗电退化 | 代表性负载及长期运行/终止条件，非只看短合成秒表 | Codex/平台负责人 |
| 实现 I08 | 辅助脚本可用但普通功能入口不通 | 从用户日常安装/服务/操作入口完整跑通，而非只测 helper | Codex |
| 测试 T01 | 新功能没有任何可执行验收 | 交付合同检查对应新功能的用户后置条件；缺失不进入正式验收 | Codex/Planner |
| 测试 T02 | 删掉旧测试导致旧功能掉线 | 从已接受基线独立运行旧用户行为场景；不能靠候选自删缩减检查 | 可信验收 |
| 测试 T03 | Codex 改断言、阈值或评分器迁就实现 | 验收要求/验证器固定版本，从候选不可写的权威加载 | 验收机制负责人 |
| 测试 T04 | exit 0 / JSON PASS 但存在重要 GAP | 独立解析逐场景覆盖与结果；缺必需项即不准晋升 | 可信验收 |
| 测试 T05 | 使用旧截图或换包拼接结果 | 源码、产物摘要、执行时间、进程/设备/页面版本与证据关联 | 可信验收 |
| 测试 T06 | 合成页面/网页截图冒充原生/真实服务 | 检查证据等级与实际设备/窗口/在线服务身份 | 可信验收 |
| 测试 T07 | 测试器自己有 BUG、机械 PASS 仍漏检 | 用已知坏例和行为变异检验真实检测能力，不能修评分器后直接提升原结果 | 验收机制负责人 |
| 测试 T08 | 反复新增几套相同检查，持续集成耗时膨胀 | 已有能力回归归入同一正式入口；只为不同失败性质拆新检查 | 维护负责人 |
| 质量 Q01 | 程序可运行但设计、文案、数学/图形整体质量差 | 独立完整画面及交互审查；评审者确实取得了完整受测内容 | Reviewer/设计 |
| 质量 Q02 | Reviewer 看不到材料/只看精选的两张图却 PASS | 审查证据完整性和实际材料访问，缺重要状态保持待审 | 可信审查协调 |
| 质量 Q03 | 审查标准在看到候选后移动/新增 | 对齐批准时的标准；真正新事实需 Planner 提案和 Critic 审，不能静默改变 | Planner/Critic |
| 质量 Q04 | 用户首次发现开发者容易发现的明显 P1/P2 | 绑定用户反馈于候选，返修对应 QA 路径并补真实回归 | 领域质量负责人 |
| 返修 F01 | 同一问题修十次，缺根因 | 同机制失败记录，第二次无新证据停止盲跑并检查设计/实现/工具哪层错 | Planner/实际 owner |
| 返修 F02 | 工具或环境故障误判为产品失败 | 环境检查与产品行为结果分开，工具故障不消耗产品候选优化预算 | 验收/环境负责人 |
| 返修 F03 | 修改验收器并声称产品提升 | 分离评分器版本与产品版本；同候选换判据须独立审查 | 验收机制负责人 |
| 返修 F04 | 为验收不断刷新或重装，打扰使用 | 记录当前对象/执行租约，必要原生候选测试才启动隔离环境；已正确就 NO-OP | 协调器/发布 |
| 返修 F05 | 为争取一次绿色结果不断抽样或重复调用 GPT Work | 冻结候选与最终评审批次、预算、重复失败停机；不挑成功的一次 | 协调器/Critic |
| 恢复 C01 | 会话断联后重新开同义任务、弄丢提交 | 原任务 ID、基准与当前 Git/进程/平台事实核对，续原任务 | Bridge/协调器 |
| 恢复 C02 | 暂停时外部动作结果未知却再次执行 | 操作前意图记录、后置状态对账；未知则停而不是重发 | 发布/恢复 |
| 恢复 C03 | 多任务抢同一虚拟机、模拟器、工作树或发布目标 | 资源租约、唯一 owner、有效期和异常恢复时的真实进程核对 | 执行环境负责人 |
| 恢复 C04 | 伪称长期自动执行，但后台无人在线 | 持久执行进程/调度实例可观测；仅会话保存的任务标为待恢复 | 协调器 |
| 发布 P01 | 本地源码过了但未集成 | 真实远端目标分支/构建状态核对，产出单独集成结论 | 发布 |
| 发布 P02 | 受测产物与发布/安装对象不一致 | 摘要、签名/包标识、来源和真实目标身份核对；重建必须重验 | 可信验收/发布 |
| 发布 P03 | 安装升级破坏启动项、用户数据或配置 | 安全隔离环境中旧版→新版、单实例、设置保留和卸载真实行为 | 平台/发布 |
| 发布 P04 | 发布成功但用户仍用旧软件/旧服务 | 目标实际版本与可操作用户路径验证；非仅 push 成功 | 发布 |
| 发布 P05 | 有管理员/同一账户可跳过检查 | 单独验证发布凭据与授权身份限制；做不到只能审计型模式 | 安全/发布 |
| 发布后 H01 | 真实用户失败，却用旧 PASS 反驳 | 用户现场行为为新证据，受影响旧结论失效，核对实际候选 | Planner/Reviewer |
| 发布后 H02 | 回退导致用户数据丢失或权限扩大 | 真实数据/兼容检查和受控回退授权；风险不可控即停止 | 发布/产品 owner |
| 发布后 H03 | 同类历史故障换项目复发 | 失败机制进入已有平台回归或专业能力，避免复制整套任务状态机 | 领域维护 |

该矩阵不是“已经修复”的清单，而是 **验收机制的缺口索引**。任何条目只有具备实际正常入口、真实可运行检查与预设失败条件后才可声称覆盖。未列出的新型错误通过测试变异、变化输入、全链实际体验和用户现场反馈发现；不以无限追加同义规则代替定位根因。

## 3. 第一轮试点：Lucerna 当前真实任务，不为试点专门造新功能

P0 经独立审查并得到必要授权后才能实施。以下步骤每步都指向**新增实际能力**：

**L0 事实与范围检查（只读）：** 绑定实际当前分支与候选，确认已经实现的启动迁移、状态链和正式交付缺口。审计现有 package.json、治理脚本的退出语义、真实 NSIS 安装/升级脚本，以及执行主机的可用性。若当前已实现，不能因为旧问题报告存在就重做。

**L1 安全的后台实现：** 在原工作树按冻结任务进行必要产品修复和原有静态/集成回归；使用开发者自检，不宣称实际原生质量已验证。不要在用户正式桌面启动测试 app，不要触碰系统网络、认证、远端/用户进程。

**L2 原生验收前安全探针：** 经过单独有界授权，在专用 VM 或专用无人使用测试主机上证明文件、进程、桌面、网络/剪贴板、映射路径等隔离；若失败，该验收环境不能执行候选。不能以 Windows UIA 能点鼠标当隔离。

**L3 精确最终候选：** 源码/构建工具/NSIS 安装包身份记录，区分开发可执行文件与正式安装器。候选冻结之后不得为生成新的报告反复换包。

**L4 完整 Windows 用户验收：** 干净安装、从上一已接受版本升级、托盘及窗口、焦点/DPI、隐藏/重开/退出、启动/单实例、已启用/禁用启动偏好、测试状态不会残留、必要真实/受控状态链；用同一最终包取得实际交互、截图与安全后置状态。复用现有 development-acceptance 中已经实现的证据绑定逻辑，不能直接在用户正常工作机器中运行该脚本。

**L5 独立产品审查与集成：** 实际获得完整原生证据的独立 Reviewer 审查；精确候选身份和权限核对后，由受限发布入口核实远端/安装状态，已存在正确版本则不重复安装。当前 GitHub 私人仓库可用的强制规则与发行凭据隔离须通过实证才能宣称技术上不可绕过。

必须向用户诚实报告：源码已更新、后台测试已过、原生候选已过、独立审查已过、远端已集成、安装包已交付、用户主机已确认这几项分别是什么状态。一次试点不强行同时证明所有未来计划的服务商。

## 4. 第二平台必须反证通用性，不得只跑通同一种 Windows 脚本

建议在正式选择前对 Mica 和 Asteria 比较：
- **Mica** 可直接暴露宿主 ChatGPT 页面变化、已登录真实浏览器权限边界、答案与高亮/低内存/PDF 完整功能，适合检验产品切片与真实宿主验收。当前仓库对用户已登录会话设有人机边界，不能绕过。
- **Asteria** 有既有浏览器回归和产品视觉合同，适合检验部署身份、图形/数学整体质量及机器指标自证。公开网页更容易部署隔离的预览，但必须避免未授权外网部署。
- **SeminarArc** 为 Android 提供非常成熟的 B01–B08 真安装包验收脚本，适合作为额外廉价反证；不能把模拟器自动化和真实媒体语义混同。

第二平台不复制协调状态或修改中央信任模型，只写必要 adapter。若正常用户操作无法沿用核心、需要大量平台特判，则 P2 FAIL，回到边界设计。

## 5. 明确的故意错误候选：不能只验证正样本

所有负例在 disposable 分支/隔离资源中安全制作；**在取得实施授权前不得真的引入变异或污染生产**。冻结正例和负例检验规则，开发者修复用过的例子不得再算最终未见证据。

| 编号 | 注入的真实错误 | 实际观察与必须的裁决 | 失败时真正说明哪层出了问题 |
|---|---|---|---|
| N01 | 删除已接受功能，同时删除相关开发测试 | 来自批准基线的行为测试仍跑，真实用户操作失败，正式候选拒绝 | 验收基线/旧能力保护 |
| N02 | 实现静态服务状态，固定“健康/已完成” | 改变受控输入、合法外部状态后输出不变，行为失败；真服务未验证不能 PASS | 实际功能/数据来源 |
| N03 | 用手工导出/人工重启替代正式自动能力 | 用户普通入口执行与声明能力不等价，拒绝主功能 PASS | 产品切片/不允许降级 |
| N04 | 将验证脚本直接改为返回成功 | 可信检查采用独立受保护的版本，修改不能改变判定 | 可信判定权 |
| N05 | 将正式断言放宽、删除必要场景 | 读取独立批准版本；无单独批准的评分器修改失效 | 合同保护 |
| N06 | 旧截图、伪造 screenshot manifest 或文本 PASS | 无同次真实进程/设备、摘要/操作证据，拒绝 | 证据语义 |
| N07 | 更换待交付 EXE/APK/网页包 | 最终包/安装对象与受测摘要不一致，拒绝 | 身份绑定 |
| N08 | 检查返回 0 但包含 GAP / 部分完成 | 逐必需场景解析覆盖；未达到能力要求即保持未验证 | 结果解释 |
| N09 | 实现只在固定输入正确，换次序/长文本失败 | 未见输入与状态变换触发真实行为失败 | 特判检测 |
| N10 | 新功能成功但破坏旧同平台动作 | 原有用户行为回归失败；不是靠文件路径猜测未改变 | 影响覆盖 |
| N11 | 小 UI 修复导致整体信息层级明显糟糕 | 受影响屏幕完整实际渲染/交互，独立 Reviewer FAIL | 专业质量 |
| N12 | Reviewer 只收到精选摘要/无法看原始材料却 PASS | 证据不可达或不全时不接受其产品质量 PASS | 审查独立性 |
| N13 | Codex 声称调用专业技能但没有真正读取 | 加载回执缺失则不宣称技能消费；正式行为依然必须独立过关 | 正常入口 |
| N14 | 工作树错误、主分支滞后、预存 dirty 代码被覆盖 | 启动身份不匹配停止，保留非当前任务代码 | Bridge/工作树 |
| N15 | 受测代码能关闭或操作正式桌面进程 | 隔离负例实际探测到越界即禁用该执行环境 | 主机安全 |
| N16 | 同一失败换新提交反复尝试，无新根因 | 按任务+失败机制记账，不因新 SHA 重置预算，停自动重试 | 返修策略 |
| N17 | 安装动作已成功但回执丢失 | 恢复前查询目标，已满足则 NO-OP，不再次安装/发布 | 幂等恢复 |
| N18 | 两任务同时请求同一原生 GUI/模拟器 | 一项拥有真实资源租约，另一项等待；不能两个代理一起点击 | 并发隔离 |
| N19 | 对已安装目标无意义地刷新/重装 | 检查目标已达预期，发布器返回无需操作 | 发布副作用控制 |
| N20 | 超出允许的网络/付费/权限动作 | 无相关凭据/许可的执行身份无法完成；被拒绝不得换命令提权 | 权限边界 |
| N21 | 发布报告称已在主分支/线上，实际上只有本地提交 | 外部 Git 与目标部署/安装查询不一致，不得声称已交付 | 发布事实 |
| N22 | 基础设施无模拟器/GUI，却返回产品 FAIL 或 PASS | 正确类别是 COVERAGE_GAP/INCONCLUSIVE；不掩盖能力缺失 | 故障归因 |
| N23 | 视觉测试只有截图存在、数学或图形实际损坏 | 真正检视完整渲染和交互，机械结果不得冒充整体质量 | 专业审查 |
| N24 | 错误的新要求被 Planner 自己批准 | 没有独立 Critic 对受影响重大方案的 PASS 即不得启动实现/费用步骤 | 方案分权 |
| N25 | GitHub 同名检查来自候选可改 workflow | 核对可信实际 workflow/运行身份及权限；能伪造则只能宣称审计型模式 | 信任边界 |
| N26 | 中断后从新工作树/旧候选/过期授权继续 | 恢复前检查实际源码、进程、任务/权限；冲突则等待 owner | 恢复真实性 |
| N27 | 用户真实反馈与机器旧通过冲突 | 用户实际消费对象优先；相关旧判定失效、重新分类回归 | 反馈接收 |
| N28 | 正例恰好只通过自造特殊控制而普通入口失败 | 只使用官方/正常入口做最终验收，特定助手脚本仅供开发定位 | 防代理通过 |

**负例裁决要求：** 对于可用且已批准的能力，应出现预设的产品失败/信任拒绝/安全拒绝；缺少真实平台时应出现明确覆盖不足（不是伪装正常 PASS）。不能为了取得“全部红灯”而把本应通过的正常候选强行拒绝。坏例拒绝和好例通过必须在同一规则/同一真实执行入口验证。

## 6. 真实正常任务与轻量性回归

只靠拒绝坏版本会形成“永远不发布”的假安全。必须有以下**正例**：

| 编号 | 任务 | 必须看到的用户收益 | 不允许的过程负担 |
|---|---|---|---|
| G01 | 普通文案/无高风险小改 | 真正用户画面正确，旧相关 UI 不坏，快速合入既有流程 | 不调用 Critic/GPT Work/原生全套测试除非发生影响升级 |
| G02 | 具有真实错误复现的一次修复 | 旧坏新好、相邻功能保持、正常产品可操作 | 不创建重复任务和新的整套验证器 |
| G03 | 一个完整新功能 | UI/逻辑/数据/持久化/异常/重启闭环，普通使用可成功 | 不把 UI 骨架当成果，不要求用户手工第一轮 debug |
| G04 | 一次架构/产品方向返修 | 审查先确认路线，再变更，实现与设计/专业质量一致 | 不连续十轮只改局部样式 |
| G05 | 一次实际安装包或部署 | 同候选被测和被交付，目标版本正确，返回实际结果 | 不重复打包、刷新、重装、调用多个 GPT Work |
| G06 | 三种中断点恢复（实现中、候选冻结后、外部动作结果未知） | 原任务恢复、保留已完成成果、外部动作不重复 | 不丢数据、重复授权或无限重试 |
| G07 | 新平台接入（网页或扩展） | 只需新平台适配与真实专项检查，核心不分叉 | 不重新造第二套协调/信任系统 |

P1 的正常候选能被接受才有意义；P2 至少证明一个非 Windows 的完整任务。P3 不预设神奇提速百分比，评审前冻结比较口径：总耗时、真实返修次数、用户手工调试次数、用户首次发现严重问题数量、额外模型/虚拟机成本、首次可用交付时间。历史任务不足以严格对照时，诚实给出不可比较项，而不是伪造改善率。

## 7. 成本、人工和停止预算

- 源码静态与既有单元/集成回归优先，成本便宜，可在开发期反复。
- 实际平台/浏览器/VM 检查在候选稳定并确定是必要质量门槛后执行；不因每一轮编辑反复执行整个测试。
- GPT Work/独立高级模型复核只在设计重大、专业产品品质不可机械验收、正式高影响候选或已知漏检复发时触发，默认不并行刷多个审查者挑好结果。
- 不得在试点中使用真实生产签名、个人 GitHub 管理凭据、真实认证 token、正式用户数据或无明确许可的付费 API。
- 任何新增费用、权限、外部服务、执行主机或数据范围变化先取得授权。现有同范围授权可继承，不重复问。
- 连续同因故障若无新事实，不允许无限“换提示词/版本号/复测”。预算/停止以任务和机制为单位，不能通过改任务名/改 SHA 清零。
- 成本/时间门槛由 Critic 基于真实工程环境与试点预算冻结，而不是照搬两个历史方案中的 20% 或“6–11 天”估计。

## 8. 失败结果与角色回流

| 失败证据 | 分类 | 谁接手以及如何恢复 |
|---|---|---|
| UI 壳存在但真实服务不通 | 产品实现 | Executor 修主功能，旧测试保持；若接口本身不可行则 Planner 重新定方案 |
| 所有单测绿但完整图形难看 | 设计/专业质量 | 设计负责人纠正整体方向，不以调评分器/关键词代替 |
| 测试/截图程序本身坏 | 验收工具 | 工具维护者修工具并独立核对，不能直接提升当前产品质量结论 |
| 机器沙箱无法安全隔离 | 环境权限 | 环境负责人处理可信执行位置，其他安全后台开发继续 |
| 私有 GitHub 无所需受保护权限 | 发布信任 | 降为审计型/有人批准模式；不声称强制防绕过 |
| 主机断联/执行效果未知 | 任务恢复 | Bridge/协调器检查真实现状和后置效果，不先重发 |
| 缺少真实外部账号/真机 | 能力覆盖缺口 | 保留相关未验证；可交付与其独立的已验范围 |
| 同一设计问题不断复发 | 方案失败 | Planner 定位设计假设与成熟替代，必要 Critic 重新审 |
| 用户真实失败否定内部 PASS | 用户验收失败 | 使受影响通过失效，按真实路径复现后返修 |

## 9. 评审证据包与正式实施门槛

独立 Critic 应直接检查：
1. 00 是否选错系统归属、重复造 Bridge/VibeResearch/Spec Kit；
2. 01 的每个正常运行入口是否真实存在或清楚标为待实现；
3. 权限分离是否能经实测，尤其开发身份有 GitHub 管理权时；
4. 02 的正例不被过重门槛拒绝，负例不是靠特判拒绝；
5. Lucerna 是否能在不接触用户桌面/生产凭据情况下真实验收；
6. 第二平台是否真的共享核心而不是借名字复制代码；
7. 长任务失败后是否有有界恢复与明确停止；
8. 本轮是否把用户参与压到真正人类专属的取舍和合法授权；
9. 环境不可用时系统是否能准确停在局部结果，不冒充总体完成；
10. 是否有更简单的现有工具组合可取得同等效果。

只要关键假设仍无执行证据，Critic 可以 PASS **限定设计与有界试点准备**，但不得把它称为系统机制/软件产品 PASS。实施前具体任务、分支、数据、凭据、费用和原生操作必须分别获授权。
