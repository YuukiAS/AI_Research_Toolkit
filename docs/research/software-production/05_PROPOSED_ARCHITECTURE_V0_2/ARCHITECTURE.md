# 研工台：六仓库软件生产系统——完整架构提案 v0.2

日期：2026-10-13。作者角色：Planner。状态：供用户判断的完整提案，**不是已实现系统，不请求用户现在运行Critic，不包含实施授权**。研究资料继续放在用户允许的当前分支；未来正式代码仓库位置由用户决定。本版替代上级00–03中关于“只需新规范/中央验收器”及尚未选定产品形态的结论，原文件保留历史。

## 1. 选择：一个独立版本化的生产运行包，而非插件或Bridge大版本

**研工台是一套项目感知的软件生产运行包：任务监督进程＋专业智能体调用＋六仓库执行适配器＋经校准的独立验收通道＋受控交付。** 它拥有软件任务从目标到交付的推进责任，但不取代Codex编程、Bridge执行机制、专业插件或产品业务逻辑。

运行形态明确分开：

- 用户入口：在GPT Chat/Codex中用“研工台”指代同一任务；本机提供正式任务启动、继续、暂停和查看入口。自然语言入口最终只是向运行包发请求，不能自己签发通过。
- 活动任务：由任务所属主机上的监督进程执行有限的下一步、派发Codex、调用测试、取得审查结果并安排返修；不能仅生成下一段提示词后结束。
- 长期事实：继续使用各项目现有Goal、Git与发布记录。监督进程只保存不能从这些事实重建的运行标识、资源租约和外部操作对账记录，不建立第二份产品需求库。
- 质量裁决：独立测试程序/观察进程、看过完整实际产物的本地独立产品审查者以及必要GPT Work，按各自证据范围裁决。编码会话自报不推进正式完成。
- 用户观察面：第一版使用GitHub任务页/检查结果与现有对话的简明视图，不先造另一款聊天软件。接口必须足以表达当前真实成果、阻塞、下一步和是否需要用户；以后有真实交互不足才加专用图形操作台。
- 生命周期：一次任务运行到完成或真实暂停条件后退出，不默认建立中央永驻服务。要求断线后继续的任务必须提前配置真实寿命拥有者；没有在线主机只能保存和恢复，不能承诺后台在跑。

这是**独立的软件产品层**，未来宜独立分发版本；不是把代码藏进AI_Skills的一项Skill，也不是给Bridge增加第四种工作模式。首版不需要自己的数据库服务、全局队列、模型平台或插件市场。命令行是入口，GitHub事件是触发器，它们本身不等于完整工作流程。

## 2. 为什么不是其它路线

| 路线 | 为什么不选为完整体系 | 保留什么 |
|---|---|---|
| 只增加规范/Skill | 已有规则被忽视，或被执行成形式检查；无法独立否定自报完成 | 插件提供专业知识、任务理解和设计方法 |
| 只加可信验收器 | 错误产品目标、错误设计、假夹具和错误测量会被稳定执行；Mica已有验证器仍反复修 | 候选身份、结果范围与检查器校准 |
| Bridge全包 | 执行/交接不是产品含义、视觉、数据库和服务语义；现有Review/Control角色也不能被任意扩写 | 主机身份、许可、工作树、等待、已有运行寿命和发布辅助 |
| 六仓库各做一个控制器 | 重复恢复和证据处理，用户要记六套流程；已有有效项目合同又不可全删 | 项目原有业务、测试、设计与特殊分支约定 |
| 直接采用VibeResearch | 真实代码可复用，但当前调度/成熟度/指标带科研周期和Slurm语义；不能强套应用发行 | 对账、预算、最小状态和失败机制经验，逐项选择性复用，不复制整个内核 |
| 直接采用OpenHands或持久任务大平台 | 不能自动解决六仓库的独立测量、专业判断与权限；引入另一套环境/账户/运维先拖累交付 | 当真实多机长期运行超出当前后端时，作为可替换执行后端评估 |
| 独立小运行包＋现有能力 | 能把缺口集中在“真正调用、正确观察、据实推进和可靠恢复”，专业行为留在既有owner | **本版推荐**；前提是下面的接口和反例能经真实试点成立 |

本版不把“既有工具缺少跨项目接口”理解成必须重写既有工具。模块实现时发现现有Bridge或Mica控制已可完成该职责，应直接适配，删去重复模块。

## 3. 由哪些真正组件组成

建议用TypeScript实现薄运行包，优先复用官方Codex SDK而非自己发明模型会话协议；平台测试仍用各仓库现有PowerShell、Python、Rust、Gradle和Playwright。下列路径是**拟实现接口**，并非现存命令；本版没有安装、运行或验证它们。

| 拟议文件/决定性函数 | 真正职责 | 不能越过的边界 |
|---|---|---|
| `src/scope.ts::resolveTask, resolveRequiredJourney` | 从当前已批准Goal和旧能力取得本次完整路径、影响范围与真实交付目标；拒绝任务漏项、自选较小清单 | 不以模型自动补出的需求替用户批准，不重写Bobbio分支或Mica优先级 |
| `src/supervisor.ts::advance, dispatch, reconcile` | 驱动一个有界任务，调用实现/测试/审查，失败回正确owner；有活动进程才显示运行 | 不凭自报PASS推进；与已有Reviewed/Control只能一个状态拥有者 |
| `src/backends/codex.ts::startOrResume` | 经允许入口启动或继续当前Codex，流式取得工具/修改/结果事件，给视觉审查实际图片 | SDK或CLI环境必须与用户当前合法身份/配置一致；不擅自切到付费API或新CODEX_HOME |
| `src/backends/bridge.ts::inspect, resume, publishAuthorized` | 消费Bridge既有权限、工作树、运行与有界发布接口 | 不复制Bridge状态机，不直接改其CURRENT绕过角色 |
| `src/check-plan.ts::selectRequiredChecks` | 必需用户路径＋受影响已接受行为＋相关历史事故＋本次发行要求，编成最小检查集合 | 不能仅按diff文件数判风险；不能让代码作者删掉难测集合 |
| `src/observers.ts::runApprovedObserver` | 以明确包/设备/账号/输入执行项目原有真实场景，保存原始观察和证明范围 | 只调用批准入口/参数；不从候选JSON读取任意shell；初始化/清理副作用必须单列授权 |
| `src/claims.ts::evaluateClaim`、`src/evidence.ts::bindEvidence` | 检查每个声明是否有相应真实观察，是否缺测、错类、错候选、评审未到达 | 哈希只证明字节身份；不把退出0、目录存在、JSON通过升级为产品能力 |
| `src/review.ts::prepareReview, acceptReviewResult` | 给独立本地产品审查者完整实际材料，必要时交GPT Work，结果绑定对象/范围 | 用户不搬运普通子角色交接；没有真实调用入口时等待，不能假造审查 |
| `src/recovery.ts::classifyFailure, reconcileEffect` | 区分实现、设计、观察器、环境、权限、外部依赖；同因无新证据不盲重试；查询已发生效果后继续 | 不通过换SHA/新任务清零成本；不把等待外部角色当失败 |
| `src/delivery.ts::admit, inspectTarget, promote` | 核对可信结果与目标版本，已正确则不再安装/发布；执行后验证实际目标 | 发布凭据独立；不能只依赖候选提供的绿色状态；未授权不改生产 |
| `adapters/<repo>/` | 把上述稳定接口接到六仓库的已有任务、构建、原生/浏览器测试和交付机制 | 平台业务和审查语义不迁到中央；原有已批准流程不能被新层覆盖 |

这些函数可合并到少数文件，数量不代表架构价值。**决定性区别是它们在正常路径中调用真实动作和独立判断，不是给Codex打印一张清单。** 详细的输入/输出/阻断及每个历史类别的覆盖见[控制机制](CONTROLS.md)。

官方Codex SDK本次读取证实它封装CLI、支持`runStreamed()`事件、`resumeThread()`以及图片输入；这支持实现后端的可行方向，**不证明用户主机当前版本、审批策略、额度或多会话权限已可用**。不能把这份SDK介绍当本环境的自动化验收。[O1]

## 4. 每个角色是什么，不是什么

| 角色 | 实际作用 | 是否每次需要 | 不能做什么 |
|---|---|---|---|
| 用户 | 目标、取舍、数据/费用/外部效果授权，真正人类专属操作 | 必要时 | 不充当例行测试员/转发员 |
| GPT Chat Planner | 解释目标、读取真实源、选择成熟路线，决定设计/任务范围和重大失败归因 | 新目标/实质歧义/大变更 | 不能替独立审查自批 |
| 设计智能体 | 通过Frontend Design实际消费Figma/产品系统，设计整屏和主要状态，不只做最后润色 | UI新功能/重大改动；小改沿用 | 不能为实现方便改科学含义或偷偷缩功能 |
| Codex实施者 | 正常实现、开发回归、首次实际自检、常规返修 | 代码任务 | 不能拥有正式裁判/发布权，不得把被关闭功能当完成 |
| 测试/测量审查者 | 检查“观察的是否真是声明性质”，校准正坏例、审核测试迁移 | 首次接入、新测量、验收器变更或同因漏检 | 不是每次另开一次大审查；不能用自身通过自证 |
| 独立本地产品审查者 | 在用户/GPT Work之前实际看完整渲染及操作结果；找未知缺陷和明显P1/P2 | 新用户能力/实质UI变更；小改按风险 | 不接收实施者“已无问题”的结论作为答案，不修改受测实现 |
| GPT Work | 稳定候选后的独立整体体验、跨界盲区及仓库要求的最终复核 | 仓库合同/发布/重大产品变化要求时 | 不作为首次验证按钮/状态/保存/像素是否可用的劳动力 |
| 监督程序 | 任务事实、执行、检查选择、预算、恢复和归类结果的机械推进 | 有运行的任务 | 不替专业角色作审美/科学判断，不制造新授权 |
| 可信验证与发布者 | 使用被保护检查源与观察执行身份，受限集成/交付 | 相应交付范围 | 不能被产品写权限任意改写，不能拿管理员例外声称防绕过 |

角色不是同等数量的常驻智能体。普通小修复可以只运行一个Codex和相关已有检查；改变测量规则才调测量审查；重大UI才让设计与实际画面独立审查深入参与。未来正式实施所需独立方案审查仍存在，但**本轮不启动也不要求用户跑Critic**。

## 5. 一次功能开发的真实顺序

### 5.1 先锁定用户能力，不锁死代码实现

监督程序读取当前任务和用户认可基线。Planner/领域角色明确：用户怎样进入、什么输入、得到什么结果、正常/异常/取消/重入是什么、哪部分已做不重做、哪些旧能力不能坏。对于外部服务，先核实受支持的真实接口和当前权限，再做最小真实读取/隔离契约验证；不先做完整漂亮假数据界面后才发现接口接不上。

定义本次所需检查为“完整目标路径、受影响旧行为、相关历史失败、交付目标要求”的合并去重集合。已有未修的问题若是新功能必经依赖，必须在同一任务内先处理或明确依赖阻塞；无关缺陷不能让安全局部开发停摆，也不能从最终全产品完成声明中消失。

### 5.2 先验证设计与关键机制，再铺开实现

Frontend Design调用产品交互、视觉方向、组件/状态、必要Figma和文字能力，产生主屏、关键展开、错误/鉴权/空状态的真实设计目标。设计缺状态就由设计负责人补，不让Codex临场增加一张大卡片。

关键用户能力先完成一条生产纵向路径：实际输入→正式解析/业务→持久化/状态→实际UI结果。对服务接入，真实契约样例与生产解析器必须一致；对Asteria，布局坐标必须落到真实屏幕；对Bobbio，权威仍是Zotero；对Mica，关闭扩展不能算附加收益；对SeminarArc，点击保存后必须实际写入；对CUHK Date，真实表单流程不能被API代跑。

### 5.3 边开发边检查，但不边开发边刷新用户软件

Codex用小而明确的失败复现和相邻回归推进。夹具允许复用，但只替换声明的外部输入，不能另造最终业务状态或headline；数据来源/场景类型明确。真实服务证据、受控状态证据和纯逻辑证据分别保留。

合并一批相关改动后，才在任务隔离的应用/浏览器/设备上检查实际行为与画面。用户当前实例不承担试验。禁止每次修改都重建发行包、重开完整产品或重复整套GPT Work。

### 5.4 实施者自检之后，还有一次内部独立检查

首先执行确定性功能/回归；其次由独立本地产品审查者看当前完整必要画面、主要动作及真实状态，不能只看精选局部裁剪。它不以生产者填写P1/P2=0作为结论。新增/修改验收器时，测试/测量审查者先证明原坏候选确实被它识别、好候选能通过；不能冻结一个恒零计数器。

若产品自检或内部独立检查发现基础P1，修复与复测由原Codex任务内部完成，不交用户或GPT Work再次发现。同类失败没有新增根因证据，退回正确机制层，不新建同义Goal。设计错则回设计，观测错则修观测器，外部服务错则不改产品语义。

### 5.5 冻结稳定候选，专业复核，受控交付

产品源码、实际运行包与签名/安装包按真实构建关系绑定。运行证据、交接说明、最终回执分开，不让文件包含自己尚不存在的提交哈希。修改说明文档不必重新跑所有运行测试；修改实际运行包或对应验收语义则使受影响结果失效。

满足内部条件后才进入仓库规定的GPT Work整体复核或最终用户步骤。集成与发布身份检查必要声明全部有效，实际所需检查没有被跳过，产物和目标一致，权限在范围内，已达目标就不重复执行。源码合入、安装包生成、发布、用户机器生效是不同声明。

## 6. 如何不再靠“fixture越刷越绿”

每条夹具必须说明它模拟的是哪一处依赖、根据哪个真实契约或观察、使用哪个实际业务模块、能证明哪项性质。**允许模拟I/O，不允许模拟本轮要验收的核心答案。**

四条硬规则由测试计划、项目驱动和结果消费一起落实：

1. 正式状态链不得有只对测试输入有效的语义。Lucerna不能给Workstation塞`FIXTURE`再让真实聚合器忽略它。
2. 必需真实证据不可由更多合成成功替代。增加100个夹具也不能证明R2已接通或当前ChatGPT能用。
3. 测量有正/坏对照。Asteria的交叉数输入变坏仍恒零，就应使这个观察器失去对应裁决资格，而非把它锁定成为可信基线。
4. 同一次失败回放若没有新证据，不产生新进度。记录实际产品差异、根因和成本；不得仅更新截图、任务号和自报结论来消耗另一次审查。

本地回归集不是禁用对象。要停止的是**用其证明不了的成功冒充产品完成**。SeminarArc通过实际安装包黑盒找到服务崩溃、通过观察器校准撤销OCR假阴性，就是应复用的正例。

## 7. 防回归和防验收篡改：保护的是用户行为，不是旧实现字串

现有已接受用户能力先绑定到有效基线和项目真实检查。新增功能的验收预期在正式候选评估前得到独立确认。实施者可补开发测试、重构内部实现；但不能单方面删除旧用户能力、降低正式断言、挑选更容易的输入后继续使用原来的通过结论。

`check-plan.ts`从独立批准集合选择必要场景，`evidence.ts`核对执行与原始结果。涉及旧测试迁移，测试审查者记录旧行为由哪个新检查继续保护，区分该退休的是实现细节还是用户保证。Asteria修布局可迁移旧RC实现断言，不得一起失去科学真值/真实渲染保障。基线比较必须包含批准base到候选的提交差异、暂存与未暂存状态，不只查工作区是否干净。

程序、裁判和发布仍由同一高权限身份任意改写时，只有“审计型验证”，不宣称技术强制。达到强制型必须用独立受保护运行位置和发布凭据，对同名假检查、修改验证器、跳过测试等做负面实测。GitHub官方说明有写权限者可提交检查状态，必需检查可指定来源App；而跳过的作业也可能显示成功。因此**绿色图标不是判定本次必需检查真正执行的充分条件**。[G1–G3]

发布准入需依据被批准的本次检查集合，核对实际运行身份、结论、覆盖和产物。最终汇总作业即使前置失败也要执行结果解释，不能因依赖失败而被跳过后让合并误放行。对确实不适用的检查记录有依据的排除，而不是全部一律不许跳过。

## 8. Bridge和插件怎样参与，不制造重复控制

### Bridge

复用Host的CODEX_HOME/批准/工作树/运行身份，复用有界发布和外部等待，寿命交由现有真正拥有进程的后端。`persistent-run prompt kickoff`只是生成授权文本；tmux/既有调度器是否真正运行必须实测，不能给Windows桌面任务凭空加tmux就称无人值守。

默认日常软件任务使用项目现有Lite/普通任务入口，研工台填补其产品级调度与证据消费，不强制升级所有任务。**已经使用Reviewed或Control的任务，以该现有CURRENT和角色协议为唯一拥有者**：研工台适配结果，不建立平行状态机，不强行添加被Review明确禁止的Verifier/哈希证明图。若确实需要改变现有协议，应明确提出改动，不静默实现第四种Bridge模式。[B1]

### workflow-core

负责工作方法、权限/阶段/停止与真实证据原则的专业指导和正常触发；程序负责把这些要求接入实际运行。已有规则未生效先修调用/消费，不再增加同义规则。它不因为是通用工作流插件就自动拥有六种产品的专业判断。

### Frontend Design及领域插件

Frontend Design在需求/设计/实现中/整屏审查都参与，负责产品层级与视觉而非仅美化。`product-ux-planning`、`visual-direction`、`design-system-tokens`、有需要的`figma-design-to-code`、`responsive-accessibility-review`及科研产品能力按任务选择；Clear Writing只在含义与信息角色清楚后润色。Android/Compose、Rust原生、数据库/匹配/隐私、科研语义仍由专业owner和真实代码测试承担。不能调用一次插件就宣称专业正确。[F1]

插件安装包/配置和实际当前会话加载版本分开记录；升级后旧会话没有加载，就通过合法新会话继续原任务。插件重放是验证插件使用的特定入口，不是授权嵌套Codex随意操作生产机。

## 10. 不过重，也不能放弃正确性

选择检查不能只靠一个模型给风险打分。基本集合有四部分：本次用户承诺真正需要的路径、当前修改影响的旧能力、这些路径曾暴露的失败机制、当前交付类型必需的证据。重复项合并，不相关的246项不全部跑。

- 文案/小样式：沿既有设计，相关屏幕及布局回归；不自动Planner–Critic、所有设备、GPT Work。
- 单点逻辑修复：旧坏新好和相邻正例；不重做产品架构。
- 新用户能力：最小真实纵向路径先通，再扩状态/错误/持久化与内部独立产品检查。
- 核心共享状态/认证/存储：扩大至全部消费者和失败路径，不能因只有一个文件就缩小。
- 正式发布：精确目标、相应平台、所需独立结论、升级/部署后置结果；不把每次源代码提交都当发布。

首次接入项目需要一次**校准现有基线**：被历史用户推翻的绿色报告不能当好样本，存在有效已接受行为则保留。不会要求所有六仓库先停工重建整套测试；先接Lucerna正在需要的任务，再用不同平台的真实任务检验公共边界。

## 11. 连续执行、失败归因与不扰民

一次交办绑定一个任务、允许的资源/目标、当前工作树与候选。监督进程监听真实Codex/测试事件并按阶段推进。它不能保证主机永不离线，但可以保证已完成代码、证据与外部动作有可重建事实：恢复先查询进程、Git、包、实际安装/部署、原授权，再继续缺的步骤。

已有进程不重复启动；已消费的票据不再使用；已安装正确版本不重装；安装回执丢失先查目标，不盲重试。无必要GUI动作不进入用户桌面。资源租约按实际浏览器上下文、模拟器、原生测试机和发布目标，而不是只按任务文本。

故障分类进入同一任务：代码→Codex；设计→设计负责人；测量器→测量负责人；输入/夹具→准备者；外部依赖→对应环境；权限→真实授权方；审查争议→Planner。没有新事实的同机制重复失败停止“盲跑”，但可以继续根因取证；不把整个目标每次改成新Goal。等待外部角色不计返修，不将Bridge的等待下限当自动失败deadline。

“减少用户/GPT Work发现P1”的目标，是把首轮真实运行、事务/状态回归和完整画面检查移到内部交付前。**不是承诺第一次代码生成零bug，也不是取消独立外部审查。** 单次交办可以包含合理内部修复；若需要用户重新选产品方向/新凭据/费用，仍必须暂停对应动作。

## 12. 完成判据与撤回条件

本版完整提出了目标形态、组件和责任；尚没有运行包，不能写已解决全部复发。正式有效性要在获准试点时逐类证明：

1. 同一真实用户任务，正确实现能完成；隐藏功能、固定假数据、跳过实际UI、删旧测试的实现不能获对应能力通过。
2. 验收器能对历史坏例产生正确失败信号，同时不过度拒绝正常好产品；错误测量不会因被保护而变可信。
3. 明显整屏/状态/动作P1在内部阶段被发现，外部Work不再承担首次基础QA；漏出则作为生产系统回归，不只修当次产品。
4. 至少桌面与一种非桌面共用核心，不为每个平台复制状态机；小任务不被强行全流程评审。
5. 断线、证据修复、外部效果未知时恢复原任务，避免重复请求/发布；预算按任务根因不按新SHA重置。
6. 总体收益看首次真正可用交付时间、用户调试次数、同因返修、旧能力回归及真实总成本，不预设无证据的固定提速百分比。

如果只是把246项分配给12个角色，或把旧脚本集中运行但不修它们的观察缺口，这条路线失败；如果需要先建庞大平台才能继续Lucerna，也应收缩。**防止已知问题再次被当成完成交付，是可以设置明确失败条件的目标；任何有限测试/模型不能证明全部未来缺陷永不出现。** 这个限制不能被拿来放松已知事故的逐项覆盖。

## 13. 与旧资料的关系及实际写入范围

旧账本保留原始证据、性质与固定快照；新架构的K01–K12映射和新增LX/AX根因见[控制机制](CONTROLS.md)，完整示例见[Lucerna一次功能开发](LUCERNA_FEATURE_WALKTHROUGH.md)。本轮只写研究分支，不改六仓库产品、中央插件/Bridge、不创建服务或发布、不运行Critic。
