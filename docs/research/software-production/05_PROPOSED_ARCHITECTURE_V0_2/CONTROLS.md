# 逐项问题如何进入具体防复发组件

本文件与[架构v0.2](ARCHITECTURE.md)共同阅读。246项原始问题的逐项来源、性质、现有脚本已在[六仓库账本](../04_SIX_REPO_AUDIT/README.md)和[CSV](../04_SIX_REPO_AUDIT/problem-control-map.csv)保存；本轮[补查](INCIDENT_ADDENDUM.md)保留25项新增/细化观察，不重复冒充独立事故数量。

下面将CSV的K01–K12直接绑定到**拟议程序调用点、真正执行的旧脚本/专业角色、失败条件、校准反例和范围**。因此任意一项问题的完整定位是：问题行→K条目→本文件具体函数→该行列出的本地脚本/角色→规定实际观察。没有“一个负责人会处理”的空白控制。K不是12个新服务；未来实现可合并文件，但必须保留这些不同性质的证据责任。

所有`src/*.ts`均为拟议运行包代码，不是本轮已经创建或执行的程序。所有现有脚本仅拥有已经核查的能力；只读源码不是当前生产功能验收。

## 2. K01：防止漏需求、做小半截、旧任务无限重开

**触发位置：** 任务接入、变更范围、准备候选和宣布完成四处。不能只在结束时看TODO勾选。

**输入：** 原始当前要求、被批准Goal、既有产品/设计来源、实际已接受能力、本次交付类型和授权。程序校验引用及集合，Planner判断语义。任务文本/外部文档属于输入，不能自行扩大命令/凭据权限。

**输出：** 每项用户能力对应完整操作路径、必须保留项、相关依赖、证据要求和合法排除。最终原集合每一项只有已证明/获准延期/仍缺证据，不能由实施者用一个较小集合覆盖。未实现backup-health不能关闭其报警；“能打开设置”不等于“已配置且正常工作”。

**正/反验证：** 原目标含设置/正常读取/错误恢复/重入，候选只有设置页时拒绝完成；实现四者则接受。过期Goal中停止限制不能覆盖后来的明确同范围授权，但新效果仍不授权。已接受功能已经存在时不得重做。

**覆盖：** 所有CSV含K01项；新增LX01/LX06/LX18。只检查集合仍无法发现错误产品目标，因此需要Planner/领域判断，不能把JSON完整当需求正确。

## 3. K02：防止审美假绿、错误产品结构、把设计文件当完成

**触发位置：** 新UI功能设计、第一条纵向功能渲染、稳定候选的完整产品审查。旧界面局部小修只看受影响位置及共同组件，不重新搞全产品设计。

**具体agent：** Frontend Design协调器选`product-ux-planning`、`visual-direction`、`design-system-tokens`；有正式Figma才选`figma-design-to-code`；按需响应式和科研产品能力。文案先有用户目的、状态、主体、相邻内容和不可改意义，再交Clear Writing。

**决定性输入：** 正式设计本体、目标功能所需的整屏/展开/错误/鉴权/空态、同一候选实际画面与操作结果。Bobbio当前Figma不是任选灵感；Lucerna自己的设计系统也不能被一堆额外卡片覆盖；Asteria要看图能否顺着关系阅读而非只有箭头计数。

**硬性质与判断分开：** section顺序、单一展开、可达焦点、主标签是否裁切、实际SVG与DOM边界可由项目测试检查；视觉层级、密度、认知负担、自然文字和科学解释由有视觉/领域能力的独立模型检查。来源没有支持的模型含义不得为文案好看而发明。

**校准：** 在上线此审查路径前，用Asteria历史坏全屏（不仅局部crop）和Bobbio/Lucerna已明确拒绝的画面对审查者作校准，同时给真正可接受样例。若模型仍把坏例评为可交付，不把它晋升为可靠裁判；改提示、材料或模型的有效范围，再验证。校准集用过不再叫未见数据；不要反复挑一次好判定作为最终结果。

**复发处理：** 有多轮同一设计机制失败时回设计；若正确设计被实现偏离，修实现不改Figma；不向用户发送未收敛的每一版。覆盖K02/K08及LX17/AX01–AX05。不能保证模型永不漏美学问题，因此不作“某模型零P1的自报=质量确定”的错误等同。

## 4. K03：防止假功能、状态错误、降级实现

**不是新增一个通用业务agent。** 对各仓库使用对应实际业务实现和领域负责人：

- Lucerna：`ResourceRuntimeState`、`WorkstationLiveStatus`、`resource.contribution_state()`、Longleaf与Vault呈现测试。输入来自实际生产者，观测行/顶部/托盘/CTA整个下游。`guard-01056r4-state-contract.mjs`是源结构守卫，不能代替运行测试。
- Bobbio：安全隔离Zotero的选择、批注往返、改色/删除、缓存重建与PDF不变；当前/历史知识归属数据模型。不能另做不兼容的批注世界。
- Mica：当前重构适配器、AnswerDocument、低内存、高亮和PDF模块；附加收益和不破坏宿主分别验。未知块不能过滤掉后说全文精确；不开功能不能过收益门槛。
- SeminarArc：`EndSeminarUseCase.kt`/`RecordingServiceStarter.kt`，Room/WorkManager结果和真实持久化；无录音结束不得错误启动前台服务，保存toast必须来自真实写成功。
- Asteria：`trace.ts`/`session.tsx`/`viewProjection.ts`/`graphPresentation.ts`及科学源。方向集合、Clear、选中与追踪、布局坐标必须正确，不靠更改模型真值让图变简单。
- CUHK Date：密码共用生成契约、介绍/同意/历史/照片生命周期、问卷语义和隐私。诚实无匹配允许成立，不能假造配对；真实已批准信任政策迁移不等于假活体provider。

**正/反验证：** 明确输入变化应导致哪些真实结果变化；已知正常输入和没有额外干预/错误时不应改变。异常路径与取消/重启都属于新功能，不是未来优化。覆盖所有K03及LX02–LX16。

## 5. K04：谁执行真实用户路径，怎样防API替UI或fixture替live

| 仓库 | 既有决定性调用 | 观察对象和补充要求 |
|---|---|---|
| Lucerna | `development-acceptance.ps1`及close/capture辅助脚本 | 明确EXE/进程/窗口/动作；安装语义另跑NSIS生命周期。真实服务读数需来自正式调用链，受控状态不能冒充live |
| Bobbio | `Invoke-BobbioReaderAcceptanceSafe.ps1`与真实资料前后审计 | 明确测试实例和不同真实/测试data目录；原生fake API性能脚本另标，不据此推断Zotero互通 |
| Mica | 重构分支fixture/低内存/highlighter/PDF脚本＋实际扩展/宿主/PDF观察 | `acceptance/cli.mjs`只校验已有包，不替原始观察；最低证据类别由被验能力决定 |
| SeminarArc | `run-blackbox-acceptance.ps1`的Serial/ApkPath/Scenarios和导出检查 | 真正安装后应用、系统选择器、输入read-back、重启持久化；日志/文字控件读错先修观察器 |
| Asteria | `tests/browser/asteria-v2-rc.spec.ts`与public smoke/capture | 页面按钮、连续选择、完整数学、实际屏幕坐标；应用自己暴露data属性不能代替独立几何检查 |
| CUHK Date | `runRegistrationCriticalPathHosted()`、Parent预检、handoff/no-match路径 | 在实际托管UI填相同语义的用户输入；管理API只准备隔离身份不代替用户操作，最终票据不得用于预演 |

`observers.ts::runJourney`只能选择明确已批准的上述入口与参数。不能把任何名字带verify/safe/preflight的脚本默认为只读，不能用任意传入命令执行器承接候选证据。

**缺实时依赖：** 对应声明未验证，不增加模拟次数来替代。假数据仍可用于可重复错误测试和隐私安全画面，但材料必须明确其范围。覆盖K04，尤其L07/L08、M11、S05/S11、C02/C03、LX14。

## 6. K05：检查器必须能看见自己声称测量的东西

测量审查者必须读观察器代码及原始输出，问“输入改变会不会改变结果”。只有测试名/报告字段不够。

**已知校准目标：**

- Asteria `routeGestalt`交叉和浮动标签直接0；缺routeRatio变0。修为真实独立测量或明确未测。原基线守卫仅工作区diff还需校准暂存/已提交差异。
- Lucerna治理脚本退出0仍可PARTIAL；状态守卫只查源码文字；相关checker必须被分类为工具/结构检查，不能推导真实用户能力。
- Mica同路径控制包含大量证据包变异，但不能据此证明旧坏实现真正从浏览器入口被拦住；需要保持包控制与产品坏行为两种证据。
- SeminarArc OCR0/5实际是选择器没读到EditText；对照真实控件、原始文本与人工编辑后置结果，不以错误读数修改算法。
- CUHK Date假的托管canary绕表单且换密码。观察器应输入同一语义、完成同一用户路径；不是原始数据只有个URL就算真实。

**校准函数合同：** `requireObserverCalibration`消费检查器版本、所证明性质、好/坏控制及原始结果。坏控制必须覆盖测量缺失、值变坏、身份不符和观察路径走错；正确控制必须能通过。产品含义由领域角色先确认。把所有输入都拒绝的检查器同样不合格。

发生新同类漏检时，暂停该观察器对应的通过权，保留其它已证结果，不关停整个产品。修测量后不能自动说产品被改善；应对相同真实候选重判，必要受影响场景重跑。

## 7. K06/K07：用户行为保留与候选身份

`compareBaseline`要对明确批准的base和候选比较，而非仅`git diff --name-only --`。另核对脏文件归属和暂存/未跟踪产物，不能让未提交变化污染候选。合法重构允许改旧测试内部细节，但由测试审查者核对旧用户行为仍由新检查覆盖。

`bindEvidence`区分产品源码P、不可变运行证据E、交接说明H、最终发出回执R。它们是不同来源定位，不是要求每个项目都复制四个新账本；产品已有等效字段就直接适配。原始证据文件一旦冻结不重写，manifest不哈希自己。新增报告或控制元数据不等于运行包变化；实际包/模型/提供方契约变更则重新评估相关证据有效性。

**拒绝条件：** 原始证据缺失/被改写、测错包、材料错类、未运行项、旧候选仅重标签、Reviewer没拿到对象。校验哈希仅证明字节，不能证明事实发生；实际测试执行记录和独立观察仍是必要输入。

**CI特别条件：** 官方必需检查可能接受skipped/neutral，路径过滤又可能一直Pending；因此最终准入对本次required集合要求真正执行的证据。合法不适用可排除，但排除必须由批准范围/确定影响关系产生，不由失败后的执行者自己删除任务。无关metadata漂移另作便宜检查，不阻止实际代码测试运行。

## 8. K08：独立审查不再作为第一个测试员

本地独立产品审查者在稳定候选前检查实际必要画面和操作结果；它应能在当前工具中真正取得图片或真实运行视图。官方Codex SDK可把本地图片传入独立会话，是一种实际可实现入口；是否具备所需交互/资源需实测，不由名字推定。

资料准备程序负责材料够不够和属于谁；审查模型负责视觉/领域判断。材料中不把生产者自评“全部零问题”当预设结论。先做完整真实任务观察，再看历史已知缺陷是否复发；既检查未见问题，也避免任意追加范围和移动验收标准。

对Bobbio，产品审查不能代替最后Zotero往返；对Asteria，W01不是箭头数计算器；对Mica，阅读器真实选取不能由PDF提取脚本代替；对CUHK Date，纯黑盒Reviewer仍不可读源码/DB/隐藏答案。

GPT Work只在内部机制正常后承担合同规定的整体复核。新增脚本不能冒充已连接GPT Work；实际没有接手机制时保存任务并报告具体缺口，不能虚造已运行审查。用户当前未认可架构，本轮不启动这些审查者。

## 9. K09/K10：执行、恢复和权限由谁真正保证

`backends/bridge.ts`读取当前实际Host/工作树/批准和已有运行，保持原CODEX_HOME。`supervisor.ts`对执行资源和允许效果作准入；操作是否危险看完整调用链而非脚本名。正常授权下重复执行同一效果不重新询问；新服务/费用/凭据/作用域必须另获许可。

开发身份不能写可信标准/验证器，也不能拿发布密钥；不可信候选不能在带机密的高权限作业中任意运行。专用账号/实际隔离资源负责这个边界，提示词和不同文件夹不负责。做不到时诚实处于审计型模式，不能说“无法绕过”。

`acquireResource`范围至少包括工作树、原生测试机、模拟器serial、浏览器context和外部发布目标。记录归属及实际进程，不允许两个任务一起点一个桌面。对已有Bridge Reviewed/Control拥有的任务，不再创建第二个CURRENT；监督程序只适配该owner。

`reconcileEffect`对“请求已发但回执丢失”先查真实目标。已安装/发布则完成，不重复操作；仍未知则暂停有副作用步骤。CUHK Date的一次性访问/恢复票据仍由产品自身claim/finalize事务决定，中央不能自行回填已消费状态。会话保存不等于进程仍在，Windows也不因写了Persistent Run就有tmux。

## 10. K11/K12：正常轻量与完成真实性

`selectRequiredChecks`联合目标依赖、变更影响、相关事故和交付类型；轻量不是只测变更代码，也不是每次所有246项全部跑。共享状态/认证/数据变更必须扩大，纯文案不因“跨六仓库框架”进入六路评审。

`classifyFailure`接收具体步骤、实际输入、前后状态与原始证据：实现bug回Codex；设计错误回设计；工具假阴性修工具；服务不可用修依赖或保持未验；身份污染停止该运行。连续同因无新证据停止盲重试，不以换SHA/改Goal重置预算。测试修复/报告提交不能自动产生新alpha或打扰用户重新安装。

`delivery.ts`只消费当前候选有效的必需结果，核对正式目标和授权，执行已有发布器并检查后置状态。把某功能标未配置/不可用是诚实的安全状态，但不能代替被承诺的可用新feature。反之，没有凭据的未承诺可选模块不应把无关正常功能全挡住。

## 12. 什么仍是未证明的

本页证明的是**控制设计的具体性和可追溯性**，不是控制已经实现/强制生效。运行包、真实自动接手、受限身份、观察器校准和跨平台普通入口尚未通过真实试点。未知历史材料仍可能补出不同根因；新增根因要进入相同的观察与责任机制，不靠再开一个万能检查层。

正式目标是：已知失败必须有能观测并拒绝的对应路径、正确实现能正常交付、内部调试不外包给用户。无法由有限测试和视觉模型证明“未来绝不出现任何P1”；但这不能成为放任已知恒零测量、假live、删测试或错包过关的借口。
