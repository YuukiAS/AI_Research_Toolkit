# 用Lucerna完整走一遍：一次交办，而不是一次代码生成

本例演示拟议研工台怎样开发一个完整功能，**不是新的产品任务或实施授权**。例子选择：在已有Cloudflare R2用量读取基础上，增加用户可设定的容量阈值提醒和清楚的查看入口。若当前工作树已经实现其中某部分，先复用，不重新做。这里的阈值是应用内提醒设置，不是宣称Cloudflare有某个计费上限，也不授权修改任何云端资源。

**用户期望：** 交办一次，内部能自己完成常规实现、测试、找错和返修；用户不需要逐个检查按钮、重发提示词、切换执行角色或不停安装候选。“一次交办”不表示第一份代码就无bug；未授权的凭据/费用/外部操作或真正产品取舍仍需用户决定。

## 1. 先看当前真实代码，不能拿旧事故重写整款软件

本轮实际读取 `src-tauri/src/cloudflare_r2.rs`，快照 `79dd2875d3da33c6a6d80e5e35bea812b84c1ceb`，blob `7c0bdeedc926de02adb165b4a20032c2e676f249`。已有：

- `CloudflareR2Provider::refresh`通过配置、安全存储和HTTP客户端读取；没有配置、缺凭据、鉴权与其它错误分别处理。
- 明确的`AccountR2Metrics/R2StorageClassMetrics/R2ObjectMetrics`类型，不再只是旧报告所批评的递归字段搜索。
- `state_from_contract_values`、`parse_current_stored_metrics`及正常/部分/缺字段/畸形响应回归。
- `save_setup_transaction`，以及`r2_config_failure_restores_previous_working_pair`、`r2_credential_failure_restores_old_token_without_changing_config`等事务测试。

因此**不能说Lucerna没有真实R2实现，也不能重复修一遍旧parser**。真正需要核对的是：现有真实配置/读数是否在本次合法环境可用，当前被交付版本是否走这段实现，以及新增提醒能否使用它并保留其错误/未知语义。源码有这些函数并不等于本轮已访问真实账户。

同时，`scripts/guard-notification-policy.mjs`已经检查稳定事件键、仅fresh数据可提醒、现有持续时间策略、原始错误不进通知等性质；它读`src-tauri/src/lib.rs`源码，属于便宜结构守卫，不是“用户已收到一次正确提醒”的运行证据。

## 2. 第一步不是画一张大卡片，而是确定完整交付合同

监督程序用`scope.ts::resolveTask/resolveRequiredJourney`找到当前任务/分支/设计，不建另一个恢复Goal。Planner与领域负责人确认以下具体能力：

1. 用户能在既有R2设置/详情里设定阈值、保存、取消，并在重新打开后看到正确设置。
2. 用量来自正式提供程序；未配置、未知、部分、过期和鉴权失败不能变成零用量或健康。
3. 在当前产品通知政策允许的条件下，越过提醒阈值触发一项可理解且不刷屏的提醒；同一事件的微小数值变化不能每次当新事件。
4. 行、顶部/托盘和详情对“什么超了、证据是否新鲜、用户能做什么”一致，不能一个正常另一个报警。
5. 现有其它服务状态、密钥/配置事务、敏感草稿清理、窗口与通知行为不能回归。
6. 交付的真正包在正常运行模式中工作，不残留测试按钮或模拟状态，不要求用户重新设置已存在的认证。

这一步输出小而明确的能力集合及现有来源，不输出五份平行规范。阈值默认值/反复提醒策略如现有合同已有则沿用，确实新增产品取舍才由用户决定。不是让执行者为了测试容易自行选一个永远不会触发的阈值。

## 3. 第二步先证明真实读取和测试替身是同一语义

**负责者：** Codex实现者＋接口/测量负责人。

现有真实配置可用且权限覆盖只读时，先从正式`CloudflareR2Provider::refresh`取得最小读取结果，核对实际用量/时间/缺失项，不将token、账户细节和私有余额写进公开材料。凭据缺失时只能请求一次必要的合法配置，不能伪造“连接通过”。

同时把有效接口契约和已批准的脱敏响应做为开发回归输入，经过相同的`state_from_contract_values`和后续聚合，**只替换HTTP输入，不替换本次被验证的业务状态或headline**。

负责校准者故意给正常、部分、鉴权失败、畸形、字段缺失和旧数据。检查器需要证明两点：正常合法响应能正确到达UI；坏数据确实不能成为“正常0用量”。更多假数据成功不替代真实接通证据。

**这阻止旧坑：** LX01设置页冒充完成、LX03错误schema、LX14夹具绕聚合、L08真实认证已有却还围绕假状态开发。

## 4. 第三步先定整屏结构，再实现一条纵向功能

**负责者：** Frontend Design的产品交互/视觉/组件能力＋Codex。

沿Lucerna已有产品结构，在R2原有行/详情增加必要的阈值与当前状态，不擅自把托盘变成另一页Dashboard。设计需要明确默认、已配置、越限、未知/过期、鉴权、保存失败和取消后的样子。可选未配置模块不和紧急状态等权。

实现者先接通：设置入口→持久化阈值→真实资源读取→共享状态/通知判定→用户看到的行/详情/提醒。一旦这条实际路径可执行就观察，而不是先写完各组件再拼。

接口和输出保持typed语义：真实提供方状态、聚合贡献和用户呈现分别有明确映射，不在UI通过标签或severity猜状态。若新增状态需改共同类型，必须回归所有消费者，不能仅在R2加局部别名。

**这阻止旧坑：** LX12自由字符串错配、LX13弱证据冲掉Checking、LX15旁路icon、LX17设计顺序/权重偏离。内部整屏检查在这一阶段发生，不等最后让GPT Work指出多张大卡片。

## 5. 第四步用确定性测试消灭重复故障，而不是不停刷新正式软件

**既有脚本/代码：** `cloudflare_r2.rs`内测试、`lib.rs`中的正式聚合/通知机制、`test-longleaf-presentation.mjs`、`test-vault-presentation.mjs`、`guard-notification-policy.mjs`、`guard-01056r4-state-contract.mjs`。

**需要补充的本次行为测试**由当前项目测试承载，名字/文件在实施时按仓库惯例落地，不新建通用测试框架：

| 输入/操作 | 必须结果 | 会阻止哪种低配方案 |
|---|---|---|
| 合法且新鲜用量低于阈值 | 正常且不发提醒 | 一律报警也能通过的错误标准 |
| 合法且新鲜用量越阈值、达到既有持续策略 | 状态和原因正确，允许的一次通知 | 不实际实现提醒/功能默认关闭 |
| 同一事件继续越限，读数小幅变化/反复刷新 | 不因新数值重复通知 | 不稳定事件键、每次刷新刷屏 |
| 用量缺失/部分/过期 | 明确未知或旧数据，不伪造零/正常/新告警 | 静默退路、假健康 |
| 鉴权失败与网络暂不可达 | 不同用户状态，不能一起引导重新配置 | 错误语义被吞并 |
| 保存失败、取消、切换管理面 | 设置/凭据按事务保持，敏感草稿清除 | 只测按钮成功返回 |
| 托盘切换、失焦、原生关闭后重开 | 所有敏感数据按实际窗口生命周期清除 | 只修前端Hide按钮、后台路径漏清理 |
| 其它服务正常/检查中/未知/失败组合 | 既有贡献语义不变；R2可选未配置不污染全局 | 为修一个模块破坏其它服务 |

通知计时与失败注入可以使用受控时钟和输入，避免真实桌面不停等待/刷新；最终原生通知行为在独立环境做有限操作确认。测试替身与真实I/O只在明确边界分开，测试控件绝不留到用户运行实例。

**结果处理：** 若检测失败，监督程序自动回同一Codex任务并附实际输入、前后状态和失败观察；不让用户复制测试日志再告诉它“继续”。同因重复但没有新证据时先审输入/实现/观察器，不能继续刷新取一个好画面。

## 6. 第五步内部审查必须独立拿到真正的产品

测试通过后，`observers.ts::runJourney`在已验证安全的隔离环境运行实际候选。复用`development-acceptance.ps1`的同次进程/窗口/截图绑定及现有捕获辅助工具，**不在用户当前桌面实验，也不声称该脚本自己覆盖安装和专业品味**。

对本次功能至少取得：正常行和详情、提醒状态、未知/鉴权路径、保存/取消/重开结果及相关全屏。整屏不能只有折叠态或只裁一张R2卡片；其它服务和布局仍要在同一个真实画面中可读。动作要有真实命中与后置结果，不是函数被调用。

内部独立产品审查者看到实际画面和行为材料，不先收到实现者“零P1/P2”的答案。它检查提醒意义、层级、重复文案、按钮用途、展开后的焦点、状态是否矛盾，以及正常首屏有没有被新功能破坏。机械布局检查负责可计算的问题，审查模型负责整体判断。它若发现明显P1/P2，由监督程序交原实现者修复，再只重验受影响范围。

**为什么不继续把GPT Work当第一轮QA：** 原来是实现者自报完成→用户/Work发现基本问题；这里是实际业务回归→独立内部操作/完整画面审查→内部返修完成后，才允许准备外部审查。新发现的同类基础P1意味着内部生产机制漏检，必须修该机制，不是仅给产品再起一个rN任务。

## 7. 第六步冻结同一真实候选，不为报告反复造版本

源码/运行包稳定后记为P。原始运行观察和必要脱敏材料冻结为E，交接说明H引用P/E，不要求文件包含自己尚不存在的提交哈希。明细报告改字不会自动触发重新打包或全量截图；实际运行包、提供方契约或验收语义改动才使受影响结果失效。

`evidence.ts::bindEvidence`核对：每项声明指向当前候选的真实观察，所需surface确实存在，摘要来自冻结字节，原始来源与脱敏派生区分。不会再出现49/92哈希不符、缺截图却台账称有、旧候选文字换名即复用。

正式发行包若签名/打包改变对象，需要对真正将交付的最终安装包做相应安装和启动验证，不能拿开发EXE截图替安装器背书。安装生命周期已有正确证据且本次包/脚本变化没有影响时，可按明确影响范围裁剪；不能任意继承，也不机械重做全部旧实验。

## 8. 第七步交付前先看用户实际目标，不自动重装

仓库合同要求GPT Work时，内部就绪后按当前准确候选发出一份完整审查材料；未配置自动接手不能虚称已经运行。用户不负责在每个内部子角色之间传递结果。

`delivery.ts::admit`拒绝缺必需结果、错误包、未授权或被篡改裁判。`inspectTarget`核对目标分支、待交付包及当前安装状态；已正确则不重复安装/刷新。安装效果未知的中断先核对后置状态，不能重复下发。只在获准的效果范围内发布，不借当前feature动生产网络或其它账户。

用户最后应该得到的是：“这个功能在某个实际版本中可用，哪些路径已验证，是否已经在目标安装/部署中生效。”不是要求用户手动证明阈值保存、按钮能点、颜色对不对和退出不丢数据。

## 9. 故意做坏时怎样拦截

| 偷懒/回归 | 对应拒绝位置 |
|---|---|
| 只有设置页和假读数 | 真实提供方路径及完整声明集合未通过，不能关闭feature |
| 读取出错就返回0 | parser坏输入/缺字段控制失败，真实未知语义不成立 |
| 为安全默认禁用全部提醒 | 正常越限正例没有结果，功能收益门槛失败 |
| 给fixture单独返回漂亮headline | 生产者输入→共享聚合→实际UI的独立路径不一致 |
| 为过测试删掉旧Longleaf/全局状态测试 | 受保护旧行为集合仍必需；基线到候选diff和迁移审查阻止删除保证 |
| 修改监测值/校验脚本直接返回PASS | 校准坏例和固定批准观察源拒绝；候选无权写最终裁决 |
| 整屏难看但局部组件合法 | 内部独立实际画面审查不过；不能用测试次数代替 |
| 不断刷新/发通知直到截图合适 | 同任务资源租约、操作预算和同因记录触发停止盲重试 |
| 报告/截图旧版本，安装包新版本 | 候选及冻结证据绑定失败 |
| 仍需用户重新输入已经存在的凭据 | 任务入口先读当前合法配置；只有真实新权限/凭据才询问 |

这里的拒绝机制是拟议条件，不是本轮已经实际完成的负例测试。其成立必须由最终普通入口的真实正/坏候选验证，不能只修改几个JSON字段然后声称所有低配实现都能防住。

## 10. 对“一次性开发”的准确承诺

这套结构支持的目标是：一个被充分明确且获授权的功能由同一持续任务内部完成实施、验证、返修和交付，减少在旧事故中无效循环。它需要先有校准过的项目基础、有效执行主机和相应真实测试条件；不能把这些尚未成立的条件当已经存在。

代码可以第一次有错误，但内部要发现并按根因修；不能让用户/GPT Work反复成为第一发现者。若外部审查仍大量发现历史同类P1，说明运行体系没有通过验收，应修测试/观察/设计消费入口，而不是再宣称“下一版一定好”。

不承诺所有未知缺陷永不出现；承诺的是对已登记失败有明确实际控制和严格反证，未验证的能力不包装为完成。这个区别不是放松目标，而是避免再次用无法证实的保证换取用户批准。
