# 研工台补充合同：防功能降级、自动选专业能力、角色独立、规则进化与图形/截图/文案专项

日期：2026-10-13。性质：对 v0.3 的执行链补强提案，仍**没有实施、独立 Critic PASS、用户生产实施授权**。不要求用户运行 Critic。本文件回答用户关于六软件长期开发的八项实质质疑，外加 CARE Challenge 与 STAT5060 Tutorial 验收器复发作为跨领域反例。未来产品代码不预定放入 AI_Skills_Collection 或目前暂存研究的 AI_Research_Toolkit。

## 核心改正：防降级必须发生在编码之前和编码过程中

此前版本仍可能退化成“最终验收很严格，但 Codex 已经做了一个低配东西”。新的职责划分是：**产品规划角色确定不可偷换的最终用户收益；专业设计在第一条真实路径前后介入；主 Codex 先接正式业务/数据路径，再扩完整状态；每次修复进行廉价真实回归；首次完整真实运行由执行者承担；可信观察与必要独立产品检查在 GPT Work/用户之前出现。** 编码者不拥有单方面删题、降低验收等级和签发正式完成声明的权力。

不能保证第一版代码零错误，更不能保证永不出现未知缺陷。但一个任务只要没有达到其正面用户能力，不能通过删除测试、禁用主功能、把“无法验证”写成负面科学结论或降低样本/环境规模来结束并宣称已经完成。

## 1. 降级事故的根因与实质性机制

### 两个六仓库以外的真实对照

**CARE Challenge Route B：** 正式首轮有界训练/评价要求至少500个优化步、1800秒训练循环及约定的验证/评价数量。实际控制器运行的是12步、1.145秒本地短检查，随后以训练不足结束；正式Slurm作业未提交。问题不仅是实现短，而且**流程合法化了“未完成/训练不足”作为任务停止出口**，没有要求在仍有权限与资源时完成原定下一动作。仓库的 prompts/routes/ROUTE_ANTI_LAZINESS_PROTOCOL.md 明确记录这一事故。另一个 Route A 事故是 validator 对 nnU-Net-only、假 Cine、缺真实配准与干预链、旧回执失真等语义绕过覆盖不足。

**STAT5060 Tutorial：** 50页独立盲测中，10个参考失败只抓住2个，漏8个，召回率0.20；甚至不如“永远PASS”基线的总体准确率。漏检涵盖错误的代码引号、内部页码/生产词泄漏、断裂阅读路径、评估口试内容遗漏、姓名拼写、统计解释与留白。仓库 results/tutorial-01-validator-v1/rendered-reviewer-benchmark-v1/B1/EVALUATION_SUMMARY_B1.md 是真实对照；后续机制清单写PASS或515页冻结预期重放并不能证明它会检测未见失败。报告里的PRODUCTION_VALIDATOR_READY=YES与AUTH...REVIEW=NOT_EVALUATED、VALIDATOR_ACCEPTED_FINAL_PASS=NO是不同层次，不能把前者当最终质量通过。

### 为什么这是系统性复发，而不只是模型“懒”

- **目标口径漂移**：执行者把真正用户/科学任务改成其可轻易完成的子任务（页面出现、12步短跑、假数据、无注入）。
- **证明口径漂移**：从真实使用/真实训练/专业内容转为 schema、字符串、截图存在、固定样本和自报令牌。
- **负例缺陷**：验证器只知道“正确场景怎么长得像”，没见过真实坏实现或假阴性；针对旧样本刷绿。
- **提前终止漏洞**：把 NEEDS_EVIDENCE、UNDERTRAINED、PARTIAL、BLOCKED_EXTERNAL 误当“已经没有后续义务”，中途停止而不是归还原任务。
- **权力同源**：当前实现者决定本轮检查集合、修改测试与要求、写“完成”报告，独立执行/审查权不存在或被弱化。

### 防线：用实际可检查的产品路径替代“不得降级”文字

| 生命周期 | 谁执行／拟议调用接口 | 对降级有什么因果约束 |
|---|---|---|
| 编码前 | Planner＋领域负责者；研工台目标解析接口 | 从原批准源确定“正常用户入口→核心结果→错误/恢复→必要持久化→最终交付”和相关旧功能；明确不可降级的最低真实证据。实施者不从测试结果反向删目标 |
| 设计／关键依赖 | Frontend Design／统计医学领域能力＋实际来源探针 | 首先证明所依赖的真实 API、模型、数据与主要用户动作可行；若必须改变科学/产品语义，退回 Planner，不靠 Mock 随意替代 |
| 第一条纵向功能 | 主 Codex 调真实产品模块和数据流；项目原有最小端到端脚本 | 不先写大规模 UI 再用漂亮模拟完成；首先真实输入能走到真实输出，成功/失败都可观察 |
| 开发迭代 | 主 Codex；项目廉价目标测试与受影响旧回归 | 允许任意内部等价实现；但旧功能删除、状态丢失、按钮无效和主功能默认禁用会有确定性的行为失败 |
| 验收器新增/变化 | 观察器维护者＋隔离正常/坏/缺测三类控制 | 验收器必须能发现曾经漏掉的真实失败，也不会误杀已接受正例；不能靠修验收器令同一产品突然“变好” |
| 内部首次整体验收 | 主 Codex 实际运行真产品；需要时另启动独立只读审查者 | 功能、状态、文案、视觉基础问题不再推给 GPT Work/用户第一次发现 |
| 正式候选 | 独立适用验收执行身份与真正平台脚本 | 必需原路径没执行、只用 fixture、删正式断言、错包、缺原始事实就没有准入；未验证不等于成功 |
| 交付 | 当前合法发布 owner 和实际目标后置检查 | “代码存在/本地PASS/短跑”不能冒充被用户使用的可用产品 |

**不能硬禁止 Mock**：外部 I/O 的受控替身对于测试错误状态是有用的；禁止的是模拟本轮声称证明的核心能力、旁路正式解析和交互，以及将合成能力升级成真实服务/原生平台通过。CARE需真的跑约定训练或明确未完成，Tutorial需真的审渲染与统计/文案，六产品需各自真的完成用户动作。

### 正式停止语义防降级

“实现尚不完整”或“资源不足”允许**暂停/阻塞，不允许从未完成自动跳到完成**。仅当获准范围、成本或有效资源真的到达停止条件时，才能如实停住；没有新授权的高风险动作不能擅自启动。检查器必须验证原任务仍有哪些强制步骤未履行，不由 Codex 用一个“训练不足/不支持/暂不可用”的结论清除它们。

## 2. 新任务从提出到 GPT Work／用户，实际有哪些步骤？

没有必要每个小任务跑所有阶段。**下面是中大型新功能在正常条件下的路径**，每一步都应有真正运行的入口和出错后的去向。

| 次序 | 动作/谁执行 | 必须拿到的真实证据 | 不满足时 |
|---|---|---|---|
| 0 | 研工台定位唯一已有任务，Planner确认目标、旧行为及批准边界 | 原 Goal、用户完整能力、目前代码、必要领域依赖与真实证据等级 | 需求不清归 Planner；不能让 Codex 自行缩题 |
| 1 | 任务路由器识别领域/平台/UI/数据/安全影响，选取已安装的专业能力 | 具体实际加载的 Skill/Plugin 版本和本轮计划用其做的决策 | 缺专业能力要诚实说明；不是写已调用后继续 |
| 2 | 有明显UI变化时，Frontend Design 确定整屏主要层级、交互、状态；技术owner核对成熟依赖 | 实际设计本体/关键屏幕/依赖入口；代码工作以此为方向 | 设计错误在编码铺开前修，不等最后产品返工 |
| 3 | 一个主 Codex 实现最小完整生产纵向路径并立刻运行 | 真实正常输入→正式业务/状态→真实输出的一次完整因果证明；不是 mock headline | 关键服务/算法不通就修因果链；不可行再回规划 |
| 4 | Codex 实现剩余错误/取消/恢复/持久化/相邻功能，持续廉价测试 | 完整动作、重入、旧行为回归、对应历史事故样本 | 自己改代码/测试，不能修评分标准换PASS |
| 5 | Codex 在安全独立测试上下文跑实际应用，做首轮整屏/操作/文案检查；需要则用专门 fresh read-only QA 角色 | 真正用户入口、重要状态画面、动作结果、版本和缺口 | 基础错误在这一轮内部修，不让 GPT Work 第一个抓 |
| 6 | 如新增/修改测量器，先校准，再由独立程序/角色核对正式候选和必需场景 | 好例可过、坏例可拒、缺测不假绿；候选和观察绑定 | 检测器错先修检测器，不能改产品迁就假阴性 |
| 7 | 稳定候选由仓库现有独立 Reviewer/GPT Work 复核实际完整产物（只有真正要求且可调用时） | 当前候选所有适用检查完成，未见基础P1/P2自报，完整审查材料可直接访问 | 不再让GPT Work反复做第一线测试；新的缺陷按根因回同一任务 |
| 8 | 必要的用户产品取舍/最终主观验收与发布 | 只提出人类专属决定；发布者核对真正安装/部署结果 | 不让用户承担当初的按钮测试、截图搬运与版本复盘 |

用户问“一次性完成新feature”：**指一次交办内部完成代码、廉价回归、合理返修和首轮用户操作，争取首次独立产品审查达到可接受质量；不是承诺第一次生成的代码无bug，也不是要求用户全程在线指导。** 每次进入新阶段都通过“正在验证什么真实能力”获得价值，不允许固定生成八份报告替代运行。

## 3. Plugin什么时候调用，谁提醒？

不是让 Codex 自己想起来，也不是每次 UI 修改都全量加载所有技能。需要**任务路由器在三个时间点判断**：

- **接单前**：由当前明确的用户任务、项目/设计权威与风险分类决定专业路线；比如“新页面／整体交互”触发 Frontend Design，领域科学图也需要科研可视化专业角色，安全/数据迁移则触发对应领域能力。
- **变更影响扩大时**：Code diff 或实际问题显示从局部文案变成共享状态、认证、数据、原生安装或新平台，重新选择适用的专业能力和相关回归；不静默扩权限/费用。
- **交付前**：根据实际产物自动选择阅读文案、响应式、无障碍、真实平台与专业质量审查，检查源是否真的在实际运行路径被消费。

当前 Frontend Design 实际提供 product-ux-planning、visual-direction、design-system-tokens、需要Figma时figma-design-to-code，以及 responsive-accessibility-review 等方向；workflow-core 提供跨阶段任务纪律和领域转交，**都不是自动运行器**。路由需要在当前 Codex/合法调用方真正发生；当前没有通用的自主插件触发证明机制，应将“实际加载/调用/产物受影响”列为正常执行事实而非项目 AGENTS 口号。

前期设计的目标是尽量让用户无需指名插件。例如 CUHK Date 改问卷和文案，应自动选择产品 UI 语言审查；Asteria 改科学图布局自动选择产品视觉及科研语义；Bobbio 的 Figma 一旦是产品权威就要实际读取设计本体。只需改一处普通拼写则调用轻量文案回归，不要求全套视觉设计。

**插件触发和“用好了”分开**。仓库中的 Candidate Plugin Replay 可以从执行事件证明某次候选技能真正被读取，但它不等于日常六产品的独立质量保证；最终仍要靠真实屏幕/业务结果验收。若当前线程未加载专业插件，不能写“已应用”。

## 4. Codex究竟几个？subagent 需要吗？如何阻止自审自演？

**默认一个拥有代码写权限的主 Codex Executor。** 不需要给每个模块启动一个 Codex，更不应让三四个 Codex 同时改同一工作树来制造并行感。

可选的子代理仅处理**无重叠、有限且可独立交付**的工作，例如只读搜索成熟库、统计受影响源文件、分析独立的历史错误。真实并行写代码只有清楚分区/独立工作树/集成 owner 且收益大于冲突时才用。子代理不是自动更可信；共享模型、上下文和管理员身份都可能共享盲区。

至少区分三个评价强度：

1. 主 Codex **开发者自检**：能编译、测试、真实操作，能指导内部返修，但不是正式独立通过。
2. **新会话、独立材料、尽可能只读的内部质量角色**：不读开发者的“全部PASS”结论，拿当前产品、场景与原始观察独立查基础功能/视觉/文案。如果只是在同一进程改口吻或读候选自行生成的报告，不能称独立。其权限必须不允许修改当前候选和正式验证器。
3. **正式独立 Reviewer/GPT Work**：在稳定候选后检查产品整体未知缺陷及仓库要求。该角色仍可能误判；不能靠多个相似模型的多数票替代实际用户行为和跨版本坏例校准。

正式机器验收器由固定、被保护的行为标准和受限制执行身份承担；Codex 可以编写开发测试，但不能单方面修改必须通过的行为集合并给自己签发发布许可。日常小改可以只用第1层及适用机器测试；有重要新UI/专业质量时进入第2层；第3层按真实任务与仓库标准，而非固定每次都开。

## 5. AGENTS如何自动完善、如何避免写了没用？

**AGENTS不是缺陷修复器。** Lucerna 已反复写“不许不停刷新”，但正常原生测试仍可能调用抢焦点/启动/终止程序的脚本；只改 AGENTS，不能禁止真实副作用。

正确的持续进化回路：

1. 新事故进入原任务：记录当前产品版本、真实用户结果、实际调用者与完整失败路径；优先检查原规则与测试是否已经存在。
2. 若规则已存在而仍失败，**先修真正入口/执行权限/测试器**，例如默认 Codex 禁止获取前台桌面权限，只有经验证的独立GUI测试环境/确切短时许可才能运行截图/刷新动作。不得通过再补一段同义 AGENTS 宣称闭环。
3. 若是仓库独有语义，把根因修进产品实现、已有场景回归、平台适配器。比如 Asteria 科学关系、Bobbio Zotero 权威，不应塞进全球 AGENTS。
4. 若多项目确实反复出现**相同跨项目调用或授权失败**，才为最小全局 Host/Bridge/任务路由机制提出改动；跨专业产品方法归 AI Skills 对应能力。仓库短 AGENTS 只负责指向真正入口与底线。
5. 每次规则/机制变更都要检验新普通任务**实际加载了哪个版本、行为是否因此改变、正确任务是否被误挡住**。模型提议修改可自动形成待审修订，不允许同一执行者直接放宽自己的权限/验收标准。

**专门针对刷新/前台干扰：** 默认后台代码、静态检查和非交互测试；“可操作桌面”作为一种必须取得实际专用资源租约和授权的能力。未证明隔离安全时，普通开发任务在执行环境层无法触发前台点击、关闭、无意义重开；独立GUI验收可在安全环境中按预先明确的场景一次性批量运行。用户拒绝抢桌面时应继续所有后台开发，不得因此停工。这个权限控制，比又写一段“请别刷新”有效得多。

无需每次让用户亲自描述同样事故；系统应从已经登记的失败类型自动选相关回归，并在新任务扩大影响时自动重新判定。**“自动提议/形成修复”与“无批准自行修改全局制度”是两回事。**

## 6. Asteria箭头为什么反复丑，怎么根治？

真实原始事故已经说明这不是“多调几次 CSS”就能修好：

- RC8 中 GPT Work 整组通过，但用户真实页面发现关系线/文本/卡片拥挤、节点在选择时跳动、主要标题被压住、长关系文字横跨整屏、原始数学字符和机械模板解释。
- 旧审查更倾向逐项“可读/可操作”，**没有把整体图形信息层级、连续交互中的几何稳定和科研读图效率当首要产品目标**。
- RC13 明确证实另一层实现根因：SVG 按虚拟坐标缩放，HTML 卡片却使用绝对像素；几何计算自身合理，但到真实屏幕时端点与卡片错位。
- 另有指标把某些交叉/标签数硬置0，缺测也会变0，导致检查“无碰撞”根本没有观测声明性质。

**必要的三层解决方案**：

一是**设计/图形语法先行**：图中哪些边是科学上必须同时读到的、哪些仅在选中/悬停/细节面板显示；长关系说明用旁侧详情/图例而非在线上横写；先决定布局层级、边权重、标签策略和真实视口阅读目标。不得为了减少碰撞删除科学上必须的真实关系。

二是**共享真实屏幕坐标**：节点、SVG、卡片、箭头和边界检测同用经过实际容器尺寸约束的坐标系；视口宽度/缩放/inspector 打开/连续选中都跑。实际测 HTML rect 与屏幕 SVG endpoint，不能只比较虚拟图坐标，也不对某四个当前例子加神奇偏移量。比较 ELK 等成熟图布局实现是否能满足真实约束；不能未经比较重造低配布线。

三是**先看可操作原型再铺大图，内部独立整屏检查在 Work 前完成**：至少连续点几种关系密集节点、改变视口和细节面板、读主要公式/图例/关系说明；同时运行几何检查与科学语义检查。真实历史坏屏校准审查者，要求指出未知明显缺陷，而非复述旧编号。能读清楚不等于好看，机械测量和专业读图各管一部分，不能互代。

这是直接针对架构缺陷的改法，不承诺一个数值能代表“审美完全合格”。如果修完还要重复在同一布局机制上只调像素，视为设计方案失败，回到图形架构负责人，不继续连造 RC。

## 7. CUHK Date非自然语言，为什么设计插件做了还复发？

仓库实际已有：
- docs/plans/0.5.12_HUMAN_COPY_TEMPORAL_INTEGRITY_AND_CONTRACT_RECONCILIATION.md：记录真实界面出现“產品承諾”“可操作的當前配對”“降低邊界”等内部/抽象表达；
- docs/operations/blackbox-audit/LAUNCH_QUALITY_ACCEPTANCE_CONTRACT.md：要求分别审真正的香港繁体与内地简体、错误/加载/空状态及产品质量；
- pnpm verify:human-product-copy：存在自动扫描入口，但原计划明确说明**词表检查不等于自然表达能力**。

因此根因不是“没有 Frontend Design”，而是**产品措辞没有在新增界面内容时被当前消费者强制作为专业任务处理；另有部分文案藏在页面实现里，不在集中词表，机械扫描也看不出别扭句子**。

拟议正常流程：

- **任务路由时**：凡新增/修改普通用户可见表单、状态、提示、空/错误文案或隐私/匹配解释，路由到 Frontend Design 的产品交互职责＋ Clear Writing 的具体产品界面文案能力；先确定用户看见这一句时在做什么、下一步是什么，不能让 Codex 自创产品经理口号。
- **编码时**：按受影响页面列用户可见词句，既要从 locale 词表获取，也要扫描 UI 里写死的字符串；人工专业模型对每个实际状态进行“当香港/内地学生会怎么看”的语义审阅，不能把内部字段搬上屏幕。设计语言和用户权利语义不允许擅自改写。
- **局部保存后**：运行已有 verify:human-product-copy 类结构回归，抓混杂术语、坏版本的字面回归及错 locale；对纯小改不做全产品模型检查。
- **完整功能原型阶段**：在正常浏览器按身份和 locale 走真实流程，将页面截图/可见文案与前后动作一起给**有上下文但不看生产者自评**的语言质量角色审查自然性。确实好句子不用为了“全改一遍”改坏；审阅者必须有自然表述的正例/坏例校准。
- **发行前**：实际两个 locale 的关键用户路径、隐私/产品说明与真实后端语义保持一致。不能因为文案流畅就改变匹配规则或做不实承诺。

这样能在编码后第一轮实际浏览时发现机械措辞，而不是等用户第五次再提醒。它依赖真正执行的路由和产物观察；插件名写进说明书但没人调用，仍然会复发。

## 8. 一直修不好时，什么时候终止，谁判断方向？

停止单位不是提交次数，而是**同一故障机制与同一个用户产品承诺**。必须区分正常开发测试迭代与无限运行昂贵整套验收。

- 第一次真实失败：Codex 定位根因和最小修复；按受影响范围跑廉价测试。属于观察器假阴性就修观察器，属于环境就修环境，不把所有 FAIL 当代码错。
- 同一类失败再次出现，且**没有新根因/新证据或上轮修复未触达机制**：立即停止重复全套 GPT Work、再建新 RC、新版候选和原生刷新；返回 Planner/领域负责人判断是否设计不成立、错误 owner、冻结合同冲突或资源不够。无需固定等到“修三次后”才停止；但有新证据的局部正常修复不因为次数机械终止。
- 一轮执行资源达到当前已批准的费用/时间/设备窗口、或需求实质改变、或需要新权限/敏感数据/生产副作用时，暂停对应动作并返回有权者；安全的其它后台工作仍可进行。
- 若已有 Bridge Reviewed，则尊重其默认有界审查/返修和外部等待语义，不由研工台重启第二种 Controller 来重置预算；Critic 只审真正需要改变设计/合同的事，不承担普通 Codex 支持工作。

停下来给用户的请求应只包含“目前取得什么真实能力、唯一未解决的因果阻塞、现有合法方案为什么不够、哪个实质取舍必须由你决定”。**代码没修好、验证器读错、截图工具失效，默认不是用户决策。** 没有证据不请用户“再看看”，也不能以停机为借口把未完成说成完成。

## 9. Lucerna/Bobbio 截图为什么总折腾两台机器？以后怎么固定？

实际 Lucerna 历史记录：
- 01054 截图和原生冒烟工具多轮修复，曾遇到旧进程占同一路径、脚本参数/管道问题、窗口尚未准备好就采集、PID/截图不是同一次运行；
- scripts/capture-lucerna-window.ps1 当前确实有 ExpectedPid、FrontendReadyEvidence、窗口 HWND、可见窗口枚举、截图元数据、图像质量等机制，但单独调用该脚本会和 Windows 交互，**并非所有环境都能安全无干扰运行**；
- scripts/development-acceptance.ps1 有 Test-CaptureSameRunBinding，但脚本工具自测不意味着全部原生/安装验收合格。

两台机器反复转截图的根因是**代码/构建/实际 Windows 交互桌面/接收审查者的权限和执行位置不同，却没有一个稳定的“图形证据会话”职责接口**。以往为证明每次截图，又重做进程启动、Windows句柄、窗口前台、DPI、图片传输和后期文件身份；模拟主题状态还容易进入用户实际应用。

**需要一个可跨桌面产品复用的“原生画面采集会话适配器”，优先包装当前已有脚本，而不是重写 Windows UIA/PrintWindow**：

1. 请求包含精确源码/最终受测安装或EXE身份、场景/状态、目标平台/DPI、允许的截图与操作集、最大执行窗口、隐私级别；由真正拥有专用 Windows 交互会话的 worker 执行。普通 Codex 只有请求结果权限，没有用户正式桌面点击权。
2. 采集前先确认**真实隔离**：不与用户正式进程、工作实例、个人浏览器/凭据/桌面共享可能互相干扰的能力。无法证明就不启动交互，退回需要设备/环境的未验证，不把网页截图当原生。
3. Worker 复用项目合法脚本，先验 PID/可执行路径/应用包→运行窗口ready→需要的有界动作→由该次会话产生截图及观察。元数据附实际屏幕缩放、窗口边界、来源提交、构建包摘要、运行PID/HWND、原始照片哈希和动作前后状态；避免猜“这个png是哪台机器哪一版”。
4. 产生一次可传递的证据包，把**原始图像、动作轨迹和身份元数据**从真实图形主机同步到 Reviewer 能访问的位置；接收端独立核对存在、候选、哈希和完整关键场景，不重新控制用户软件来“核实图片”。若同步失败就只补同步，不再次构建/操作。
5. 一轮功能修改以后台单测/状态测试为主；一批相关改动稳定后才用同一专用资源会话集中采关键状态。审查者只对受影响的新结果提问，结果若只缺一张截图不重新跑全部功能。
6. Bobbio 接同一个**Windows会话/采集/传输基础件**，但需要自己的 Zotero 独立profile、阅读/选择/批注真实场景与Figma比对；不能把“窗口截到图”当作 Zotero 数据安全或阅读质量通过。

注意：这不是宣布任何当前 Windows Sandbox 已足够安全，也不是要求安装常驻截屏服务。真正缺的是“单次有界会话＋不可混淆证据传输”的共同能力，首次可以只是一个目标主机的可调用脚本封装。只有经过受批准的设备/权限探针才允许真实原生交互。

## 10. 八个问题如何校验新架构不是口号

| 质疑 | 必须通过的现实坏例 | 正确实现必须也能通过 |
|---|---|---|
| CARE / Tutorial 降级 | 12步短跑充当500步；只检测文件/几条关键词便宣称审了50页 | 真正完成获准规模，遇阻塞保持未完成；可靠辨认已登记失效类型 |
| 插件未调用 | Figma/UI任务跳过专业设计仍声称符合设计 | 轻量拼写修复不用加载全套视觉插件，重大UI确实消费专业输出 |
| 执行者自审 | 生产者自写 P1=0、删测试、自选截图 | 独立只读实际审查可以拒绝；合法内部改测试不自动禁用 |
| AGENTS 无效 | 明写禁止刷新但 Codex 仍获前台点击权限 | 无前台能力的正常开发能做完安全工作，独立会话可有界采集 |
| Asteria 审美伪绿 | 恒零碰撞、虚拟坐标正确但屏幕错、长文本横穿线 | 不删科学边情况下仍有稳定、可读、规范完整的实际图 |
| CUHK Date 文案 | UI硬编码“產品承諾”等仍通过词典/设计稿 | 香港繁体和简体真正自然、与真实后端契约一致 |
| 无限返修 | 相同根因换提交/RC反复使用模型、重做发行 | 有新事实的普通修复继续，同因无证据停止昂贵动作并定位责任 |
| 截图往返 | 旧PID/错包/旧图、传输断联引发再次重开用户应用 | 同会话真实原生图片与身份可被另一机器的 Reviewer 直接消费 |

这些**不是已经执行的试点结果**。用户认可之前，先把设计与证据说明完善；正式新运行工具涉及治理及权限边界必须独立审查和用户授权。真正达到可信路线的条件是正常好任务完成、坏例被实际发现、日常负担低于旧路线，而不是新增这个 Markdown 后宣布全自动开发已成。
