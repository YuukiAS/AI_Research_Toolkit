# 研工台 v0.3：六仓库软件生产架构——经过反证后的修订提案

2026-10-13。**这仍是未获用户认可、未接受独立 Critic、未实现的软件生产方案，不是部署成功。** 所有文件继续留在 AI_Research_Toolkit 原研究分支；不改变六个产品、Bridge Kit、AI Skills 的运行配置。

## 最重要的改变

v0.2 说必须自建一个 TypeScript 监督进程；**v0.3 撤回这个默认前提。** 实际调查证明两点：
1. Bridge 的 Reviewed/Control 有自己的控制器，不能叠加第二套同一执行任务状态。
2. 在本轮固定的六个产品仓库提交中，都未发现其标准 Reviewed/Control/Persistent Run 安装目录；不能假设现有六个产品已经被 Bridge 自动协调。与此同时，GitHub Spec Kit 最新版已经有真实步骤状态、工作流恢复、条件和人工关卡，但其 Shell 步骤使用用户当前权限，不能当安全隔离。

**推荐的最终产品对象仍叫“研工台”：一个连续负责用户软件交付目标的产品任务入口，配有可版本化的完整功能准入、专业设计/开发、真实观察、校准、审查及受控发行能力。** 它不重复管理每次 Codex 进程：各次实际执行由项目现有 Codex/Bridge 或经过真实试点证明可用的成熟步骤运行器管理。对于普通单次小修，不应常驻任何大型调度服务。

这不是退化成只负责发布的验收器。用户提出“开发一项功能”后，研工台必须知道产品目标与实际进展，协调设计、真实纵向实现、用户入口测试、内部返修、必要独立审查，直到获得真实可用交付或遇到真实权限/环境边界。

## 统一生产能力具体是什么

每个新功能的必需验收集合应由**完整目标用户路径＋受影响旧能力＋相关历史真实失败＋当前交付对象**合并得到，不能只让 Codex 选好测的组件；也不能让每次改字都执行所有测试。

专业角色按实际问题分工：Frontend Design 在首个可操作界面原型前后负责信息结构与整屏质量；Codex 完成完整用户行为和开发者首轮自检；实际平台脚本观察后置结果；测试/测量负责人校准正常/坏例；独立产品审查者看到完整实际产物之后再判断整体质量；GPT Work 只在仓库正式阶段适用时出现，不继续承担第一轮按钮、保存、状态错误检查；真正受限发布身份依据有效候选和授权执行真实交付。插件提供专业能力，Bridge 提供执行/授权/工作树和已安装时的任务恢复；研工台负责这些能力有没有被实际接起来并服务于同一产品目标。

六仓库适配保留真实差异：Lucerna 的状态与服务/原生安装；Bobbio 的 Figma/Zotero；Mica 的当前宿主和 PDF/低内存；SeminarArc 的 APK/真实媒体；Asteria 的科学语义/图形审美；CUHK Date 的多用户隐私/真实注册与托管服务。不能统一替换其项目内的专业脚本。

## 什么时候才有资格说路线可信？

- **结构可信**：给定真实产品任务，能指出当前任务拥有者、实际运行器、质量检查入口和授权来源，且不需要第二套重复状态机；存在明确的可用正常入口，不只是提示词。
- **机制可信**：在安全隔离中运行正常和历史故意坏候选，真的能拒绝假数据、删测试、验收自证、错误版本、视觉退化、重复刷新与越权，而且正确实现仍能通过。
- **日常可信**：桌面和非桌面两类真实任务证明：用户不再是基础问题的第一轮测试员；同一功能交办能完成有界内部返修；额外成本、重复检查、人工等待和无用新版本明显少于原开发方式。

没有取得真实正常入口、独立审查环境和发布权限之前，不得将这些判据标成 PASS。不能保证所有未知未来缺陷永不发生，但**历史已经暴露的假数据/假观察和不做真实验收，却仍被宣布完成，必须视为生产系统本身失败。**
