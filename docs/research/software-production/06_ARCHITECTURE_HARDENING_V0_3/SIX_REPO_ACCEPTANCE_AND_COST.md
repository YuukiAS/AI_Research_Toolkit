# 六仓库怎样真正接入、怎样证明不会靠造假过关

性质：只读证据驱动的试点设计。不是已经在六台平台运行的测试成绩；未授权不使用任何生产凭据、设备写操作、真实用户数据、签名或部署。验证顺序必须先正常正例，再用独立、可回收的错误候选检验阻断；不能单纯设计一个“所有内容都拒绝”的伪安全工具。

## 1. 每个仓库的真实决策工具和三个必要反证

表中写真实已存在的项目入口；需要扩展的检查标为“新增适配/观察”，不是假装现有工具已支持。对应的原始事故编号和说明见六份账本以及晚期补查。六仓库不需要换技术栈、不需要统一分支策略，也不必复制一个新状态机。

### Lucerna：状态/外部服务/隐私与桌面交付

- **现有决定性程序**：Rust 的 ResourceRuntimeState 和正式 aggregation；scripts/test-longleaf-presentation.mjs、test-vault-presentation.mjs、guard-01056r4-state-contract.mjs；scripts/development-acceptance.ps1 的同次进程与截图绑定；src-tauri/windows/startup-hooks.nsh；已有原生产品审查。普通 lint 的文字守卫和 SelfTest 不等于原生验收。
- **正例 L+**：假设在已接受 Cloudflare R2 真实读取上新增阈值通知，用户可配置→保存→正式读取→正确提醒→抑制重复→取消/重进；其它服务正常与故障状态传播不回归。在合法受控输入层替换响应必须仍使用正式解析与聚合。最终装包验证仅在有权且隔离的 Windows 目标执行。
- **坏例 L−1**：只显示设置页、Cloudflare 未配置或读数硬编码，却标“已实现”；声明核对必须失败或仅确认设置边界。已有产品代码不会因“出现设置卡片”自动提供外部能力。
- **坏例 L−2**：在 fixture 塞正式业务不认识的 live_status，或让 Headline 从 mock 独立生成；应由生产链输入→聚合→全部相关显示的变化输入回归拒绝。不能只扫字符串，因为语义旁路可换写法。
- **坏例 L−3**：修改台账/截图/版本标识而不做对应动作，或只修报告就反复重构/重装；证据链和发布目标查询必须拒绝旧包，同时避免正确包重复安装。
- **明确边界**：实际用户桌面、正在运行的正式 Lucerna、个人凭据和网络服务状态不在未经批准的普通 QA 内；这些限制不能变成停止其它安全后台功能开发的借口。
- **第一轮验收成功意味着**：一个新功能的正常与异常真实纵向路径通过，旧状态回归未退化，内部首次真实操作/视觉检查先于 GPT Work；不能只宣称脚本自测通过。事故参照 L07–L33、LX01–LX20。

### Mica：真实 ChatGPT 宿主、附加收益和证据伪造

- **人工/权限边界**：没有用户合法登录态的自动操作授权时，真实宿主宣称保持未验证；不能通过擅自抓取用户会话来补齐。不能覆盖活动重构的已批准目标，也不能把延期的 Notion/高级恢复拉回当前首版。事故参照 M01–M46。

## 2. 同一公共能力，六种完全不同的检查手段

| 公共性质 | 共用机制 | 留在具体产品的真实实施 |
|---|---|---|
| 完整用户功能 | 目标→正常入口→真实后置条件→错误/重入→交付声明 | Rust状态、Zotero/Reader、ChatGPT扩展、安卓研究流程、科研图、托管注册 |
| 旧能力保护 | 冻结既有用户性质/重要旧场景，不允许候选单删 | 不同语言的测试、Compose/Playwright/原生读写及 Figma/统计语义 |
| 不用假数据冒充 | 每项声明标实际输入来源与证据等级，若核心路径由模拟代跑则不通过 | 实际各项目用户入口与服务/媒体/设备数据 |
| 独立产品质量 | 审查者实际取得同一候选完整画面/交互并有发现，校准历史坏例 | 科研可读、阅读器/扩展、服务状态、小屏操作和本地化 |
| 不无限返修 | 同任务按故障原因追踪，重复无新证据停止昂贵复测 | 本地程序保持原有精简聚焦检查，只有受影响性质重验 |
| 安全与真实发布 | 身份、授权、候选与真实交付目标绑定，未知副作用不重试 | Windows安装、Zotero数据、扩展包、APK、网页/后台部署、托管用户状态 |

## 3. 验证“不会过重”的实际对照

必须为每个仓库至少保留三个等级的场景，而不是机械给六仓库一张相同大清单：

- 小修：单一可复现文字/局部逻辑，沿用设计权威＋受影响回归；不会启动全部专业角色、外部收费审查、全量原生/安卓压力。
- 完整新功能：在一轮正常授权任务内完成入口→真实逻辑→状态/错误/持久化→实际UI、关联旧回归和首轮产品自检；内部返修而不由用户代查。
- 发行/重大架构变更：按风险补充隔离环境、全产物独立审查与安全凭据/发布；同一最终候选身份可核实。

正式试点需要比较：首次真正可用交付时间、用户手工测试次数、内部/独立审查发现的历史同类 P1、同因返修次数、执行与外部模型成本、重复构建/刷新和最终安装状态。不能用“脚本数量增加”或“反例全部红”衡量成功。

## 4. 实施前先取消四种虚假的完成宣称

1. 审查计划和脚本存在，不等于真实产品实际执行；
2. 正反控制能识别坏 JSON，不等于识别坏实现；
3. 机械检查绿，不等于独立完整视觉/科学质量合格；
4. 源码合入，不等于用户实际运行的版本正确。

报告必须分别说已验证的正常入口、被测候选、证据类型、真实未测范围和额外权限需求。当前六产品本轮均未在真设备/真实已登录服务上重新运行，本文件不能提供其最新发行资格。

## 5. 剩余未闭合的能力事实

- 六仓库历次事故并非每份历史评论/私有材料都已穷尽；已有246项与LX/AX补充是有证据的阶段性集合，而非“全历史都已经解释完”。
- 六项目已经安装的 Bridge 模式、Codex主机/登录/可恢复流程没有在本轮核实；不可从 README 推断。
- 独立审查若没有真的可用工具与完整材料，仍需等待或合法人工交接，不能通过另建同身份模型来制造独立性。
- 私有仓库的保护规则、受测程序隔离和发布凭据尚未实测分权；强制发布应保持未证明。
- 本轮是反证设计，不是单项新功能已经被一口气交付的运行证据。

完整事故与当前脚本定位：上一轮 04_SIX_REPO_AUDIT 的六份逐行来源表，05_PROPOSED_ARCHITECTURE_V0_2 的原始事故补查；本 v0.3 明确要求把正例、历史坏例和未见输入放进真实正常运行路径，而不能用新表格替代测试。
