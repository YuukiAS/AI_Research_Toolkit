# v0.4：不再用“内部独立审查”四个字代替实际实现

2026-10-13。继续用户允许的原研究分支。本轮只做来源审计、隔离CPU反例与设计修订，未改CARE、STAT5060或六个软件，未启动Critic/模型审查、训练、部署或新系统。

## 这轮实际新增了什么

**一是CARE的40项逐条账本。** 不再只重复Route B的12步例子：追溯SRR Lite、M8、M9、M10与Route A/B/C、ASE R1，在原始审计、当时源码和有效修订之间核对。40项含不同模块的实现缩水、跨轮复发、证据被过度命名和验证器盲区；不是40次独立实验，不是40个当前仍然存在的BUG。仅有禁止规则而没有发生证据的项没有放入凑数。

**二是对历史源码做了低成本实际反例。** 直接执行旧ASE训练辅助函数，发现：无T2五类映射把scar标签5连续变成4再变0；6000步提前进入C而不是要求的10000步；B阶段最高encoder层仍被冻结。这些本可以在正式长训练前被小测试发现。本轮没有重新训练整个模型，也没有用这些局部结果宣称新体系已经可靠。

**三是把内部独立审查固定成真实进程方案。** 默认一名写代码的Codex E，一次由任务拥有者而非E发起的新顶层只读Codex审查R，一个不用模型、实际运行项目场景的观察器O。写清谁启动、明确CLI参数、新上下文/只读快照、批准源、原始材料、受控输出、追加观察请求和返修出口。研发新功能关键机制形成后、长训练/大面积UI铺开前就审，不能只在最后检查报告。

**四是插件派发有具体调用者和例子。** 任务拥有者D在阶段入口运行拟议的`classifyImpacts/resolveInstalledSkill/buildExplicitRoleInput`；本轮核对到真实Skill名为`frontend-visual-systems`和`product-ui-copy`，不是泛泛说调用“一个文案模型”。新增CUHK Date问卷自动触发这两个具体入口和现有文案/浏览器检查，不依赖用户再提醒。

## 最重要的架构修订

原提案把很多希望放在“设计通过→Codex实现→最后独立验收”。CARE证明：**设计审批不验证尚未写出来的代码。** 即使合同非常详细，真实入口仍可换阶段、删损失、改采样、跳过恢复状态。必须增加的是“实际实现形成后、重大成本投入前”的忠实性检查，不是再叫Planner写得更长。

对应六软件：第一条生产服务/状态/UI链能跑就检查，不能先把mock UI铺满；Asteria第一幅可操作图就检查真实坐标与科学阅读；Bobbio第一条Reader/Zotero动作就看真实关系；Mica关闭注入不能代新增收益；SeminarArc和CUHK Date都要读取实际用户输入与真正持久结果。

研工台仍是产品任务的连续负责人，执行阶段不与Bridge已有CURRENT竞争。插件提供专业任务能力，Bridge负责合法主机/工作树/授权与真实已安装运行模式，项目观察器和独立R负责实际实现与证据。不能靠一个更大的模型、一个更长AGENTS或多数票自动得到正确产品。

## 没有把什么说成完成

当前没有证明R模型能识别所有40项，没有安装受控分发器，没有实现操作系统级审查/发布身份隔离；上文CLI是待批准的接口示例，不能拿去绕过当前Bridge的嵌套Codex与审批规则。真实全部历史旧分支、评论和私有运行材料尚未穷尽；旧ASE源码的缺陷不自动等于当前CARE仍有同缺陷。

用户认可之前不发送或运行Critic。下一轮即便继续补设计，也必须以这40项和原六库246项真实来源为约束，不从README重写另一套空洞架构。旧[六库账本](../04_SIX_REPO_AUDIT/README.md)、[晚期事故补查](../05_PROPOSED_ARCHITECTURE_V0_2/INCIDENT_ADDENDUM.md)与[v0.3执行边界](../06_ARCHITECTURE_HARDENING_V0_3/README.md)继续有效；本页补的是内部检查与显式派发的具体实现合同。
