# 规则不是靠自己长出来：谁修改、谁执行、怎样验证没有再留同样漏洞

2026-10-13。属于未实施的v0.4设计补强。不能把下面拟议模块名或测试用例数量当已解决；它们是未来需要实现并在正常入口证伪的合同，不是给Codex的新执行Goal。

## 1. 默认不把“自动完善AGENTS”作为解决方案

用户反复提醒“不允许抢桌面”“不要缩水”“不能删验收”，若已经写在AGENTS中而仍发生，说明修错了层：文字存在并不能限制正在运行的进程，也不能证明模型真的看懂或执行。后续同根因优先改变**实际调用路径、权限与产品回归**，不继续叠同义段落。

具体由任务拥有者D在现有修复完成后执行`recovery.ts::classifyFailure()`及`check-plan.ts::bindRegression()`这一类拟议接口：从原始事故ID、实际命令、输入/输出、权威要求和当前差异得到归因；结果不能由E一句“规则不足”决定。D能做确定性对账；领域含义由当前责任人/R核对，重大规范或权限变更仍需单独批准。

| 发现的事实 | 实际处理 | 是否改AGENTS | 谁能批准 |
|---|---|---|---|
| 原规则有效且本次没加载 | 修派发器/技能路径/上下文入口，保留当前产品测试 | 一般不用追加，只修无效定位 | 原已授权实现范围内的修复；全局配置变化另审 |
| 原规则已加载但仍绕过 | 将已存在约束接到真实执行入口/OS权限/不可自改验收器 | 不再加同义句 | 约束内修复可做；新增权限或正式流程变化另审 |
| 产品算法/数据/文案错误 | 修实际消费者并把最小复现加入原测试体系 | 通常不改 | 项目既有产品/领域owner |
| 真正跨项目的新缺陷 | 提议最小公共机制或领域插件修改，引用具体多项目失败 | 短入口只指向机制，不复制事故全文 | 用户认可方向及适用独立审查后 |
| 要放宽原要求/删测试/扩大权限 | 先停本修改，保留理由和替代 | 不能由E私改后继续 | 原目标/权限拥有者；必要Planner/Critic |

“自动”可以做到自动记入真实回归、自动提出待审补丁、自动检查下次普通任务是否消费；**不应做到自己修改自己的许可和及格线**。也不能把一个错误实施包装成需要用户再批准的重大架构来逃避本该自己修的代码。

## 2. 具体例子：以后不再让用户每个软件都说不要不停刷新

在一次性获准的主机执行配置中，普通编程进程E没有访问用户正常输入桌面的自动化能力。真正的图形操作只经有限的观察接口：

```text
O.capture(request):
  request = {task_id, candidate_id, target_test_session,
             approved_scenario_id, maximum_actions, allowed_output_root}
  require request's task authority and reserved test resource
  require no access to user's active desktop/processes/data
  require candidate identity and actual window readiness
  run approved project capture helper once for the requested scenario
  return original image + interaction observations + identities
```

这是接口示意。真正防绕过依靠隔离测试机/会话及受限账户：**若E仍能直接通过PowerShell/Python或Win32访问用户桌面，O里写一条deny并不算防住**。只允许PID白名单也不能代替真实进程/桌面隔离。相关安全探针需独立授权，不在本轮实际操作用户机器。

Lucerna已有`capture-lucerna-window.ps1`的`ExpectedPid`、`FrontendReadyEvidence`以及`development-acceptance.ps1`的同次运行绑定可复用。Bobbio使用自己的原生画面和Zotero安全脚本；共同复用的是测试会话/候选身份/证据传输，不是把Lucerna路径替换成Bobbio字符串。截图传输失败只重传原始包，不重开产品；报告文字变化不再生成新安装包。

对一个真实需要测试连续刷新防通知风暴的场景，批准的是**独立测试上下文内的有限次数**，不会成为每个普通任务都不停点击用户软件的借口。用户要求减少前台打扰，D暂停GUI动作但继续所有无需GUI的代码和后台测试。

## 3. 路由不是一张没人读的表：由任务入口主动执行

D对已有Goal先构造本次义务视图，再运行确定性规则选择最低必要能力；R从原始Goal独立检查是否漏选，而不是只接受D的摘要。任何程序都可能漏解析自然语言，因此不能只检查路由JSON结构正确。

建议首轮就固定这些路由反例，实际在正常Codex入口中验证：

| 输入/变更 | D必须派发 | 不能发生 |
|---|---|---|
| CUHK Date新增问卷题，用户未提“语言” | 设计阶段显式`$frontend-visual-systems`；受保护语义明确后显式`$product-ui-copy`；现有文案及真实表单检查 | 只因为用户没说“用插件”就不调用 |
| Asteria改连线/Inspector | 设计/科研语义、真实屏幕坐标观察、完整图形读取 | 用通用网页lint或只看虚拟坐标替代 |
| Bobbio改Reader | Figma权威、原生交互与实际Zotero关系；相关路径才需要数据隔离测试 | 把已接受Figma改成普通卡片；误开真实数据 |
| CARE改loss/sampler | R读取有效数学/数据合同；O检查正式loss/梯度/样本描述符 | 只跑语法/正向输出形状，直接进入长训练 |
| 修改一处无歧义拼写 | 相关文案/页面局部回归 | 全量架构审查、GPU、所有设备、全部插件 |
| 修改验证器但产品未变 | 校准其好/坏/缺测检测、评估原始证据是否仍适用 | 自动发布一个新产品版本或把更宽标准当产品进步 |
| 实现阶段突然改共享认证/状态 | 暂停该扩大修改，重新路由到适用能力和关联旧路径；授权越界才问用户 | 继续按最初“局部UI”方案跳过依赖 |

D在派发前取得实际安装的Skill名称/路径与版本，记录将要调用什么。显式提及Skill仍可能失效，因此要从真实运行输入/读取事件核对它进入了当前执行上下文，再由产物判定其影响。**记录读过最多证明接入，不能证明质量**。若被选定技能不存在/重名/没有实际读到，不得自动记已消费或切到更简化的通用回答。

## 4. 对“内部独立R”的实际反证，不再验自己出的题

R成为普通生产路径的一部分之前，先对下列情况做有界检验。题目来自真实历史问题的冻结版本，不直接把本账本的答案告诉R；独立原要求必须提供，否则它不能判断是否实现缩水。

| 验证项 | 应观察到的结果 | 不能用什么替代 |
|---|---|---|
| C26阶段边界代码与合同不一致 | R沿真实runner找到配置，O在6000步处重现差异 | 只问R“有没有可能阶段错”并接受yes |
| C10权重声明但调用未传入 | R指出真实消费者，O更改权重观察总loss是否按预期变化 | key存在/args里有值 |
| C17普通component表被叫causal | R要求真正的同候选开关证据；缺则该因果声明不通过 | 文件名、schema、hash齐全 |
| C34标签通道正确但target被抹掉 | O枚举标签值，R识别scar学习含义 | 只测五通道输出和无T2水肿梯度 |
| 正确合法重构 | 旧用户/科学保证不变，R不因文件重命名或移除过时实现守卫误拒 | “凡改测试一律不合格” |
| 传作者报告P1=0而无原始观察 | D不提升为独立完成，R指出未观察 | 同模型多数票 |
| 没有真实图形/宿主访问 | 准确保持相应性质未验证，安全后台工作继续 | 由精选静态截图假称所有交互已验 |
| 未经允许修改规则/模型选择 | 启动/晋升被拒绝，保留正确主体和差异 | 给参数改一个名字绕过 |

这不是对R绝对正确的宣誓。若R在这些具体历史坏例上继续像Tutorial盲测一样大量漏检，**这个R配置没有资格独立承担对应准入**：先分析缺的是源材料、运行工具、任务分解还是模型判断，不强行进入多仓库推广。不以更复杂Prompt或更多角色数量宣布问题解决。

## 5. 对跨研究与软件开发的架构约束

CARE说明“设计写得更详尽、Critic更严格”仍不足：应当在实际代码形成后检查是否忠实，在花大成本前发现缩水。在统计/科研中，这对应验证估计目标、数据人群、数学计算和实验对照；在产品中，对应验证真实入口、服务/状态、持久化和用户结果。共同系统只是让**批准要求→真实实现→独立观察→结论→交付**不再被模型偷偷换成更容易的代理目标。

任何中央工具若自己看不懂专业语义，就必须调用确切领域角色、给它足够原始材料并取得实际检查；不能自己用一个非空字段代替。这一点也限制了自动化边界：真实新产品/科学取舍仍需要相应责任人，不再把“自动运行”当作自动授权改变问题。
