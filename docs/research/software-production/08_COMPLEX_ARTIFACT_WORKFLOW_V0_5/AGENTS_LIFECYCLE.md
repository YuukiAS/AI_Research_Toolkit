# AGENTS全生命周期：开发中维护、整理、淘汰，而不是靠用户逐句管

2026-10-13。回答U04/U15。设计目标是：AGENTS随着项目真实变化保持简洁、正确、可执行；旧经验真正进入后续普通任务，同时避免“文档越写越长、规则覆盖彼此、运行根本不消费”。本轮不改任何产品AGENTS、全局CODEX_HOME或实际Host权限。

## 1. 明确谁负责，不把维护永久留给用户

**主实现者负责说明本次代码/入口/依赖改变；阶段结束由任务运行器自动触发一次规则维护检查；维护职责由一个有明确文件范围的Codex维护调用承担；合入权依据改变的语义分级。** 这不是新增常驻智能体，不需要每次用户说“顺便更新AGENTS”。

没有规则相关变化时，程序做便宜的差异/路径检查即可，不启动长模型维护任务。实际出现规则冲突、运行入口变化、重复事故、失效路径或超出加载预算，才让维护调用整理文本和提出补丁。维护代码属于研工台的`continuity.prepareRulePatch`/实际项目维护脚本职责；如果已有仓库工具提供同等能力，直接接它。

首次接入时一次性确认维护范围：允许修什么文件、哪些是用户固定要求、哪些权限/产品目标不可自改、怎样处理本地人工内容。**用户认可这套工作流以前并未授予所有仓库的自动规则改写权；当前只设计。** 将来获准范围内的常规维护不再每一条问用户。

## 2. 维护触发点，不用额外长期开监控服务

| 触发 | 实际程序动作 | 需要模型吗 |
|---|---|---|
| 每个任务起点 | 读取真正生效的指令链、检查路径/命令和版本是否可用，识别override及范围 | 机械盘点通常不需要；冲突语义才需要 |
| 任务修改运行入口、目录、构建/测试命令、平台/插件依赖 | 对照当前规则引用，找过时路径/命令和已被替代步骤 | 有实质整理时一次维护调用 |
| 原规则存在但再次事故 | 查实际派发/加载/权限/观察是否失效，不能直接归“规则不够” | 需要根因判断，优先复用当前角色 |
| 一项历史临时限制已有明确新授权或阶段终结 | 提议终止其有效期、归档或改为更窄规则 | 需要核对原授权和真实状态 |
| 规则重复、互相冲突或指令链接近实际加载上限 | 合并同义项、下移领域说明、保留最高要求与可用入口 | 是，但结果需语义和行为回归 |
| 阶段/版本收口 | 把已批准规则补丁随任务合入，检查后续普通会话能读到；无变化明确无须更新 | 只处理本轮影响，不全库重写 |

不存在“隔三天自动把所有AGENTS重写一次”。维护由真实开发事件触发，避免规则维护本身打断产品交付。

## 3. 规则怎样增删改并迁移

每个待修改规则必须判一种处理方式：

| 处理 | 最小证据 | 例子 |
|---|---|---|
| 保留 | 仍有效的目标/安全要求或当前入口 | 不操作用户正式桌面、不触真实Zotero资料 |
| 更新 | 新实现/批准决策使旧路径、版本或条件失效 | 捕获脚本已改为统一会话入口，AGENTS不能继续调用废弃脚本 |
| 合并 | 多段要求语义相同、作用域兼容 | 三处“不要刷新”合为一个默认后台与合法GUI测试入口，而不是删掉限制 |
| 下移 | 只适用于子系统，根文件无需全文 | Android服务生命周期细节放安卓目录/领域说明，根只保留必须使用的真实入口 |
| 迁移到可执行控制 | 原问题可由程序/权限可靠阻断 | 实现者不能改最终golden、不能使用未获准设备serial、不能自报完成 |
| 退休 | 有明确替代/范围结束/原规则错误的证据，且原保护由新机制承接或经批准取消 | 旧版本临时“不要继续”已被新获准任务取代；过时文件不再参与加载 |
| 归档 | 解释历史但不再指挥当前任务 | 旧事故全篇/旧RC规则放历史资料，避免当成今天必须全部重做 |

**不能因为规则很久没触发就删除安全规则。不能因为当前测试通过就删旧保护。不能以“简化AGENTS”改变用户原有边界。** 退休必须说明保护义务去了哪里；真正放宽权限或产品/科学标准不是文档清理，走对应的方案批准。

维护结果只需当前任务中的补丁和简短的语义变更说明；不强制为每条规则建一个中央数据库、评分器或审批单。已有规则来源和Git历史能说明的，不重复造账本。

## 4. 怎样审批，又不让用户每条都维护

- **不改变规范含义的整理**：拼写、已批准路径/命令同步、重复项合并、保持作用域的结构整理，可在一次性维护授权范围内随普通代码评审处理。主实现或维护调用可以写补丁，但不能自己声称独立审过。
- **改变执行行为但保持已有目标/权限**：比如原规则已经禁止抢桌面，现在把调用接到安全采集接口。由当前项目技术/质量负责人核对并做新旧回归；不能借此偷偷申请更大操作系统权限。
- **改变目标、许可、全局规则、独立性或预算**：Planner提出具体差异，适用时独立Critic和用户决定；不是每条文案都上交。没有批准就保留现行规则，候选补丁不能给自己当前任务发新许可证。

在Bridge Review/Control中，维护属于其合法实现/审查任务范围，不能另加能改CURRENT的Maintainer Controller。触及中央AI Skills/Bridge正式行为时才使用对应维护协议和跟踪；不能因产品里改一个路径就扩展到中央新插件。

## 5. 怎么保证新规则真的进入下次执行

当前官方Codex文档说明：指令在运行/会话开始时构建；全局及从项目根到当前目录逐级发现；`AGENTS.override.md`优先于`AGENTS.md`，还可能有配置的备用文件名；默认合并字节上限32 KiB，但实际配置可不同。因此**“文件已提交”不等于当前旧会话已经加载新指令**。

任务入口必须做以下实际检查：

1. 确认当前主机、工作目录、项目根和真实Codex身份；不凭另一个机器的CODEX_HOME推断。
2. 按当前安装版本的正式发现规则读取生效链，核对override遮蔽、嵌套作用域和字节截断。不能只数根AGENTS大小，也不能无批准提高全局上限。
3. 对维护后文件检查命令/路径真实存在，关键义务没有在合并/下移中丢掉。领域规则下移后，任务从根启动是否会实际获得它，需要由派发器在相关阶段显式读入，不能以文件放在那里为由假设已加载。
4. 旧运行会话若持有过时指令，在安全检查点保存进度，由原任务拥有者按合法入口重启或建立新上下文；不无条件终止工作、不修改随机缓存或复制用户认证。
5. 用实际输入/读取记录确认消费，再用代表性普通任务验证行为。模型复述“我读了规则”只能辅助定位，不能替代对副作用、实际测试调用和产物的观察。
6. 规则维护失败保留原有效文件和补丁，不“修到可以解析”为止就提升；真正执行边界未接通时不得宣称规则已经防住复发。

官方来源（2026-10-13读取）：https://developers.openai.com/codex/guides/agents-md 。本文据此设计加载检查，但未验证用户主机实际配置。官方样例里的审批选项不构成本项目修改审批策略的授权。

## 6. 把Lucerna的“不要不停刷新”做成机制，而不只改文字

旧文字有效但实际脚本仍能调用前台窗口动作，根因是**执行能力没有被限制、截图和产品开发没有分开**。

拟议规则维护应同时交付：根AGENTS简短指向后台默认与图形测试入口；原调用方不再直接操纵用户桌面；独立观察端只接受批准的候选、场景、目标会话和有界动作；进程/会话权限实际隔离。若主Codex可绕过包装器调用Win32/Python/PowerShell抢同一桌面，修复没有成立。

正常新任务必须有两种回归：后台功能开发不申请前台操作也能继续；在合法隔离会话内的必要截图/通知压力可成功。不能把所有GUI操作一禁了之，结果每次又要求用户代截屏。用户拒绝打扰不等于授权取消产品验收，也不等于要求全部停工。

Bobbio继承这个宿主基础约束，但自己的Zotero数据/协议处理器隔离仍在项目安全入口；维护者不能把两者合成一句“用Safe脚本”后认为所有风险相同。

## 7. 维护本身的验收：避免AGENTS越变越坏

必须检验以下正反情况，不能仅检查Markdown格式：

- 合并重复指令后，原受保护行为仍被实际阻止；合法任务没有多一道审批。
- 退休临时停工指令后，新获准任务可以继续，未授权旧操作仍不可做。
- 子目录规则下移后，从正常项目入口发起相关任务也会消费它；无关任务不加载整个领域长文。
- 引用不存在的命令/插件路径，启动预检明确指出，不静默换低配替代。
- 维护补丁试图删除验收、改允许设备或扩大凭据范围，被分类为语义/权限变更，不进入自动整理通道。
- 只改文档/指令格式，不使产品候选、原始截图或模型checkpoint自动失效；改实际科学含义/行为才重新判相应证据。
- 规则已写仍复发，追实际加载与行为控制，不再自动生成第四条同义禁止句。

## 8. 当前交付承诺的准确范围

这一流程可以让维护成为正常开发的自动责任，而不是用户的逐句工作；但**当前尚未在六个仓库部署维护器或授予常规自动合入范围**。设计一旦被认可，应先用一个真实过时规则和一个仍有效安全规则做正反试点，证明既能淘汰又不丢保护。没有这个结果不能把AGENTS更新次数称为自主学习能力。
