## 2. “为什么能挡住”必须是一条因果链

对每个已声明受保护的能力，后续实现必须满足以下条件：

1. **要求没有被偷偷换掉**：源于有效用户/产品/科学目标，独立验收的义务不由当前候选删改。
2. **观察真的发生**：运行的是本次用户正常入口/真实算法，输入、动作、产物和被检查对象可以追溯；没有用模仿最终答案的夹具代跑。
3. **参考没有抄错实现**：从原公式/用户后置条件/独立正确基线获得；能拒绝历史坏例，也不会误拒正确等价实现；缺测不是零。
4. **结果被真正消费**：只有该阶段实际执行且满足时才允许进入相应昂贵/发行环节；单个退出码、模型口头PASS或未执行的绿色作业不能替代。
5. **实现者不能绕过裁决**：实际账户/目录/工具/凭据权限防止修改冻结标准、伪造结果或直接发布。若未分权，诚实标为审计型而不是强制型。

例：B6指标是病例编号公式。第1点要求逐病例真实预测评价，第2点独立观察端取得实际预测/GT，第3点独立重算Dice，第4点不接受只有旧CSV，第5点阻止实现者换掉裁判。五点真正接通时，这个具体错误不能通过该入口；如果仅在文档中给它分配一个检查名，尚没有这样的保证。

同理，Asteria恒零计数需要真实几何观察和校准；Bobbio数据隔离需要实际路径/实例/前后审计；自然文案和审美还需要能处理该类材料的专业审查。不能从一个确定性例子推导所有未来语义错误都不会漏。

## 3. 不同“防护”不要混成一个PASS

| 防护强度 | 成立所需证据 | 正确报告 |
|---|---|---|
| 已归因 | 原要求、原错误和对应消费者/观察缺陷有可追溯来源 | 该历史问题已有因果解释 |
| 可检验设计 | 明确好/坏/缺测输入、真实执行入口与预期、权限和失败回流 | 具备可执行的反证设计，仍待实现/验证 |
| 局部复现 | 实际运行冻结函数/最小场景，结果可重复 | 仅此函数/环境下的缺陷被复现 |
| 机制通过 | 独立观察和准入程序在相同正常入口拒绝坏候选并接受正确候选 | 对这些声明/平台/候选具有经测防护 |
| 普通使用有效 | 真实新任务、修复和交付中减少旧机制复发与用户首轮调试，无不成比例成本 | 才可考虑持续使用和推广 |

本轮达到的是已归因、可检验设计和一个新增局部复现，不是最后两级。历史材料已显示某些原项目脚本抓住真实问题，它们应复用；但新统一运行包尚未消费并重新证明这些能力。

## 4. 验证路线必须同时检验成熟交付和不过重

不是固定“全部反例变红”就合格。批准有限试点之后，至少应在真实正常入口完成三种任务：明确局部修复、完整新能力、实际交付。Lucerna先用已经存在的正常开发目标，不为展示框架无端添功能；再选一种非桌面消费对象，证明核心不需要复制分叉。

对这些任务保留以下对照：

- 正确实现能交付；不会因为审查者自己发明阈值、某个工具假阴性或文档提交漂移永远无法结束。
- 已登记关键坏实现会被实际检查发现：假数据/代理指标、未接真实入口、测试与产物被一起改、旧功能丢失、默认禁用、错误版本、缺测却PASS。
- 一次交办内部完成合理返修；主实现可使用有界子任务，但外层只有一个有效任务拥有者；真冲突由对应owner解决，不向用户反复甩日志。
- 在实现中、候选后、外部动作回执丢失时中断，恢复查询现实而非重发；已安装正确版本不重装，图片传输失败不重建程序。
- 小改不会调用全部模型/原生平台/完整科研检查；新增专业职责确实影响产物，而不是仅增加加载日志。
- 规则维护能够合并/退休过期指令，同时保留现行安全与用户目标，并在新正常会话实际生效。

度量以真实首次可用交付时间、用户第一轮调试次数、历史同类严重漏检、同根因重复返修、重复构建/截图/模型/发布成本为主。没有可比历史时不能伪造改善百分比；也不以“建了多少脚本、写了多少规则、审了多少轮”作为收益。

## 5. 当前剩余缺口及精确补证方向

| 缺口 | 已知定位/最小需要 | 不应采取的替代 |
|---|---|---|
| CARE早期复现实验分母 | 早期M0–M7/MLoRA/FSCF各自原prompt、有效实现commit、runner、结果；原Batch恢复表不能提供的部分需原历史资产 | 不复制M8/其它模型错误填满空白，不声称30多个名称全都已复验 |
| 若干主线/私有明细不可读 | 固定ref目录与blob读取404，保留可读的修复原文；有可访问原附件时再补 | 不拿目录存在或manifest present当全文已经读取 |
| 真实任务拥有者/模型/插件 | 在目标主机确认已安装Codex、Bridge模式、实际身份/Skill解析和合法派发；明确费用与后端 | 不用仓库README推运行状态，不拷贝认证或擅改CODEX_HOME |
| 验收私有性/写权限 | 受控源、独立参考、最终样本与发布身份实际分权及绕过反例 | 不以另开会话、文件名或只读CLI单独声称强隔离 |
| 内部审查真实检测力 | 用原要求而非标准答案，运行好/坏/缺证据场景，统计漏检与误拒，冻结批次 | 不用格式正确、总准确率、多个相似模型投票自证 |
| 领域完整性/用户消费 | 真实Windows/安卓/宿主浏览器/托管服务/研究材料；相应授权及资源 | 不用图片、模拟I/O、合成数据或小规模动作顶替更高等级声明 |
| 自动规则维护 | 授权明确的维护范围，测试一个真过时规则与一个仍有效保护，并核对实际加载 | 不在未认可架构时偷偷改所有产品AGENTS |

这些不是要求用户亲自补每条。能从已授权连接继续读取的由当前研究者/将来任务owner补，能在任务内合法修复的归对应执行者。只有原始资料不在可读范围或实际需要新设备/权限/费用时，才提出最小具体请求。

## 6. 这份研究自身也必须接受的否证

若同一要求在本目录只出现模块名而没有实际消费者、输入/判据/失败归因，本设计仍不够具体。若审查必须不停靠用户复制提示词，它还不是可持续流程。若为阻止这些错误必须让每个小任务经历CARE式几百提交身份重绑，路线过重。若最终只是要求Codex读更多文档，路线过简。

因此v0.5给出的是明确可证伪的运行与职责合同，**不是保证所有未知未来问题绝不出现**。对于已明确应被阻断的历史错误，真正接入后仍被报告完成，必须判生产机制本身失败，不能引用此前Critic/PASS否认用户真实反馈。
