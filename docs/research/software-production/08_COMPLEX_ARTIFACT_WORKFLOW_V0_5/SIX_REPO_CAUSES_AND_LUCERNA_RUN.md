2026-10-13。依据既有246项逐条源账本及LX/AX晚期补查；本页不是把历史故障全部当成当前仍坏，也不重复生成第二份246项事实库。旧账本中的每项原始来源、类型和具体脚本仍保留，本页明确这些组件在v0.5的什么阶段真正被调用，以及怎样证明对应防线不是口号。

## 2. 用什么具体性质检验“防复发”，不是只跑更多测试

已有246项逐项表不能仅因为分配了组件就标已解决。对每类控制记录三个层级：**归因已证实、对应检查已实现且校准、当前正常入口已经执行并拦截历史坏实现**。只有第三层才允许声称该入口具有防护；当前本轮主要完成前两者中的设计/局部研究，没替六产品做正式运行。

| 跨仓库问题族 | 对应决定性程序/角色 | 好例必须怎样通过 | 坏例必须怎样失败 |
|---|---|---|---|
| 缩小目标/禁用主功能 | `resolveEffectiveRequirements`＋领域忠实性审查＋真实正面场景 | 等价实现给用户完整承诺，不因内部重构误拒 | 设置存在但服务未连、默认关闭高亮、12步代正式训练不能完成 |
| 输入/模块/资源不消费 | 正式入口追踪＋参数/数据干预观察 | 正常真实输入走原业务/科学链 | 已下载但不用、loss权重不传、深尺度未进入最终结果、mock headline |
| 假评价/同源验收 | 独立参考与观察端、验收权分离 | 真好产物实测满足标准 | 公式分数、恒零测量、复制CSV、直接API绕UI、协调伪造JSON不获通过 |
| 旧功能回归 | 公开历史场景＋受保护用户性质＋影响选择 | 合法改实现但旧结果仍成立 | 连同旧测试一起删功能仍被独立旧行为发现 |
| 整体审美/语言/学科错误 | 首个原型专业设计＋实际完整产物审查 | 可读、自然、科学忠实的整屏/文档通过 | 局部控件/KaTeX存在却图丑、中文机械、统计解释错误不能靠结构绿灯 |
| 观察器假阴性 | 正常/坏/缺测三类校准与真正输入回读 | OCR实际正确、正确语言/模型不误杀 | 读错控件/错输入/错误阈值先归测试器，不逼产品迎合 |
| 无限返修/乱刷新 | `classifyFailure`＋原任务预算＋专用会话租约 | 有新因果证据的必要修复继续 | 同因无新证据刷Work、新RC、新版本或重装被停止并归因 |
| 身份、环境、交付混用 | 真实进程/设备/数据/包/部署核对，语义身份稳定 | 同候选合法安装/升级/重入通过 | 错包/旧图/假原生/污染身份/未发布不能叫完成 |
| 规则失效 | [规则生命周期](AGENTS_LIFECYCLE.md) | 正常入口消费新规则，旧保护不丢且文档更简洁 | override遮蔽/截断/旧会话/改规则降低标准不被自批 |

## 3. Asteria箭头：这次具体改的是设计机制，不是又加一个“美观检查”

RC18原复审直接说明：固定节点后再跑通用障碍绕路，产生长折线、蛇形、离开局部区域又折回；去掉箭头和标签仍丑。正确方向是先安排节点/层次/通道，使关系自然可画，再用局部避让。另有真实HTML/SVG坐标错配和恒零指标，这三类不能混成同一个CSS问题。

因此新的大图任务在**第一幅可操作图**就执行：设计者决定科学关系表达和总览/细节层级；实现者用同一实际坐标系统；观察端测真实边端点与卡片边界、选中/缩放/Inspector变化；专业审查者完成一次“从节点读关系与解释”的真实任务。先独立看全图再对历史发现，不只勾旧编号。

需要校准的坏例是历史的长绕路/密集线结/节点跳动，不只是某一张截图文件不存在。正确例必须保留真实科学边、公式和多模型可读性；不能删关系或硬编码CAT-TRACE某几个ID刷过。布局算法与成熟依赖可以替换，但真值源和用户阅读目标不可偷偷改变。

这只能提供有直接证据的专业质量控制，不能用“审美分大于阈值”形式化保证所有人永远满意。如果同一结构再次被独立完整审查或用户否决，判布局/设计方案失败，停止又一轮像素小补丁。

## 4. CUHK Date语言：什么时候查，不让用户每次再说

新页面、表单、状态/空/错误信息、隐私/匹配解释都会触发产品文案职责。派发者实际启动`$frontend-visual-systems`确定内容位置和作用，再启动`$product-ui-copy`处理香港繁体/内地简体；不是只对locale文件做词替换。

实施时同时统计翻译资源和页面硬编码的用户可见文字。已有`verify:human-product-copy`等检查用于已知坏词/混杂语言回归，**完整原型还要结合前后动作审整句话**。例如“可操作的當前配對”词面可能可解释，但不是用户自然理解的状态提示；“等待”必须说明谁在等谁、此刻能做什么，不能改变真实匹配/隐私语义。

复核在内部首次实际浏览阶段进行；用户和GPT Work不再承担发现明显内部术语/状态矛盾的首轮责任。纯拼写小改只复核相关页面，不重复全产品语言审查。

## 5. Lucerna完整例子：基于现有R2读取增加容量阈值提醒

这是设计演示，不是授权新增产品任务。当前固定源码 `src-tauri/src/cloudflare_r2.rs` 已有 `CloudflareR2Provider::refresh`、真实凭据读取、`fetch_state`、可缺失的容量/请求指标和`save_setup_transaction`回滚；**不能再把它当未接真实API重新造一遍**。本轮只读源码，不访问用户真实Cloudflare账户。

### 接单和专业准备

任务拥有者先确定已有来源和本次目标：读已有可用容量信息，阈值设置保存/取消正确；达到阈值产生一次合理提醒；重复读取不刷通知；未知/过期/鉴权错误不能当零或正常；其它提供方和托盘原行为不回归。需要新增指标/外部权限时先分清本来API是否支持，不能凭UI造数。

验收职责从此目标制定公开的状态/通知/持久化场景及独立变化输入；最终真实数据和原生行为证明另有等级。Frontend Design沿现有紧凑托盘结构设计最小修改，产品文案说明实际用户动作，不另建一页大卡片。

### 主实现者与子代理怎么分

- 子任务一：纯阈值判断/去重逻辑及开发测试，在明确独立模块内提交。
- 子任务二：设置组件、状态文案、可达性和对应开发测试；不得改真实认证或核心聚合。
- 主实现者：正式R2输入接入共享运行/聚合、通知触发、持久化、取消/隐藏/重新打开行为，并集成两部分。它必须看真实组件结果，不能接受两个“PASS”就结束。

这些子代理没有正式验收写权限。接口或文件冲突由主实现集成，不能同时改同一状态源；无法拆分的部分主实现自己做。

### 第一条正式链就检查，而不是全部mock画面做完后再说

观察端对合法边界响应做正常/缺值/鉴权/网络/过期变化，仍经过正式解析、聚合、卡片/顶部/托盘和通知逻辑。R核对是否只改UI最终状态，是否缺值被当0，是否未配置却声称服务已连接。

真实API数据能力有合规可用凭据才单独验证；没有时可完成阈值/状态逻辑与UI，但不能宣布真实提供方整体验收完成，也不擅自抓生产密钥。已有用户授权及配置应按合法范围复用，不重复要求用户输入。

### 内部首次质量检查必须拦下什么

| 旧问题式实现 | 实际观察/拒绝 |
|---|---|
| 所有提醒默认关闭取得安全 | 正常越限正例没有用户收益，不算功能完成 |
| 网络失败当0容量 | 缺值/失败语义与正常0不同，状态/提醒不应被错误抑制或显示健康 |
| 子服务失败而顶部Available | 同一输入沿全部消费者核对，不能只看当前卡片 |
| Cancel清了输入但托盘隐藏未清秘密 | 对不同真正隐藏原因及重开进行检查，不以一个按钮测试替代 |
| 每次读到稍变值都通知 | 连续相同事件/抖动场景验证去重与恢复，不在用户桌面刷输入 |
| 保存返回成功但重启丢设置 | 真实存储回读/进程重启的后置验证，不能仅handler被调用 |
| 为方便展示留下fixture控件/假账户 | 稳定发行候选以干净正式模式启动；开发状态不进入默认产品界面 |
| 新功能局部正确但整屏更重、更重复 | 独立看完整托盘、正常/错误状态、焦点与文案，内部先修再交Work |

### 截图跨两台机器不应该再研究一遍

研工台请求一次**候选明确、场景有限、资源专用**的图形证据会话；Windows观察端复用现有 `capture-lucerna-window.ps1` 与同次运行绑定，不重新发明HWND/DPI/PrintWindow。该端负责实际进程/路径/窗口就绪、必要动作、截图和原始记录；接收审查者拿到同一证据包，不要求再打开用户应用核实。

采集、传输、审查是三个不同步骤。图片传输失败只补传，报告错误只改报告，候选没变不能自动重建/重装。两台机器之间保存便携的候选/运行/场景身份，私密主机路径、凭据只留受限环境。截到窗口证明画面，不证明全部动作/真实服务；需要的后置观察一起保存。

普通Codex不拥有用户当前桌面的自动点击权，专用VM/测试会话是否隔离必须实测；无法安全执行时只停该原生部分，继续背景开发。Bobbio可复用会话/证据传输基础，但Zotero实例与资料安全仍走其自己的脚本。

### 返修、Work与用户

同一任务中把真实失败交主实现修，按因果影响复测；观察器自身错先修观察器。一次集中内部审查后一次针对性复核，同根因无新证据停止重复完整Work或新RC。真实技术/设计问题先由对应owner/Planner处理，不每条都让用户决定。

只有稳定候选满足适用内部真实检查与专业观察，才进入仓库要求的GPT Work；用户只处理真实登录/权限/产品取舍或最终主观接受。若Work再次首先发现大量已登记类型的基本P1，应归为**内部检查路径失效**，修消费者和测量，不只是把产品再重写一轮。

“一次交办”意味着内部完成合理实现与返修，不承诺第一份代码无bug。当前仍未执行此新功能或这套调度；这是可以据此检查是否真正接通的完整运行合同。

## 6. 三种任务重量，六项目都必须过正例

- **小改**：现有设计和来源明确，局部实现/测试/相关屏幕；没有全量GPU、全平台、全套Reviewer、重复规则报告。
- **完整新功能**：第一条正式路径、影响旧行为、领域设计/内容、真实平台操作和一次集中的内部质量检查。
- **高风险或正式交付**：加独立参考/权力分离、真实数据/安装/迁移/发布后置检查，遵守已有Control或其他获准机制。

完整性来自每个承诺有相应证据，而不是每个任务执行全部检查。最终验证应比较真实交付时间、用户首次发现的历史同类严重缺陷、人工介入、重复构建/Work/部署次数与费用；只增加报告和钩子没有减少这些负担，路线就没有成立。
