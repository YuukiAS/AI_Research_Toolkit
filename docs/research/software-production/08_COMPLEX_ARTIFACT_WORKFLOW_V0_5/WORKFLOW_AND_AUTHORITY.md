# 研工台 v0.5：连续交付复杂产物的实际工作流程

日期：2026-10-13。对象是软件、网页、深度学习模型和科研/统计产物的一项真实交付任务。**这是待用户认可的设计，不是已经安装或通过验证的系统。** 本轮只写研究分支，不启动Critic或生产实现。本文替代旧稿中含混的“一个内部审查者”“路由器提醒”“统一监督器”；其他文件中的过程若冲突，以本文与同版验收/规则合同为当前提案。

## 1. 最终应该是什么，而不是再换一个架构名

推荐对象仍叫 **研工台**：一个独立版本化的任务运行包，包含可执行的阶段派发、专业能力解析、项目观察适配、验收结果消费和规则维护。它给用户一个持续的交付目标，不要求用户在每次代码/测试/审查错误后重新发提示词。它不是新的编程模型，不是只有提示词的插件，不是最后才出现的验收器，也不重新开发通用工作流引擎。

第一版的正常入口是**实际开发机上已授权的任务运行器**，复用该项目的Codex/Bridge；不是声称当前ChatGPT对话已经能直接控制那台机器。产品界面先使用现有任务/拉取请求和一份从事实生成的进度，不先开发独立聊天客户端。需要跨会话持续运行时明确真实寿命拥有者；没有主机/进程时只显示暂停可恢复，不说后台正在做。

代码归属将来由用户决定，现在仍只是AI_Research_Toolkit中的研究包。专业插件在AI Skills分发，Bridge提供跨仓库执行原语，项目保留自己的源要求、测试与产物。新包只补**这些已存在能力没有被正常开发真正消费**的部分。

### 只需要四组程序接口

| 程序组（拟议，不是现存文件） | 具体函数责任 | 复用什么而不重造 |
|---|---|---|
| 任务适配 `task-adapter` | `resolveOwner`、`resolveEffectiveRequirements`、`classifyChange`：识别唯一目标、当前任务阶段、有效修改和影响范围 | 项目Goal/AGENTS/当前Git；已安装Bridge的CURRENT/授权；不创建竞争账本 |
| 阶段派发 `stage-dispatch` | `resolveSkill`、`launchRole`、`waitOwnedRun`：实际启动指定角色、给定上下文/权限、预算、收集执行结果 | Codex正式CLI/SDK、已安装Bridge阶段入口；没有现成多步运行器才比较固定版Spec Kit，不自研DSL/队列 |
| 观察与准入 `assurance` | `executeScenario`、`validateObservation`、`admitClaim`：运行批准场景、核对实际观察、限制完成声明 | 六项目和CARE真实脚本、独立参考计算；不是把所有脚本迁到中央重写 |
| 恢复与维护 `continuity` | `classifyFailure`、`reconcileEffect`、`prepareRulePatch`：分流、重入、去重、规则更新/退休 | Bridge工作树/运行恢复，Git与实际安装/部署/作业事实；不使用状态文本推测外部效果 |

程序名字不是新增能力证明。每个函数必须有明确消费者、输入和实际后置条件；如果只把它写进AGENTS却没有调用，接入未完成。

## 2. 谁真的运行：主实现可以有子代理，独立验收不是它的子代理

**主实现Codex不是单兵手写一切。** 它是本次实现的集成负责人，可以用子代理做有清晰边界的代码探索、独立模块实现、开发测试和文档；最终自己合并并验证完整用户路径。并行写同一文件/数据库/桌面不允许；每项子任务有文件/资源归属、验收结果、时限和集成责任。为了凑并行数拆高度依赖任务反而增加成本，应由主实现保留。

例如Lucerna用量提醒：可把纯阈值/抑制重复逻辑及其开发测试交一个子代理，另一子代理处理设置组件和文案；主实现负责正式R2输入、共享状态、原生通知与保存/取消的集成。两个子代理都属于实施侧，**没有一个能给正式候选签发独立通过**。科学模型可并行检查数据契约和原公式实现，但共同训练入口、数据版本及最终loss由主实现集成，不把合成测试交给一个子代理后直接相信。

### 运行中的角色与进程

| 责任 | 由谁启动 | 它实际能读/写什么 | 结果由谁处理 |
|---|---|---|---|
| 主实现者与开发子代理 | 现有任务拥有者；子代理由主实现在预算内派发 | 当前批准实现工作树、开发测试、允许数据；不可写冻结要求/受保护验收/发布凭据 | 主实现负责集成，任务运行器检查实际候选 |
| 验收设计者 | 实施前的合法Planner/Verifier阶段 | 原要求、原理论/设计、既有已接受行为、历史坏例；此阶段不看新候选 | 冻结可公开标准与独立参考/样本，见验收合同 |
| 忠实性审查者 | **任务运行器的派发函数**；不是主实现者自己选择是否调用 | 新只读会话，原始批准源＋真实候选＋独立观察；不读作者自评作为答案 | 只提交带证据发现，不能改产品/评分器；交原角色修复 |
| 产物质量审查者 | 同一合法阶段派发者，按UI/研究内容影响触发 | 真实整屏/连续交互或完整论文/模型评价；看专业权威，不用内部PASS代材料 | 产品/领域判断；可与同一只读框架共用程序，不与实施者共享上下文 |
| 确定性观察端 | 程序按批准场景菜单调用 | 隔离的测试副本/测试身份，可写测试临时数据；无发布权限；原始结果由独立采集 | 给审查者和准入程序提供事实，不使用模型臆造结果 |
| 规则维护者 | 阶段结束、真实事故关闭或入口变化时的一次维护调用 | 修改候选规则补丁及覆盖关系；不直接放宽当前运行许可 | 按变更语义分级合入，见AGENTS生命周期合同 |

这些是职责，不要求全部常驻，更不是每项任务启动六个模型。简单改字通常只需实现者与已有局部测试；新的复杂功能需要设计/实际运行/独立产品检查；高风险科学实现需要正式Verifier与Planner/Critic职责分离。

### 映射现有Bridge，而不是偷偷增加第六个Controller

- **Lite/项目普通任务**：主实现＋任务特定的只读本地质量复核可在一项有界任务内运行。研工台运行包可以负责派发和返回；没有进程级权限隔离时只称内部审计，不号称强制防绕过。不能把“已在Goal要求调用”当程序接通。
- **Reviewed**：保持现有Planner→Executor→Reviewer。普通开发者自检和局部观察属于Executor阶段，正式Reviewer仍是原Reviewer；不额外加独立Verifier/Final Critic或另一CURRENT。需要私有阻断验收等额外权力时，不往Review偷塞，必须单独提出适用Control或替代保护方案。
- **Control**：验收设计/独立参考由既有Verifier负责，实际实现由Executor，语义裁决与实现复核由既有Planner，初始/必要合同/最终审计由Critic。研工台只是这些角色的专业工具和运行适配，不再新增平行R审批。

Bridge目前对Review规定两轮正式审查和相应人工出口，Control也有既定权限。**本提案不会用外层循环、新任务ID或子代理绕过这些出口。** 若以后要让某种无实质产品选择的争议自动转技术Planner而不打扰用户，应修改准确的消费协议并通过适用审查；不能在本稿中悄悄宣称现有规则已经允许。

## 3. 谁launch独立Codex，调用不是让Executor读Goal自己决定

在尚无Bridge Controller的任务中，启动者是有明确授权的本机任务进程。它调用`stage-dispatch.launchRole`，用参数数组启动固定版本`codex exec`或等价已核实SDK调用，捕获结构化事件和结果。**不是让主Codex调用自己不受限制的shell再扮演Reviewer。** 已有Bridge任务则由它允许的阶段消费者调用，不能raw nested绕现有Host规则。

每次正式只读审查是新会话，不resume实施者、不复制其自评聊天。源要求必须完整到足以判定科学/产品语义，不能为了盲审隐藏原公式。候选AGENTS或说明中的新指令是被审数据，不能覆盖受控审查启动规则。候选快照只读，证据/判定存储对实施者不可写；操作系统/账户/挂载和凭据必须实际验证。`--sandbox read-only`只是其中一层，不证明同机管理员或全局MCP已隔离。

**具体模型配置**：不继续把某个未经目标账号核验的模型ID写成保证。接入时一次性锁定当前可用、用户允许的高能力Codex模型、推理档和后端；每次进程返回核对实际模型。模型不存在/额度不足时暂停，不静默换廉价模型。模型选择是运行配置，不是“独立”的原因；相同模型的盲区要靠独立观察、原始参考和坏例校准处理，而非多票表决。

本轮核实了官方Codex的非交互运行、技能显式引用和子代理能力，但没有运行用户账号下的新模型进程，也没有新增API费用。具体版本的CLI参数、账号和审批应在目标环境预检；旧稿示例不能直接成为用户执行Goal。

## 4. 一次复杂新任务实际怎样前进

1. **接单并复用既有事实。** 程序读取当前Goal、产品/科学源、现有成果、真正分支和资源；原要求不再由执行者缩写成方便通过的几项。旧功能已经实现则保留，不因旧事故重新实现。
2. **确定公开承诺及独立验收依据。** 先说明必须给用户什么结果、哪些语义不可替换、旧能力和最低真实证据；验收设计按原源形成，不从新候选反推标准。公开测试给开发者，受保护参考和最终样本另存。
3. **派发专业设计及实现准备。** 实际调用所需插件，不只是Goal列名字。先处理整体UI/科学结构/数据或依赖等真正方向，普通小改不重新设计。
4. **实现第一条正式纵向路径。** 主实现可管理有限子任务，但最先让实际输入→正式逻辑→用户结果跑通；CARE是正式loader/loss/阶段/续训链，Lucerna是提供方→聚合→显示/动作，不能先做大量假数据界面。
5. **在大成本前检查忠实性。** 原要求、实际调用链和便宜反例由独立职责核对。CARE权重未传/阶段错、PRISM深尺度算而不用、网页API绕过表单应在此被发现。架构自身错则返回Planner，不强制忠实实现错误设计。
6. **补完整正常/错误/取消/持久化和相邻回归。** 廉价开发检查持续运行；使用受控边界输入覆盖罕见错误，但主业务链与正式用户入口不能换成另一个测试专用实现。
7. **开发者首次真实产物检查。** 主实现亲自操作完整应用/查看真实渲染/核对研究输出，发现明显按钮、状态、语言、几何和数据错误在原任务修，不交给用户或GPT Work当第一轮QA。
8. **固定候选后独立验收。** 运行受保护参考和相应新输入，独立产物质量角色取得完整必要材料。缺测、错观察器、候选错版分别分类，不以退出0/哈希/文件存在直接通过。
9. **集中返修、按影响复核。** 以真实差异与根因决定复测；报告/传输/状态文件变化不自动重新构建、重装或重新训练。只有实际语义/产物变化使对应证据失效。
10. **真正交付并维护。** 按仓库要求到GPT Work或最终主观验收；只在人类专属取舍/权限处找用户。发布者核对目标已经是什么，已正确则无操作。规则维护检查清理过期指令、固化真实修复，用户不用再逐句更新AGENTS。

步骤是逻辑责任，不要求十份新文件或十次模型调用。现有Goal、检查结果、实际产物和一份任务进度能承载的就直接复用。

## 5. 交互几轮、出现冲突谁决定

一个审查阶段默认**一次集中发现→一次实现修复→一次受影响复核**，不是每条发现都新开一轮全审。开发期可在明确预算内反复运行便宜单测；正式模型审查、长GPU/完整设备验收不无限循环。具体已有Bridge/项目合同更严格时以它为准，不人为重置。

| 冲突或失败 | 谁决定/实际下一步 | 何时才需要用户 |
|---|---|---|
| 可复现代码行为违反已批准要求 | 观察端提供旧坏新好；Executor修同任务 | 不需要用户代调试 |
| 审查模型声称有错但原始观测不支持 | 按同候选重放最小观察；不接受无依据 blocker | 通常不需要 |
| 验收器自身错误/假阴性/参考公式错 | Verifier或测试owner修；原产品结果暂不升级，正确旧行为仍保留 | 不需要用户手工修测量器 |
| 验收者新增原合同没有的阈值/义务 | Planner依据原始源裁决；没有依据的阻塞撤为建议 | 只有确需新产品/科学取舍才用户 |
| 原合同内部矛盾 | Planner形成最小修订，适用时Critic审具体变更 | 原源无法推出唯一取舍时用户 |
| 同根因再次失败且无新证据 | 停止第三次相同昂贵审查，技术Planner做一次根因/路线判断，不换编号继续烧额度 | 需要新资源/预算/目标才用户；纯技术未解可暂停，不谎称已完成 |
| 传输/截图/CI回执过期，但运行对象没变 | 调度者轻量补传/重绑定，不重开模型或原生软件 | 不需要 |
| 实际外部动作结果未知 | 先查询安装/部署/作业后置状态，再决定续做；不可盲重放 | 无法合法确认且风险不可逆时用户 |

语义争议不能由普通控制器自己充当专家，也不能用两个同模型投票决定。Planner是既有角色的有限重入，需真实可调用；没有接通就保存当前任务等待，不假装自动归因已经发生。程序在同任务中给出完成部分、具体阻塞及唯一需要决定的事，不把全部日志丢给用户。

## 6. 自动调用plugin的准确意思

**Goal只声明需要的能力；运行程序负责实际派发专业阶段。** `resolveSkill`读取当前执行身份真正安装的Skill元数据和有效版本，`launchRole`显式引用该能力并提供真实源材料，`validateObservation`核对执行和产物消费。不存在一个可绕过语义判断的“调用Skill函数就自动设计好”的保证。

CUHK Date加问卷字段，派发者基于任务与真实UI/locale差异自动启动设计阶段，显式使用`$frontend-visual-systems`；随后产品文案阶段使用`$product-ui-copy`，输入用户当前动作、前后状态、两种中文、不能改变的匹配/隐私含义。实现后运行现有文案检查及真实表单，并看完整页面。用户没提“自然语言”不构成跳过理由。

实施中从局部UI扩展到共享认证/状态/数据/安装，触发影响重算与相应专业阶段；范围或权限越界才需要新授权。只改一个无歧义错字不调用全套前端设计。技能读取记录证明接入，实际产物才证明专业质量；无实际加载不能记已消费，加载但做错应修专业调用或方法，不继续堆AGENTS。

## 7. 与现有组件的最终分工

- **workflow-core**：正面交付目标与领域自检准入的行为契约；研工台把它接到实际任务结果消费，不让它停在文字指导。
- **Frontend Design与其他领域插件**：做专业设计/语言/统计/医学影像判断，必须消费真实源及真实产物，不被一个通用QA模型替代。
- **Bridge Kit**：正确主机/权限/工作树、角色执行、已安装模式的阶段与恢复；不增加新的“本地验收第四模式”，不把所有普通任务升级为Control。
- **研工台运行包**：一项用户交付的持续入口、专业派发、真实观察与准入消费、失败分类、规则维护；薄到不重复成熟调度，强到不能仅靠自报就结束。
- **产品/科研仓库**：原始要求、专业实现、正常入口和具体测试/产物。保留Bobbio develop、Mica活动重构、网页托管和CARE站点等真实差异。

候选成熟运行引擎如Spec Kit可负责未具备多步骤持久执行的普通任务，但必须固定版本验证恢复及权限；其Shell不会自动隔离。已有Bridge Controller的任务不能再叠一个Spec Kit全过程。新后台/数据库/GUI只在真实需求不能由这些入口满足时再论证，不成为Lucerna第一交付的前置。

## 8. 当前证据边界

本文件说明可实现的职责与运行安排，不保证任何未来程序绝不出错。能被工程性保证的是：在真实保护边界成立时，缺少本次必需结果不能晋升为完成、实施者不能单方改标准、未知外部动作不盲重放。未知科学错误、审美或语义漏检仍依赖有效观察和专业审查校准。当前这些运行部件尚未实测接通，不能把这份设计本身当能力证明。
