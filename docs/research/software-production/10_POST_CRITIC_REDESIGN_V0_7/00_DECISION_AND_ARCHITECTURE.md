# 研工台 v0.7：接受根本否决后的新架构选择（Planner R1）

日期：2026-10-14。设计阶段；此处“v0.7”是**新的待独立复审提案**，不意味着已实现或有任何Critic关闭阻塞。旧v0.6四卷及PDF保存作历史被审对象，不覆盖旧事实。当前只在原研究分支改研究文件，不改七个产品/科研仓库、Bridge、Skills、生产凭据或执行环境。

## 0. 为什么必须作实质改向

用户上传的 v4.zip 有 **GPT-5.6 REJECT** 与 **GPT-6 REVISE** 两份可辨认的独立审查；GPT-6的decision和independent_architecture_review_R1属于同一次审查、不能凑成第二位REVISE；v4/gpt5.5.md字节长度为0，**其审查内容目前不可读**。不能谎报已解决不存在的第三份意见。

我**接受 GPT-5.6 的方向否决**：v0.6“既薄又统一拥有任务调度、阶段状态、专业派发、审查、准入、权限、恢复、规则维护”的十二项职责组合，真正强制就变第二套控制面；不强制又像报告包装。这不是再补字段、增加Reviewer或写20页合同能闭合的。也接受GPT-6指出的两条具体设计缺口：早期检查在Bridge实际状态与预算中无合法位置；本机只读/原生预检不能约束继承工具及脚本传递的副作用。

保留用户的**产品目标**（一次交办、内部完成真实功能/科学路径与合理返修、已知降级不假绿、尽量不让用户搬运截图或反复维护AGENTS），撤回“独立统一运行体系/十二项中央执行组件”这一**实现主张**。今后“研工台”最多是用户可读的生产保证方式/安装组合名称，**不是拥有第二份任务状态和决定谁继续执行的常驻程序**。如果连此名称都会误导，则可直接不用。

## 1. 新目标：可组合的生产保证协议，不是新任务运行器

最小公共组成只有：
1. **现有唯一执行拥有者**：项目当前合法Codex任务入口；中等复杂度可选择安装并实际启用Bridge Reviewed；高风险/长GPU科学工作在确有需要且经批准时使用Bridge Control或原合法控制。Bridge CURRENT/已有Goal始终是该执行任务唯一阶段与预算来源。
2. **项目原生的可执行准入检查**：真实数据/用户入口、生产消费者、领域数学或GUI后置条件、平台隔离和受信任候选。它们放在目标仓库的**现有脚本/测试/CI/环境**，由原任务Owner调用并消费，绝不把模型/Windows/网页专业语义搬到中央。
3. **技能实际消费约束**：产品设计、写作、医学影像、统计等由 AI_Skills_Collection 维护真实Skill/Plugin及安装版本。任务计划定位需要能力，现有Executor/Bridge的合法阶段**实际触发**技能并观察对产物影响；若没有可审的运行读取事实，不能仅因Goal包含名字就宣称消费成功。跨插件正式入口缺失先修AI Skills调用/安装，不新增另一套技能路由数据库。
4. **最小跨系统保证记录（可选，不是状态机）**：引用已有task/Goal与批准源、profile类型、候选实际身份、原始观察来源/类别、结论范围、当前真正的role owner和下一合法动作。**只读聚合已有来源**，不得产生第二个CURRENT、第二套Reviewer轮次、重复重试预算、发布命令或新的状态“平台真值”。
5. **现有CI/受保护验收/发行设施**：可信独立参考和测试者在实施者不能单独篡改的权限域运行；只有对应GitHub分支保护、检查来源和实际主机权限经过测试，才称真正技术性阻断。若尚无分权，准确声明“审计级质量保障”，不得谎称实现者无法绕过。

“检测结果决定不许下一个副作用”所需**硬入口**不在图里的中央盒子：例如高成本Slurm提交必须经过受授权的集群提交者＋项目入口检查；Windows图形必须在实际隔离会话/受控帐号才能执行；GitHub发布由受保护环境和发布凭据决定。**如果执行者仍拥有原始sbatch、管理员桌面或直接生产发布凭据，任何研工台脚本在同一身份里写 deny 都不强制。** 先承认并整改真实权限；不能默默宣称有Gate。

## 2. 三种任务强度，但不创造三套状态机

| 当前任务种类 | 状态/运行Owner | 早期检查（在成本增加前） | 正式独立判断 | 默认成本边界 |
|---|---|---|---|---|
| 明确文案/局部修复 | 现有项目Lite/Codex单次任务 | 项目原有lint/受影响行为，开发者自查 | 不强制新增审查模型；已有受保护CI按仓库策略 | 不启GUI、全量设备、昂贵Work或长时Controller |
| Lucerna等完整产品新功能 | **只有实际安装/授权Reviewed才选择其唯一CURRENT/Watcher**；未安装时仍按当前项目任务运行，不自称自动持续 | Executor阶段的项目确定性真实纵向检查和内部产品预检；失败会阻止**被该项目受控入口管理的**昂贵/原生动作，不占Reviewer轮次 | 完成候选后进入已有 READY_FOR_GPT_REVIEW，再由已有Reviewer及适用GPT Work判断，至多已设置的轮次 | 一次集中内部测试、正式审查前稳定候选、原任务定向返修；没有Review入口不能假装异步自动续跑 |
| CARE等高成本科研/正式安全任务 | 现有合法Control/科研Controller且经过本次任务批准；如未启用则按获准科研实际owner | 原Requirement Ledger/领域Verifier的数学、采样、checkpoint/恢复及真实数据先验检查；只有受控Slurm提交入口获得有效准入后才能增加高成本 | 合同要求的独立Verifier/Planner/Critic各占原有角色，不再平行增加审查者 | GPU预算、数据/outer泄漏、正式停止、恢复与试点额度由原合同统一拥有 |

这里“产品交付”与“科研探索”是**成功/停止语义配置**，不是自建两份机器CURRENT：产品能力需要真实交付且不偷偷降级；探索研究允许获准的NO_GO/证伪，并保留真实方法/数据/结论谱系。不得把QIF的正确NO_GO当缺陷无限续训，也不能将科研探索允许的假设调整带入固定软件发行合同。

## 3. 哪些v0.6职责明确删除、分配或降级

| 旧中央职责 | v0.7唯一拥有者与处理 |
|---|---|
| 任务定位、审查状态、角色交接、返修次数、等待/重入 | Bridge已安装模式/项目当前任务，保证记录仅引用；**取消独立Supervisor、中央CURRENT与第二总预算** |
| 用户科学/产品义务、受影响回归语义 | 各项目批准Goal、原论文/Figma/用户行为；Planner/领域角色拥有语义，不靠中央AI模型重写规范 |
| 技能派发/可用性/成熟度 | AI Skills拥有技能生命周期；实际Codex/Bridge阶段执行具体调用，实测消费；共享记录不再调度所有插件 |
| 主Codex子代理 | 主Executor基于现有Codex机制局部拆分，集成owner始终一人，不复制子代理调度/状态引擎 |
| 第一条真实路径与独立参考 | 各项目原有正式入口、受信任验证环境；对不可信数据/伪测试的直接反证由项目管理 |
| 观察器、原生平台与数据权限 | 目标仓库及合法测试帐号/机器；不创建“通用万能观察器”或默认执行任意命令的插件 |
| 产品审美、医学/统计语义、文案判断 | 具体领域专业Skill与真正取得全产物的现有Reviewer/领域负责人；必须经真实产物质量校准 |
| 发行与交付证据 | 项目发布方法、CI受保护来源、实际安装/部署；共享保证记录只引用候选和证明类别 |
| AGENTS自动整理 | 仓库自己的规则Owner与当前任务合法维护阶段，变更分级；跨项目真实共性才交AI Skills/Bridge；不授权中央大规模自动删规则 |

若今后一个项目确实缺持久多步执行，请比较**为该任务安装现有Bridge Reviewed/Control**与Spec Kit run/resume。Spec Kit的Shell可执行命令并沿调用者权限运行，不承担安全强隔离；不能把它与Bridge第二次同时作为任务推进Owner。VibeResearch经验可参考，不能移植研究循环/新数据库到全部软件。

## 4. 所谓“通用性”：只有共同结果语义，不要求七仓库同一种验收

每项目保留原生“正常入口—专业事实—真正后置结果”检查。
- Lucerna：Rust provider/聚合/托盘/Windows受控native进程与截图；缺值/过期/鉴权/发送失败不冒充健康和发送成功。
- Bobbio：Figma真设计、独立Zotero实例及真实dataDir/更新缓存/协议处理器检查，真实注释与Reader往返。
- Mica：真实ChatGPT宿主、扩展开关收益/不伤害双条件、性能不仅JS堆、PDF复杂交互/真正加载扩展版本。
- SeminarArc：获准APK/模拟器/设备、Room持久化、OCR/录音/导出实际内容，并能推翻错误选择器的假阴性。
- Asteria：实际DOM/SVG屏幕几何和科学图整体可读、真实交互状态、不能让零计数指标冒充测量。
- CUHK Date：正式托管浏览器可见注册/问卷、多persona/一次性票据、隐私和双中文产品文案。
- CARE：真实model/data/label/loss/optimizer/sampler/checkpoint、正式预测和统计口径以及获准NO_GO，不能只看脚本/训练时间。

**接入不是每仓重新手写上述全套。** 第一项检查是现有正式脚本足够了吗，覆盖语义对吗；缺的仅修该项目。为公共记录选择最短适配：现有命令产出的通过/失败+能力/来源定位，并把缺观察记录成NOT_PROVEN。无需把原项目数十种状态全复制成中央枚举。

## 5. 为什么用户仍可能一次交办而不用多轮转发

**明确限定承诺**：在真实启用的Reviewed/Control或具备合法既有持久任务机制时，由其原Watcher/调度继续同一任务；其Recorder记录合法Reviewer决策，Executor修一次，预算到期按原合同停，并生成最终报告。对于未安装此机制的Lite项目，不能说“自动后台做到最后”，只可由现有Codex在同一次获准会话内执行较多步骤，外部独立Review无法自动启动时需要合法交接。这是当前架构必须诚实承认的功能边界，而不是偷偷给所有Lite加一个新Daemon。

新方案未来如实测只有在新运行器中才可能做到“无需多轮用户转发”，那是对本节路线的重大反证：回到Planner比较成熟引擎与最窄Bridge扩展，而非恢复v0.6的十二组件中央运行包。

## 6. 诚实的验证与保留的否决条件

未来经独立PASS与用户授权后，先在Lucerna使用现有Bridge+本地脚本作为**真正基线**，再只加入确实必需的受信任检查/消费适配；在历史坏例、正确例、缺测例比较新增用户P1、误拒、手工介入、耗时和额外配置量。再用CARE无新增长GPU的旧数学/指标反例检验科学配置，并选择一个与Windows不同的平台验证共性。不允许只测合成PASS，而用户继续首次发现基本严重错误。如果基线已经同样有效，不创建公共新包；如果只有原平台专属修复有效，也不要造中央产品。

本轮没有修改Bridge/AI Skills/七仓库，没有运行Windows/Slurm/付费模型，也没有重验六库全部真实运行。**“阻塞项有拟议关闭方法”不等于Critic已将其关闭。** 完整评审逐项处置见 [01_BLOCKER_DISPOSITIONS.md](01_BLOCKER_DISPOSITIONS.md)；实际调用/权限方案见 [02_ROLE_EXECUTION_AND_CAPABILITY_BOUNDARIES.md](02_ROLE_EXECUTION_AND_CAPABILITY_BOUNDARIES.md)；领域与可信评审见 [03_DOMAIN_EVIDENCE_AND_REVIEWER_QUALIFICATION.md](03_DOMAIN_EVIDENCE_AND_REVIEWER_QUALIFICATION.md)。
