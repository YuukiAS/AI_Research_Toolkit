# Lucerna新实例、PDF事实修复与这轮仍没有证明的能力

## 1. Lucerna原实例必须补的两个已读源码反例

原v0.6第四卷拟议的“R2用量提醒”只是说明一项完整桌面功能的示例，没有授权实施。独立GPT-6在Lucerna现有main的src-tauri/src/lib.rs里指出真正会伤害此例的情况，本轮已直接核对对应函数。

**（一）通知尚未真正发送就被持久记为已经提醒**：NotificationGate::evaluate_incident对当前通知事件推进incident状态和通知层级，maybe_notify_product先将门控状态保存到磁盘，然后才调用真实系统通知API的show()；其返回错误时记录notification=failed，但没有对已持久的已通知状态做对应撤销。这说明可能存在“系统显示失败、同级后续事件却持续被抑制”的序列。它是源码顺序支持的**未Windows实测反例**，并非断言R2提醒已经在代码中实现。

**（二）数据暂时不可观察被当成事件真正恢复**：clear_recovered_incidents根据本次events缺席移除事件；当服务数据过期、无真实新观测时事件可能暂缺，并不等于实际故障/越限已恢复。新鲜数据回来又可能作为新事件重复通知。不能靠“连续三次相同使用量不重复”测试替代“有效→过期→恢复原越限”“通知发送失败→重试”“真正从越限回到阈值内→下次越限”的状态序列。

**（三）R2缺失指标与汇总可用性**：CloudflareR2Provider::refresh、fetch_state和state_from_contract_values已有正规调用，但缺少部分请求指标不一定使整体状态变未知；应检查业务语义与正式应用父/子/顶部显示，不能把某Option为None的解析单元测试当实际用户不再看到假健康的证明。条件性的数据缺测与合法数值0须保持不同。

### 正确的职责不是再造一套提醒数据库

- **Lucerna现有项目Goal/产品Owner**先决定提醒的事件同一性、有效数据/暂时缺失、真正恢复、合法去重和错误可见性，以及设置保存/取消/重启；不让纯阈值子代理擅自决定所有发送语义。
- **当前主Executor**在现有NotificationGate和正式R2运行状态上实现，不再写第二套“事件已发”存储；可让子代理处理纯值计算/文案，但通知、持久化、跨提供方状态与集成仍归主Executor。
- **本地开发测试**用可控时间和send-result抽象构造发送成功/失败、连续相同、过期/恢复、操作取消、进程重启、相邻Longleaf失败的正反输入；只有真正使用现有通知入口才有证明价值。失败后的重试政策以用户/产品约定为准，不能自行实现无限重发或伪造“必达通知”。
- **真正Win测试Owner**在独立测试会话运行现有development-acceptance.ps1与capture-lucerna-window.ps1，并补合法动作后置观察；前提是02中的进程/窗口/真实桌面隔离成立。现有Same-run绑定只能证明候选图来自正确进程，不能证明系统通知真的显示在用户系统或所有按钮完成了动作。
- **已有Bridge Reviewer/GPT Work**只在候选稳定、源码/可执行/证据同一且现有模式到达合法审查状态后审；Work若首先发现明显旧类P1，责任归项目内部Producer/观察入口，不由中央新Controller反复重启全部流程。
- **用户**只需处理真正的新通知产品策略、额外敏感凭据、合法安装/最终主观选择；普通前端、阈值、按钮、截图错误不应不断转交给用户。

### 一次交办如何不无限追求“完全没有错误”

在未获准备案之前，不声明本功能已实现或已消耗真实R2账号。假设后来有合法Reviewed：设计的正面能力和现有回归进入其PLAN_FROZEN；主Codex在EXECUTING内先跑便宜真实Provider→聚合→通知检查，不能用fixture最终头部替代；稳定后在专用Windows会话批量真实操作和截图；只有具备相应真实原生观察才进入正式READY_FOR_GPT_REVIEW；第一次Reviewer查完整产品，必要一次实施修复，再第二次Review。当前Bridge最多两轮且会正确终止，不让研工台重置次数。没有专用Win环境时只能诚实标原生未验证，不要求在用户忙时直接抢桌面。

需要验证新保证是否让用户更省心：比较原Lucerna现有规则+脚本和加上受保护的真实准入之后的同类型任务，记录首次到Work前被Producer抓到的严重问题、每项用户干预、额外调用、重启/截图、错误拒绝及真正安装候选。不因“更多自检记录”评分更高。

## 3. 用户“全部历史问题都能避免复发”的可测边界

将每条真实事故映射到“现有受信消费者”的正坏例只证明**机制可设计**，并非机制已经存在，更不等于未来所有未知问题零发生。特别注意：
- 六库246条包括历史修复、规则/范围、推断和重复表述；LX20/AX5多数与主账本同根因，不是25个新的当前故障。
- CARE40＋新增52有跨模型复发及观察盲区，统计应先按真实实验/候选/根因去重；MLoRA/FSCF部分原始单次实验、早期M0–M7及Batch0–6逐次现场仍缺。
- 首次试点不改六仓库或CARE的源合同，先比较已有正常执行+真实项目脚本与加入最小保证引用/受信任准入后的增量效果；同任务受信者可用、坏候选可拒/好候选可过、用户/Work不再承担第一轮大批基本P1、成本不过重，才考虑复用第二平台。
- 独立评审者在实际盲测上不合格时要撤资格、退回真正观察/专业裁判，不能为维持流程顺利自动调低指标；不能用高技能模型的新会话替代其资格。

## 4. 两个来源缺口不能靠Planner自行宣布关闭

1. **用户上传的第三份审查是0字节**，无法知道是否存在额外阻塞；本轮只对两份完整可读审查负责。需要真正原文后才可新增对应处置，不让用户手工逐行整理，禁止猜测。
2. **独立PDF渲染缺失**：已经给出了固定PDF对象及所需最小验证，必须由可访问该二进制的审查者实际完成才有结论。此阶段的元数据修复可完成，不必因此重新训练/重编业务产品。

不得向用户声称“全部三个Agent已复核PASS”“v0.7已实施”“已经保证永远不出降级”，不应把等待真正独立审查当作产品缺陷需要反复返修。同样也不能借这些事实缺口合理化另一套无限Central Controller。
