## 3. 一次性接入成本怎样测，而不是凭“少量适配”猜数字

不提供虚构分钟数或准确文件增量。对每仓实际试点前记录当前正常入口的：
- 已安装Bridge模式/任务主人、是否已有持久Watcher和真正外部Reviewer；
- 现有命令是否可直接给原始证据和失败类别，唯一确需写的新桥接代码/脚本；
- 新增可维护代码行、配置文件、重复契约/状态数量；是否改旧分支/本地凭据/已有专业Skill；
- 用户发提示词/搬图片/手动介入次数、从目标到真正交付的耗时和资源费用；
- 历史真实坏例拦截率、正确实现误拒率、无法判断的弃权/阻塞次数、同任务可恢复性与用户首次发现P1数量；
- 若不采用公共包，仅修项目内真实调用入口，是否达到等效收益。

**硬否决**：每仓再加另一套Controller/CURRENT、由项目复制中央状态和业务数据、无法保护用户数据却宣称安全、频繁以长表格替代操作、好候选反复误拒、和基线比较无净增益。这样的通用层不值得继续。

## 4. 七仓映射中的权限/安装证据缺口

这轮只能依据公开仓库树、历史分支源及当前连接信息；六产品之前固定Git树没有发现标准automation目录，不表示用户机器没有Bridge。之后独立Critic不能据此主张Bridge已经安装，也不能因此无条件否定使用现有Bridge作为合理候选。每仓是否配置受保护GitHub检查、项目CI是否自动运行、当前CODEX_HOME安装什么Skill、Win GUI是否真正隔离、CARE谁实际有权sbatch，都必须在获准的真实环境核实。没有真实证据只能是**设计满足形式上的正确归属**，不能提升为正式运行保障。
