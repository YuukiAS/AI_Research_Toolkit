## 2. 关键问题族：必须复用现有实现、证明实际消费

### Lucerna：正常功能存在，但用户第一次看到仍有明显失败

1. L02/L04/L06/L09：重复卡片、密度过重、视觉层级和自然语言问题；测试/设计文件全通过却不能代替真实整屏品质。必须用同一候选实际 Windows 完整画面+交互+已存在 Figma/产品设计依据与合格视觉审查；不是截图数量或禁词表。
2. L07/L08：测试状态进入正式用户界面，正式认证/Provider 明明存在却长期用假数据。必须区分真实 Provider→聚合→界面/通知和隔离替身，交付环境无测试控件；夹具仅证明限定开发分支。
3. L05：CSS 缩放不能证明实际 Windows DPI；需真实窗口、进程路径、操作系统缩放与同候选采集。
4. L10/L11：为了简单 UI 小改反复构建、打开/关闭、强行刷新前台与通知压力路径，浪费时间并打扰用户；只在有影响时跑对应验收，隔离真正的 Windows 观察。
5. 晚期 LX01-LX20：状态父子传播、未配置服务、Longleaf/Vault/R2、本地凭据、未知/过期状态、通知门控失败后仍标已通知、取消/恢复/重开；需核对当前来源、各种失败序列的真实业务后置和旧行为不回归。
6. 所有 Windows 真实操作先确认实际运行进程、桌面会话、用户数据/凭据、安全权限。现有 capture-lucerna-window.ps1 可触发 ShowWindow/SetForegroundWindow，不可当作完全只读。禁止把实际桌面干扰包装成无副作用截图。

### Bobbio：设计源未真正消费和个人 Zotero 资料安全

1. Figma 文件必须真的读到具体节点、布局、设计系统，且 Reader 真界面/交互与之符合，不能只在 Goal 引用一句。
2. Zotero 数据目录隔离不能靠 Safe Profile 之名取得可信身份；必须核验进程、dataDir、URL handler、缓存/更新机制、批注往返与个人资料副作用。
3. 现有 Invoke-BobbioAcceptanceSafe.ps1 的 PreflightOnly 分支可能在正式检查前传递 Apply。需查全调用链，第一项变更发生前即完成授权与隔离。
4. 新系统只读取/复用现有验收包装和平台约束，不移植 Lucerna 的 Windows 截图、通知测试或第二数据存储。

### Mica：关掉用户功能并不是把它做对

1. 控制 DOM/JSON 夹具不能证明真实已登录 ChatGPT 当前宿主、扩展包与原生输入共存。
2. 关闭扩展、禁用高亮得到“无损害”不是实际实现高亮/保留/恢复；正收益与不损害都需独立观察。
3. 长对话、低内存、真实 PDF 跨页选择、刷新/导出/恢复必须与当前受测安装包绑定。
4. 先复用现有 acceptance/cli.mjs、validator.mjs 及控制语料，明确哪些是开发自测、哪些需要合法真实宿主，不采集用户未授权登录态。

### SeminarArc：合成测试、系统选择器、程序误判

1. 真实 APK/序列号/Android 服务、照片→OCR→Room→重开→ZIP 内容必须来自同一受测候选。
2. Android 系统选择器/OCR/编辑框读取若出错，必须判观察器失效，不能强迫修正确应用来适配错误选择器。
3. 3,750次压力操作只能证明其覆盖的崩溃/稳定性边界，不能证明真机麦克风录音、所有权限、真实 OCR 内容质量。
4. 复用黑箱脚本、视觉 golden 和压力回归；基线不可由实施者随意更新以产生假绿灯。

### Asteria：检测指标恒零，画面仍显著不好

1. SVG 代码中的虚拟坐标不等于真实浏览器中的 DOM/SVG 渲染坐标；需实际测线段端点、投影和屏幕布局。
2. 碰撞数写死零、缺失比率归零不是不存在问题的证据；同时承认其他有效的检查，不能为了驳回旧方案将全部测试统称为假。
3. RC 多轮检测通过仍有绕线、关系层级不清、公式乱码/可读性与交互不成熟；必须有首个可操作原型的完整屏幕审查和稳定候选上的交互审查。
4. 不许通过删除科学关系或给固定节点特判使碰撞减少。

### CUHK Date：假用户路径、授权和自然中文

1. 真实注册设置密码页面曾出现 same_password 返回422；用 page.evaluate(fetch) 或直接后端 API 成功并不能证明可见表单真实注册。
2. 两个身份、会话隔离、一次性票据、认证、问卷、保存/重入、删除/隐私和真实部署必须各自绑定合法身份，不得误用别的受测环境。
3. 简体/繁体并不等于自然产品语言；必须真实阅读上下文、完整页面和具体香港用语。硬编码英文/机器标签不能靠词表扫描完全发现。
4. GitHub Quick CI 若跳过关键检查却显示成功，必须核对原确定集合是否实际运行；不能通过轻易跳过本次必需验证制造“已发布”。

### CARE：应覆盖的是科学机制与真实实验，不只是“能运行训练命令”

1. CARE:C01–C05 等低配模型：承诺的 U-Net 编解码与跳连被换成浅层 stem、私有专家未实际得到独立模态、伪多尺度、浅层重建、候选不经过正式生成消费；必须检查实际模型调用结构、计算图和最终输出关系，允许科学等价实现但不接受结构名冒充机制。
2. B4/B5/B6 权重接续：看到前阶段令牌不等于真正 load weights；需要核对当前模型参数来源、优化状态和真实训练/推理消费者。
3. B6 代理分数：完美预测和空预测曾由纯函数返回同分；受测代码说明它是开发代理而非官方成绩。不得升级为真实医学指标，需要独立模型预测/GT/病例级计算的受保护比较。
4. PRISM 深尺度计算未影响最终路径；检查前向图和必要梯度/消融，不以中间张量存在代表模型机制有效。
5. DG 梯度方向、ASE 训练阶段/无T2有效分母、MMRD 滑窗/空间逆变换与 model plans：必须对应有效科学合同和真实推理/训练路径，不能用随机小张量或旧 Verifier 无依据新阈值误拒。
6. 合法科学 NO_GO、模型失败与实现缩水严格分开；发现假指标和错误训练时修计算链，科学信号弱时不得强迫编造正结果。
7. Slurm：优先复用 CARE 专用路由、作业依赖、finalizer、监测/节点抢占恢复；已提交/排队/运行/等待记账非完成。权限隔离与 Longleaf 特殊 sq 视图必须由实际站点规则确定。
8. 早期 M0–M7、MLoRA/FSCF 等私有历史部分证据尚未完整恢复，不能通过从92条登记外推出“所有模型历史已穷尽”。

## 3. 两个非常明确的 v0.8 映射错误

在旧 v0.8 的 363 行 CSV 中：
- CARE:C01 是“医学模型浅层替代完整结构”，却被关联 C-PASSWORD|C-CRITICAL——这属于网页注册/关键路径组件。
- Lucerna:L07 是“测试状态/控件残留”，却被分类成 SCIENTIFIC_SEMANTIC_DRIFT 并推荐 DOMAIN_FORMULA_AND_FORWARD_PROBE——应归入正式环境清洁与真实原生发布检查。

本轮程序检查发现，CARE 原40条中至少38条出现了 C-PASSWORD/C-WEB/C-CRITICAL/C-REVIEW 等明显来自另一个项目的组件代码。**这是旧矩阵的错误关联，不可继续用于自动选择测试、统计防复发覆盖或给执行 Prompt 下发指令。**

新05索引特意保留旧映射作审计来源，但把所有行的真实交付保护设为 NOT_VALIDATED_ON_NORMAL_ENTRY。新索引的项目组与专业场景仅用于选择需要回到哪个项目核源，不代表已经完成逐例精准归因。

## 4. 正式研究必须实际补的四层连接

对05索引的每条（可先分根因族，但无遗漏）：

1. 来源真实性：源文件存在吗？编号、原描述、当前性、证据强度是否准确？重复报告/风险/历史已修是否已标明？
2. 正常入口：这个问题当时具体在哪个正式用户/科研运行路径发生？现有脚本/组件是否真的被该入口调用？
3. 决定性控制：应该由该领域哪个真实消费者观察哪个行为？需否决哪个历史坏例，还要放过哪个同等正确例？是否缺额外资源/权限？
4. 当前保护状态：实际部署/运行、适用范围和同候选证据是否成立？没有实测的只填设计候选或待验证，不可写 PASS。

跨项目通用机制只有被两个以上真实项目消费且有净收益才能考虑抽取。不是每条源记录都要新增脚本，更不能把五类现象全部交给一个通用 AI 审查模型。

## 5. 候选研究方案必须证明减少的是哪种真实失败

用户关心的是：第一次交付少多少严重问题；是否不再靠用户不断提醒；发现失败的准确层级；返回原任务的闭环是否真的执行；修复是否保留已有好功能；重复夹具和无意义运行是否减少；是否能长时间排队而不烧 Codex；新适配实际多耗多少时间。没有成对基线和准确证据不得报告“全面覆盖”。
