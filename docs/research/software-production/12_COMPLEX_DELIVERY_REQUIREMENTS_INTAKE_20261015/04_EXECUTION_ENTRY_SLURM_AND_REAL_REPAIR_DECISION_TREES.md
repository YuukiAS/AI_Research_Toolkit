# 最关键的技术问题：Codex 入口、完成后返修、Slurm 等待与真实观察

> **材料类型：旧助手拟议的执行方式与情景分析，可能包含有争议的架构选择；不作为独立研究初始输入。** Slurm 策略请先直接阅读 CARE 当前规则与站点事实。本文件只在候选方案形成后用于检查遗漏的故障分支，禁止把这里列的“处理方式”当用户已选的答案。


性质：**研究问题及准入测试规格，不是经实机验证的现有产品实现**。设计研究不得只引用抽象“监督器”“独立验收器”，必须给出真实宿主上的具体进程、API/命令、可执行阶段、信任与权限、错误路径和恢复对象。

## A. 用户从 Windows Codex App 发送：谁实际收到？

原始用户操作仍是向 Windows Codex App 输入自然语言任务。至少必须实证比较以下三种入口，而不是先决定“安装钩子就接管”：

1. 原生 App + 全局/插件生命周期钩子：UserPromptSubmit 是否在真实 Windows App 版本运行、是否获得原始输入与准确工作区、如何区分复杂任务/小修、阻断响应是否生效、若把任务转交给受管执行器后如何确保原任务不再执行。单次提示词运行钩子不证明接管 App 正在运行的会话；插件安装与执行脚本信任必须在真实环境完成。
2. 在原生 App 中显式的任务交接：若无法合法无缝拦截，是否可通过官方受支持的动作一次将当前任务交给受管运行，而不是复制原 Prompt、重新填分支/权限；任何必需额外用户动作须准确计入成本。
3. 新产品控制台持有 Codex SDK / App Server 会话：谁执行 turn/start、保存 thread_id、允许什么工具/权限、谁可以 cancel/resume、能否与用户日常 App 共享账户配额。**这属于候选方案，不得把新控制台当成已批准的入口。**

对于三种方案，必须在实际 App 版本列出 Hook 输入、响应、工具调用权限，双执行/失败降级测试，不能声称一个已被允许提示词钩子的阻断可技术强制覆盖所有工具。

参考：OpenAI 官方插件及生命周期钩子 https://developers.openai.com/plugins/build/plugins 、https://developers.openai.com/docs/hooks；官方 Codex 作为平台 https://developers.openai.com/blog/codex-as-a-platform 。需记录检查日期和目标机器版本，不能复用模型推断。

## B. 服务器 Codex：真正常驻的是谁？断线后谁恢复？

在 Longleaf，应先获取真实当前实例的 CODEX_HOME、仓库工作树、Codex 工具版本及与 Remote_Compute_Infrastructure 的访问隔离。当前 codex/AGENTS.longleaf.md 记有 USERS / OVERFLOW 两个独立命名空间，切换工作树不能自动变更身份；现有 sq 命令扩展用户作业清单视图，不能只用 squeue -u 当前默认视图判断 htzhulab 无作业。

候选可编排的稳定入口：codex exec 的非交互式运行和结构化输出、明确 session id 的恢复；真实现状须核来源及实机版本。现有 Bridge ai_bridge_kit/reviewed_runner.py 中 executor_prompt()、run_codex_event() 使用 subprocess.run 运行 codex exec 并将 stdout 追加到 watcher 日志。该运行代码**尚不等于已经提供跨平台的完整实时事件采集、同会话外部返修和可靠图形界面**。改造方案须定位源码修改范围，保证 Reviewed 当前发布、失败限制和状态所有权不破坏。

用户在 Windows App 与 Longleaf 上可以看任务，但必须清楚进程实际跑在哪台机器、谁有写入权、账号/凭据在哪个范围，不能在 Windows UI 上把服务器任务的资源调度权凭空创造出来。

## C. Codex 说“完成”后真实有缺陷，谁在合法阶段继续它？

必须给出以下真实数据通路、不可跳过的权限和最低反证：

步骤1：执行者 Codex 给出实现候选身份，不得自行改原批准要求、正式受保护测试参考或 Reviewer 判决。

步骤2：在当前有效阶段由**现有权威任务执行入口**判断是否可提交独立检查。对 Bridge Reviewed：源码 ai_bridge_kit/reviewed_handoff.py 的 record_review() 只允许 READY_FOR_GPT_REVIEW 或受限定的 WAITING_FOR_CI，正式 Reviewer 不得在 EXECUTING 时凭空调用该接口；若需早期检查，必须明确属于开发侧低成本探针、独立受权资源前门或经过另审的 Bridge 正式扩展，不能隐形新增一次审查。

步骤3：有资格的真实观察者对照原要求直接打开同一候选的真实 Windows 应用 / 浏览器 / APK / 扩展 / 模型预测和科学数据。确定性验证不等于审美/科学质量；专业 Reviewer 必须具领域准入依据。观察者必须提供实际动作和后置事实，不能只读 Executor 报告。

步骤4：发现产品失败时，Reviewer 产生可复现证据与影响范围，**由原权威控制器**在已有合法 Review/Control 状态中转回 Executor；Codex 只能在原允许任务/预算/分支下修复。检测器失败进入检测器修复，缺外部数据保持 NOT_PROVEN，不得计产品失败或烧另一轮正式审查次数。

步骤5：自动返修后必须以最终同一候选跑适用回归和真实观察。旧正确能力不得因修复而丢失；超过合法审查轮次、缺实际 Reviewer 自动触发器或缺恢复权限的情形必须明确暴露，不得宣称“自动闭环”。

重点反证：故意让 Lucerna 的假状态包与正确真实状态包都提交检查；系统能否在用户介入前让错误包实际被拒绝、给出来源并驱动返修？若仅诊断出错误但没有合法继续 Codex 的能力，此路径没有完成交付目标。

## D. Slurm 具体执行与等待：十二类真实分支

原项目当前规则见 CARE_Challenge/.agents/skills/slurm-routing-partition/SKILL.md、prompts/CONTROLLER_TASK_PROTOCOL.md、wiki/EXECUTION.md，所列 2 小时×12 次只适用于相应 CARE Goal，不可全局硬编码。

| 情景 | 真实Owner与处理 | 不能宣称 |
|---|---|---|
| D01 尚未有授权 | Controller/合法执行入口在 sbatch 前检查任务、分区、时间、数据、账号与预算，等待批准相关副作用 | 项目文档写有权限就等于真正获批准 |
| D02 已有合法兼容分配 | 检查 job ID/节点/工作目录/运行环境与实际权限后复用 | 进程 RUNNING 便代表 GPU/服务可用 |
| D03 正常资源排队 PENDING (Priority)/(Resources) | Slurm 保有队列，持久监测器低频观察；Codex 会话可退出，任务不报失败 | 超过几分钟就 BLOCK 或反复启动 Codex 查询 |
| D04 无效账号、QOS、分区、依赖永不满足 | 立即定位拒绝/不合理等待的实际根因，在原权限可修则局部修，改变费用/资源需批准 | 错误提交也要固定等待24小时 |
| D05 预期长等且其它分区兼容 | 按 CARE 规则研究 htzhulab/a100-gpu/volta-gpu 允许路由，检查科学一致、镜像锁、预算及取消权限 | 未授权并发提交或静默迁移异构 GPU |
| D06 多分区竞争已有一条启动 | 经原授权机制取消**自己尚未开始的对应镜像**，验证实际调度与文件锁，记录取消结果 | 模型单纯发出 scancel 文本就算成功 |
| D07 所有允许队列持续 pending | CARE 当前 Goal 按项目的12次×2小时持续记录；仍然 pending 表示等待/调度阻塞，不是科学任务完成 | 凭第1次 pending 就 BLOCK，或长期占用 Codex 会话 |
| D08 节点抢占/失联 | 核查原作业终态、检查点、代码和配置同一性，按原合同有限恢复/同语义替换 | 不核旧作业便再次提交，导致重复训练 |
| D09 作业完成但输出缺失 | 原项目 collector/finalizer 核原始日志、检查点、实际预测与指标，能补收集则补收集；仍缺则 NEEDS_EVIDENCE | sacct COMPLETED 即训练质量 PASS |
| D10 训练脚本真实失败 | 区分科学缺陷、脚本/环境故障、OOM/节点故障；只有同语义和获准资源可自动限次重跑 | “任何失败都重来”或任意重置任务轮次 |
| D11 无法查询 Slurm / 监测进程死亡 | 保留已知 Job ID、真实隔离锁和最后核查时间，恢复后先 reconcile 真实调度状态，再考虑动作 | 把网络断线解读成 job 不存在并重提 |
| D12 科学上合法 NO_GO | 有效数据/模型/指标的负结论按批准的科学终止标准收口，提交可靠负面结果和限制 | 为追求“交付成功”继续无授权高成本训练 |

真实科研执行中，Slurm 任务所有权属于集群，目标 Controller/科学任务负责解释运行与科学状态，新系统控制台只应显示实际执行/等待与合理下一步；除非有经独立审查且明确授权的资源提交角色，否则不能夺取 Slurm 管理权。

CARE 已经有 scripts/ops/submit_care_dependency_finalizer.py 的 afterany finalizer 和项目本地监控/汇总；研究者需核实它在具体当前 Goal 是否真实消费，而不是为每个科研仓库发明新的低配调度器。

## E. 怎么让用户能亲眼判断每个组件不是假的？

最小真实事件要求：哪个目标任务/主机/工作树/候选；哪个合法执行组件/版本生成；是工具真实执行、资格审查、真实受控观察、还是模型文字建议；原始日志在哪；哪个请求、动作、后置结果；是否会改变任务权威状态；消耗多少资源，若不可计量显式未知；证据失效触发条件。

至少研究三个用户页面：任务总览（包含真实活动/等待/异常/下一步）、单任务时间线与真实产物（可展开原生窗口/网页 trace/Slurm job 及报告）、组件诊断（逐组件最近真实使用/未调用/失格/过期/权限不足）。页面必须有自然中文、真正功能与可读性；旧候选或模拟事件必须大字标明，不能展示“已验证”。

关键反证：断网后页面是否凭旧状态继续绿色？测试器未运行时是否标“未验证”？Codex 报告成功而后台训练仍排队时是否显示训练未结束？是否可以追到此数据是哪个程序直接采集，而非 LLM 自述？

## F. 选型竞争的必要证据，而不是先定架构

候选至少包含：不建新产品只修普通项目入口；最小扩展 Bridge/各仓；纯专业插件+受保护各仓测试；独立控制台但不重造控制器；独立受管执行器但要求正式排他权；成熟多步执行/恢复实现。每条路线填写上述 A–E 全过程：谁起动、谁干预、谁验收、谁恢复、谁真正放行、额外安装与维护成本、正确结果可能被误拒的情形。没有真实观测不打分为“已能实现”。

**研究阶段不实施或运行 Windows、Slurm、登录态、真实生产环境。** 下一步仅可提出有边界的实机技术探针计划：目标机器/身份、准确接口、作用域、批准事项、成功/失败/原状恢复，以及失败将否决什么路线。
