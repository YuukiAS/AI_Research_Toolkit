# KeelArc（暂名）：复杂任务自动交付系统——独立架构决策研究 R1

## 任务性质

你担任独立的高级系统架构研究负责人。本轮不接受既有 v0.6–v0.8 的架构结论为前提，也不得把用户与上一助手讨论的“独立仓库 + Bridge 扩展 + Codex 钩子 + 独立验收器”当成既定方向。它仅是待证伪候选。

用户希望一次向 **Windows Codex App 或服务器 Codex** 输入复杂任务，系统就能在实际执行中监督与纠偏：避免降级实现、假数据/无限夹具循环、旧能力被破坏、专业技能未使用、假验收、错误的自然中文/视觉质量，以及无意义的 Codex 和 GPU 消耗。Codex 宣称“完成”不代表真实产品/模型完成；必须有一个真正能够检查、退回、恢复和交付的闭环，且用户能从可靠的可视化界面和原始事件看到每个组件是否发挥作用。适用于 Lucerna、Bobbio、Mica、SeminarArc、Asteria、CUHK_Date、CARE，未来扩展到 Shione、科研模型及复杂报告。普通小修绝不能承担所有高风险环节，用户只应在目标、科学/产品重大取舍、权限、费用及不可逆影响上做决定。

**本任务只读研究与可执行验证方案设计，不创建仓库、不实施代码、不运行用户 Windows 桌面、不提交或取消 Slurm 作业、不进行付费/敏感外部操作。** 需要实机或外部资源验证的关键假设，必须提出最小、有边界的技术探针及其权限/副作用/费用/恢复路径，明确标为待实测，不能假装通过。正式实现应在独立 Critic 审查及用户授权后进行。

## 二、必须先回答的架构问题（不得先选仓库再找理由）

A. **真实入口**：用户在 Windows Codex App 输入提示词，在服务器 Codex CLI/SDK 输入提示词，分别发生什么？哪个程序、哪一 API/钩子可读到原始任务？是否能可靠转交或继续当前会话？若原生 App 不能被可靠接管，必须明示功能缺口、兼容模式与用户操作成本，不得说“自动接管”。比较原生 Codex + 本地 CI、只扩展 Bridge、独立受管执行器、组合模式，以及一项成熟实现替代。

B. **真实介入**：在编码前、工具调用中、首次真实数据链、Codex 宣告完成、最终候选验证、发布/训练之前，谁有权干预？干预由何种实际进程/API 触发，输入/输出是什么，能否被执行者绕过？钩子可以诊断不等于可强制阻断；强制的关键点必须有外部受保护权限或可信运行器实现。

C. **谁真正发现缺陷并自动返修**：Codex 完成后，是谁拿原要求和同一最终候选，真实运行 Windows GUI、浏览器、Android、扩展、科研模型和科学评价？哪项使用确定性断言，哪项需要经过准入校准的专业视觉/语言/科学审查？结果如何回送到原合法任务，再让 Codex 同范围修复？如何防止 Reviewer 漏检、误报、临时新增门槛、测试工具自身错误、无限返修？

D. **长任务和 Slurm 的真实边界**：明确实际 job owner、`sbatch` 提交授权、作业标识/配置签名、`PENDING` / `RUNNING` / `COMPLETED` / 失败/等待记账的区别。优先复用 CARE 的任务依赖与 finalizer，以及项目现有专业路由技能：排队不消耗 Codex 循环；合理等待不自动 `BLOCKED`；错误的 QOS/依赖不能空等；允许的分区竞争、失败重试、取消镜像要有独立权限、锁/幂等与费用约束；集群无资源时保存任务并择时恢复；节点预占/网络断线/任务重启后不重复提交或覆盖检查点。**不能把 CARE 的“两小时一次、12 次”直接硬编码到所有科研项目**，Longleaf 特殊队列视图应检查现有 `sq` 约定。需列出至少八个明确的状态转移与异常分支。

E. **不会破坏现有好东西**：对原仓库真实功能、设计、文案、科学公式、权重/训练人群、文件、个人数据、权限提供“不可降级”保护。正常单次修改与不相关旧任务不得触发重复构建、Windows 前台窗口刷新、GPU 训练或漫长批次验收。

F. **可视化和审计**：什么事件由哪个真实进程产生，怎样绑定任务/分支/候选/运行环境/验收器版本；界面怎样显示真实调用、未调用、证据不全、运行等待、专业审查结论、进度、令牌/真实费用、恢复次数；哪些只是观察性的、不具强制权。提供可运行数据流协议和三个具体页面示意（任务概览、任务全程与专业证据、系统组件诊断），不能停留在卡片/状态描述。

G. **持续运行 vs 第二套状态机**：必须明确唯一任务推进权威。若增加独立产品，证明其新增的生产逻辑无法低成本放在 Bridge；同时禁止两个执行器并行接管同一任务、同时给出不一致完成结论。

H. **自举验收**：新系统本身是复杂软件，它必须在最早可行版本上用真实运行入口开发和验证自身，包括中文自然度、Figma 实际设计、浏览器完整渲染、事件来源、恢复和版本身份；不能用模拟仪表盘冒充运行中的系统，也不能自己给自己授予最终独立 PASS。

## 三、独立比较和选择，不允许文档竞赛

最低比较五条路线：①不建新系统，只补原 Codex 与七仓现有正式检查；②仅最窄修 Bridge 现有执行器和 Review/Control；③独立产品 + 稳定 Codex 运行接口 + 复用 Bridge 权威；④独立受管执行器，逐步替换 Bridge 相应执行部分但保留可靠能力；⑤明确考察至少一个成熟执行/任务编排替代。各路线必须给出：用户真实入口、可实施接口、运行所有权、受保护验收来源、项目适配工作量、额外常驻进程、资源消耗、故障恢复、是否侵入现有项目、维护成本、可视化能力、失效时是否会错报成功。拒绝使用抽象“更稳”“更成熟”作为证据。

先用硬约束剔除无法覆盖自动返修、完整专业验收、同候选证据与不频繁打断用户的路线；其余再按真实交付质量、人工打断、总交付时间与算力/令牌成本、维护负担比较。没有直接实测数据只能给区间性定性判断和待测项目，不得杜撰性能数字。允许结论是“尚不能选出胜者”，但必须指出最便宜的一项可证伪验证及明确的决策分叉，不能再泛泛研究。

## 四、必须提供可执行而非纸面上的验证设计

将以下问题分别设计成可在独立授权后执行的最小技术探针，每项写清：目标真实主机、目标仓库/分支、调用的准确命令或 API、需要权限、不能触碰的真实资源、预期事件、直接成功证据、失败/反证、结束与恢复操作、费用上限及如果失败选择什么替代。不能在只读研究阶段实际执行或声称 PASS。

- Windows Codex App 原生输入能否可靠观察/接管/交接（必须防双重执行）；
- 服务器上 Codex 结构化事件及原会话恢复/外部返修；
- Codex 自称完成但真实 Lucerna 状态链仍失败时，独立观察如何自动退回并最终检查同一候选；
- CARE 真实数学/模型坏实现被便宜前置检查拒绝，正确实现通过；
- CARE Slurm：长时间排队、无效分区/QOS、计算节点抢占、最终输出缺失、监测进程断线、任务重复启动、正常科学 NO_GO；
- 验收器误报/漏报和规则被开发者同轮篡改；
- 原产品不应改变的场景，包括不相关小修不触发额外 GPU、桌面 GUI 与 GPT Work；
- 研工台自身的真实事件流、自动返修、中文文案和视觉设计。

不得只跑合成测试或假页面得出系统可用结论。早期可以有廉价开发对照；最终必须规定真实最终候选、真实入口、正例/坏例/缺测例，及用户首次验收前的内部质量闭环。
