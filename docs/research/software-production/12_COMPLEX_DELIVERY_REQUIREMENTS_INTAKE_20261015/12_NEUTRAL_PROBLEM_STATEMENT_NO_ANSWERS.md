# 独立研究的问题陈述——只提需求和待解问题，不提供方案

**阶段：供用户审阅的问题输入，尚未发送 GPT Pro。**
本文件刻意不预设新仓库、插件、Bridge 升级、控制台、状态机、钩子、独立审查者或其他架构。旧研究中的“研工台”“KeelArc”只是历史代称，不代表产品设计已经决定。

## 一、用户要获得的实际结果

用户在 Windows 和服务器环境使用 Codex 开发软件、网站、移动应用、深度学习模型与科研成果。希望一次说明目标和大方向后，系统尽可能自主完成完整且高质量的交付，显著减少重复解释、用户首轮发现严重缺陷、无止境返修、模拟检查冒充真实能力、已有功能被破坏、错误阻塞以及 Codex/计算资源浪费。

复杂任务应能接入；不同平台和科学领域可有专门做法，但接入及日常运行负担不能抵消生产效率。用户必须能随时看到系统真实执行了什么、用了哪些能力、花费什么资源、为何停下或认为完成。这个要求也适用于系统自身的开发、界面、语言及验收。

以上是目标，不意味着已经存在满足目标的技术组件。

## 二、尚未回答的根本问题

1. **入口**：用户像现在一样在 Windows Codex App 或服务器 Codex 发送自然语言任务时，系统怎样实际生效？如果某个入口无法被可靠接入，用户真实需要额外做什么？如何避免同任务被执行两次？
2. **执行责任**：一个跨多个阶段的复杂任务由谁持续负责？断线、会话结束、主机重启或执行过程变化时，怎样保留已有工作、不产生新的混乱？
3. **假完成**：Codex 自称已经实现或交付，但用户实际使用仍有严重问题时，谁能发现？发现的证据从哪里来？如何真正继续原任务完成修复，而不是只产生一份审查意见？
4. **真实能力**：怎样尽早发现低配替代、实现缩水、代码只跑模拟数据、真实输入从未到达最终消费路径、指标与真实模型输出无关等问题，同时不误杀合理正确的其他实现？
5. **质量**：谁能真正评估界面审美、实际完整交互、自然中文、用户可见的文字、正确数学/统计/医学语义？评估者本身出错怎么办？
6. **回归**：开发新能力时，怎样避免破坏已经做好的功能、设计和科研假设？何时检查局部，何时必须检查完整成品？
7. **资源调度**：科研实验需要 GPU/Slurm 时，是否需要提交、已提交后长期排队、队列不可用、作业失败、节点抢占、结果缺失或科学上合理的负结论，分别怎样处理？怎样防止等待期间不断消耗 Codex 额度、重复提交或无意义地要求用户介入？
8. **权限与安全**：真实用户桌面、Zotero 个人资料、浏览器账户、安卓设备、HPC 数据与资源、Git 发布权限如何处理？用户授权一次后哪些动作能连续执行，哪些变化必须重新获准？
9. **已有工具**：AI Skills、Bridge、各项目脚本、持续集成、已有调度和领域检验到底有哪些能力真正可用？哪些已宣称具备却从未进入实际用户任务？
10. **可观察性**：用户怎样查明每个组件是否真的被调用、用了什么来源、做了什么、实际是否有效、谁花了多少时间与资源？系统自己的日志/界面失效时怎样不制造假完成？
11. **适配与规模**：如何让六个现有软件、CARE，以及未来 Shione、其他深度学习/科研项目使用，而不是每个仓库重新搭一遍、每次小修改都付出复杂流程成本？
12. **自我质量**：这个系统本身如何避免成为另一个 UI 难用、文字不自然、功能半成品、验收造假、崩溃难恢复的复杂项目？
13. **架构选择**：有无必要新建软件产品/独立仓库？在不用新系统、重用现有能力、改造现有软件或采用成熟依赖之间，哪种路线确有可观察的净收益？凭什么相信证据而不是设计者的断言？
14. **长远收益**：怎样衡量最终成熟交付的质量、完成时间、用户打断、资源消耗、错误拒绝及维护负担？假如新系统让总体开发更慢，如何判定不值得继续？

这些问题是研究对象，不是要求按此列表制造14个新模块、14种角色或14道固定关卡。
