# 用户要求：只描述目标与约束，不给架构答案

本文件是 GPT Pro 第一阶段的必读输入。它只整理用户明确要求解决的问题和不可接受结果；不规定必须做成插件、Bridge 大版本、独立产品、控制台、状态机或任何其他技术形态。

## 1. 最终目的

- 用户只把有限精力放在需求、产品方向、科研判断和真正需要本人决定的事项上。
- 复杂任务应尽可能一次交办后持续推进到成熟可用结果，而不是反复要求用户重新解释、恢复、手动同步状态或替系统发现明显缺陷。
- 判断系统是否有价值，要看实际完成速度、首次交付质量、用户介入次数、返修次数、Codex/计算资源消耗和长期维护负担，而不是看新增了多少规范、测试、状态或文件。

## 2. 强制适用范围

复杂交付至少包括：
- 原生桌面软件、网站、浏览器/宿主扩展、Android/移动端；
- 深度学习模型、长时间训练、Slurm/HPC 计算；
- 统计/科研代码、科学分析和复杂科研产物；
- 现有七个现实来源：CARE、CUHK_Date、Lucerna、Asteria、Bobbio、SeminarArc、Mica；
- 未来 Shione、其他深度学习模型和新科研/工程项目。

统一能力必须允许按平台和领域适配，但适配不能显著拖慢开发，也不能每个仓库重新造一套完整系统。

## 3. 必须解决的真实失败

系统必须针对真实开发中已经反复出现的问题，而不是只针对理想流程：

- 为了快而做低配替代、降级实现、手工退路、硬编码或只实现表面功能；
- 长时间依赖 fixture、synthetic data、mock/假 Provider，开发接近结束仍未接真实数据或真实宿主；
- 测试全绿、CI 全绿、截图齐全，但真实产品仍错误或难用；
- 已经做好的功能、交互、科学语义和配置被后续修复破坏；
- Figma/已有设计实际没有被读取和消费；视觉质量、布局、交互仍明显差；
- 面向用户的中文/多语言不自然，内部流程词、机器状态和开发语言泄露到产品或说明；
- 应调用的 Plugin/Skill/专业能力没有自动进入真实任务，仍靠用户反复提醒；
- AGENTS / 项目规则长期堆积、重复、失效或根本未被真正加载执行；
- Reviewer/Verifier 本身错误、漏检、误拒，最后逼产品迎合错误检查；
- 一有问题就 BLOCK、无限返修、无限重跑、不断刷新 fixture、重复做完整验收；
- 长任务中断、工作树/身份错、规则没加载、重复审批、已经完成却未发布/未集成；
- 资源和设备问题被混成产品失败，或资源等待期间持续烧 Codex 额度；
- mock/synthetic/内部 API 被冒充成 live/正常用户入口；
- 需要用户做一次真实操作后，系统没有继续后置验证、恢复和交付闭环。

## 4. 用户平时的真实入口

- 用户主要是在 Windows Codex App 或服务器 Codex 中直接发送任务。
- 研究必须回答：正常使用时系统到底怎样介入这一入口，而不是默认要求用户复制 Prompt、上传 ZIP、手工创建很多任务文件或改用完全不同的工作方式。
- 如果某种技术路线确实无法无缝接入，必须准确说明新增了什么用户步骤、为什么不可避免，以及是否仍然有净收益。
- 同一个复杂任务不能因为新系统存在而被两个执行器重复执行。

## 5. “Codex 说完成了，但其实没做好”必须真实闭环

- Codex 自己认为完成，不等于真实产品/科研结果已经完成；
- 需要有人或某个真实程序检查实际消费对象，而不是只读 Codex 自报；
- 一旦发现问题，必须能推动原任务在合法范围内继续修复，而不是只生成一份 Review 报告后停住；
- 不能把所有问题都重新抛给用户；
- 检查器出错时，应修检查器或正确归因，不能强迫正确产品改错；
- 科研任务允许合法的负结果/NO_GO，不能为了“交付成功”逼出假正结论。

## 6. 资源、Slurm 与长期运行

- 深度学习和科研任务可能需要 Slurm/GPU，系统必须处理提交、排队、长时间等待、无效配置、节点抢占、作业失败、结果缺失、监控断线和科学负结果。
- 正常排队期间不能让 Codex 持续轮询、无限消耗额度。
- 已有作业和现有结果不能因为会话中断就被重复提交或覆盖。
- 资源权限、费用、分区/硬件兼容、取消与重新提交边界必须服从真实项目和站点规则，不能由通用流程假设。
- 用户已经明确授权的同范围操作不能反复索权；真正改变资源、费用、数据、外部副作用或科研方向时才需要重新决定。

## 7. 质量、设计与专业能力

- 前端/界面类复杂任务应自动获得真正适合目标平台的设计与产品能力，不局限网页。
- 有 Figma/既有设计时必须实际读取并实现，而不是在 Prompt 中声明“对齐”。
- 验收必须面向用户真正使用的对象：桌面程序看真实窗口/通知/安装与状态；网站看真实浏览器；Android 看真实 APK/系统交互；插件看真实宿主；模型看真实数据/前向/损失/梯度/预测/指标；科研看科学含义和可复现性。
- 纯后端、数据、运行时、一般文档修改不应因为统一系统而被迫跑整套视觉/产品流程。

## 8. 可观察性

- 用户必须能看见系统每一步到底做了什么，而不是相信“某个组件应该起作用”。
- 至少要能判断：谁在执行、用的哪个任务/候选、实际调用了什么能力、测试/实验是否真的运行、为什么等待、为什么返修、为什么认为完成、花了什么资源。
- 可视化和日志本身不能形成第二套互相冲突的事实来源。
- 系统自己的前端审美、自然语言、稳定性、断线恢复和真实性，也必须按同样标准开发和验收。

## 9. 不接受的“解决办法”

以下不能单独被当成目标已经解决：
- 再写一份更长的规范、Prompt 或 AGENTS；
- 新增一个 Skill/Plugin 然后继续依赖 Codex 自觉；
- 开发结束后多加一道通用 Reviewer；
- 增加一个薄 wrapper，但真实执行入口和自动返修仍不存在；
- 建一个庞大中央控制器，让日常开发明显更慢；
- 用测试/CI/截图/文件存在/哈希/回执/合成 benchmark 冒充真正用户能力；
- 固定增加大量角色、审批、状态或验证次数；
- 因为旧方案投入很多就必须继续它；
- 因为 Critic REJECT/REVISE 就自动另造新系统。

## 10. 架构研究本身的要求

- 不预设答案是 Bridge Kit 大版本、AI Skills 新插件、独立新仓库、Codex hooks、App Server、另一套 agent runtime 或别的东西。
- 必须比较现实替代，包括“不建新通用系统，仅修现有入口”的路线。
- 必须主动寻找会推翻候选路线的事实，而不是等用户逐项指出漏洞。
- 在关键技术假设未经证明前，不得把候选方案包装成“已经最优”。
- 用户允许花时间研究，但不接受反复在未经实证的 v0.x 文档之间来回推翻。
