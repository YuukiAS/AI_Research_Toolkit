# 必须回答的问题：只列问题，不给旧答案

本文件是 GPT Pro 第一阶段的必读输入。问题来自旧“统一软件开发流程”研究中整理的历史问题、当前对话以及七项目暴露出的现实失败。这里不指定模块、角色或技术路线。

## A. 产品本体

1. 最终究竟应该做出什么可运行的东西？它为什么比只修现有 Codex / Bridge / 各项目入口更有价值？
2. 这个东西安装在哪里、谁维护、怎样升级、怎样在新项目接入？
3. 什么任务必须进入它，什么任务不应该进入，怎样避免小修也付出复杂流程成本？
4. 如果它有自己的 UI、服务或运行时，它怎样避免自己成为另一个难维护的复杂项目？

## B. Codex 真实入口与干预

5. 用户在 Windows Codex App 直接发消息时，系统怎样真正介入？谁实际收到任务？有没有双执行风险？
6. 用户在服务器 Codex 中发任务时，如何识别正确 repo、worktree、Codex 身份和长期任务？
7. 系统什么时候只是观察，什么时候有权阻止、继续、恢复或重试？
8. 如果正常 Codex 会话无法被外部程序无缝控制，最低额外用户操作是什么？这种代价是否仍值得？

## C. 假完成与自动返修

9. Codex 自称完成以后，谁检查真实成品，而不是只看报告？
10. 谁决定检查失败是产品缺陷、测试器缺陷、环境缺陷、证据缺失还是科研 NO_GO？
11. 真正发现产品问题以后，怎样让原任务继续修，而不是另开一个完全陌生的任务或只产出 Review 文本？
12. 自动返修什么时候停止？怎样避免无限循环、移动验收标准或不断增加新要求？
13. 怎样确保最终被交付的正是被验收的那个候选，而不是旧包、旧截图或不同提交？

## D. 防降级、真实数据和旧能力

14. 怎样尽早发现实现缩水、低配替代、hardcode、fallback、mock 假装 live？
15. 怎样避免开发直到很后面仍在 fake data / fixture 上，而真实数据或真实宿主根本没走通？
16. 怎样检测“代码中存在某机制，但最终输出根本没消费它”？
17. 怎样保证修新功能不会破坏已经做好的功能、设计与科学含义？
18. 哪些测试可以开发中重复，哪些真实验收必须到稳定候选才做？怎样避免不停刷 fixture？

## E. 专业质量、Figma、自然语言和审查者可靠性

19. 谁负责完整视觉、交互、自然语言和领域语义质量？程序、专业模型、人工、现有工具各证明什么？
20. 有 Figma 或既有产品设计时，怎样证明真正读取并影响了实现？
21. Frontend Design、写作、医学影像、统计等专业能力怎样自动进入该任务，而不是用户每次提醒？
22. Reviewer/Verifier 自己漏检或误判怎么办？怎样校准、弃权和退役？
23. 怎样防止“为了错误测试通过而把正确产品改坏”？

## F. AGENTS、长期规则和已有系统

24. AGENTS/项目规则怎样长期整理、淘汰和更新，而不是越来越长或越来越冲突？
25. 规则明明已写但 Codex 没有实际消费时，应该改哪里？
26. Bridge Lite / Reviewed / Control、AI Skills、项目本地脚本各自真正拥有哪部分能力？哪些只是声明？
27. 新系统怎样避免复制 Bridge 的状态、重试、Review 轮次和发布逻辑？
28. 什么时候需要子代理、多 Codex、独立 GPT，什么时候反而应该保持单一执行者？

## G. Slurm、资源和恢复

29. 谁有权提交 sbatch 或申请 GPU？权限如何一次授权并保持边界？
30. 作业长期 PENDING 时系统做什么？如何不持续消耗 Codex？
31. Priority / Resources、错误 QOS/账号/分区、依赖错误、调度器故障应该怎样区分？
32. 什么时候可以换分区、并行 race、取消镜像？如何确认科学/计算等价和预算？
33. 节点抢占、训练失败、监控断线、未知终态、输出缺失时如何恢复且不重复训练？
34. Slurm 显示 COMPLETED 后，怎样证明真正训练、预测、聚合完成？
35. 科学结果合理为负时怎样停止，而不是继续烧算力追求“成功”？

## H. 可视化和真实日志

36. 用户到底打开什么入口查看任务？需要看到哪些状态和证据才能判断组件真实起作用？
37. 每个事件怎样追溯到真实程序、任务、候选、动作、后置结果和资源消耗？
38. 控制台或日志断线、丢事件、重启、读取旧状态时怎样避免假绿灯？
39. 可观察性怎样实现而不制造第二套互相冲突的任务事实源？

## I. 跨项目适配与净收益

40. Lucerna、Bobbio、Mica、SeminarArc、Asteria、CUHK_Date、CARE 各有什么不能被通用化掉的平台或领域要求？
41. 新项目接入实际要写多少代码、配置和测试？多久以后才能真正用于开发？
42. 哪些能力值得抽成公共系统，哪些应永远留在项目本地？
43. 怎样客观比较新系统与“不建新系统”的完成时间、首次交付质量、用户打断、返修、资源和维护成本？
44. 什么证据足以说明某条架构路线应被淘汰，而不是再补一层机制继续救？

## J. 历史研究中已经提出但仍需重新回答的问题

45. 究竟怎样杜绝低配、替代和缩水实现？
46. Codex 从接新任务到用户真正看到成品，实际有哪些步骤？
47. 谁决定何时调用插件或 Skill：Planner 写一句、Codex 自行选择，还是有其他真实机制？
48. 独立审查是谁启动、审几轮、如何防冲突全都交给用户？
49. 验收应该在什么时候发生，怎样防开发者迎合固定测试？
50. AGENTS 怎么自己整理、增删、淘汰？
51. Asteria 为什么几轮检查仍然可能很丑？什么证据才真正解决视觉质量？
52. CUHK Date 一类不自然产品语言什么时候应该自己被发现？
53. 修了很多轮还不行时谁叫停，依据是什么？
54. Lucerna/Bobbio 一类真实桌面和个人数据验收怎样不折腾用户？
55. CARE 为什么即使有复杂流程仍能发生模型缩水？公共系统究竟能防到哪一层？
56. 怎样覆盖不同项目又不让每个项目日常开发变重？
57. 什么时候才值得让用户或 GPT Work 做最后验收，而不是让用户做第一线缺陷发现者？
58. 怎样确认“用了这套系统以后，一次交办新功能的成功率和总时间真的改善”？
59. 历史问题已经登记是否等于已经解决？怎样避免这种错误结论？
60. 为什么增加更多文件或流程不等于取得成果？
61. 谁最终有权关闭复杂任务？怎样区分产品完成、运行完成、审查通过和用户接受？
