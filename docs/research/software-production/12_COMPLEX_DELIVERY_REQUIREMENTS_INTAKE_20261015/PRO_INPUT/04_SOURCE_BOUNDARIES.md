# 来源与证据边界：GPT Pro 第一阶段必须遵守

## 1. 第一阶段可以信什么

可以作为问题来源：
- 01_USER_REQUIREMENTS_NO_SOLUTIONS.md：基于用户当前和历史明确要求整理的目标与约束；
- 02_OPEN_QUESTIONS_NO_ANSWERS.md：尚未回答的问题；
- 03_HISTORICAL_FAILURES_SOURCE_INDEX.csv：七项目363条历史登记的编号、描述、旧状态与源位置；
- 对应七项目仓库当前真实源码、AGENTS、产品设计、测试、运行材料；
- 当前官方 OpenAI Codex、GitHub、Slurm、Playwright 等一手资料。

## 2. 第一阶段不能当成答案的材料

在独立提出候选架构之前，不要把以下内容当作输入答案：
- v0.1–v0.8 的架构方案；
- v0.6 第三卷里 Planner 对21问的回答；
- 三位 Critic 的 REVISE / REJECT 建议；
- 本研究目录中旧的助手加工文件；
- 之前助手提出的“独立仓库”“薄 wrapper”“Bridge 扩展”“控制台”“KeelArc”等具体产品方向。

这些历史材料没有删除。先独立形成候选，再用它们做反证和遗漏检查。

## 3. 363条历史登记的含义

363 = 六软件主登记246 + Lucerna/Asteria晚期25 + CARE原40 + CARE追加52。

它们包含：
- 历史已修问题；
- 当前或当时真实事故；
- 风险和观察缺口；
- 重复根因；
- 工作流问题。

因此：
- 不能说“363个当前 bug”；
- 不能说“给363条各配一个 gate 就覆盖完成”；
- 必须回源文件和当前仓库判断当前性与根因。

## 4. 旧线程的边界

目前没有标题“统一软件开发流程”旧 ChatGPT 线程的完整逐字导出。

现有可用材料包括：
- 旧研究中整理出的21个问题标题；
- 当前项目上下文里可检索到的用户明确约束；
- 当前续接线程的用户要求；
- GitHub 中 v0.6–v0.8 历史研究。

第一阶段应以用户目标、未解问题和现实项目事实为准，不把旧 Planner 的回答伪装成用户原话。

## 5. 实机事实的边界

仓库里存在某个脚本或规则，不等于目标 Windows/Longleaf 环境当前已经安装、运行或获授权。

涉及以下判断必须区分：
- 源码支持；
- 目标机器当前安装；
- 真实入口实际调用；
- 真实候选已经通过。

没有实机证据时明确写“待验证”，不要用配置文件或文档替代。

## 6. 第一阶段的输出要求

在阅读任何旧答案之前，GPT Pro 应先形成一个独立候选集合，并至少记录：
- 候选架构或产品形态；
- 为什么可能满足用户要求；
- 依赖的关键技术假设；
- 最可能推翻该候选的事实；
- 与“不建新通用系统”的比较；
- 需要什么最小取证或实验才能继续判断。

完成这一步后，才进入第二阶段阅读历史方案和三位 Critic。
