## 一、结论

我否决“研工台 v0.6”作为一个新的统一生产运行体系继续进入实现阶段。

否决的根本原因不是材料不完整，也不是少几个字段、测试或接入示例，而是它同时提出了两个无法兼容的目标：

一方面，研工台必须保持“薄层”，不建立第二套当前状态、调度器、工作流引擎、验证系统或跨仓库中央控制面；另一方面，它又要统一承担任务定位、义务解释、能力选择、插件调度、子代理衔接、生产链检查、独立验收、真实观测、整体评审、声明准入、故障恢复和规则维护。这些职责一旦真正具有阻断效力，就必然需要持久状态、执行所有权、能力授权、检查点、观察者身份、候选版本绑定和恢复语义，实质上就是另一个控制系统。若不拥有这些能力，它只能成为一层报告、清单和提示词包装，无法在正常开发中阻止降级实现和虚假验收。

这不是可以通过局部返修关闭的矛盾。继续在当前组件划分上增加合同、字段和适配器，只会把现有 `GPT_Codex_AI_Bridge_Kit`、`AI_Skills_Collection` 以及六个产品仓库已经拥有的职责再复制一次，形成第二个事实来源和第二套失败闭环。

本结论否决的是：

- 作为独立统一运行体系的“研工台”；
- 当前四卷报告中以十二项职责构成一个新生产体系的设计；
- 在六个仓库上继续实施该中央体系的试点。

本结论不否决：

- 统一的最小证据格式；
- 跨仓库共享的任务与候选版本标识；
- 对现有 Bridge、插件体系和产品仓库正常入口的定向修复；
- 使用成熟工作流引擎处理确有持久执行需求的任务；
- 重新设计一套不拥有第二控制面的“生产保证规范”。

## 三、架构是否应该存在

### 3.1 真实存在的问题成立，但当前解法不成立

四卷报告识别出的核心问题是成立的：

- 用户目标被替换成较容易通过的代理目标；
- 声称使用模板、插件、数据或真实入口，实际没有消费；
- 验收观察了错误对象；
- 失败只有记录，没有明确的关闭责任；
- 独立评审本身可能误判；
- 测试、截图、文件和状态回执可能被误当作真实能力；
- 多轮返修可能不收敛；
- 用户被迫反复发现同类错误并重新解释要求。

但这些问题不天然要求建立一个新中央运行体系。它们分别属于不同责任域：

- 通用任务状态、恢复和角色交接属于 Bridge；
- 插件发现、版本、调用和资源消费证据属于 `AI_Skills_Collection`；
- 产品正常入口、真实状态机、平台权限和领域验收属于各产品仓库；
- 构建与发布身份属于持续集成、受保护环境和发布设施；
- 科学正确性属于领域方法、真实数据和领域评审；
- 人机授权属于实际账号、设备、凭据和外部副作用边界。

研工台把这些责任重新收束到一个名字之下，却没有证明如何避免它成为第二个控制面。

### 3.2 “薄而强制”在本设计中不可实现

报告希望研工台不成为大型中央系统，却又要求它能：

- 决定任务采用哪些技能、插件和执行资源；
- 触发或衔接 Codex、子代理和评审角色；
- 判断第一条生产链是否真实贯通；
- 运行真实观测；
- 准入或拒绝产品声明；
- 归因失败并启动有界恢复；
- 扫描、合并、迁移甚至退休各仓库规则。

这些不是被动格式转换，而是执行权、判断权和恢复权。它们至少需要：

\[
\text{任务身份}
+\text{候选版本身份}
+\text{当前阶段}
+\text{授权能力}
+\text{执行记录}
+\text{观察证据}
+\text{评审状态}
+\text{恢复检查点}.
\]

只要这些数据能够决定是否继续、重试、发布或关闭，研工台就拥有事实状态。把它称为“轻量元层”不会改变其控制性质。

若研工台不保存这些状态，只把信息交给 Bridge 或仓库自身保存，那么它不能可靠判断：

- 当前运行是不是同一个任务；
- 重启后应该从哪里恢复；
- 哪个外部动作已经发生；
- 观察证据是否对应最终候选；
- 哪次评审仍然有效；
- 哪个失败已经被修复；
- 是否发生了重复发布或重复通知。

因此当前方案只有两种落点：

1. 真正强制执行，于是成为第二个工作流和状态系统；
2. 保持轻量，于是不能兑现核心防护。

两种都不符合原始要求。

## 四、成熟路线比较

### 路线 A：不建立新中央运行体系

直接修复产品仓库、Bridge 和插件体系中已经确定的缺口，并定义一个很小的共享证据格式。

优点是责任归属清楚，没有第二套当前状态；缺点是无法通过一个统一界面掩盖所有平台差异。这个“缺点”实际上是现实约束：Windows 桌面、ChatGPT 宿主、Android 模拟器、浏览器网站、HPC、统计分析和深度学习实验本来就不能由同一种观察器和权限模型可靠验收。

这是默认应采用的路线。

### 路线 B：按 v0.6 建立研工台

优点主要停留在概念层：统一入口、统一名词、统一登记和统一恢复叙事。

主要风险是：

- 与 Bridge 重复任务状态和角色转换；
- 与插件体系重复能力选择和调用记录；
- 与仓库本地控制器重复产品状态；
- 与持续集成重复候选与发布准入；
- 让同一个生产故障同时存在中央和本地两个关闭责任方；
- 六个适配器逐渐变成六套隐藏的产品编排器。

本路线应被否决。

### 路线 C：扩展现有 Bridge，并增加最小生产保证格式

通用的任务身份、持久恢复、角色交接、审查状态、失败责任和有界重试继续由 Bridge 管理；项目动作和验收由仓库本地实现；插件消费由 `AI_Skills_Collection` 记录。

这是推荐的公共控制路线，但扩展范围必须受限，不能把产品和科研语义继续塞进 Bridge。

### 路线 D：对普通软件任务采用成熟的规格驱动工作流

GitHub 的 Spec Kit 已提供可恢复、多步骤、条件执行、人工闸门、锁和检查点等机制，适合把明确的软件生产步骤编码成工作流。它可以作为某些任务的执行后端，但不能自动提供可信观察者，也不能证明领域正确；自定义脚本仍然可能执行错误或被错误验收。

### 路线 E：按任务类别选择成熟设施

- 多日、跨进程、必须从故障点可靠恢复的服务型工作，可考虑 Temporal 一类持久执行引擎。
- 构建和发布可使用 GitHub Actions、受保护环境、指定审批人及产物证明。
- 跨阶段证据关联可采用 OpenTelemetry 式的追踪标识和上下文传播。
- 本地桌面、设备和私有数据操作仍由仓库适配器及真实账号完成。

产物证明可以证明某个构建由哪些输入和流程生成，不能证明软件行为、视觉质量或科学正确性。追踪系统也只能记录发生了什么，不能代替授权和验收。

推荐组合是：**A 为默认，C 提供最小公共控制，D 和 E 只在任务确有需要时启用。**

| 任务定位 | 保留为共享字段，不设独立组件 | Bridge 的任务记录 |

十二项职责中，没有一项必须成为新的独立中央运行组件。它们可收敛成：

1. 一个共享证据格式；
2. Bridge 的有限扩展；
3. 插件体系的真实消费记录；
4. 各仓库的本地执行与观察适配器；
5. 受保护的发布与领域评审。

## 六、四卷报告的实质审查

### 第一卷：架构与组件合同

成立的部分：

- 正确区分“有文件、有测试”和“真实能力可用”；
- 正确要求绑定目标、候选版本、观察对象和失败责任；
- 正确承认同一管理员下的所谓独立评审不构成强安全隔离；
- 正确指出不能再建立一个重复的 Bridge 或验证系统。

不成立或未经证明的部分：

- 从共同失败模式直接跳到统一运行体系，没有证明新控制面是必要条件；
- “一个任务入口、四组执行程序、两个责任域”是设计提议，不是由证据推出的唯一架构；
- 十二项职责与“不建立第二控制面”直接冲突；
- 对评审器只提出校准意图，没有定义准入、撤销、弃权、复训或领域裁判机制；
- 对持久执行、进程死亡、幂等、重复外部副作用和跨设备恢复缺乏可执行合同；
- 对中央规则维护的权限和回滚没有可靠边界。

### 第二卷：事故与因果覆盖

成立的部分：

- 对 246、25、40 和 52 的计数边界较谨慎；
- “代理目标替换、资源未实际消费、观察对象错误、无人关闭”四类归纳具有解释力；
- 映射表提高了可追踪性。

不足之处：

- 分类覆盖不等于控制有效；
- 同一历史故障可被多个条目重复表达；
- 缺少去重后的当前基线和重新运行结果；
- 未证明十二项组件能在盲测中识别这些事故；
- 没有反事实比较：仅修 Bridge、仓库入口或评审器是否已经足够。

### 第三卷：用户问题与决策

前五类问题较准确地表达了用户目标：减少重复解释、避免假验收、控制复杂度、保持真实入口和减少不必要参与。

后续决策存在过度集中：

- 将能力选择、角色衔接、观察和恢复都纳入统一体系；
- 将规则维护也纳入中央闭环；
- 没有清楚区分哪些用户参与是流程浪费，哪些是账号、设备、伦理、费用和科学判断所必需；
- 没有证明插件被调用就等于专业能力被正确消费；
- 没有给出评审器失格后的系统行为。

因此，该卷完整记录了问题，却未完成由问题到架构的最小性证明。

### 第四卷：Lucerna 完整演练

该演练是结构化的假设走查，不是真实生产运行。十四阶段和十二个异常案例可以作为需求来源，但不能证明：

- 正常入口已经接通；
- 通知、冷却期和重复执行具有幂等性；
- 真实 Windows 安装版本和开发目录版本不会混淆；
- 证据对应最终发布候选；
- 观察器与实现者之间存在可信边界；
- 进程重启后能够正确继续；
- 同一故障不会同时被 Bridge、研工台和 Lucerna 本地控制器恢复。

Lucerna 的仓库规则已经要求真实运行状态、真实资源费用、身份验证和用户可见行为；研工台无法用一个通用观察接口替代这些本地语义。该案例反而证明：共享层最多负责证据标识和闭环状态，真正的判断必须留在 Lucerna。

## 七、六仓库适配性

六个仓库不是同一种软件的六个实例，而是六种明显不同的信任和运行环境：

- Lucerna 是 Windows 桌面与托盘程序，依赖真实登录、实时状态、通知和安装状态；
- Bobbio 涉及 Zotero、文献隔离、设计来源和 Windows 原生构建；
- Mica 运行在真实 ChatGPT 宿主中，普通账号和已认证会话无法由中央系统任意接管；
- SeminarArc 需要模拟器、受保护真机、登录态和移动端交互；
- Asteria 依赖固定公开地址、浏览器黑盒观察和发布版本一致性；
- CUHK Date 已有自己的任务票据、串行角色和上线合同。

这些差异意味着所谓“薄适配器”至少需要掌握：

- 平台启动方式；
- 真实账号与凭据；
- 状态读取方式；
- 截图或行为观察；
- 设备保护规则；
- 可恢复边界；
- 领域验收标准；
- 外部副作用。

一旦适配器拥有这些内容，它就是产品仓库的执行与验收层，而不是普通转换器。再在其上增加中央调度，日常开发会出现“双重配置”：

- 本地规则写一次；
- 研工台能力声明再写一次；
- 本地测试定义一次；
- 中央观察合同再映射一次；
- 本地状态机运行一次；
- 中央闭环再维护一次。

这与“减少六个仓库的日常适配复杂度”相反。

## 八、CARE 与科研复杂产物

CARE 的证据非常重要，但它反对的不是“缺少一个中央运行台”，而是：

- 科学目标被代理指标替换；
- 标签和损失函数语义与任务不符；
- 训练阶段冻结范围错误；
- 评审没有检查真正的科学对象；
- 多代理流程的分母、权限、版本和摘要发生漂移。

历史源码中可以看到具体科学问题，例如无 T2 情况下标签映射改变了原始瘢痕含义、某阶段冻结全部编码器参数、可用性处理采用批级缩放而非逐样本掩码。这类错误需要医学影像和优化语义审查，不会因为拥有统一任务入口而自动消失。

更重要的是，科研探索和产品发布不能共用同一种成功状态：

- 一个模型在可靠实验后得出“不值得继续”，可能是科学上成功的停止结论；
- 一个方案因假设不成立而修改研究协议，可能是正常科研进展；
- 产品发布若目标、入口或候选版本改变，则必须重新验收。

若研工台用统一的“完成—失败—返修—发布”闭环处理二者，会有两类错误：

1. 把有效的科学否定结果视为流程失败并继续调参；
2. 把科研中允许的探索性改变带入产品发布，造成目标漂移。

因此必须分成至少两种配置：

- 产品交付配置：目标和候选冻结，任何语义变化触发重新审查；
- 科研探索配置：允许假设被证伪和协议修订，但要求保留数据、方法、分析与结论谱系。

## 九、评审器并不因“独立”而可靠

STAT5060 的现有评审基准提供了直接反例：

- 50 页中有 10 个真实失败；
- 评审器只识别出 2 个；
- 漏报 8 个，召回率为 \(0.20\)；
- 总准确率为 \(0.74\)，低于全部判为通过的 \(0.80\)；
- 还出现高置信度错误通过。

它遗漏的不是边缘格式问题，而包括可复制性、内部标识泄漏、阅读路径、考核范围、身份、版面组织和统计解释。

因此，“再加一个独立模型评审”不能作为架构防护。任何有阻断权的自动评审器至少需要：

- 按领域划分的隐藏基准；
- 明确的准入阈值；
- 对高风险类别的最低召回要求；
- 无法判断时弃权；
- 连续失误后的自动撤销资格；
- 修改提示词或模型后的重新校准；
- 对科学、视觉、交互和发布身份分别指定最终裁判；
- 保留人工或领域专家终止权。

v0.6 目前只有“建立校准样例”的方向，没有可执行的资格管理合同，因而不能把评审器视为核心安全边界。

## 十一、替代架构

新的设计不应再叫“统一生产运行体系”，而应是“跨仓库生产保证规范”。它只定义跨系统必须可传递的最小信息，不拥有工作流执行权。

### 共享保证记录

每个任务最多共享以下内容：

```yaml
task_id:
parent_goal_ref:
repository:
candidate_identity:
profile: product_delivery | research_exploration
obligations:
capability_leases:
normal_entry:
evidence_refs:
observer_provenance:
review_verdicts:
failure_owner:
next_authorized_action:
```

这些字段的作用是让 Bridge、插件体系、持续集成和仓库本地工具交换事实，不建立新的 `CURRENT`、状态机或调度器。

### 职责边界

Bridge 负责：

- 任务身份和父目标；
- Planner、Executor、Reviewer、Critic 的交接；
- 有界恢复、检查点和失败责任；
- 当前有效审查状态；
- 不跨越授权边界。

`AI_Skills_Collection` 负责：

- 能力发现；
- 插件和技能版本；
- 资源是否真正被正常入口消费；
- 插件能力闸门。

产品仓库负责：

- 正常用户入口；
- 平台身份和凭据；
- 真实状态和观察；
- 项目特定失败；
- 领域验收；
- `AGENTS.md` 的语义所有权。

持续集成和发布设施负责：

- 候选提交、构建物和发布物的身份；
- 受保护环境与指定审批；
- 构建来源证明；
- 发布后的基本探测。

领域评审负责：

- 统计、医学影像、深度学习、交互、视觉或教学语义；
- 评审器资格；
- 弃权和人工裁决。

## 十二、重新设计后的可证伪试点

新方案不应先覆盖六个仓库。应在 Lucerna 上做一个最小对照试点，而且必须允许结果证明“无需新的共享机制”。

试点只选择三个历史故障类别：

1. 目标被代理指标替换；
2. 验收观察错误候选或错误入口；
3. 修复后没有明确关闭责任。

比较两条路线：

- 基线：Lucerna 本地规则与现有 Bridge；
- 候选：基线加最小保证记录及受保护候选绑定。

冻结一组未用于设计的历史或新构造案例，禁止中途换题。至少测量：

- 严重失败召回率；
- 错误阻断率；
- 从任务创建到可信关闭的人工交互次数；
- 新增仓库配置量；
- 重启后的恢复成功率；
- 重复外部副作用次数；
- 观察证据与最终候选不一致次数；
- 用户发现而系统未发现的失败数。

候选方案只有同时满足以下条件才值得扩展：

- 对严重降级的召回率明显高于基线；
- 不因大量误报增加用户确认；
- 没有新增第二套当前状态；
- 项目接入不需要复制本地验收语义；
- 进程重启后不重复发布、通知或修改；
- 所有通过结论都能绑定同一最终候选。

若仅增加登记文件、报告或机器回执，不算获得新能力。
