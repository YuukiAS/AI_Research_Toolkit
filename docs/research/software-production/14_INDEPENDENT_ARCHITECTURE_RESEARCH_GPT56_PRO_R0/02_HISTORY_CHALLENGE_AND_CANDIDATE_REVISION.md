## 一、结论

第一阶段的核心判断经历史材料反证后仍然成立：**不应建设一个新的“研工台”中央运行平台、通用任务数据库、全局调度器或统一语义审查器。** v0.6 的十二项职责若具有真实阻断权，就会与 Bridge、GitHub、Slurm、项目状态和发布权限形成第二控制面；若不具有阻断权，就只是报告和提示词包装。三份原始独立审查与 v0.7、v0.8 的返修材料没有提供足以推翻这一判断的证据。

历史材料同时指出了第一阶段候选中过于乐观的一点：仅提出“入口绑定＋证据封套＋项目门禁”仍可能变成没有人实际调用的文档协议。GPT-5.5 的 B1 和 GPT-6 的两项设计阻塞尤其有效：公共机制若不能在普通任务入口被实际加载、在首个副作用之前被有权执行者消费、并与既有 Bridge 状态和审查预算严格对应，就不能声称降低了降级实现或虚假验收。

因此，推荐候选需要进一步收缩并落到现有所有者：

> **不建立独立公共运行包；只研究一个 Bridge 原生的“交付证据合同”扩展。公共代码最多负责入口身份、候选—产物—证据的一致性校验和缺证判定。需求解释、真实探针、证据采集、专业审查、工作流推进、重试、发布与科学结论仍由现有 Bridge、项目、GitHub、Slurm 和领域负责人拥有。**

这比 v0.8 的五个 `assure` 子命令更窄。它保留 B1 要求的可执行性，但删除容易演化为影子工作流的 `plan`、`probe`、`collect` 和 `admit` 公共职责。是否连这一窄扩展都值得做，必须与“完全不新增公共代码，只修现有入口和项目脚本”的基线比较；基线等效或更好时，最终结论就是不建设。

## 二、历史材料怎样挑战第一阶段候选

### 1. v0.6：问题识别准确，架构最小性失败

v0.6 四卷正确识别了四个反复出现的因果族：用户目标被代理目标替代；声明使用的数据、插件或真实入口没有被消费；验证器观察了错误对象；运行和审查之后无人对最终关闭负责。它还正确强调第一条真实纵向路径、真实消费者、正确/错误/缺测校准、候选身份和合法科学 `NO_GO`。

但 v0.6 将这些责任组织成十二项中央职责，包括任务定位、义务解释、检查选择、技能派发、Codex/子代理集成、早期生产链检查、独立参考管理、真实观察、专业审查、声明准入、恢复和规则维护。它一方面声称不建立第二控制面，另一方面又赋予新体系决定是否继续、审查、重试和交付所需的事实。GPT-5.6 的 `REJECT` 对这一矛盾判断最准确：做强必然复制状态和权力，做薄则不能兑现强制保证。

v0.6 的 Lucerna 走查和 PDF 构建也直接说明“存在文件与报告”不能代替消费事实。Lucerna 案例仍是假设流程；PDF 虽已在冻结提交中生成，目录说明、构建源提交、产物提交和独立视觉审查状态却不同。第一阶段提出的候选—产物—消费链因此得到加强，但“中央体系”被否决。

### 2. 三份原始审查：路线分歧比表面更重要

#### GPT-5.6：根本否决

其核心结论是删除独立运行体系，只保留共享证据格式、Bridge 有限扩展、AI Skills 真实消费记录、项目本地执行/观察和受保护发布/领域评审。它列出的 P0/P1/P2 阻塞与当前十仓库事实高度一致：双控制面、薄而强制的不可能三角、同权自证、产品与研究语义混淆、适配器膨胀、AGENTS 越权、低质量 Reviewer、运行恢复、权限、产物身份、历史登记分母和组件重复。

这一审查支持第一阶段“不要新平台”的主结论，也要求进一步收缩公共状态和角色。

#### GPT-5.5：要求最小可执行能力

其 `REVISE` 并不接受只有原则和分工。B1 要求明确最小运行入口、输入输出、不可改边界、候选身份和与 Bridge/项目脚本的连接；B2–B3 要求可信证据和 Reviewer 准入；B4–B7 要求逐仓成本、成熟工具复用、产物身份和逐项覆盖。

这对第一阶段候选构成真实反证：若“证据封套”只是另一个仓库文件，没有普通入口自动绑定、没有真实消费者、没有对错候选/未运行/缺证的机器校验，它不会改变用户体验。必须保留一小段可执行公共逻辑，或者直接选择基线方案。

#### GPT-6：允许薄方向，但指出合法阶段与副作用闭包未闭合

GPT-6 的两项 P1 比一般原则更具体。第一，Bridge Reviewed 的正式审查只能在既有状态和轮次中发生；v0.6 的早期独立审查、内部审查和 GPT Work 没有合法映射，容易产生影子角色和预算重置。第二，源码目录只读不意味着 MCP、插件、子脚本或原生程序没有写权限；Bobbio `PreflightOnly` 前可能执行 `Apply`，Lucerna 捕获会显示和切换窗口。安全判断必须覆盖实际进程继承的能力与完整调用链，并在首个副作用之前生效。

这要求公共合同只在现有合法阶段被消费，且绝不能把“只读 manifest”当作权限隔离。

### 3. v0.7：正确撤销中央控制，但存在“所有事情交回原 Owner”的空转风险

v0.7 接受根本否决，删除中央状态机和十二项组件，保留现有 Bridge/项目唯一 Owner、项目原生门禁、AI Skills 专业能力及可选的最小保证记录。这一改向是必要的，也清楚区分了 Lite、Reviewed 和高成本科学任务的合法角色与权限。

但 v0.7 自己承认：六仓库普通入口是否真正安装 Reviewed/Control、Skill 是否实际派发、项目检查是否被执行、受保护权限是否存在均未证明。若只是写“由现有 Owner 负责”，用户仍可能需要复制多条提示词、等待会话自觉和手工判断报告。因此 v0.7 不能单独满足一次交办目标。

### 4. v0.8：补上可执行接口，但五命令设计仍有膨胀风险

v0.8 以五个短命命令回应 B1：`inspect`、`plan`、`probe`、`collect`、`admit`。它明确不拥有任务状态、Watcher、审查轮次、重试或发布，三类证据合同和 Reviewer 准入制度也较完整。363 行矩阵全部保持 `NOT_VALIDATED_ON_NORMAL_ENTRY`，没有用表格数量冒充防护成熟度，这一点可信。

然而五个命令并非都具有公共必要性：

- `inspect` 的任务、工作树、指令和权限绑定与 Bridge 当前 readiness/context-binding 职责高度重合；
- `plan` 会复制项目 Plan、Requirement Ledger 和用户批准来源，容易形成第二义务视图；
- `probe` 必须运行项目真实业务/数学路径，本质属于项目脚本或领域 Verifier；
- `collect` 必须由平台 Owner 采集真实 UI、设备、服务或模型事实，公共命令只能读取引用；
- `admit` 若决定阶段准入，容易成为影子 Gate；若只是返回结果，则现有 Reviewer/CI 可以直接调用一个纯校验器。

所以 v0.8 解决了“没有可执行内核”的形式问题，却没有证明五个命令比 Bridge readiness＋项目门禁＋一个纯证据校验器更有净收益。它也没有获得后续独立 R2 裁决或真实试点证据。历史材料中的 v0.8 只能作为候选设计，不能被继承为当前答案。

### 5. 363 行矩阵的正确用途

v0.8 的矩阵对来源、原始状态、保守当前性、候选根因、现有 Owner、证据强度和未覆盖原因做了有价值的结构化整理。其最重要字段不是“推荐检查”，而是全部仍未在正常入口验证。

该矩阵适合作为试点的历史坏例/正确例/缺测例抽样池和因果覆盖索引，不适合作为每个任务都要运行的 363 项清单，更不能证明当前十个仓库仍有同样缺陷。六库 246、晚期 25、CARE 40＋52 是源登记，不是独立事故数、当前缺陷数或未来召回率分母。

## 三、第一阶段候选逐项修订

### 候选 0：只修现有入口和项目流程

**保留，并提升为推荐方案的正式对照和可能最终答案。** 历史审查反复强调，很多问题可以通过修 Bridge、AI Skills 实际消费和项目正式入口解决。若这些修复已经达到相同效果，不应另发公共包。

### 候选 1：GitHub 中心控制

**继续否决作为完整架构。** GitHub 可提供源码、必需检查、合并队列、部署和制品来源证明，但无法证明本地安装、真实桌面、已登录浏览器、Zotero、Android 硬件或科学语义。历史关于 skipped/neutral check、错误候选和 PDF 身份的材料进一步证明它只能拥有部分事实。

### 候选 2：Temporal 类统一 durable workflow

**继续否决作为默认。** 历史材料没有证明当前多数任务需要新持久服务；引入它会直接重建 v0.6 被否决的第二控制面。只有未来出现明确跨服务、长期等待并可靠重试副作用的独立业务流程时，另行评估。

### 候选 3：将 CARE 多角色控制推广到所有项目

**继续否决。** CARE 的冻结合同、角色权威、内容寻址和 finalization 值得复用；其状态漂移、审查目标循环、错误 Verifier 阈值和高维护成本也证明不能成为默认产品流程。

### 候选 4：按领域使用成熟工具

**保留并加强。** Nextflow/Snakemake、MLflow/DVC、GitHub、Playwright、OpenTelemetry 等只在各自问题存在且收益可证时使用。历史材料关于成熟工具的选择基本正确，但当前项目是否安装、计划是否支持、权限是否可用仍必须实证。

### 候选 5：薄型入口绑定＋证据封套＋项目门禁层

**实质修订。** 删除“独立公共层”这一实现形态，改为以下三部分：

1. **Bridge 原生入口绑定收据**：由实际 SessionStart/显式 app-server/`codex exec`/Bridge 启动点生成，记录当前任务、仓库、工作树、指令来源、Skill/Plugin 与 Bridge 运行身份。不存在或未信任时明确 `UNPROVEN`。
2. **纯交付证据校验器**：读取项目已产生的候选、产物、真实观察和门禁引用，只检查同一候选、证据实际执行、来源权限、时效和必需项缺失；不解释专业结果，不执行项目命令，不推进任务，不调用发布，不写第二 `CURRENT`。
3. **项目门禁声明**：仍由项目仓库定义。项目脚本负责真实 `probe` 和 `collect`；Bridge/CI/Reviewer/领域 Owner 负责是否消费校验结果和作出合法决定。

不再建议独立实现 `assure plan`、公共 `assure probe`、公共 `assure collect` 或拥有阶段语义的 `assure admit`。若需要命令行入口，它应是 Bridge 中的一个无状态 `verify-delivery-evidence` 子命令或库调用，而不是新的产品、Daemon 或仓库级状态机。

## 四、修订后的最小公共合同

### 1. 入口绑定收据

入口收据只陈述实际加载事实：

```yaml
entry_surface:
entry_instance_id:
session_or_thread_id:
repository:
worktree:
head_sha:
loaded_instruction_digests:
loaded_skill_plugin_versions:
bridge_runtime_identity:
sandbox_and_approval:
task_contract_digest:
observed_at:
binding_result: PROVEN | PARTIAL | UNPROVEN
```

它不创建任务。Windows 普通 App 只有在当前受信任 hook/AGENTS/Bridge 真实加载并通过一次隔离正常聊天验证后才能写 `PROVEN`；服务器显式 app-server、SDK 或 `codex exec` 可由调用方绑定 thread 和事件。不同入口各自证明，不互相冒充。

### 2. 项目门禁结果

项目继续拥有真实动作和语义。公共合同只要求每项结果声明：门禁 ID、Owner、候选身份、正常入口、原始证据引用、结果、适用范围、失效条件、证据等级和是否需要人类决定。专业输出可以是项目原有格式，公共层不强制复制全部内容。

### 3. 交付证据校验

校验器只回答以下机器问题：

- 入口是否绑定到本任务和工作树；
- 证据是否属于同一源码/构建/部署/安装/checkpoint；
- 预先要求的项目门禁是否真实执行，而非 skipped/stale/wrong-candidate；
- 原始证据是否来自声明的 Owner 和受保护范围；
- 当前声明是否超过证据范围；
- 候选或门禁逻辑变化是否使旧证据失效；
- 是否仍有未知项或明确的人类授权门。

它不得判断界面是否美观、中文是否自然、统计方法是否正确、医学损失是否忠实、科学方法是否值得继续，也不得将项目 `FAIL` 自动解释为实现错误。

### 4. 合法消费者

- Bridge Reviewed/Control 在其现有合法状态中消费；不会新增审查轮次。
- 项目 CI 或发布者在真实规则集和权限可用时消费。
- Slurm 提交者可在项目合同明确要求时消费项目科学门禁；公共校验器本身没有 `sbatch/scancel` 权限。
- Lucerna 和 notifier 只读投影，不具有决策写权限。

没有合法消费者时，校验结果只能是开发审计，不得宣传为技术强制。

## 五、Reviewer 与验证器资格的修订地位

历史材料正确证明 Reviewer 资格不能靠模型名称或独立会话获得。STAT5060 的低召回、CARE 错误阈值、SeminarArc OCR 假阴性、Asteria 恒零指标均要求好例、坏例、缺测、弃权、误拒和资格撤销。

但这不应变成中央 Reviewer 注册系统。资格仍由相应项目/领域 Owner 维护，公共封套最多记录：审查者身份和版本、资格范围、冻结校准集引用、有效期/失格状态、当前审查是否弃权。可复算事实优先由独立数值/行为参考裁决；专业审美、语言和科学解释由具备完整材料的责任人或经校准 Reviewer 辅助。

## 六、产品与科研结果语义的最终修订

历史 `REJECT` 要求分离产品交付与科研探索，方向正确；但不需要两个新的公共状态模型。公共协议只记录项目自己的决策类型和证据范围：

- 产品可以由项目决定 `RELEASE_READY`、`DOGFOOD_ONLY`、`NOT_PROVEN` 等；
- 科学项目可以决定 `PROTOCOL_COMPLETED_NEGATIVE_RESULT`、`IMPLEMENTATION_INVALID`、`FURTHER_DECISION_REQUIRED` 等；
- 公共校验器只说明该决策是否有完整、同候选、合权的支撑证据。

因此第一阶段提出的通用 `VERIFIED_COMPLETE`/`VERIFIED_NO_GO` 生命周期状态被删除。它们可以是最终报告中的自然语言结论，不能成为新的公共任务状态。

## 七、历史材料新增的硬约束

1. 任何“早期独立审查”必须映射到现有合法角色；Reviewed 的 EXECUTING 阶段只能运行项目确定性检查，正式 Reviewer 仍在其合法状态和预算中。
2. 只读源码不代表无写权限。实际 OS 账户、MCP、插件、hook、环境变量、网络、子脚本、窗口、数据目录和凭据构成完整能力闭包。
3. 安全检查必须在首个副作用之前；事后报告不能撤销真实资料、桌面、票据、作业或发布污染。
4. 正确实现、数学等价实现、合法科学负结果和无法观察的情况必须可区分；一律拒绝不是安全。
5. Reviewer 漏检或错误门槛应撤销对应资格，而不是让产品迎合错误测试。
6. 363 行历史矩阵用于抽样和因果追踪，不能转化为每任务检查清单或“全部已解决”。
7. 源提交、构建产物、运行目标、观察行为和最终消费对象是不同身份层；哈希不能替代发生过的动作和专业结论。
8. 报告、截图传输、收据或控制面变化不应自动重建产品、重跑真机或重训模型。
9. GitHub 绿色、文件存在、进程存活、Slurm 提交/运行和 watcher 心跳均不能单独证明完成。
10. 公共扩展无法在普通入口被真实加载、或没有降低用户负担时，必须取消。

## 八、剩余决定性未知与后续裁决

历史材料没有闭合以下问题：

- OpenAI 当前 hooks 在用户实际 Windows App、服务器交互入口和 ChatGPT Work 中的支持、信任及配置继承是否足以生成入口收据；
- Bridge `0.11.0` 候选是否正式分发并同步到实际 Codex identities；
- 当前项目是否已有等价候选绑定功能，使公共校验器完全多余；
- 哪些项目具有真正不可由实施者绕过的 CI/账户/设备/Slurm 权限；
- Reviewer 校准是否能在不增加大量用户维护和固定样本过拟合的情况下产生净收益；
- 两个跨平台试点能否相对基线减少总耗时、首次严重缺陷、用户干预和重复重型检查；
- 证据 schema 是否能保持只引用项目事实，而不演变为新的 DSL 和重复业务配置。

因此历史挑战后的裁决不是“v0.8 已经解决全部问题”，也不是“立即实现第一阶段候选”。当前最合理决定是：**否决新平台；保留一个更窄的 Bridge 原生证据合同作为有界、可否决的研究候选；没有基线和普通入口实证前，不授权实现或推广。**
