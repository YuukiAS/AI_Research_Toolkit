## 先把最重要的事情说清楚

以后正常开发时，你不需要自己运行验收命令，不需要记哪个项目该跑哪些测试，也不需要提醒 Codex“这次别忘了补验收器”。

你只提出任务，例如：

> 把 Lucerna 这个状态功能做好，并交付可用版本。

系统内部应该自动完成下面这条链：

```text
读当前任务和项目规则
→ 确定最后到底要交付什么
→ 判断这次改动影响哪些能力
→ 自动选出这次必须通过的验收
→ 缺机械验收器时，Codex 在当前任务里补上
→ 从项目/领域的正式入口运行验收
→ 专业能力判断结果
→ Bridge 核对这些结果是不是属于当前候选和当前消费对象
→ 不合格：阻止结束，在原任务内有限返修
→ 合格：只声明证据真正支持的完成层级
```

这套系统没有一个“万能总评委”。它故意把四件不同的事分开：

- **该验什么**：`workflow-core` 决定；
- **什么才算专业上合格**：项目或领域能力决定；
- **这些证据是不是当前这版产品的**：Bridge 决定；
- **任务现在能不能结束**：原有任务流程根据前面三者的结果决定。

这四层不能互相代签。

## 1. 一次真实任务到底是谁在做什么

先不要看抽象架构，直接看一个任务。

假设你说：

> 修改 Lucerna 的 provider 状态展示，修好后给我一个真正可交付的 Windows 版本。

### 第一步：当前 Codex 先读什么

Codex 先读当前任务的 Goal/Plan、项目 `AGENTS.md`、项目的 Delivery Assurance 适配文件和项目已有正式验收入口。

这里的 `AGENTS.md` 不保存“这次任务要跑哪几个验收”。它只保存长期稳定的东西，例如：

- 项目的正常开发和验收入口在哪里；
- 哪份设计/Goal/运行手册是真正权威；
- 项目有哪些特殊安全、隐私、科学和发布边界；
- Delivery Assurance 的项目适配文件在哪里。

### 第二步：workflow-core 算“这次到底要验什么”

`workflow-core` 把下面几类事实放在一起：

1. 这次任务准备声称到什么程度，例如只是源码修好，还是完整 Windows release；
2. 实际改了哪些源码、配置、依赖、生成物和验收定义；
3. 这些改动会传播到哪些真实消费对象；
4. 项目已有的验收能力；
5. 领域插件要求的最低专业验收；
6. 以前已经通过、而且现在仍然有效的证据。

它输出的是**本任务必须覆盖的验收义务**，不是“项目所有测试”。

例如这次可能需要：

- 状态传播是否正确；
- Windows 原生界面是否真的显示正确；
- 相关隐私状态是否没有被破坏；
- 如果目标是完整 release，还要覆盖安装/启动等 release 义务。

### 第三步：缺验收器时谁补

如果标准早就已经明确，只是没有一个能机械运行的回归或验收脚本，**当前 Codex 必须在同一个功能任务里自动补**。

你不需要提醒。

但是 Codex 只能补“怎么检查”，不能自己重新定义“什么才算正确”。

例如：

- “错误状态不能显示成 Available”已经是项目标准，那么 Codex 可以自动写回归；
- “什么样的 UI 才算视觉合格”如果属于 Frontend Design 的专业标准，Codex不能自己把标准改成“截图存在即可”。

### 第四步：谁真正运行验收

当前 Codex 调用项目或领域已经规定的正式入口。

机械检查可以直接由 runner 返回结果；视觉、科研、文稿等不能靠机械数字完整判断的部分，由对应领域能力按自己的正式标准判断。

例如 UI：

```text
Codex 运行真实界面/交互验收
→ 收集实际界面和交互证据
→ Frontend Design / 项目正式 UI 验收规则判断
→ 产生 PASS / FAIL / UNKNOWN
```

### 第五步：Bridge 做什么

Bridge 不看“这个界面美不美”。

它只检查：

- 这是当前任务吗；
- 是当前仓库和工作树吗；
- 是当前代码候选吗；
- 验收的是这次真正要交付的 EXE/运行实例吗；
- 验收定义有没有被换过；
- 证据有没有过期；
- 有没有拿旧版本、别的机器、别的产物的绿灯冒充当前版本。

### 第六步：Codex 想结束时发生什么

Codex 准备结束当前任务时，Stop Hook 触发。

如果必需验收缺失、失败、过期或身份不匹配，任务不能直接结束。失败会被送回**原任务、原工作树**做有限返修。

Phase 1 已经真实证明这条“准备结束 → 被拦住 → 原任务返修 → 新候选重新验 → 合格后结束”的接缝能工作。

如果全部必需证据有效，`workflow-core` 才允许报告当前真正已经证明的完成层级。

## 2. 到底谁负责什么

这里的“owner”不是新建一个后台机器人。它表示**某类事实最后由谁说了算**。

| 问题 | 最后由谁决定 | 实际谁执行 |
|---|---|---|
| 这次任务最终想交付什么 | 当前 Goal/项目权威；必要时用户 | 当前 Codex整理成任务输入 |
| 这次必须验哪些能力 | `workflow-core` | Resolver 自动计算 |
| 产品自己的业务规则 | 项目现有产品/科学权威 | Codex 按冻结规则实现 |
| 跨项目的视觉、统计、文档、医学影像等专业标准 | 对应领域插件 | Codex 调用领域正常入口 |
| 验收脚本怎么实现 | 已冻结标准的 owner 不变 | 当前 Codex 自动写/修机械 runner |
| 验收结果的专业含义 | 对应项目/领域能力 | 机械 runner 或领域判断 |
| 结果是不是当前候选 | Bridge | Bridge 机械核对 |
| 失败后任务怎么继续 | 当前已有 Lite/Reviewed/Control/CARE 等流程 | 当前 Codex/原 controller |
| 长训练、Slurm、finalizer 谁管 | 项目原有长任务 owner | CARE/Slurm/Persistent 等现有机制 |
| 中央能力发布和下游项目更新 | AI Skills Maintainer | 现有发布/更新工具 |
| 新凭据、付费、真实设备、外部发布等高影响动作 | 用户和现有授权层 | 获得授权后才执行 |

因此不会出现一个 Delivery Assurance“超级控制器”同时决定产品质量、Git、Slurm、UI 和发布。

## 3. AGENTS 到底谁负责，我需不需要管

你不需要手工维护 `AGENTS.md`。

这件事拆成“语义”和“机械定位”两部分。

### 项目语义谁负责

一个项目已有的产品/科学权威负责语义。它通常已经体现在：

- 项目 accepted design；
- 当前 Goal/Plan；
- 项目的正式规范；
- 已批准的科学/产品决定；
- `AGENTS.md` 中长期稳定的边界。

这里不是新造一个“项目 owner agent”。

### 机械整理谁负责

**当前执行任务的 Codex 负责。**

如果本次开发导致下面这些东西发生机械变化，Codex 应在同一任务里整理：

- 正常入口路径移动；
- 验收脚本改名；
- adapter 的 locator 改变；
- 已冻结类别新增一个目标；
- 重复或过时的入口说明需要合并；
- 中央 `da/1` 接口升级后，本项目需要更新定位。

### Codex 什么时候不能自己改 AGENTS

如果变化会改变下面这些含义，Codex 不能借“整理文档”自己决定：

- 产品成功标准；
- 科学阈值或估计目标；
- 用户授权范围；
- 领域最低标准；
- 安全、隐私或数据边界；
- 最终消费对象的定义。

这种情况先回真正的项目/领域权威冻结语义，再由 Codex 写回。

### 谁发现 AGENTS/adapter 已经漂了

未来的 `workflow-core` 负责在解析时发现：

- `AGENTS.md` 指向的正式入口已经不存在；
- adapter 指向的 runner 不存在；
- 新的验收相关文件完全没有被映射；
- 当前目标图和项目声明互相矛盾。

发现后不会让你手工整理。机械问题回当前 Codex 修；语义冲突才回项目权威。

所以 AGENTS 的闭环是：

```text
项目权威决定长期语义
→ Codex 自动维护机械定位
→ workflow-core 在每次解析中发现漂移
→ 机械漂移：Codex 修
→ 语义漂移：项目/领域权威先定，Codex 再写
```

## 4. 系统怎么判断“不验、局部验、扩大验、完整验”

这个决定不是 Codex凭感觉做，也不是因为“任务很大”就全部重跑。

`workflow-core` 按以下顺序判断：

```text
这次准备声称什么交付结果？
        ↓
实际改了哪些东西？
        ↓
这些改动影响哪些真实消费对象和依赖？
        ↓
哪些已有验收结果因此失效？
        ↓
剩下哪些义务还没有有效证据？
        ↓
决定本次覆盖范围
```

最终只有四种范围：

| 范围 | 什么时候用 | 真正含义 |
|---|---|---|
| 无专业交付验收 | 没有交付相关变化，也没有提高交付声明，旧证据仍完全有效 | 不为了形式制造验收 |
| 局部验收 | 改动能可靠隔离到一个目标和它的依赖闭包 | 只验受影响能力和邻近应保持能力 |
| 扩大验收 | 改到共享 schema、路由、生成器、adapter、验收定义或多个兄弟目标 | 覆盖整个受影响产品族/依赖闭包 |
| 完整覆盖 | 首次建立基线、整产品 release、安装/上线声明、跨仓聚合，或项目级影响关系无法可靠确定 | 覆盖本次承诺的全部必要义务 |

“完整覆盖”**不等于所有测试、所有机器、所有设备全部从零重跑**。

它的意思是：本次完整交付承诺的每项必要义务都必须有仍然有效的证据。

例如一个完整 Windows release 需要 UI、状态、安装等 5 类证据。如果这次只改安装器：

- 安装相关旧证据失效，要重跑；
- 与安装器无关、身份仍然一致的某些专业证据可以复用；
- 但不能因为只改一行，就只跑一个单元测试然后声称完整 release。

这解决的是两个相反的问题：既不能漏验，也不能每次无脑全量重跑。

## 5. 系统怎么知道该验哪些具体东西

每个任务先形成“必须证明的义务”，来源包括：

- Goal 明确要求；
- 本任务要声称的交付层级；
- 项目已有成功标准；
- 领域最低专业标准；
- 本次实际受影响的表面；
- 不能被这次修改破坏的已有能力。

然后 `workflow-core` 去找能够覆盖每项义务的现有验收能力。

只有完全相同的重复实例才能合并。不能为了少跑几个验收，把不同专业 owner、不同失败含义或不同消费对象的 Gate 合成一个总 PASS。

例如 Lucerna 一个完整 native release 可能同时需要：

```text
状态正确
+ 原生交互正确
+ UI 实际表面合格
+ 隐私边界没坏
+ 安装生命周期成立
```

这些可能共享一次实际运行或截图采集，但结果仍然是不同义务，不能一个“综合绿灯”全部代签。

普通小后端 bug 如果完全不影响 UI，就不会因为项目“有 UI”而强行跑 Frontend Design。

## 6. 新失败出现时，是加一个新验收器，还是加一条回归

默认**先归入已有能力**，不是每发现一个 bug 就新建一个 Gate。

系统比较六件事：

1. 验的能力是不是同一件事；
2. 需要的证据是不是同一种；
3. 正常用户入口是不是同一种语义；
4. 专业判断者是不是同一个；
5. 失败意味着什么是不是同一种；
6. 它支持的交付声明是不是同一种。

如果已有 Gate 能表达这六项，新失败只会：

- 加一条回归；
- 加固现有 validator；
- 或补一种缺失证据。

只有已有能力真的表达不了其中至少一个关键维度，才创建新 Gate。

这就是防止系统以后长成几百个同义验收器的规则。

## 7. 验收器到底怎么写，谁负责写

必须先分清两个东西：

**验收标准**回答“什么算正确”。

**验收器 runner**回答“怎样把这个标准机械执行或收集证据”。

这两者不能由同一个执行者随便一起改。

### 标准已经存在，只缺 runner

这是最常见情况。

当前 Codex 必须自动完成：

```text
读取已经冻结的标准
→ 取得定义版本和已知好/坏例
→ 写或修 runner
→ 先验证 known-bad 必须失败
→ known-good 必须通过
→ 缺关键观察必须返回 UNKNOWN
→ 再拿当前候选去验
```

用户不参与。

### 标准本身不存在

Codex不能自己发明。

- 新项目业务标准：项目权威先定；
- 跨项目视觉/统计/文档/医学影像标准：对应领域插件先定；
- 新科学 estimand、模型路线、停止条件：科学权威先定；
- 新权限、费用、数据或外部发布：用户授权。

标准一旦冻结，runner 仍由 Codex 实现。

### 开放式专业质量怎么验

不是所有 Gate 都应该硬编码成“脚本返回 0”。

例如视觉质量可以是：

```text
runner 负责打开/渲染/操作真实界面并收集完整证据
→ Frontend Design 按冻结标准判断
→ 返回 PASS / FAIL / UNKNOWN
```

科研同理：脚本负责生成 checkpoint、prediction、metrics 和可追溯证据，科学 owner 判断这些证据是否足以支持对应科学主张。

## 8. 怎么防止 Codex 为了通过而把验收器改松

这是架构里的硬边界，不靠“提醒它自觉”。

本任务开始时，必需 Gate 的**定义身份**会被冻结。

被冻结的是：

- 标准；
- 阈值；
- rubric；
- applicability；
- known-bad / known-good；
- 必要证据表面；
- 可支持的交付声明。

Codex 可以改 runner 的程序实现，但不能靠改上面这些东西让当前候选变绿。

如果验收定义真的需要修改，必须形成新定义版本并重新解析本任务。旧版本的 PASS 不能继续支持新标准。

以下做法都不允许：

- 把阈值降到当前产品刚好能过；
- 删除失败 fixture；
- 把真实安装验收改成“文件存在”；
- 把真实 UI 改成 mock/DOM 存在；
- 从 adapter 里删掉失败 Gate；
- 用当前候选自己生成 golden；
- 没证据就把产品失败写成“环境问题”。

Bridge 和 `workflow-core` 会通过定义摘要、runner 身份、fixture 身份、候选身份和结果失效规则识别这类变化。

如果产品和 runner 同时修改，两者必须分别记录身份，不能“测试也改了，所以绿了”就算完成。

## 9. 到底是谁“验收通过”

没有一个单独的人或模型拥有所有 PASS。

必须分四层：

| 层 | 它能说什么 |
|---|---|
| 项目/领域专业能力 | “这个 UI / 科研结果 / 文稿 /统计性质符合对应标准” |
| runner/collector | “我真实运行/采集到了这些观察” |
| Bridge | “这份结果确实属于当前任务、当前候选、当前消费对象，而且没过期” |
| `workflow-core` | “本任务承诺的所有必需义务都有有效结果，所以现在最多可以声明到这个交付层级” |

因此：

- 单元测试 PASS 不能直接推出“产品可交付”；
- Bridge PASS 不能推出“UI 好”；
- Frontend Design PASS 不能推出“安装包就是当前这个”；
- Slurm COMPLETED 不能推出“科研结论成立”。

只有这些结果在同一个当前交付对象上闭合，任务才可以结束。

## 10. 交付不是一个“完成/没完成”按钮

系统会区分：

- **源码已成立**：代码和局部不变量正确；
- **已经集成**：从正式集成入口工作；
- **产物已准备好**：EXE、PPTX、PDF、checkpoint、报告等最终产物通过对应质量检查；
- **已经安装**：精确产物装到指定环境并验证；
- **真实运行**：指定版本在真实宿主/部署/正式科学运行对象上工作。

高层缺证，不会把低层已经完成的工作说成失败；但低层也不能冒充高层。

例如：

> 源码和安装包都正确，但真实 Windows 机器还没有完成原生验收。

正确状态应该是“产物已准备好，真实安装/运行仍未证明”，而不是“全失败”，更不能写“全部完成”。

---

## 11. 长任务、Slurm 和断线谁管

Delivery Assurance 不接管它们。

CARE、Slurm、Persistent Run、项目 finalizer 继续做它们本来负责的事情：

```text
提交/启动
→ 排队/运行
→ checkpoint
→ 终态
→ 收集 prediction / metrics / report
```

Delivery Assurance 只记住：

- 这件长任务属于哪个当前任务；
- 当前 job/run 是哪一个；
- 结束后应该回到哪里；
- 最终应该消费哪些产物。

Hook 不轮询 Slurm，不自动重提 job，不因为 heartbeat 还在就说“任务正常完成”。

长任务结束以后，原 owner 产出终态证据，再回同一个任务完成后续验收。

## 12. 新项目第一次怎么接入

你不手工写 adapter。

第一次正式接入时：

```text
项目决定启用 Delivery Assurance
→ Codex 读取 AGENTS、正式合同、现有测试/验收入口、构建和最终消费对象
→ 自动生成最小 ADAPTER.toml 和项目 gates.toml 草案
→ 已知机械信息直接填好
→ 只有无法推导的产品/科学语义才交项目权威确认
→ workflow-core 做一次完整基线解析
→ 后续任务按实际改动选择局部/扩大/完整覆盖
```

以后下面这些机械变化也由 Codex 随任务自动更新：

- 新 target；
- runner 路径变化；
- 正常入口移动；
- 已有类别新增一个输入类型；
- 中央接口版本升级后的 locator 变化。

如果是新的产品/科学类别，先冻结新标准，再更新 adapter。

---

## 13. 中央能力更新以后，谁去改所有项目

AI Skills Maintainer 负责发起和跟踪受管适配，不让你逐仓库手工改。

中央领域描述、`workflow-core` 或公共接口发布时，Maintainer 根据正式更新影响确定哪些受管项目需要适配。

每个项目仍然单独验证实际安装/加载身份和正常入口。

中央更新完成但某些项目还没适配时，状态只能是“正在适配”，不能说“全系统完成”。

## 14. 你以前反复遇到的问题，现在分别由什么机制解决

| 以前的问题 | 现在由什么解决 |
|---|---|
| 测试全绿，但真实产品还是坏的 | 必须验真实消费对象；机械测试不能代签领域验收 |
| Codex 一直刷 fixture，没跑真实入口 | 证据真实度和 normal entry 是 Gate 的正式组成 |
| 用户成了第一 QA | USER_READY 前必须消费项目/领域自己的自检结果 |
| 修功能时根本没加回归 | 标准已存在时，Codex 同任务自动补 validator |
| 每发现一个 bug 就继续堆新规则 | 新失败优先进入已有 Gate 的回归库，六维不兼容才新建 Gate |
| Codex 把测试一起改松然后 PASS | Gate definition、runner、fixture、candidate 分离绑定，定义变更使旧结果失效 |
| 验的是 A，发布的是 B | Bridge 绑定源码、产物、安装实例、运行对象和验收结果身份 |
| 改一点东西又全部从零重跑 | `workflow-core` 按影响范围选局部/扩大/完整覆盖，并复用未失效证据 |
| 又只测一点就声称完整 release | 完整 release 要覆盖全部承诺义务，不能靠局部绿灯 |
| AGENTS 越来越乱、入口过期 | 项目语义由项目权威持有，Codex 自动维护机械 locator，解析器发现漂移 |
| 不同项目规则被硬塞进一个中央系统 | 项目规则留项目，领域标准留领域插件，Bridge 只管机械身份 |
| Slurm/长任务又出现第二个调度器 | DA 不拥有 scheduler，继续消费项目原 controller/finalizer |
| 工具/环境问题被误判成产品失败 | 产品、validator、证据、环境、权限、科学 NO_GO 分开归因 |
| 用户不断被问可以由 agent 自己解决的问题 | 只有真正 HUMAN_ONLY/授权问题才打断用户 |
| UI、PPT、论文只检查文件存在 | 对应领域 Gate 必须检查真实渲染/实际表面/内容与证据 |
| 旧候选的 PASS 被新候选继续复用 | 候选、定义、runner、fixture、环境变化都有失效规则 |

## 15. 你实际需要做什么

正常情况下只有一句：

> 做这个功能。

之后你不运行验收命令，不维护 Gate，不整理 adapter，不手工更新 AGENTS，不自己判断验收范围。

只有下面这些事情确实只能由你完成时，系统才应该停下来问你：

- 新的产品或科学方向选择；
- 输入真实账号/凭据；
- 物理设备确认；
- 私有数据授权；
- 付费、部署、删除、公开发布等高影响动作；
- 平台要求的 Hook 精确定义信任；
- 任务合同明确保留给你的最终主观接受。

即使出现这些人工动作，动作完成后也应该恢复同一任务继续验收，而不是让你自己接管后续流程。

## 16. 现在已经设计完什么，还没实现什么

### 已经设计完

架构层现在已经回答了：

- 谁负责选择验收；
- 谁负责制定标准；
- 谁写机械验收器；
- 谁判断专业质量；
- 谁核对候选身份；
- 谁决定局部/扩大/完整验收；
- 何时新建 Gate、何时只加回归；
- AGENTS 和 adapter 谁维护；
- 怎么防止执行者把验收改松；
- 多产物/跨仓库怎么绑定；
- 长任务怎么交回原 owner；
- 什么时候用户必须介入；
- 失败后回谁处理。

这些不应该再留给实现者重新设计。

### 还没实现

现在真正缺的是生产代码：

1. public `da/1` 还要从 v0.3 机械冻结成独立接口文件；
2. Bridge 的生产 Hook/身份/新鲜度/Stop 核心还没实现；
3. `workflow-core` 的影响分析、Resolver 和交付准入还没实现；
4. Frontend、统计/科研等领域描述文件还没正式生成；
5. Lucerna、CARE 等项目 adapter 还没落地；
6. 生产 Gate `DA-G10`–`DA-G15` 还没通过；
7. 正式发布和受管项目适配还没完成。

所以现在准确的状态是：

> **“谁负责什么、怎么决定验收、怎么写验收器”已经设计清楚；系统本身还没有生产化。下一阶段应该开始写这些代码，而不是继续重新讨论架构。**

## 17. 接下来真正应该怎么推进

下一步先把 public `da/1` 机械冻结。随后两条主线并行：

```text
                  ┌→ Bridge：身份、证据新鲜度、Stop/恢复
public da/1 freeze
                  └→ workflow-core：影响分析、验收选择、交付准入
                         ↓
                 领域 descriptors
                         ↓
              Lucerna + CARE 两个独立试点
                         ↓
                 第三个不同类型项目
                         ↓
                 正式发布和受管适配
```

Bridge 和 `workflow-core` 分别实现、分别验收，不能变成一个跨仓库巨型 Codex 任务。

Lucerna 和 CARE 也必须是两个独立完成对象：一个证明桌面软件/原生 UI，一个证明科研长任务/Slurm。两边都成立后，再用第三种项目检查公共层有没有偷偷写死前两个项目。
