# 交付保障：以后一个任务怎样从“做完了”变成“真的可以交付”

交付保障（Delivery Assurance）解决的是“假完成”。过去最麻烦的情况往往发生在 Codex 已经写了代码、跑了测试、生成了文件，甚至给出了完成报告之后：桌面程序没有经过真实宿主，网站没有验证部署后的页面，训练任务结束却没有可靠的检查点和预测结果，PPT 或报告只确认“文件存在”却没有检查最终成品，或者测试和实现一起被改松以后全部变绿。交付保障的目标，就是让这些情况不能再直接进入“完成”。

以后正常使用时，你仍然只需要提出产品或科研任务。比如“把 Lucerna 这个功能做好”“把 CUHK_Date 这个流程修到可以上线”“完成 CARE 这轮训练并给我可信的结论”。系统负责判断这次需要检查哪些能力、哪些旧证据还能继续使用、是否需要补新的自动检查、应该做局部验收还是完整验收，并把所有结果绑定到当前这版产品和最终交付物。你不需要记验收清单，也不需要提醒 Codex 加测试、整理证据或维护项目接入配置。

这套机制把几种完全不同的责任分开了。`workflow-core` 负责回答“这次必须证明什么”；项目规则和领域插件负责回答“怎样才算专业上合格”；当前 Codex 负责实现、补检查程序、运行正式入口和返修；Bridge Kit 负责确认这些结果确实属于当前任务、当前版本和真正要交付的对象；原来的 Lite、Reviewed、Control、Persistent Run 等流程继续负责任务推进、等待、恢复和预算。这样可以避免一张单元测试绿灯、一份截图、一个 Slurm 终态或一个文件哈希独自宣布整个任务完成。

现在还不能把它当成已经上线的系统。Stop Hook 的关键接缝已经用真实运行证明：Codex 准备结束时可以被拦住，在原任务和原工作树中做有限返修，再对新版本重新检查。完整架构也已经通过独立审查。接下来仍要真正实现 Bridge Kit 的生产核心、`workflow-core` 的验收选择与准入、领域验收描述，以及 Lucerna、CARE 等项目的实际接入。你现在要判断这套设计是否值得进入实现；系统当前还不能直接使用。

## 谁负责什么

| 组成部分 | 负责什么 | 你可以把它理解成什么 |
|---|---|---|
| 当前 Codex | 实现功能；自动维护本次任务带来的机械变化；标准已经明确时补回归和检查程序；运行正式验收入口；整理证据；在原授权内返修 | 干活的人 |
| `workflow-core` | 根据任务目标、实际改动、依赖关系、最终交付对象和已有证据，决定这次必须验哪些能力、覆盖多大范围，以及最多可以宣布完成到哪一步 | 验收选择和交付准入 |
| 项目自己的仓库 | 保存项目自己的产品/科研规则、最终交付对象、正式入口、项目接入配置和项目特有参数 | 这个项目自己的事实来源 |
| 各领域插件 | 保存跨项目可复用的专业标准，例如界面、演示文稿、科研写作、统计建模、医学影像等如何判断质量 | 专业评判规则 |
| Bridge Kit | 核对任务、仓库、工作树、当前版本、最终交付对象和验收结果的身份与新鲜度；在任务结束前执行拦截和有限恢复 | 防止“验的是 A，交的是 B” |
| Lite / Reviewed / Control / Persistent Run | 继续负责原来的任务推进、审查、预算、等待、恢复和长任务寿命 | 原有任务控制流程 |
| AI Skills Maintainer | 负责中央能力正式发布后的更新影响、受管项目适配和发布收口 | 中央能力发布与下游更新 |
| 用户 | 决定无法从现有合同推导的产品/科研选择，并授权真实账号、私有数据、付费、部署、物理设备等高影响动作 | 真正需要人拍板的地方 |

这张表里有一个关键边界：专业质量由专业能力判断，Bridge Kit 只检查身份和新鲜度；任务能否继续由原来的任务流程决定，交付保障不会再造第二套任务状态机。

## GPT Work 到底补了什么

GPT Work 的作用很具体：它把此前 v0.2 里仍然可能让实现者临场猜的地方逐项找出来，再补成确定规则。原来的大方向已经有了，但“到底怎么发现验收能力、怎么判断影响范围、什么时候可以复用旧证据、怎样防止 Codex 自己把测试改松、多产物怎么绑定、完整验收到底是什么意思”这些地方还不够闭合。GPT Work 主要补的是这些缺口。

它先重新检查了全部需求和历史失败。83 条需求全部有对应机制；7 个真实项目中的 363 条历史记录也逐条归类。这 363 条包含历史失败、风险、重复根因和工具误判，不能把它们当成 363 个今天仍然存在的缺陷。最终没有变成 363 个验收项，而是收敛成 26 类可以跨项目复用的专业能力和 9 类控制责任。363 条记录里，80 条主要属于任务控制、身份、权限或恢复，226 条应该进入已有验收能力的回归库，15 条属于“标准已经有，但缺检查程序”，37 条需要加固已有检查程序，4 条当时环境暂时无法运行，1 条确实需要人工参与。这个结果说明，大多数历史问题的根因在于已有标准没有被真正消费、证据强度不足，或者任务控制和专业验收混在了一起。

GPT Work 还补了几项对实现很关键的规则。能力发现不再依赖平台并未承诺的自定义插件字段，而是从实际已安装、已启用的插件位置读取固定验收描述，再结合项目自己的接入配置。影响分析也不再只看“这次改了哪些文件”，而是看从批准基线到当前版本的全部实际变化、下游依赖、最终交付对象和应该保持不变的能力。这样可以挡住“代码只改一行，所以只测一行”这种过度简化。

证据也被拆得更细。系统要分别记录“实际观察到了什么”“这个观察离真实使用有多近”“是谁做出的观察”。例如，真实 Windows 程序配模拟 Zotero 后端，可以证明一部分原生行为，但不能证明真实 Zotero 往返；真实页面截图也不能自动证明页面交互和数据链路都成立。这个区分直接解决了过去大量“看起来是真实验收，其实只验证了半条链”的问题。

GPT Work 还把“新增一种验收能力”与“给已有能力加回归”分开。判断时比较六件事：要验证的能力、需要的证据、正常入口、专业判断者、失败含义、能支持的交付范围。已有能力能够完整表达时，只增加回归、加固检查程序或补证据；只有这些关键维度真的出现新语义时，才新增验收类别。这样可以控制复杂度，避免每个缺陷都长出一种新的验收类别。

对旧证据的复用也有了明确规则。产品或最终交付对象变化，会让受影响目标的旧证据失效；标准变化后，如果原始观察仍然可靠，有时可以重新判断而不用重新采集；负责采集证据的程序本身有问题，就必须重新采集；环境发生变化时，只能复用与新环境仍然等价的证据。完整验收因此不需要每次从零跑所有机器，但也不能继续吃已经失效的旧绿灯。

最重要的一项补强是防止“自己出题、自己降标准、自己通过”。验收标准、验收程序、测试样本、当前产品和原始观察分别绑定。当前 Codex 可以修检查程序的代码，却不能为了让当前版本变绿而降低阈值、删除坏例、缩小适用范围、把真实安装换成文件存在、把真实界面换成模拟页面，或者从项目接入配置里删除失败的验收项。标准真的要变，就进入新的标准版本，原来的通过结果随之重新评估。

GPT Work 还把源码、构建物、安装包、已安装实例、部署、数据、训练检查点、预测结果和报告分开绑定，避免一个“候选版本”概念把所有东西混在一起。它同时明确了长任务继续由 CARE、Slurm、Persistent Run 和现有终态收集程序管理，交付保障只消费结果和恢复定位，不再造第二个调度器。

这轮研究本身也保留了证据边界。它确认“架构职责是否完整”和“83/363 是否都被覆盖”这两件事，但没有把自己包装成严格盲、严格独立的一致性证明，因为此前审计建议已经进入过同一研究上下文，当时也没有真正运行生产版验收解析器。后来由独立 Critic 对 v0.3 直接审查，才把正式架构权威冻结下来。这个历史事实仍然保留，不需要改写成 GPT Work 自己完成了最终封板。

## 一次任务从开始到结束，实际会发生什么

假设你说：“把 Lucerna 的状态展示修好，并给我一个真正可以交付的 Windows 版本。”

第一步，当前 Codex 读取任务目标、项目 `AGENTS.md`、项目正式规范、项目接入配置和已有验收入口。它先确定你最终要拿到什么。这里“修一段内部逻辑”和“交付完整 Windows 版本”对应的验收范围不同。

第二步，`workflow-core` 查看从批准基线到当前版本的全部实际变化，再沿项目的依赖关系追到最终交付物。它同时检查哪些旧证据仍然有效。比如只改安装器时，安装相关证据通常失效；一个与安装器完全无关、绑定仍然一致的界面证据可能继续使用。

第三步，`workflow-core` 把本次任务要证明的事情列出来，再与项目和领域已有能力对应。Lucerna 的完整 Windows 交付可能需要状态传播、原生交互、实际界面、隐私边界和安装生命周期。一个完全隔离的后端缺陷不会因为项目“也有界面”就强迫你跑完整界面验收。

第四步，如果某项标准已经明确，但缺一个可运行的自动检查，当前 Codex 同任务补上。例如明确知道“错误状态不能显示为 Available”，却没有回归测试，就由 Codex 写回归。这里不用问你。

第五步，Codex 从正式入口运行这些检查。机械检查直接产出观察结果；界面、科研、统计、文稿等需要专业判断的部分，把真实产物交给对应领域能力判断。缺少关键证据时，结果必须是“无法判断”，不能因为没有看到明显错误就写成通过。

第六步，Bridge Kit 核对这些结果到底属于谁：是不是当前任务、当前工作树、当前代码、当前 EXE、当前部署、当前检查点或当前报告；标准是否发生过变化；证据是否已经过期。它只做这类机械核对，不重新判断界面美不美、统计推断对不对。

第七步，Codex 准备结束任务时，Stop Hook 读取本次必须完成的验收。如果仍有失败、缺证、过期证据或身份不一致，就阻止结束，并把具体问题送回原任务返修。返修以后产生新版本，再检查受影响部分。

第八步，所有必需结果都成立后，`workflow-core` 才给出当前最多可以宣布到什么程度：源码成立、已经集成、产物可以交付、已经安装，或者已经在真实环境运行。原来的任务控制流程据此结束任务。

## 怎么决定局部验收还是完整验收

系统先判断这次交付承诺需要覆盖多大范围；测试数量只是最后执行量的结果。

| 实际范围 | 什么时候使用 | 你应该怎么理解 |
|---|---|---|
| 无额外专业验收 | 没有交付相关变化，没有提高交付声明，已有证据仍然完整有效 | 不为了仪式感再跑一遍专业验收 |
| 局部验收 | 改动能够可靠隔离到一个目标和它的依赖范围 | 验这个功能、已知坏例以及邻近不能退化的行为 |
| 扩大验收 | 改到共享数据结构、路由、生成器、项目接入配置、验收定义或多个兄弟目标 | 覆盖整个受影响产品族 |
| 完整验收 | 首次建立基线、准备完整发布、安装/上线、跨仓库整合，或影响范围无法可靠拆开 | 本次完整交付承诺的每项必要能力都要有有效证据 |

完整验收允许复用没有失效的证据。比如只改 Lucerna 安装器的一处配置，但这次准备交付完整 Windows 版本，安装相关部分要重新验证；与这次变化无关、身份仍然一致的界面或其他专业证据可以继续使用。完整验收要求完整覆盖，执行上仍然只补跑缺失或失效的部分。

再看两个不同例子。CUHK_Date 如果只修一个完全隔离的后台边界条件，而且最终只准备交付这个局部修复，通常做局部验收；如果修改了注册和交接流程共用的认证或数据结构，就会扩大到多个兄弟流程。CARE 如果只修一个不会改变科学结果的日志格式，不需要重新训练；如果改了训练器、数据处理、恢复训练语义或科学估计目标，就必须沿受影响链重新证明检查点、预测、指标和结论。

旧证据能不能复用也有明确边界。标准只改了判分规则，而原始观察仍然完整可靠，可以重新判断；采集证据的程序有缺陷，就要重新采集；产品、环境或最终交付对象变了，就按影响关系使相应旧结果失效。这样既能避免重复劳动，也能挡住旧绿灯长期漂移。

## 验收标准和验收程序怎么产生

先分清两件事。“什么算正确”是验收标准；“怎样实际检查”是验收程序。

项目特有的产品行为由项目自己的正式规则决定。跨项目通用的视觉、文稿、统计、医学影像等专业要求由对应领域插件决定。科研任务中的估计目标、模型假设、路线晋级和停止条件由项目及领域科学规则决定。权限、费用、真实数据和外部发布继续由用户和现有授权层决定。

标准已经存在、只缺检查程序时，当前 Codex 自动补。一个合格检查程序至少要经历三种情况：已经确认的坏例必须失败；已经确认的正确例必须通过；关键证据缺失时必须返回“无法判断”。这三步成立后，它才有资格检查当前版本。

例如，一个状态缺陷的坏例是“断开后仍显示在线”，正确例是“断开后进入离线状态”。检查程序首先证明自己能分开这两个情况，再去检查当前版本。界面验收如果需要真实 Windows 原生界面，但当前只拿到模拟页面，就只能写“无法判断”；CARE 如果只知道 Slurm 作业已经结束，却没有检查点、预测结果和指标，也只能写“无法判断”。

出现全新的产品或科研标准时，Codex 不能自己发明。项目特有的新行为由项目负责人确定；跨项目专业标准由对应领域负责人确定；科学估计目标或路线判断由科学负责人确定。标准确定后，Codex 再负责机械实现。

一个项目本地的验收能力也不会因为“看起来通用”就立刻进入中央插件。至少要有两个真实项目证明它们在验证能力、所需证据、正常入口、专业判断者、失败含义和支持的交付范围上确实一致，并且两边都完成接入验证，才考虑提升成中央能力。

如果项目标准和领域标准发生冲突，同一事项只保留一个真正有决定权的来源。项目特有业务语义回项目负责人，跨项目专业最低标准回领域负责人，科学标准回科学负责人。系统不会投票，也不会自行挑“更严格”“更便宜”或“当前能跑”的那个版本。

## 怎么防止 Codex 改松验收让自己通过

这件事靠结构约束，不靠一句“不要作弊”。

任务开始时，当前需要的验收标准会绑定具体版本，包括阈值、适用范围、坏例、正确例、必要证据和能够支持的交付结论。验收程序、测试样本、产品版本和原始观察分别记录自己的身份。

Codex 可以修验收程序的实现，但下面这些行为不能直接产生可信通过：降低阈值、删除坏例、缩小适用范围、把真实安装换成“文件存在”、把真实界面换成模拟页面、把真实第三方往返换成假后端、从项目接入配置里删掉失败的验收项，或者用当前产品自己生成一个只对自己有利的“标准答案”。

标准真的需要改变时，要形成新的标准版本并由真正负责这项语义的一方确认。旧标准下的通过结果随后按失效规则处理。产品代码和测试代码同时变化，也必须分别记录，不能因为两边一起变绿就自动宣布任务完成。

另外，哈希、新会话、文件存在和单元测试通过都只是辅助事实。它们可以帮助证明“这是哪个对象”，但不能代替专业观察。需要真实界面时就看真实界面，需要真实 Zotero 往返时就跑真实往返，需要科学结果时就看检查点、预测、指标和报告。

## 谁运行验收，谁判断专业上通过

当前 Codex 负责调用正式入口和收集证据。专业判断由对应领域承担。

界面质量由 Frontend Design 或项目已经批准的界面验收规则判断。Codex 负责打开、渲染和操作实际界面；如果项目要求独立审阅，就继续使用已有独立审阅流程。Bridge Kit 不给界面打分。

统计方法由 Statistical Modeling 和项目自己的统计/科研合同判断，包括估计目标、假设、诊断、敏感性分析和结论边界。程序可以计算指标，但“程序顺利退出”不能代替统计判断。

科研结论由项目和对应领域的科学规则判断。CARE 的 Slurm 作业完成以后，还要分别确认检查点、预测、指标、恢复一致性和最终科学解释。科学结果支持“这条路线不值得继续”时，这可以是合格的负结论；系统不会为了拿到一个正结果而强迫继续训练。

用户面对的文稿、README、论文说明或报告如果属于本次交付物，则由 Research Authoring / Clear Writing 等正式写作能力承担相应质量检查；演示文稿的最终渲染质量由 Presentations 等对应能力负责。这里同样不能用“文件生成成功”代替成品质量。

Bridge Kit 最后只核对：这些专业结果是否属于当前任务、当前版本、当前环境和当前最终交付对象，验收定义有没有变化，证据是否仍然新鲜。它不会重新做视觉、统计或科学判断。

## AGENTS.md 谁负责，怎么保证它不会越写越乱

你不需要手工维护 `AGENTS.md`。

`AGENTS.md` 保存长期稳定的项目入口和边界：正常开发和验收从哪里进，哪份设计或运行手册是权威，项目有哪些特殊安全、隐私、科研和发布边界，项目接入配置在哪里。每次任务临时选了哪些验收项、当前通过还是失败，不应该写进这里。

里面的“语义”由项目自己的正式规则决定。产品成功标准、科学阈值、统计估计目标、安全边界、最终交付对象和用户授权，都来自项目现有设计、任务目标、规范和已经批准的决定。当前 Codex 不能借整理文档自行改这些内容。

日常机械整理由当前任务的 Codex 负责。验收脚本改名、目录移动、项目接入配置中的路径变化、正常入口变化、已有类别新增一个目标、重复或过时的定位信息需要合并，这些都应该随当前任务一起更新。中央接口升级后，由 AI Skills Maintainer 发起受管适配任务，再由对应项目的 Codex 更新机械定位。

`workflow-core` 在解析任务时负责发现漂移。比如 `AGENTS.md` 指向的正式入口已经不存在，项目接入配置引用了不存在的验收程序，或者新的验收相关代码完全没有被映射，这些情况都不能静默变成“无需验收”。路径和定位问题交给 Codex 修；真正涉及产品或科研语义的冲突，才回到项目或领域负责人。

所以这条链很明确：项目规则决定长期语义，Codex 自动维护机械内容，`workflow-core` 持续发现不一致，AI Skills Maintainer 负责中央升级后的受管适配。用户不承担日常维护。

## 多产物、跨仓库和长任务怎么避免半完成

交付保障会把真正被消费的对象分开跟踪。源码、构建物、安装包、已安装实例、部署服务、数据集、训练检查点、预测结果、报告或文档都可以是不同的交付对象。

因此，源码测试通过只能证明源码层面。任务如果要交付 Windows 安装包，还要有针对那个精确安装包和安装后实例的证据。网站本地测试通过，也不能代替真实部署后的页面、接口和身份检查。

CARE 这类科研任务里，Slurm 作业完成只说明作业生命周期到了终态。检查点、预测结果、指标和科学报告必须分别与当前代码、数据和作业绑定。任何一项缺失，都只能限制在已经证明的层级，不能把整个任务写成“科研完成”。

跨仓库任务也一样。前端仓库和后端仓库各自通过，只能说明两边各自成立。如果接口版本、数据结构或真实调用没有被观察，就不能声明集成完成。跨仓库交付需要额外证明两边的当前版本真的兼容并实际连通。

长任务继续由原来的运行机制持有。Slurm、CARE 的现有任务控制流程、Persistent Run 和项目终态收集程序负责排队、运行、等待、检查点和终态。交付保障只记住这件长任务属于哪个当前任务、当前作业是谁、结束后要消费哪些结果、应该回到哪里恢复。

如果 Codex 或 SSH 断开，已经由 Slurm 或 Persistent Run 持有的工作继续运行。作业结束后，原有收集程序生成检查点、预测、指标等结果，再恢复同一个任务完成剩余验收。交付保障不会持续轮询 Slurm，也不会自动重复提交、取消或重训作业。

## 新项目第一次接入怎么办

你不需要自己写项目接入配置、验收列表或验收程序。

第一次接入时，Codex 读取项目 `AGENTS.md`、正式规范、现有测试和验收入口、构建方式以及用户最终会拿到什么，然后自动生成最小的项目接入配置和项目专属验收能力草案。能够从仓库机械确定的路径、脚本、构建物、目标关系和正常入口直接填好。

真正需要项目负责人确认的是无法从现有材料可靠推导的业务或科研语义，例如“哪个对象才是正式交付物”“项目特有状态怎样才算正确”“某个科研阈值是否确实是当前任务的标准”。涉及真实账号、设备、数据、费用或部署权限时，仍然走现有授权。

首次接入会建立一次完整基线，让系统知道这个项目有哪些交付对象和验收能力。以后正常任务再根据实际变化选择局部、扩大或完整验收。路径、正常入口、已有类别目标或验收程序变化，由 Codex 随任务自动维护；中央 `workflow-core` 或领域能力升级时，由 AI Skills Maintainer 发起和跟踪受管项目更新。

## 过去那些具体失败，这套设计怎么挡

下面这张表直接对应此前反复出现的问题。

| 过去的失败 | 现在靠什么挡住 |
|---|---|
| 单元测试和构建全绿，但真实产品仍然不可用 | 最终完成必须消费真实交付对象和对应专业验收，机械测试只证明它能证明的那一层 |
| Codex 一直刷测试样本或模拟数据，真实入口一直没跑 | 验收描述明确要求正常入口和证据真实度；模拟数据只能支持相应较低层级 |
| 开发到后期还在假数据、假后端、假页面 | 最终声明绑定真实环境和真实消费对象；模拟证据不能升级成真实部署、真实第三方或真实科学结果 |
| 为了赶进度偷偷做低配实现 | 冻结目标、领域标准和最终消费对象一起进入验收；与这些标准不一致的降级实现不能靠局部测试宣布完成 |
| Codex 修改测试或阈值，让当前实现刚好通过 | 标准、检查程序、测试样本、产品和原始观察分开绑定；标准变化会使旧通过结果失效 |
| 修了缺陷，却没有补回归 | 标准已经明确时，当前 Codex 同任务自动补回归或验收程序 |
| 每发现一个缺陷就继续新增一条中央规则 | 优先归入已有专业能力；只有六个关键维度出现新语义才新增验收类别 |
| 改一点东西就把全部机器和测试从头跑一遍 | 按真实影响范围选择局部、扩大或完整覆盖，并复用仍然有效的旧证据 |
| 反过来只跑一点就宣布整个产品发布完成 | 完整发布必须覆盖全部承诺义务，局部绿灯只能支持局部结论 |
| 验的是旧版本，最后交的是另一个版本 | Bridge Kit 绑定任务、代码、构建物、安装实例、运行对象和验收结果身份 |
| 源码过了，但安装包、部署或真实宿主没验 | 各交付对象分别记录完成层级，高层没有证据就不能冒充完成 |
| Slurm 作业结束就被写成科研完成 | 作业终态与检查点、预测、指标、报告和科学结论分开验 |
| 两个仓库各自通过就被写成集成成功 | 必须有当前两边版本的真实兼容和连通证据 |
| AGENTS.md 越来越乱，入口和真实仓库不一致 | Codex 自动维护机械内容，`workflow-core` 发现漂移，语义变化才回项目负责人 |
| 用户自己变成第一轮验收人员 | 项目和领域自己的验收先完成，最终交付前必须消费这些结果 |
| README、报告、PPT 或中文说明“文件有了”但质量很差 | 对应 Research Authoring、Clear Writing、Presentations 等领域验收检查最终成品，文件存在只算机械事实 |
| 环境坏了却被写成产品失败，或者产品失败被甩锅给环境 | 产品缺陷、验收程序问题、证据缺口、环境问题、权限问题和科学负结果分开归因 |
| 同一范围内不停回来问用户是否继续 | 能由现有规则推导和自动修复的事情继续处理；只有新的目标选择、真实授权或必须人工完成的动作才打断用户 |

这里也有一个边界必须保留：交付保障只能执行已经存在或已经被冻结的产品/科研标准。一个从未在项目规则、领域标准或当前任务里定义过的产品选择，它不能凭空猜出来。遇到这种真正的新语义，必须先由相应负责人确定标准，再继续自动化。

## 七个真实项目分别会怎么用

现有研究已经用 7 个项目检查这套架构是否只适合一种软件。

| 项目 | 交付保障重点检查什么 |
|---|---|
| Lucerna | 产品状态是否真实、Windows 原生交互、实际界面、隐私边界、安装和生命周期 |
| Bobbio | 数据隔离、安装、Zotero 原生批注往返、状态、性能和实际界面；当前里程碑状态来源冲突在项目接入前仍需先冻结唯一权威 |
| Mica | 真实宿主适配、性能、实际界面、导出内容与来源保真；真实登录态仍按项目权限边界处理 |
| SeminarArc | Android 安装包、持久化、真实媒体处理、文档输出、界面、压力恢复和真机能力 |
| Asteria | 科学图本身是否正确、几何和量测是否可靠、整图科学可读性、界面状态以及真实部署 |
| CUHK_Date | 注册关键路径、一次性交接、身份隔离、隐私、真实内容、界面和部署后的实际页面 |
| CARE | 正式训练入口、参数和数据机制、实验规模与总体充分性、检查点/预测/指标证据、恢复训练一致性和科学结论 |

这些项目不会把自己的规则写死进中央解析器。它们通过各自项目接入配置绑定到同一套公共接口。项目之间可以共享专业能力和机械框架，但每个项目的真实入口、阈值、设备、URL、数据和最终交付对象仍由项目自己定义。

## 作为用户，以后正常要做什么

正常情况下，你只给任务本身。

你不需要自己决定该跑哪些验收，不需要选择局部还是完整验收，不需要提醒 Codex 给新缺陷加回归，不需要维护验收程序清单，不需要整理证据，不需要自己写项目接入配置，也不需要手工维护 `AGENTS.md`。长任务已经交给 Slurm、CARE 或 Persistent Run 后，你也不需要因为 Codex 会话断开就持续盯着。

系统真正应该回来问你的情况很有限：出现新的产品方向或科研取舍；需要真实账号或凭据；需要物理设备确认；需要使用私有数据；需要付费、部署、删除、公开发布等高影响动作；或者当前任务明确把最终主观接受保留给你。

用户完成这些必要动作以后，系统继续恢复原任务完成剩余验收，不应该把后半段流程转交给你手工完成。

## 现在完成到哪一步，以及是否值得继续推进

已经证明的部分包括：在 `codex-cli 0.160.1` 的受测环境中，受信任的项目级 Stop Hook 可以在 Codex 准备结束时拦住不合格候选，在同一任务和工作树里做一次有限返修，对新版本重新检查，并处理用户中断、重复/并发事件、错误身份、旧证据和权限不扩张等边界。这个实验只证明关键接缝可行。

已经设计并通过独立审查的部分包括：谁决定验什么、谁定义专业标准、谁自动补检查程序、谁核对版本身份、怎样选择验收范围、怎样处理标准冲突、怎样复用或使旧证据失效、多产物和跨仓库如何绑定、AGENTS 和项目接入如何维护、长任务如何回到原流程、用户什么时候才需要介入。这些职责已经冻结，实施阶段不应该重新发明。

还没有实现的部分包括：公共 `da/1` 接口的独立冻结文件；Bridge Kit 的生产 Hook、身份、新鲜度、拦截和恢复核心；`workflow-core` 的影响分析、验收选择和交付准入；领域插件的正式验收描述；Lucerna、CARE 等项目的真实项目接入；生产阶段的 `DA-G10`–`DA-G15`；最后的中央发布和受管项目适配。当前架构通过不等于系统已经可用，也没有自动授权 Windows、Slurm/GPU、真实账号、付费、项目修改或正式发布。

基于已经完成的研究和独立审查，这套设计已经有足够信息进入下一阶段。合理的推进范围是：先机械冻结公共 `da/1` 接口，然后分别准备 Bridge Kit 与 `workflow-core` 的独立实现包；公共接口稳定后并行准备领域验收描述；再用 Lucerna 和 CARE 做两个性质不同的真实接入，并用第三种项目检查公共层是否存在过度特化。每个实现包仍然单独接受规划、独立审查和能力验收。这里的“推进”指进入受控实现；正式发布仍然要等实施验证完成。

如果后续真实实现证明关键假设不成立，例如正常入口根本无法强制、项目接入无法可靠覆盖真实目标、专业观察无法建立，或者这套机制带来的成本明显高于它减少的返工，那么相应能力应当收缩。正式架构允许现实证据推翻实现假设，不能因为设计文档已经写全就强行投产。
