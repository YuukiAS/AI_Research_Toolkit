# Delivery Assurance：以后开发任务怎样从“做完了”变成“真的可以交付”

Delivery Assurance 要解决的不是“再多跑一些测试”，而是一个更具体的问题：Codex 很容易在代码能编译、单元测试变绿、作业跑完或文件生成之后就说任务完成，但这些现象并不等于用户真正要用的东西已经可靠。桌面软件可能测试全绿却打不开真实流程，网站可能接口通过却没有完成真实部署，科研训练可能作业结束却没有可靠的检查点和结果，PPT 或论文也可能文件存在却没有经过最终成品检查。Delivery Assurance 的作用，就是在任务准备结束时，把这些“看起来完成”与“真正可交付”区分开。

以后正常使用时，你不应该自己管理这套验收。你仍然只需要提出任务，例如“把 Lucerna 这个功能做好”“完成 CARE 这轮训练并给我可信结果”“把网站这个功能做到可以上线”。系统负责判断这次需要检查什么、哪些旧证据还能用、是否要补新的自动检查、应该检查局部还是完整交付，并把结果和当前这版产品绑定起来。只有遇到新的产品或科研取舍、真实账号或凭据、物理设备、私有数据、付费、部署、删除、公开发布等确实需要你的决定或授权的事情，才应该回来问你。

这套系统也不是一个新的中央平台。它把职责分开：`workflow-core` 负责决定这次必须证明什么；项目自己的规则和领域插件负责定义什么才算专业上合格；当前 Codex 负责实现功能、补自动检查并运行它们；Bridge Kit 负责确认这些验收结果确实属于当前任务、当前版本和最终交付对象；Lite、Reviewed、Control、Persistent Run 等原有流程继续负责原来的任务生命周期和恢复；AI Skills Maintainer 负责中央能力发布后把需要的更新送到各项目。没有任何一层可以拿自己的“通过”替代其他层。

现在的状态也必须分清。Stop Hook 已经通过真实实验，证明 Codex 准备结束时可以被拦住、在原任务里做一次有限返修，然后对新版本重新检查。完整的生产架构也已经通过独立审查。但这些只说明“机制和职责已经设计清楚”，不说明系统已经可以直接使用。Bridge Kit 的生产核心、`workflow-core` 的验收选择逻辑、领域验收描述和 Lucerna/CARE 等项目接入仍然要真正实现和验证。

## GPT Work 到底补了什么

GPT Work 不是又做了一遍同样的架构，也不是只补了几条文字。它真正做的是：**把 v0.2 里“方向大致对，但很多关键地方仍可能让实现者自己猜”的部分逐项找出来，并改成可以落地的确定规则。** 这一步很重要，因为 Delivery Assurance 最怕的就是表面上说“要真实验收”，实现时却仍然可以通过换标准、漏对象、拿旧证据或只跑局部测试来绕过去。

它先做了两件全量核查。第一，把此前 83 条需求全部重新对应到架构机制；第二，把 7 个真实项目里累计的 363 条历史失败和风险逐条归类。结果不是造 363 个验收项，而是收敛成 26 类可复用的专业能力和 9 类不应该被误当成专业验收的控制责任。363 条里，80 条主要是任务控制、身份、权限、恢复等问题，226 条属于已有验收能力应该补回归，15 条是标准已经有但缺验收程序，37 条是已有验收程序不够可靠，4 条当时环境暂时不可运行，1 条确实需要人工参与。这个结果说明：过去大量问题并不是“还缺一种全新的 Gate”，而是已有标准没有被真正消费、证据太弱，或者控制层和专业验收混在了一起。

更具体地说，GPT Work 对原方案补了这些关键机制：

| 原方案里容易出问题的地方 | GPT Work 补上的东西 | 为什么重要 |
|---|---|---|
| 只知道“有很多历史问题”，但覆盖不完整 | 把 83 条需求、363 条历史登记逐条映射，并纠正旧的 286/363 覆盖误判 | 防止架构看起来完整，其实漏掉一批真实失败 |
| 能力发现曾依赖并不存在的自定义插件清单字段 | 改成从实际已安装、已启用的插件根目录读取固定支持文件，再结合项目接入配置 | 不再依赖平台没有承诺的字段 |
| 证据只有一个粗糙“类型” | 拆成“看到了什么”“真实到什么程度”“是谁观察的”三部分 | 能区分真实程序配模拟后端、真实设备、独立审阅等不同强度，避免假升级 |
| 影响分析可能只看当前文件差异 | 改成从批准基线到当前版本的全部实际变化，再加项目目标、依赖关系和应保持能力一起判断 | 防止已提交改动、配置、生成物或下游影响被漏掉 |
| 不清楚什么时候复用旧验收、什么时候新建验收项 | 固定成六个方面比较：验证什么、需要什么证据、从哪里验、谁判断、失败意味着什么、能支持什么交付结论 | 防止一个 bug 一个新 Gate，也防止把本来不同的能力硬合并 |
| “完整验收”容易被理解成全部重跑 | 明确完整验收是“本次完整交付承诺的每项义务都有有效证据”，允许复用未失效证据 | 同时避免漏验和无脑全量重跑 |
| 一个验收项只有一个结果文件，容易不同机器/目标互相覆盖 | 每次运行按验收定义、目标、环境和入口形成独立实例 | 防止 Windows A 的绿灯覆盖 Windows B，或旧版本覆盖新版本 |
| Codex 既改产品又改测试，容易自己放宽标准 | 把验收标准、验收程序、测试样本、当前产品和原始观察分开绑定；标准变化会使旧结果失效 | 直接堵住“产品和测试一起改到绿”的假完成 |
| 旧证据什么时候还能用不够明确 | 分开处理“标准变了”“验收程序变了”“产品变了”“环境变了”等情况 | 只重跑真正失效的部分，也不误吃旧绿灯 |
| 源码、安装包、运行实例、模型结果和报告容易混成一个“候选” | 建立明确的交付对象关系：源码、构建物、安装包、安装实例、部署、数据、检查点、预测、报告分别绑定 | 防止“源码过了=安装包过了”“作业完成=科研结果过了” |
| 新项目怎么接、以后谁维护不够清楚 | 固定为 Codex 先自动生成最小项目接入配置，项目负责人只确认无法推导的业务/科研语义；中央更新由 AI Skills Maintainer 发起受管适配 | 你不需要自己写 adapter 或逐仓库维护 |
| “完成”还是一个过于粗糙的全局状态 | 区分源码成立、已经集成、产物可交付、已经安装、真实运行等不同层级 | 高层缺证不会抹掉低层成果，但低层也不能冒充完整交付 |
| 长任务容易被 Delivery Assurance 再接管一次 | 明确 Slurm、CARE、Persistent Run、现有 finalizer 继续拥有运行寿命，Delivery Assurance 只消费结果和恢复定位 | 不再造第二个调度器 |
| 整体职责以前还不够闭合 | 写成 22 行完整交接表：每一步谁决定、谁执行、输入什么、输出什么、失败交给谁、什么时候需要用户 | 让实现者不能在真正动手时再临场决定职责 |

GPT Work 还补了一条很重要的“反作弊”原则：**哈希、另一个会话、单元测试绿灯、文件存在，都不能自动证明专业验收可信。** 如果要求的是实际 Windows 界面，就必须看到对应实际界面；如果要求的是真实 Zotero 往返，就不能拿模拟接口替代；如果要求的是科研结论，就不能拿 Slurm 作业完成或日志存在替代。

同时，GPT Work 没有把自己的研究结果说得比事实更强。它确认了“架构职责是否完整”和“83/363 是否都被覆盖”这两件事，但它没有声称自己完成了严格盲、严格独立的一致性证明，因为前面的审计建议已经进入过同一研究上下文，而且当时也没有真正运行生产版 Resolver。这个方法学缺口后来由独立 Critic 对 v0.3 直接审查来关闭，而不是把 GPT Work 自己那次失败硬改成 PASS。

因此，GPT Work 对整套 Delivery Assurance 的价值可以概括成一句话：**它把原来“方向对”的方案，补成了“实现时不应该再由 Codex 自己猜标准、猜责任、猜验收范围”的方案。** 现在正文后面讲到的验收范围、验收程序、防放宽标准、多产物绑定、新项目接入、长任务边界等，很多关键细节都是这一轮 GPT Work 补齐的。

## 谁负责什么

| 组成部分 | 负责什么 | 明确不负责什么 |
|---|---|---|
| 当前 Codex | 实现当前功能；维护因本次改动而变化的路径和接入信息；在标准已经明确时自动补回归和验收程序；运行正式验收入口；整理证据；在原授权内返修 | 不能为了通过而自己降低标准、改阈值、删坏例、换成更弱证据，也不能自行扩大权限 |
| `workflow-core` | 根据当前任务目标、实际改动、依赖关系、最终交付对象和已有证据，决定这次要验哪些能力、验到多大范围，以及最后最多可以声明完成到什么程度 | 不定义界面好不好、统计方法对不对、科研结论是否成立，也不替用户授权高影响操作 |
| 项目自己的仓库 | 保存这个项目自己的产品/科研规则、最终交付对象、正式验收入口、项目接入配置和项目特有参数 | 不复制整套中央系统，也不能通过项目配置删掉已经生效的领域最低标准 |
| 各领域插件 | 保存跨项目可复用的专业标准，例如界面、演示文稿、科研写作、统计建模、医学影像等应该怎样验 | 不管理 Git、工作树、会话、任务状态或 Slurm 作业 |
| Bridge Kit | 核对任务、仓库、工作树、当前版本、最终交付对象和验收结果的身份与新鲜度；在任务准备结束时执行拦截和有限恢复 | 不评价界面审美、统计推断、科研结论或文稿质量，不成为第二个 Slurm 调度器 |
| Lite / Reviewed / Control / Persistent Run | 继续负责它们原来承担的任务推进、审查、预算、等待、恢复和长任务寿命 | Delivery Assurance 不重新建一套任务状态或第二个“完成”按钮 |
| AI Skills Maintainer | 负责中央 `workflow-core` 和领域能力正式发布后的更新影响、受管项目适配和发布收口 | 不替某个项目宣布真实机器已经验收通过，也不替领域插件决定专业标准 |
| 用户 | 决定无法从现有合同推导的产品/科研选择，并授权真实账号、私有数据、付费、部署、物理设备等高影响动作 | 不维护验收清单，不写项目接入配置，不提醒 Codex 加测试，也不手工整理 AGENTS.md |

## 一次真实开发任务里，系统怎样决定要不要验、验什么、验多少

假设你说：“把 Lucerna 的状态展示修好，并给我一个真正可以交付的 Windows 版本。”

系统不会先查一张固定测试清单。它先看这次任务最终要交付什么。如果你只要求修好一段内部逻辑，所需证明会比较窄；如果你要求“完整可交付的 Windows 版本”，那么安装、启动、实际界面、状态传播以及任务明确要求的其他能力都可能成为必须证明的内容。

接着，它看从任务开始时批准的基线到当前版本究竟改了什么，以及这些变化会影响哪些最终对象。这里不仅包括刚刚修改的文件，也包括已经提交的改动、配置、依赖、生成物、验收定义和受影响的下游对象。然后再看哪些旧证据仍然有效：如果某个界面验收绑定的是同一个未受影响的界面和同一个仍有效的产品版本，它可以复用；如果安装器、运行环境或验收标准已经变化，相关旧证据就必须作废。

最后，`workflow-core` 把“这次必须证明的事情”和项目、领域现有的验收能力对应起来。比如 Lucerna 的完整交付可能需要证明状态传播、原生交互、实际界面、隐私边界和安装生命周期；CARE 的科研任务则可能需要证明正式训练入口、检查点、预测结果、指标、恢复一致性和科学结论。它只选择与本任务真正相关的能力，不会因为项目里“还有 UI”就强迫一个纯后端修复去跑界面验收。

如果项目自己的标准和领域标准发生冲突，系统不能自己挑一个“更严格”或“当前更容易执行”的版本。谁对这项语义真正负责，谁来裁决：项目特有的产品行为由项目规则负责，跨项目专业最低标准由对应领域能力负责，科学估计目标和模型判断由科学规则负责，权限和高影响操作由用户和现有授权层负责。在冲突没有解决前，只能诚实限制可声明的完成程度，不能选一个方便的标准继续往前。

### 局部验收、扩大验收和完整验收有什么区别

这里判断的是“本次交付承诺需要覆盖多大的范围”，不是“跑多少条测试”。

**无需额外专业验收**，适用于没有交付相关变化、没有提高交付声明，而且已有证据仍然完整有效的情况。普通必要检查仍然可以有，但不会为了形式再造一轮专业验收。

**局部验收**，适用于改动可以可靠隔离到一个目标和它的依赖范围。例如一个局部后端 bug，不改变共享数据结构、路由、生成器、项目接入配置，也不影响界面，那么只需要对这个功能、对应坏例和邻近不应退化的行为做检查。

**扩大验收**，适用于改动碰到多个兄弟功能共同依赖的部分。例如修改一个被多个页面共用的状态解析逻辑，虽然改动只有几行，但影响不止一个界面，就需要覆盖受影响的整个产品族，而不能只验最初报错的页面。

**完整验收**，适用于第一次建立项目基线、准备声明完整产品可交付、安装或上线、跨仓库整合，或者当前影响范围根本无法可靠拆开的时候。完整验收的意思是“这次完整交付所承诺的每一项必要能力都必须有有效证据”，**不是每次把所有测试、所有机器、所有设备从头跑一遍**。没有被本次变化影响、而且身份和有效期仍然满足要求的旧证据可以复用。

三个例子可以把区别说清：

- 修一个完全隔离的后端边界条件，只准备交付这个局部修复：通常是局部验收。
- 修改一个被多个界面共享的状态或数据结构：即使代码量很小，也可能需要扩大验收，因为兄弟功能都可能受影响。
- 只改了 Windows 安装器的一处配置，但这次要声明“整个 Lucerna Windows 版本可以正式交付”：仍然需要完整覆盖这次发布的全部承诺；不过没有失效的界面、功能等证据可以复用，不需要机械重跑所有东西。

## 验收标准和验收程序到底是谁写、怎么工作

这里必须把“什么算正确”和“怎样检查”分开。

验收标准回答“什么才算合格”。项目特有的业务行为由项目自己的正式规则决定；跨项目通用的视觉、文稿、统计、医学影像等专业要求由对应领域插件决定；科研任务中的估计目标、模型假设、路线晋级或停止条件由项目和领域的科学规则决定；权限、费用、真实数据、部署等边界由用户和现有授权层决定。

验收程序回答“怎样把已经确定的标准实际检查出来”。如果标准早就已经存在，只是缺一个可运行的检查程序，那么**当前做功能的 Codex 必须在同一个任务里自动补上**，不需要你提醒。例如，一个确定性 bug 已经明确了错误行为和正确行为，却没有回归测试，Codex 应该补回归；一个已有输入类别新增了具体场景，也应该补相应检查。

如果连“什么才算正确”都还没有定义，Codex 就不能自行发明标准。新的项目业务要求先由项目规则确定；新的跨项目专业标准先由对应领域插件确定；新的科学判断先由科学规则确定。标准确定后，Codex 再负责把可以机械化的部分实现出来。

一个项目本地的验收能力也不会因为“看起来挺通用”就立刻塞进中央插件。只有至少两个真实项目证明这项能力在要验证的能力、所需证据、正常入口、负责判断的人、失败含义和支持的交付范围上确实一致，并且两个项目都完成了适配验证，才考虑把它提升为中央领域能力。这样可以避免把某个项目的私有规则误当成全局标准。

### 一个验收程序应该怎样证明自己不是摆设

先拿一个已经确认的坏例。验收程序必须把它识别为失败；如果坏例也能通过，这个验收程序没有资格给当前产品背书。

再拿一个已经确认的正确例。验收程序必须让它通过；如果正确例被拒绝，说明验收程序自身可能有问题，不能逼着产品去适应错误的验收程序。

还要有一种情况：关键证据根本没有拿到。此时正确答案必须是“无法判断”，而不是“通过”。比如界面验收要求实际原生界面，但这次只拿到了模拟后端截图；科研验收要求预测结果和指标，但只知道 Slurm 作业结束了。缺少关键观察时，系统必须承认没有证明，而不能因为“没看到失败”就给绿灯。

只有上面这些基本校准成立后，验收程序才对当前版本运行。当前版本如果通过，结果还必须记录它检查的是哪个产品、哪个环境、哪份标准和哪次实际观察，之后 Bridge Kit 才能判断这份证据能不能用于当前任务。

### 为什么实现功能的 Codex 不能顺手把标准改松

因为标准、验收程序、测试样本、当前产品和最终证据会分别绑定。Codex 可以修验收程序的实现，但不能为了当前版本变绿，顺手降低阈值、删除坏例、缩小适用范围、把真实安装换成“文件存在”、把真实界面换成模拟页面，或者从项目接入配置里删掉失败的验收项。

如果验收标准确实需要改变，就必须形成新的标准版本并由真正负责这项语义的一方确认。旧标准下得到的通过结果不能直接拿来支持新标准。这样，“产品代码和测试一起改了，所以现在全绿”不会自动等于任务完成。

## 谁运行验收，谁最终判断“通过”

当前 Codex 负责调用正式入口和收集证据，但不同类型的专业结果由不同的正式能力判断。

界面好不好，不由 Bridge Kit 判断。当前 Codex 负责打开、渲染或操作真实界面并收集证据，Frontend Design 或项目已经批准的界面验收规则负责判断视觉、交互和状态是否合格。如果项目要求独立审阅，继续使用项目已有的独立审阅流程，而不是新造一个 Delivery Assurance 审阅角色。

统计方法对不对，也不由 Bridge Kit 判断。统计建模领域能力和项目自己的统计/科研合同负责估计目标、假设、诊断、敏感性分析和结论边界。机械脚本可以算数字、检查结构，但不能用“程序返回 0”代替统计判断。

科研结论是否成立，由项目和对应领域的科学规则判断。CARE 的 Slurm 作业显示完成，只能说明作业生命周期到了终态；是否产生了正确检查点、预测结果、指标，证据是否充分，以及结论是否支持路线晋级或停止，都要由 CARE 自己的科学合同和领域判断继续完成。科学结果如果支持“这条路线不行”，这可以是一个合格的负结论，而不是必须继续训练到成功。

Bridge Kit 只判断另一类问题：这些专业结果是不是属于当前任务、当前版本、当前机器或环境、当前最终交付对象，标准有没有变、证据有没有过期。它不重新给界面打分，也不重新做统计推断。

最后，`workflow-core` 检查本任务要求的所有验收是否都有有效结果，并计算“目前最多能声明完成到什么程度”。原来的 Lite、Reviewed、Control 等任务流程再据此决定当前任务是否可以合法结束。任何一层的“通过”都不能替代其他层。

## AGENTS.md 谁负责，项目以后怎么自动维护

你不需要手工维护 `AGENTS.md`。

`AGENTS.md` 里应该放长期稳定的项目入口和边界，例如正常开发/验收入口在哪里、哪份设计或运行手册是权威、项目有哪些特殊安全和科研边界、项目接入配置在哪里。它不应该保存每次任务临时选择了哪些验收项，也不应该变成第二套任务状态记录。

“里面应该写什么”由项目自己的正式规则决定。也就是说，产品行为、科学标准、安全边界和真正的交付对象来自项目现有设计、Goal、规范和已经批准的决定，不由当前 Codex 临时发明。

日常机械整理由当前执行任务的 Codex 负责。如果验收脚本改名、目录移动、项目接入配置中的路径变化、已有类别新增目标、重复定位信息需要整理，这些都属于当前任务的一部分，Codex 应该一起更新。中央接口升级后，需要更新项目定位信息，也应由受管适配任务自动完成。

Codex 可以自动修改路径、入口、机械定位和已经冻结类别下的配置；它不能借整理 `AGENTS.md` 改产品成功标准、科学阈值、统计估计目标、领域最低标准、用户授权、安全/隐私边界或最终消费对象。出现这些变化时，先由对应项目或领域规则确定新语义，再让 Codex 写回。

系统还必须能够发现 `AGENTS.md` 已经过时。例如它指向的正式入口已经不存在，项目接入配置引用了不存在的验收程序，或者出现了新的验收相关改动却完全没有映射。这些都不能被静默当成“无需验收”。机械漂移交给 Codex 修；真正的语义冲突才交给项目负责人或领域负责人判断。

## 多产物、跨仓库和长任务怎样避免“半完成”

Delivery Assurance 不把一个任务压成一个简单的“通过/失败”。它会分别跟踪源码、构建物、安装包、已安装实例、部署服务、数据、训练检查点、预测结果、报告等真正被消费的对象。

因此，源码测试通过并不能自动证明安装包也通过。如果任务要交付一个 Windows 安装包，就必须有针对那个精确安装包和安装后实例的证据；源码层面的通过最多只能说明源码层已经成立。

科研长任务也是一样。Slurm 作业完成，只能说明作业结束；检查点、预测结果、指标和科学报告是不同的交付对象，必须分别有与当前作业和当前代码绑定的证据。不能拿“作业 COMPLETED”代替“科学结果可靠”。

跨仓库任务也不能把“两边各自绿了”当成已经集成。例如一个后端仓库和前端仓库各自测试都通过，但接口版本、数据结构或真实调用没有验证，这仍然不能声明集成完成。跨仓库交付必须额外证明双方实际兼容、真实连接，并且对应的是当前要交付的两边版本。

### 长任务不会被 Delivery Assurance 接管

Slurm、CARE 的现有任务控制流程、Persistent Run 和项目已有的终态收集程序继续管理长任务。Delivery Assurance 只记录“这件长任务属于哪个当前任务、现在由谁继续、结束后应该消费哪些结果、应该回到哪里恢复”。

如果 Codex 或 SSH 断开，已经由 Slurm 或 Persistent Run 持有的工作继续按原机制运行，不需要一个新的 Delivery Assurance 守护进程持续轮询。作业终态后，原有收集程序生成检查点、预测、指标等结果，再恢复同一个任务，重新检查这些结果是否属于当前版本并完成剩余验收。

所以 Delivery Assurance 不会成为第二个 Slurm 调度器，也不会自动重复提交、取消或重训作业。

## 新项目第一次接入时，我要不要自己写配置和验收器

不用。

第一次启用时，Codex 应先读取项目的 `AGENTS.md`、正式规范、现有测试和验收入口、构建方式以及最终用户真正会拿到什么，然后自动生成最小的项目接入配置和项目专属验收能力草案。已经可以从仓库机械确定的路径、脚本、构建物和目标关系直接填好，不应该拿来问你。

项目负责人只需要确认无法从现有材料可靠推导的业务或科研语义，例如“哪个对象才是正式交付物”“某个项目特有状态到底怎样才算正确”“这个科研阈值是不是任务真正采用的标准”。如果涉及新的账号、设备、数据、费用或部署权限，则仍然按现有授权规则问你。

首次接入需要建立一次完整基线，因为系统要知道这个项目有哪些交付对象和验收能力。以后正常任务再根据实际改动选择局部、扩大或完整验收，不会每次重新做首次接入。

后续如果只是路径、正常入口、已有类别目标或验收程序变化，Codex 随任务自动维护；如果中央 `workflow-core` 或领域能力升级，AI Skills Maintainer 负责发起和跟踪需要更新的受管项目，不让你逐仓库手工改。

## 作为用户，我以后还需要做什么

正常情况下，你只需要给出产品或科研任务本身。

你不需要：

- 自己决定该跑哪些验收；
- 自己选择局部还是完整验收；
- 提醒 Codex 给新 bug 加回归；
- 自己维护验收程序清单；
- 自己整理证据；
- 自己写项目接入配置；
- 自己维护 `AGENTS.md`；
- 因为长任务在等待就持续盯着它。

真正应该回来问你的，是现有合同无法替你决定的事情：新的产品方向或科研取舍、真实账号或凭据、物理设备确认、私有数据使用、付费、部署、删除、公开发布等高影响动作，以及任务本来就明确保留给你的最终主观接受。用户完成这些动作后，系统也应该恢复同一个任务继续验收，而不是把后续工作甩给你。

## 现在完成到哪一步

### 已经证明或设计完成

已经有真实证据证明：在受测的 `codex-cli 0.160.1` 环境中，受信任的项目级 Stop Hook 可以在 Codex 准备结束时发现不合格结果，阻止结束，在同一会话和工作树里进行一次有限返修，对修复后的新版本重新检查，并在证据新鲜且合格后正常结束。中断、重复事件、错误身份、旧证据和权限不扩张等边界也在这一阶段做过验证。

生产架构本身也已经通过独立审查。谁负责选择验收、谁制定专业标准、谁补验收程序、谁核对版本身份、怎样决定局部或完整验收、怎样处理长任务和项目接入，这些职责已经冻结，不应该在实现阶段重新发明。

### 还没有实现

系统现在还不能因为这份设计通过就直接投入使用。下面这些仍是生产实现工作：

- 把公共 `da/1` 接口从已批准架构中机械冻结成独立接口文件；
- 在 Bridge Kit 中实现生产级 Hook、版本身份、新鲜度、拦截和恢复核心；
- 在 `workflow-core` 中实现影响分析、验收选择和交付准入；
- 给需要的领域插件生成正式验收描述；
- 给 Lucerna、CARE 等项目建立真实项目接入配置并接到现有验收入口；
- 完成生产阶段仍未验证的 `DA-G10`–`DA-G15`；
- 最后完成中央发布和受管项目适配。

### 下一步真正要做什么

先冻结公共 `da/1` 接口。随后 Bridge Kit 和 `workflow-core` 分成两个独立实现任务并行推进：前者负责“证据是不是当前版本的、什么时候拦住结束”，后者负责“这次到底该验什么、最多能声明完成到哪里”。公共接口稳定后，各领域插件可以并行准备自己的验收描述。然后用 Lucerna 和 CARE 做两个性质不同的真实项目接入，再用第三种项目检查公共层有没有只适配前两个项目。最后才进入正式发布和受管项目更新。

因此，现在最准确的判断是：

> Delivery Assurance 的职责和工作方式已经设计清楚，关键 Stop Hook 接缝也有真实证据；但生产系统本身还没有实现。下一阶段应该开始冻结公共接口并分别实现 Bridge Kit、`workflow-core` 和真实项目接入，而不是把“架构通过”当成“系统已经可用”。
