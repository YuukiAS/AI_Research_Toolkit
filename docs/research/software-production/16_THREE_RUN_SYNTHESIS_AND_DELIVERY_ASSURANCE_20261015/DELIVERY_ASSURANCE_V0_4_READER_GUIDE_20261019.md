# 交付保障 v0.4：这套架构为什么能落地

## 现在改了什么

v0.3 的问题不是公共方向错了，而是只把通用规则写完整，没有把七个真实项目逐一接到这些规则上。这样一来，项目真正实施时仍可能临场决定“最终验什么、从哪里验、谁负责、缺哪条证据算不算完成”。v0.4 把这部分补齐了。

现在每个项目都有一条明确的交付链：从源码和任务目标开始，经过项目现有的构建、运行、验收和专业判断，最后绑定到用户真正拿到的程序、安装包、部署页面、训练结果或报告。Delivery Assurance 不替项目重新造验收器，只负责确保本次任务选中了该选的入口、结果属于当前候选、缺证据时没有越级宣布完成。

## 用户以后需要做什么

正常情况下，用户仍然只说“做这个功能”。

系统自行完成以下事情：

1. 确定最终要交付的是源码、构建物、安装后的程序、在线服务、训练结果还是完整产品；
2. 看这次实际改动会影响哪些对象；
3. 从项目和领域已有能力中选择最小但充分的验收；
4. 标准已经明确但缺自动检查时，由当前 Codex 同任务补上；
5. 从项目正式入口运行检查；
6. 失败时回原任务返修，不新建任务洗掉预算或历史；
7. 只对证据真正支持的层级报告完成。

只有真实账号、私有数据、物理设备、不可逆发布、付费操作、无法推导的产品/科学选择或最终主观接受才打断用户。用户不负责维护 Gate、adapter、`AGENTS.md`、路径清单或测试脚本。

## 谁负责整理 AGENTS

这次已经明确：

- 项目 owner 决定 `AGENTS.md` 应表达哪些长期规则；
- `workflow-core` 判断当前任务是否触发整理；
- 当前任务的 Codex 调用 Project Instructions Editor 0.3 完成整理和提交；
- PIE 0.3 读取当前 root/nested AGENTS、项目正式合同和 adapter，生成可读修改预览、完整新版本、权威来源表和覆盖报告；
- Bridge 只检查执行时到底加载了哪份 AGENTS 和 mandatory source，不负责写内容；
- AI Skills Maintainer 负责 PIE 0.3 的中央发布和下游适配。

所以不是“谁碰到顺手整理”，也不是“用户发现乱了再提醒”。项目语义属于项目 owner，机械整理属于 Executor + PIE，加载身份属于 Bridge。

`AGENTS.md` 只保留未来任务在行动前必须知道的稳定内容，例如正常入口、权威来源、权限边界、验收 locator 和长期不变量。详细 Gate rubric、全部历史失败、当前任务状态和会频繁变化的版本清单继续放在各自正式文件中，避免 AGENTS 无限膨胀。

## 为什么 adapter 不能漏掉验收

项目 adapter 不是一张可以自由删减的 Gate 清单。最终义务是以下几部分的并集：

```text
领域最低标准
+ 项目正式合同
+ 当前任务目标
+ 实际改动影响
+ 不应被破坏的能力
```

adapter 只能增加项目义务、绑定具体参数和真实对象，不能删除领域最低标准。未映射但可能影响验收的改动必须标成“无法判断”，再扩大到受影响的依赖范围，不能因为没有匹配规则就变成“不需要验收”。

每个项目都要做故意漏项的负例：删除一个必需 Gate、目标、nested AGENTS 或 authority locator，普通任务入口必须拒绝 `USER_READY`。这比检查配置文件“字段齐全”更重要，因为它直接证明漏一项时系统不会假完成。

## Gate 多了会不会每次全部跑

不会。范围分为四档：

- 没有影响真实产品/产物/科研表面，也没有提高交付声明：不额外跑专业 Gate；
- 改动能稳定隔离在一个目标和依赖闭包内：只跑局部 Gate；
- 改了共享状态、路由、schema、生成器、adapter 或 validator 定义：跑受影响产品族；
- 首次接入、整个产品发布、安装/在线整体声明、跨仓整体完成或无法安全拆分的多产物：做完整义务覆盖。

完整覆盖不等于所有测试、设备和机器从零重跑。没有失效的旧证据可以复用。Gate 数量多、代码多或任务看起来复杂，都不是全量条件。

## 七个项目分别怎么工作

### Lucerna

系统把源码、Windows EXE、PID、native UI、provider 状态和独立审查绑定起来。fixture、旧截图、错误 PID 或 Producer 自评都不能代替 fresh native review。用户只在真实 OS 动作或最终产品接受时介入。

### Bobbio

系统绑定开发 branch、milestone、Windows Reader、隔离 Zotero profile/data、PDF hash 和真实 annotation 往返。0.2.0 已接受证据不能直接证明 0.3.0。当前 milestone 文档漂移会先返回权威冲突，而不是任意挑一份文件。

### Mica

系统区分 synthetic fixture、隔离浏览器、真实登录态 ChatGPT 和低功耗设备。自动流程完成 build、E2E、版本和诊断；真实账户/设备只留下最后一次边界清晰的人工观察。用户不再被要求打开 DevTools 找普通问题。

### SeminarArc

系统绑定源码、APK、签名、安装实例、Room/文件、可见流程和导出物。Emulator 可以证明安装和大部分用户路径，但不能代签真实麦克风、相机和厂商后台行为。设备不可用只冻结硬件声明，不阻断其余开发。

### Asteria

系统把科学图真值、浏览器几何、整体可读性和固定公网部署分开判断。实现与 validator 同轮修改时，必须保留旧标准对照和真实坏例，不能靠新测试全绿自签。它被选为首个低成本纵向接入，用于尽早验证公共链路。

### CUHK_Date

系统分别绑定源码、staging Web/API、数据库、campaign、一次性票据、persona 和最终报告。producer rehearsal 与 final batch 必须完全分离。完整 staging 验收仍不能自动授权真实 Matching。

### CARE

系统绑定代码、配置、数据划分、Slurm job、checkpoint、prediction、metric、aggregation、validator 和科学结论。Slurm 终态只证明运行结束，不证明科学完成。Delivery Assurance 不提交或取消作业，只消费 CARE controller/finalizer 的结果。

## 为什么这不是一个新的中央大系统

公共层只做三件机械工作：

- `workflow-core` 选出本任务必须证明的义务；
- Bridge 核对任务、候选、最终对象和证据身份；
- adapter 把项目已有入口和通用能力对应起来。

真正的 UI、科学、统计、PPT、论文、设备和产品质量仍由对应项目和领域能力判断。长任务仍由 CARE、Slurm、Persistent Run 等现有 owner 管理。没有新数据库、常驻服务、中央 Gate registry、第四工作流或第二任务状态机。

## 为什么不会因为下一个简单问题又推翻架构

v0.4 不只回答“谁选 Gate”，还逐项回答了谁维护 `AGENTS.md`、adapter、validator、locator、权威文件、证据、claim、长任务和正式发布；也明确了标准冲突、环境缺口、旧证据、partial completion 和用户介入怎样处理。

此外，七个仓库都冻结了：

- 最终消费对象；
- 正常入口；
- 唯一负责人；
- 已有验收器；
- 正向完成链；
- 最高风险负向链；
- 同任务恢复路径；
- 人工边界；
- 声明上限；
- 漏项变异测试。

以后若有人问“这个项目谁整理规则”“漏了一个 target 怎么办”“旧 milestone 能不能继续用”“真机没测能不能说完成”，答案已经在合同中，不需要重新设计整个系统。只有真实 repo 事实与合同直接冲突时，才对具体字段返修。

## 现在还没有完成什么

这仍是设计候选，不是生产系统。尚未完成：

- v0.4 独立 Critic 审查；
- 公共 `da/1` 接口冻结；
- Bridge、`workflow-core`、PIE 0.3 和领域描述的实现；
- 七仓 adapter 实际写入和正常入口验收；
- 正式 release 与下游机器适配。

因此当前正确状态是：架构返修已经形成，可以送独立 Critic；不能交给 Codex 开始生产实现，也不能称 Delivery Assurance 已上线。
