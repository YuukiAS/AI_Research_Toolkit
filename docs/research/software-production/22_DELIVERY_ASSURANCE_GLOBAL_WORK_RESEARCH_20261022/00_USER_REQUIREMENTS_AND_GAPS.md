
# Delivery Assurance：完整架构研究的用户承诺与当前缺口

**性质：研究输入，不是架构冻结、Critic 批准或生产实现。** 必须与上一轮第 21 号文件中的 36 项职责、315 个具体问题和反例共同使用。本说明来自本次连续对话的用户直接纠正，禁止将单一 Mathpix 示例误当成全部产品范围。

## 1. 用户真正要求的结果

用户主要时间应该用于决定要做什么，而不是充当验收器设计人员、回归检测员、运行日志解读员、Codex 返修调度员和多仓库维护者。普通功能指令应能在实际受支持的日常入口自然进入既定工作流，不要求每次手工设置 Goal、写执行提示词、补充“检查旧功能”或呼叫某个 Skill。真正必须人工决策的产品/科学选择以及账号、设备、费用、数据和发布权限仍然保留。

正式目标同时包括：完整的非降级实现、已有能力不退化、真实最终产物可用、有界持续返修、合理的运行成本、可恢复的任务状态、正常使用体验，以及中央能力长期更新后七仓继续正确工作。该目标不等于“验收器越多越好”。

## 2. 历史对话暴露的设计和沟通失败

- 曾多次以抽象“组件负责什么”“由 workflow-core 选择”“Codex 会收到失败”为答案，却答不出哪个真实代码入口调用、输入输出在哪里、谁读取并消费、失败怎样回活跃执行者；必须用真实调用链替代抽象职责图。
- 曾把普通无 Goal 的 Codex 对话从完整自动保障中排除，再说“只需一句功能请求”；必须正面研究日常入口的真实支持条件与尽可能低摩擦的解决方式，不得靠缩小承诺假装成功。
- 曾把 Bridge Stop 一次续修、Lucerna 最多三轮独立审查、Review/Control 自有预算混为一谈；必须分别核对真实代码和合法恢复权威，不新造竞争循环。
- 曾现场为 Mathpix 编写一次性的验收例子；研究必须先给一般性架构，再对至少三种异质产物深入演绎，对全部七仓分别具体落地。Mathpix 是反例之一，不是整套架构的中心。
- 还没有完整解释验收程序从何而来、何时发现缺失、如何按标准自动创建、如何证明验收程序本身正确、何时运行、如何把失败交还给原任务、如何修改/关闭/退休，以及每轮向用户报告新增和已运行的检查。
- 还没有证明项目配置之外的旧功能会被自动保护，也没有证明错用测试模拟、过时截图、未加载插件或过期证据时，所有日常入口能阻止假完成。
- 多轮版本的文档和覆盖矩阵不能替代真实工程证据；以前的 83 条要求、363 条历史登记、26 类能力及 36 项职责/315 个问题只是核对输入，不能说“覆盖”就代表问题已解决。
- 用户希望像 CAT-TRACE 零槽位方法的解释：先具体说明现实困难、旧方法为什么失败、每一项数学/系统变换解决什么、举数值或运行反例证明差异、哪些边界仍未证明，而不是堆状态字段和架构术语。

## 3. 组件的最低可解释标准

每个必要组件必须回答：要阻止哪件真实历史事故；为什么现有代码挡不住；现有功能是否可以直接复用；首次接入与普通任务由哪个实际函数触发；接收什么输入、从哪里读到、生成什么结果；下一段真实代码从哪读取结果；缺少标准/程序/环境/权限分别怎样表现；正例、已知坏例和应保持不变的旧功能怎样通过同一正常入口检验；后续怎么修复、回滚、升级或退休；用户每轮最终能少做什么。这些是组件解释要求，不代表应创建同等数量的新模块。

必须先画一张适当颗粒度的**整体真实运行架构**，按用户任务生命周期逐步讲出各部件之间的因果链，再对每个组件给实际源码例子。不接受 36 个目录名代替架构，不接受选一个漂亮样例代签七仓。

## 4. 必须覆盖的用户可见任务报告

每次普通任务完成时，先说明功能是否真的在声明环境可用、旧功能的受影响检查是否成立和是否仍需用户动作。随后明确列出：

- 新增了哪些验收器，各自保护什么、在哪里维护；
- 哪些已有验收器新增回归、加固或复用；
- 本轮实际执行了哪些验收、基于哪个最终候选、结果和原始证据在哪里；
- 哪些合法未执行或复用旧证据，理由是什么；失败和未证实项不得被隐藏；
- 哪些验收器被修改、禁用、合并或退休，由哪项标准授权、原有保护如何保持；
- 没有新增验收器时，应说明“本轮没有新增，因为已有类别覆盖/该任务无需新增”，不是省略这部分；
- 本轮可自动修的缺陷是否已经修好，若停止，最后合法恢复入口在哪里。

这份汇报必须由真实任务及验收结果生成，不让用户手工维护清单。

## 5. 七仓及工具的审查范围

七个真实消费者：Lucerna、Bobbio、Mica-for-ChatGPT、SeminarArc、Asteria、CUHK_Date、CARE_Challenge。两个核心基础设施：AI_Skills_Collection、GPT_Codex_AI_Bridge_Kit。研究承载仓库为 AI_Research_Toolkit。方法解释对照参考 CAT-TRACE 的 2026-10-21 zero-slot 说明。

此前已有的项目原生测试、领域插件、Bridge Lite/Review/Control、独立原生/黑盒审查、CARE/Slurm 控制器都应先查当前运行机制和可复用性。任何新中央服务、数据库、状态机、任务控制器或万能评分器必须正面证明不存在成熟且更简单的替代。

## 6. 用户授权和本轮边界

允许在 AI_Research_Toolkit 的既有研究分支、约定研究目录内写入逐阶段设计文档和索引。禁止在这次 GPT Work 研究中直接修改 Bridge、AI Skills 或七仓生产源；禁止启动真实账号、私有数据上传、部署、付费、GPU/Slurm、物理设备及正式发布。设计成熟后另按现行 Planner–Critic 合同独立审查及单包获权实施。

必须将 GitHub 实际写入权限和写后回读放在 GPT Work 第一个动作；写不进去直接停并报告精准原因，不得退化成只有本地文件或聊天文字。每完成一阶段就持久化真实进度、源码引用、决定和未解决问题。独立审查尚未发生时不得声称 PASS、可交 Codex 实施或七仓生产可用。
