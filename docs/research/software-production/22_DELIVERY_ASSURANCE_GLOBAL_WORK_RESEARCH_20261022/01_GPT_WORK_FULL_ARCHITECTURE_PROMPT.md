## 3. 不预设当前方案正确：先调查现实，再做架构取舍

首先用 GitHub 当前源码建立真实能力/缺口图：明确哪些函数和脚本存在、哪些只在设计文档里、哪些是未实现设想、哪些功能已由各仓成熟程序实现。研究至少比较三条路线：(A) 仅强化既有项目和 Bridge 正常入口；(B) 保留并精简 Delivery Assurance 的通用选择/交付准入层；(C) 在确有证据时采用其它成熟执行或专业验收能力。允许提出更优组合；不得为了复用旧提案保留没有真实价值的部件。

比较时不仅看架构概念，还要看：用户少操作多少、需要新增哪些运行调用、所有正常宿主是否能触发、失败是否能真正自动恢复、错误放行风险、维护成本、首轮接入成本、每任务成本、Git/权限边界与跨仓更新。既不能为了万无一失全部变成重型流程，也不能退化成依靠模型自觉执行几句提示词。

在调研后**先交一份可读的整体候选架构**：一张标明具体既有执行入口和数据流向的总图（可用 Mermaid），一个普通任务正向链及一个坏候选的失败—自动修复链。解释与旧方案相比删除、复用、重构、新增了什么组件，各自阻止哪个实际失败；不要求 36 项职责变成 36 个组件。先把这份初步架构写入 GitHub，再用后续核查迭代。

## 4. 每个真实组件必须交出“可运行的机制说明”

无论最终归为多少组件，必须逐项按照以下要求写明，不能以“符合合同”代替：

- 组件存在理由：一个七仓历史事故的具体场景，旧执行路径为什么失败，为什么项目已有成熟能力仍不够。
- 责任边界：哪个仓库拥有源码和标准，哪个真实进程/现有执行角色执行，谁可修改，是否与 Bridge/领域插件/项目控制器重叠。
- 触发：哪个普通用户消息、启动函数、钩子事件或具体代码变化使该组件运行。列出现存函数名和拟新增调用位置，区分已验证事实与设计提案。
- 输入输出：来自哪份实际任务、规则、状态、数据、目标图或运行对象；输出文件/结果的字段、来源、版本和位置；接下来哪个函数/角色具体读取并消费。必须给一条可追踪的消息和证据实例。
- 判断方法：关键分支的规则或算法、代价、必要前提、不确定时的安全处理。缺少任务包、标准、程序、设备、权限、插件或证据分别怎么办。
- 三种反例：应成功的真实正例、必须失败的已知坏实现/错误证据、不应受本轮修改影响的旧功能；说明同一正式入口为何会给不同结果。
- 失败与恢复：谁接收完整失败内容、怎样在原任务继续、已有轮次/预算怎样消费、用户何时确实需要介入。
- 生命周期：新增、更新、版本迁移、合并、停止使用、退出/回滚、影响消费者和旧回归；每次任务怎样自动生成面向用户的变更报告。
- 实施与可证伪性：最小代码改动、复用程序、运行/维护开销、实际可否决试点，以及目前尚未直接验证的平台能力。

若一个组件无法说明“哪个真实代码接收上一步的输出并启动下一步”，即使有正确的接口类型或 PASS 表，也必须标为架构缺口。

## 5. 验收器是贯穿案例，必须回答完整生命周期，但不能成为整套架构的唯一主题

明确通用专业标准、项目专业标准、测试程序、回归样本、真实观察者、运行器和任务验收结果是不同对象。至少完整解决：

- 初次接入时从哪里找到当前正式要求、已有验收程序和旧功能；如何不让用户编写清单。
- 每轮任务哪个具体调用点比较用户新要求、真实代码影响与现有覆盖，何时复用已有类别、补回归、加固现有程序或确实新增一类验收。
- 标准已经明确但程序缺失时，哪个现有入口向当前 Codex 传递怎样的具体工作项；Codex 如何获取原始合同和输入、写在哪里、回报哪个执行结果；新标准不明确时如何回唯一专业负责人。
- 新验收程序怎样用已知好例、历史坏例和关键证据缺失例校准；如何防止固定样本、实现与阈值同改、假截图、错误采集器和自我签字。
- 代码变更/目标关系/发布时间决定哪些验收现在要跑；如何说明局部、扩展和完整范围，怎样复用真正未失效的旧证据。
- 验收结果具体怎样被下一个程序读取，怎样路由产品缺陷、程序缺陷、证据缺失、环境障碍、权限需求与真实科学负结论；如何同任务修复、重新运行受影响检查和独立审查。
- 维护者或用户以后要调整、临时停用、永久退休、合并/拆分某一验收能力时找谁，如何防止关掉它便把旧保护一同删除。
- 每轮功能交付的中文报告必须说明：本轮新增的验收器及各自保护的能力、加固/复用的旧验收器、实际执行的清单及结果、合法没运行或复用旧证据的理由、修改/关闭事项、仍未证明范围。没有新增也要明确说明为什么没有，不要求用户自己查日志。

至少给出一个拟议项目适配/验收定义的真实格式示例、一个可实现的检查程序核心、一个任务选测的输入输出、一次具体失败结果及其逐跳返修消费过程。所有示例标注“已有实现”或“待实现设计”，不能把伪代码冒充生产源码。

- 按整体架构逐跳运行的示例：由谁输入、哪个现有函数/拟新增入口接收、什么被执行、产生什么、谁消费；

## 7. 历史问题覆盖必须能被反向核对，而不是一次性勾选

重新读取现有 83 条用户要求、七仓 363 条历史登记、26 类专业能力总结及第 21 号文件的 36 项职责/315 个问题。不要把历史已修、风险登记、重复根因或评分器误判说成当下仍然存在的产品缺陷。

## 8. 对整套架构主动进行破坏性提问与替代方案审查

至少主动检验：没有任务包的普通 Codex 请求；已安装 Skill 未被模型调用；项目适配本身漏登记旧功能；缺验收程序；缺专业标准；模拟/硬编码值侥幸通过；产品和验收阈值一起改松；旧截图/错误 PID；真实账号/设备不具备权限；Stop 未获信任或禁用；Lite 预算耗尽；Reviewer 反馈无人消费；外部等待或 Slurm 终态；跨仓多对象版本错配；中央插件更新但消费者仍用旧载荷；验收器被要求临时停用或退休；小任务被升级为无意义全量审查；真实用户报告仍然冗长难读。第 21 号文件中的其他负例也须有可追踪处置。

对每个有可能否决架构的反例，说明：预计走哪条真实代码链、哪个断言/观察识别、谁读取结果、能否自动修复、最终是否合法保持未完成。不得编造执行过的结果；当前只读研究不能运行的真实设备、账户或昂贵试点，明确列为后续需授权的实施验证。

## 9. 最终实施必须分阶段覆盖七仓，包含成本、回滚和真实验收

给出从公共层到七仓真实接入、正式安装、维护和回退的完整依赖关系。每阶段写清：

- 新增何种**用户可以实际使用的能力**，而非新增多少描述文件；
- 仓库、当前稳定基线、具体修改入口/文件、任务边界、哪些既有程序不应改变；
- 在进入 Codex 前必须由 Planner/Critic 冻结的产品、权限、接口和验收决定；
- 与普通功能任务一致的验证方式：正向完整用户链、最高风险坏例、不应改变的旧能力、真实最终对象、同一候选、预算/数据/安全边界；
- 可归因的失败恢复、受管分支/工作树、依赖冲突与正式发布/消费者适配；
- 在规模扩展前实际比较人工提醒次数、成功完成率、错误放行、无意义返工、模型/运行成本与维护成本；净收益不成立时应收缩或取消新增机制。

不允许把一项整体改造写成不可控的七仓巨型 Codex Goal。中央 Bridge、workflow-core、专业插件、项目本地适配、维护/发行应按真实 source authority 分包；实现前独立 Critic 审查和必要用户授权保持有效。既有成熟实现优先选择性复用，不得静默降级。

## 10. 必须持续写入 GitHub 的最终产物

在 WORK_OUTPUT 下至少形成以下**互相定位但不复制全文**的文件；阶段保存可以增补但不允许另造平行真值：

- README.md：一屏中文先解释推荐架构、用户正常使用方式、与旧方案的决定性改变、明确未证实事项，链接下列完整产物。
- CURRENT.md：真实阶段、已完成/未完成、最后提交、重要来源、新发现风险和恢复点。
- 01_REALITY_AND_ALTERNATIVES.md：当前真实源码与宿主能力、已实现/仅设计/未知、主要替代方案及取舍。
- 02_ARCHITECTURE_AND_COMPONENTS.md：最终推荐整体架构图，逐组件“场景→为什么需要→真实入口→输入输出→消费方→失败恢复→旧行为保护→维护→成本”，包括删减与无须新增的理由。
- 03_END_TO_END_EXECUTION_AND_VALIDATORS.md：普通请求和特殊执行模式的逐跳调用合同、验收器生命周期、真实格式/伪代码、动态选测、失败交接、改动/关闭、每轮用户可见汇报样例。
- 04_SEVEN_REPOSITORY_ADOPTION.md：七仓逐仓真实代码入口、至少三条深度完整故事、七仓最高风险反例、具体实施/回滚/完成证据。
- 05_HISTORICAL_COVERAGE.csv 及 05_COVERAGE_SUMMARY.md：可按原历史编号反向核对的全量映射与真正无法闭合的关键缺口，不能以表格大小代替结论。
- 06_IMPLEMENTATION_AND_EVALUATION.md：逐包实施顺序、依赖、权限、试点、受保护的最终验收、成本、何时允许正式发布和以后退出机制。
- 07_INDEPENDENT_CRITIC_PACKAGE.md 与 08_CRITIC_PROMPT.md：可以由另一个独立 Critic 不依赖本对话就检查源码、完整用户承诺、每个组件和七仓可行性，并对真实阻塞给 PROCEED/REVISE 的完整送审包。

每完成现实调查、候选架构、部件调用、七仓落地、覆盖矩阵与实施审查中的任一阶段，都先完成该阶段文件，再写回 CURRENT.md 并检查 GitHub 可回读，再继续。设计中被后续反例推翻的旧选择必须修订原权威文件、留下修订原因，不要把互相冲突的多版 Proposal 堆在新目录。

## 11. 质量标准：研究结束后必须能从全局和细节两侧被问穿

最终正式汇报先用连续自然中文讲清一张架构图和一个完整任务例子，具体说明一项请求以后用户少做哪些事情。每个组件的存在都有至少一个真实历史事故、机制级解释和代码/接口锚点。每个“自动”都有真实触发者、受信任入口、实际接收者和消费结果。每个错误有失败原始证据、责任方、合法自动继续或具体停止边界。每个验收器有从被发现、创建到运行、维护及关闭的完整生命周期。七仓都可按照同一架构接入，但不会被强迫全部采用同一重型流程。

不得以资料数量、章节数量、测试清单、成功回执、流程图完美或旧评审意见“PASS”代替设计可行性。不能把“架构完整”写成“已经实现”。存在平台不支持、缺专业标准、缺授权或缺运行证据时，明确标注并给可审查的设计与补证要求；若该未知会改变关键架构选择，则保留设计未闭合，不得交执行包。

你是本轮架构研究 Planner，不是独立 Critic。只能提出候选并内部找反例；正式中间结论必须交给另一独立 Critic，实施许可仍按 AI Research Stack 当前角色合同运行。本轮不写生产代码、不启动高成本试点、不交可直接执行的 Codex Goal。

**最后一条验收要求：若独立审查者任意选取一个历史真实故障，或用户提出一个从未事先专门准备的普通功能，仍需要用户追问“谁调用验收器、消息谁收到、为什么这次运行、坏例怎样被抓、失败后谁继续、以后怎样关闭、最终我能看到什么”，这份研究就没有达到用户目标。要在 GitHub 中诚实写明未闭合点，不得自称完整。**
