### 2. 如何避免源头上遗漏要求和旧功能

检查入口发现器、前后源码依赖图、共享模块变更、删除/重命名、动态未知消费者和旧功能抽样能否在实践中发现遗忘的保护面。不能把项目适配文件当作它自身完整性的证明；也不能给出无法兑现的“发现全部未知功能”的绝对承诺。低风险文档变动仍应避免无意义全量测试。

### 3. 验收器如何从需要它走到真正使用它

至少用一个高风险真实场景和一个完全不同的普通任务贯穿：哪一步发现没有检查程序，何时只是增加既有类别的回归，何时确需新类别；谁读专业标准并向当前 Codex 发什么具体工作项；新检查怎样用 good/bad/missing/unchanged 校准；如何选择运行时机、采集真实观察、绑定当前候选、避免标准与实现一起改松；哪个原程序消费失败并启动合法返修。

必须设计每次任务最终的用户侧变化报告：本轮新增/加固/复用/执行的验收器、受保护旧能力、合法未执行或复用的理由、真实运行结果、当前成品层级、失败与用户需要的唯一动作。无新增也说明原因。还要解释以后怎样修改、临时停用、合并或退休验收，而不悄悄删除原有质量承诺。

### 4. 故障结果必须真正被接收而且可恢复

从一份真实结构化 Feedback 逐跳追踪：谁写、哪个父进程/当前模型工具调用/原 Controller 真正读、实际下一回合怎样启动、DELIVERED 与 ACKED 如何观察、RESOLVED 凭什么成立。特别攻击：
- Lite 原版一次 subprocess 的设计怎么在有预算时精确恢复同一 thread；
- Review watcher 真正运行/未运行时谁消费、不能用退出码或虚构 Reviewer 决定替代；
- Control 现有 RuntimeAdapter 仍是抽象接口，具体 Executor/Verifier 调用是谁，Controller 自身不在运行时怎么诚实等待；
- Stop Hook 未信任/超时/畸形结果、父进程崩溃、重复反馈、任务取消、用户中断、共享修复预算与安全副作用不得反复执行；
- 等待外部模型、长任务或科学负结果不能被误认成产品缺陷并无限修到正面。

如果合同需要原父进程、具体角色消费者或已有活动控制器，却没有明确可实施的函数与退出/恢复路径，必须在这一轮设计闭合，不能留给 Codex 自行发明第二套调度系统。

### 5. 是否真的更轻，接口和迁移是否值得

将新 da/2 的唯一正式消费者、旧版本只诊断读取、能力协商、影子核验、逐仓启用和回滚锁定到实施合同；改了冻结接口必须另交独立 Critic，不继承旧 da/1 的旧结论。
